# Data Defender — User Journeys

## Roles

- **Preparer** — Senior accountant responsible for investigating and signing off on flagged anomalies assigned to them.
- **Reviewer** — Accounting manager or controller who reviews the preparer's work and moves items to resolved.
- **Rule Owner** — The person who created and maintains a rule; receives fallback assignments when dynamic assignment fails.

---

## Journey 1: Preparer — Triage and Clear Assigned Anomalies

### Entry Point: Email Notification
The preparer receives an email notification alerting them that transactions with anomalies have been assigned to them. The email includes a direct link that opens the Transactions Explorer pre-filtered to their assigned open items.

### Step 1: Triage in the Transactions Explorer
The Transactions Explorer acts as a real-time conveyor belt — transactions are posted to the GL and immediately evaluated against active rules. The preparer toggles to the **Transactions Focused** layout, which puts the transaction list and detail panel side by side, removing the rules view to reduce noise.

### Step 2: Investigate a Flagged Transaction
The preparer clicks a flagged transaction. The detail panel opens showing:
- Full transaction data (amount, date, account, subsidiary, memo, ERP link)
- Which specific rules triggered the flag
- Assigned preparers and reviewers (with a sparkle icon indicating AI dynamic assignment)

### Step 3: Signal Intent
The preparer changes the transaction status from **Open → Investigating** to signal to reviewers that they are actively looking into it.

### Step 4: Remediate
Options depending on the issue:
- **Jump to ERP** — Click the hyperlinked Transaction ID to open the source ERP (e.g. NetSuite) and correct the entry directly.
- **JE Pilot** — Click the JE Pilot button to hand off to FloQast GEM, which drafts a proposed correcting journal entry. *(Future: GEM will suggest the likely fix.)*

### Step 5: Document and Sign Off
The preparer leaves a comment explaining how they handled the anomaly (e.g. "Posted a reversing JE to correct the misclassification"). They then apply their **sign-off** on the transaction.

### Step 6: Move to Next
Repeat for each assigned transaction. The pre-filtered view keeps the queue visible.

---

## Journey 2: Reviewer — Review and Resolve

### Entry Point: Notification or Direct Navigation
The reviewer is notified when preparers have signed off on anomalies assigned to them for review, or they navigate to the Transactions Explorer and filter to items awaiting their review.

### Step 1: Review Preparer's Work
The reviewer clicks into the transaction detail and reads the preparer's comments and sign-off to understand how the anomaly was handled.

### Step 2: Sign Off and Resolve
The reviewer applies their own **sign-off** and moves the transaction status from **Investigating → Resolved**. This closes the item and updates the dashboard KPIs.

---

## Journey 3: Handling AI Insights (Non-Deterministic Anomalies)

Some anomalies come from algorithmic analyses (Account Fingerprints, pattern detections) rather than explicit rules. These are surfaced as insights rather than rule violations.

### Step 1: Review the Insight
The user reads the AI-generated finding, which describes what pattern was detected and over what lookback period.

### Step 2: Acknowledge or Dismiss
The user makes a definitive decision:
- **Acknowledge** — The finding is valid; the user accepts it and it is marked addressed.
- **Dismiss** — The finding is a false positive or not actionable; the user dismisses it with context.

Both actions clear the item from the queue and update its status.

---

## Journey 4: Rule Owner — Create and Manage Rules

### Step 1: Create a Rule
The rule owner navigates to the Rules section and defines a rule using accounting logic (e.g. "Transaction amount > $1M", "Preparer = Approver", "Entry posted after period close").

### Step 2: Assign Owners and Reviewers
The rule owner specifies which preparers and reviewers should be assigned to anomalies generated by this rule. If left as **Dynamic Assignment**, the system uses AI to route based on the impacted GL account; if dynamic assignment fails, it falls back to the rule owner.

### Step 3: Set Risk Weight
The rule owner sets a 1–10 risk weight that feeds into the overall risk score displayed on the transaction in the Transactions Explorer.

### Step 4: Monitor
The rule owner can click into a rule to see a read-only view and navigate to all transactions where that rule was triggered.

---

## Status Lifecycle

| Status | Meaning |
|---|---|
| Open | Anomaly detected, no action taken yet |
| Investigating | Preparer has acknowledged and is actively working on it |
| Resolved | Reviewer has signed off and closed the item |
| Addressed | AI insight has been acknowledged or dismissed |
