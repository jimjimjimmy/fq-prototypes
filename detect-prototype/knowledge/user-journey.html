How accountants use Detect

An end-to-end view of how preparers, reviewers, and admins move through Detect — built from the prototype's existing surfaces and grounded in the most recent product context (PRD, 5.14 demo to FQ Accounting, 5.15 sync with Gaurav).

Primary user
Accountants — preparers, reviewers, admins
Trigger
Continuous · notification-driven, mid-month
Detection sources
AI baseline (24-mo fingerprint) + deterministic rules
Terminal states
Correct · Accept · Dismiss → Reviewed

Personas

P
Preparer
Senior Accountant
Triages the assigned-to-me inbox, investigates anomalies, asks for context via comments, and applies the first sign-off.
R
Reviewer
Accounting Manager / Controller
Reviews preparer work, gives the final sign-off, monitors rule health and false-positive trends over time.
A
Admin / Ultimate Owner
Controller / Director
Configures global rules, fallback assignments, and serves as the catch-all for any anomaly that can't be routed.

Journey phases

01 First-time setup Admin

First load gates behind a COSO acknowledgment — explicit opt-in to AI evaluating the GL — followed by a 3-step onboarding wizard:

  • Ultimate Owner — fallback assignee of last resort
  • Anomaly Assignment (optional) — per entity-account combination
  • ERP Field Mapping (optional) — Vendor / Reversal / etc.

02 Trigger — continuous, not periodic Preparer

The PRD's atomic truth: Prevention is more valuable than detection. Users come in mid-month, driven by notifications (cadence configured in Settings).

"Teresa just posted something that triggered my rule. Detect flashes something and tells me, hey, do you want to look at this?"— 5.14.2026 demo to FQ Accounting
03 Triage — Transactions inbox Preparer

Lands in the inbox filtered to Assigned to Me. Cards are prioritized by severity score (0–100, banded as Low / Medium / High) and materiality. Two flag sources:

  • AI Detected — purple sparkle badge, anomaly model
  • Rule Detected — blue circle badge, references the rule and its version

InboxPanel.tsx   FilterSortModal.tsx

04 Investigation — Detail panel PreparerReviewer

Opens the detail panel with transaction details, GL impact, and one anomaly card per flag — naming the rule (with v{n} version) or the AI category, plus model reasoning. Right rail carries Assignees, Comments (line-level threads), and the Activity Log.

DetailPanel.tsx

05 Resolution — every anomaly reaches a terminal state Preparer
  • Create Journal Entry — correcting JE drafted JournalEntryModal
  • Add to Close Checklist — routes work into Close CloseTaskModal
  • Dismiss — with reason; trains the model on false positives DismissModal
"A signal without a clear next step is noise. Every alert must map to a decision, an owner, and a remediation path."— Detect PRD, Atomic Truths
06 Insights — the unknown unknowns Preparer

The Insights tab catches expected-but-missing activity at the account level. For each insight the user sees missing transactions across Current Period · Prior Month · Prior Quarter Same Month · Prior Year Same Month. Per-row Why this suggestion? disclosures call out the cadence pattern Detect found (monthly cadence, recurring contract, ingestion delay, recently active vendor, materiality framing) and surface 3 next-step CTAs.

"We think you missed $128,000 of accruals — which should be broken up as 20K to Amazon, 45K to Google…"— 5.14.2026 demo to FQ Accounting

InsightsView.tsx

07 Sign-off & handoff PreparerReviewer
  • Preparer applies their sign-off in the Assignees card (Transactions or Insights)
  • Reviewer examines the work, signs off → status flips to Resolved
  • New finding after sign-off → insight enters the Redo state with amber alert + stale-sign-off indicator
08 Rules maintenance — long-running loop ReviewerAdmin

Reviewers and admins return to the Rules workspace to tune coverage as the business changes. Each rule carries a v{n} tag; edits create a new version with a full history. Deactivation requires confirmation with historical-impact framing.

Auto-assignment cascade

When an anomaly fires, Detect walks down a four-step cascade until it finds an owner. Last stop is the Ultimate Owner so nothing falls into the void.

Level 1
Dynamic Assignment
Match the account's existing Preparer / Reviewer from Reconciliations
Level 2
Fallback Assignees
Per-account list uploaded during onboarding
Level 3
Rule Owner
For rule-detected anomalies, the rule's author
Level 4
Ultimate Owner
Global catch-all configured in onboarding
