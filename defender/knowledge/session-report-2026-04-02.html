The most important lesson from this session: treat Figma designs and Design Bar decisions as the source of truth, not the prototype's existing architecture. How It Worked

The session progressed through three distinct phases. Each phase built on discoveries from the previous one, and each required a different combination of tools and sources.

Phase 1: Figma Discovery and Workflow Mapping

The session began by pulling design context from Figma. An early discovery reshaped the entire approach: the Figma files contain dedicated workflow pages (032726-Rules with 20 sections, 031626-Transactions with 32 sections) that tell the story of complete user journeys, not just individual component designs.

Claude Code navigating the Figma file structure, discovering the Rules and Transactions workflow pages and querying Design Bar via NotebookLM for context on the specific workflows shown in each page.
The Rules workflow map: 20 sections including Empty State, Rule Builder, Edit Rule, Deactivation, Version Viewing, and Dynamic Assignment — each with prototype status and gap assessment.
The Transactions workflow map: 32 sections covering the full investigation flow from empty state through sign-off, comment threading, and deleted ERP handling.
The 52 sections were organized into three implementation tiers: Tier 1 (core workflows), Tier 2 (workflow enhancements), and Tier 3 (visual polish). This prioritization drove the session's build order.

Phase 2: Architecture Correction and Functional Prototype

This is where the session's most important correction happened. I noticed that we'd been treating the Bolt prototype's architecture as the source of truth and trying to match Figma into it. The Figma designs showed rule editing as an in-place transformation of the Rule Details panel. The Bolt scaffold had implemented it as a completely separate form component. We inverted the approach.

Architecture Mismatch

The Bolt prototype separated "viewing" and "editing" into different components and tabs. Figma treats them as two states of the same panel — view-only fields become editable inputs without navigating away. This mismatch affected 10 interactive elements that looked functional but did nothing when clicked.

The automated audit revealed 10 interactive elements in edit mode that did absolutely nothing when clicked — dropdowns, buttons, sliders, and inputs that were rendered as visual elements only. The Rule Creator had all of these working; the edit mode did not.
Cross-project insight: Catalyst personas (Sarah Chen, David Park, Maria Gonzalez) mapped directly to Defender roles (Preparer, Reviewer, Controller). Sarah's "5-second rule" — she should identify her next action within 5 seconds of opening any view — directly informed empty state design and severity indicator placement.
Frequent checkpointing: each batch of changes was committed and verified before moving on. The session produced 20+ commits with descriptive messages, creating a reviewable history of decisions.

Phase 3: UI Cleanup, New Views, and Verification

The final phase focused on design system compliance and implementing three new Figma designs that arrived mid-session. A 38-item FlowUI audit drove the cleanup work, replacing hardcoded values with CSS variables and raw HTML with FlowUI components.

Multi-view verification: Transaction Details with 5 anomaly cards, Rules Grid with 19 rules showing version badges and status colors, and Design Bar findings surfaced via NotebookLM — all cross-referenced in one pass.
Six cross-product design system findings from Design Bar: AI color transition, floating windows, sign-off simplification, AI component standardization, AG Grid patterns, and designer constraints. These inform the broader DS roadmap beyond Defender.
The window.__test harness enabled programmatic verification: each test called a harness function, took a screenshot, and assessed the result. This caught issues that visual inspection alone would miss (like the checkbox onChange vs onCheckedChange bug).

What We Learned

Figma MCP Tools

get_design_context silently returns empty for large component instances (>1500px) with no error message. This was the session's biggest technical blocker. We built a Deep Instance Probe — a Figma Plugin API script that traverses inside opaque instances — and added it to the figma-fq skill as a permanent capability.

get_screenshot was the most reliable tool across all node sizes. Combined with get_metadata for structural navigation and the new probe for deep data, the three-tool combination (Probe + Token + Screenshot) became the standard pattern for component matching.

Design Bar and NotebookLM

The most valuable insights came from querying Design Bar transcripts before implementation, not during debugging. Knowing that Gaurav described insights as "unknown unknowns / process drift" before building the Insights Grid meant we got the conceptual model right on the first pass.

The gap: text/chat communications aren't captured. Only Gong audio transcripts are in NotebookLM. Slack threads where decisions happen between sessions are missing entirely.

FlowUI Design System

CSS variables with hex fallbacks (var(--flo-sem-color-*, #hex)) are a clean pattern — the prototype works with or without the FlowUI theme loaded. The session surfaced one significant API gotcha: FlowUI Checkbox uses onCheckedChange, not onChange. This cost ~30 minutes of debugging on the Manage Panels feature.

Process

The most impactful process insight: audit existing code before building new features. ~40% of the features we identified as "gaps" in the Figma analysis already existed in the prototype. We also learned that window.__test harnesses are essential for verifying flexlayout-react interactions programmatically — without them, each test requires navigating the full UI visually.

Mid-session course correction: Benjamin asked Claude to pause implementation and produce a comprehensive status report with gap analysis before continuing. This check prevented building features that already existed and surfaced the architecture mismatch early enough to fix it.

API Gotchas Discovered

Checkbox: onCheckedChange vs onChange

FlowUI Checkbox uses onCheckedChange as its callback prop. The standard React onChange is silently ignored — the checkbox renders and toggles visually but never fires the callback. This cost ~30 minutes of debugging on the Manage Panels modal. The FieldSettingsPanel component already used the correct prop, but there was no documentation flagging this inconsistency.

Appendix D: Process Improvements

Pre-Session Checklist (proposed)

  1. Pull ALL screenshots from relevant Figma pages first — don't drill into nodes until you have the full picture
  2. Query Design Bar for the product area before writing any code
  3. Audit existing prototype code for what already exists (~40% was pre-built in this session)
  4. Identify architecture mismatches between Figma's interaction model and the prototype's component structure
  5. Build data layer and types first — catches structural issues before JSX work begins

What Worked Well

  • Git worktree isolation — no merge conflicts, clean branch history
  • Frequent commits — 20+ commits created natural checkpoints
  • Plan mode workflow — explore, plan, approve, execute caught the architecture mismatch early
  • Multi-source triangulation — Figma + Design Bar + FlowUI + personas converging on the same feature
  • window.__test harness — programmatic verification without manual clicking
  • Mid-session status checks — Benjamin's request to "pause and audit before continuing" was the session's most valuable intervention

What Didn't Work

  • Architecture-first thinking — treating the Bolt scaffold as a constraint instead of a suggestion
  • Broad NotebookLM queries — timed out; focused questions worked better
  • Screenshot-only verification — misses state bugs; need richer assertions
  • get_design_context silent failures — wasted time before discovering the size limitation
