The questions, in order

From Rebecca's comment on Kristin's mockup. Each question narrows the path.

Rebecca: "Do you want to use a pre-built connection or build a custom connection (files, API)? If pre-built, then they can choose from either our DC API standard integrations or our CDC connections. What system if pre-built? What type of connection (file, or API) if custom? If we have two types of systems, then we show them the options for basic vs. enhanced. Basic is for just accounts and balances. Enhanced is broader. I also think having a path for people who don't need to answer questions and know exactly what they are doing is useful."
Q1

Pre-Built or Custom?

Sets the entire downstream path. Most users land in Pre-Built; Custom is for files, API, or SFTP.

Pre-Built FQ-supported integrations — DC API standard (e.g., QBO direct) or CDC (e.g., NetSuite). FQ owns the source mapping.
Custom User-controlled transmission — file upload, API, or SFTP. User defines the schema.
Q2a

If Pre-Built: which system?

The familiar source picker — QBO, NetSuite, Sage Intacct, Salesforce, Workday, etc. Vendor abstraction stays: no Fivetran in any label.

This is the column from Kristin's mockup ("Which System?") — it shows up here, scoped to Pre-Built only.

Q2b

If Custom: which connection type?

File Manual Upload — .xlsx / .csv with schema inferred from a sample.
API User-defined API endpoint — FQ pulls from a customer-hosted source.
SFTP SFTP push/pull — existing pattern, retained per Kristin's note ("let's keep what's there now").
Q3

(Conditional) Basic or Enhanced?

Only fires for systems that have two tiers. QBO is the known case today.

Basic Accounts and Balances only.
Enhanced Broader scope — transactions, dimensions, etc. Definition per source.
Generalizable: treat this as a per-source attribute. If a future system adds tiers, it inherits this screen automatically. If a system has only one tier, Q3 is skipped.
Q4

Express path — "I know what I'm doing"

For repeat users and implementation team members who don't need to be guided. Bypasses progressive disclosure entirely.

In the progressive-disclosure model below, this lives as a "Show all options" link near the top of the screen. Clicking it swaps the guided sequence for a single-screen picker (Kristin's mockup pattern) where the user picks System + Data at once.

Lean: single-screen bypass — reuses what Kristin already designed and gives implementation-team users a fast path. Search becomes valuable later when source count grows past ~12.

Recommended interaction model: progressive disclosure

The decision tree above is the logic. Progressive disclosure is how we deliver it — one screen, questions revealed sequentially as the user answers each one. Inspired by Dropbox's onboarding pattern: prior answers stay visible and editable, the screen feels like a single conversation rather than a stack of wizard steps.

How it behaves

  • One screen, one title. "Add a connector" or "What are you connecting?" Sub-line: "A few quick questions to get you set up."
  • Q1 appears first. Pre-Built or Custom? — presented as a clear binary selection (specific control TBD in wireframes).
  • Q2 reveals after Q1 is answered. Pre-Built → system picker (compact logo grid). Custom → the three connection-type options (File / API / SFTP). The same Q2 slot, different content based on Q1.
  • Q3 reveals only when needed. If Q2 = QBO, Basic vs. Enhanced appears with a brief subtitle: "Since you picked QBO, we need one more thing." Otherwise this question doesn't exist.
  • Prior answers stay editable. Click any earlier answer to change it — downstream questions adjust live.
  • Progress indicator at the top. Fills as the user advances. Sets expectation of remaining work.
  • "Show all options" link near the title. The Q4 express bypass — swaps the guided flow for a single-screen picker (Kristin's mockup).
  • Continue is disabled until required answers are present. No premature progress.

Why this fits Data Studio better than a traditional wizard

  • Conditional questions feel natural. Q3 only fires for some sources — progressive disclosure handles "appears or doesn't" cleanly. A wizard would need an awkward "skipped step" UI or unbalanced step counters.
  • Q2 branches dramatically. Pre-Built → system picker is visually rich (logos, descriptions). Custom → three lightweight options. Progressive disclosure swaps the same slot's content based on Q1; a wizard would need two distinct screens.
  • Audience profile. Admins set up connectors infrequently — maybe once a quarter. The "remind me what I'm doing as I go" feel of progressive disclosure serves a returning-but-not-frequent user well.
  • Editing is cheap. Click an earlier answer to change it. No "Back" button needed.

Trade-offs & mitigations

Concern Severity Mitigation
Conflicts with the express path High "Show all options" link near the title bypasses progressive disclosure to a single-screen picker (Kristin's mockup). Default = guided; opt-out for power users.
Compact selectors don't scale past ~6 options Medium Lightweight selection works for Q1 (2 options) and custom-type Q2 (3 options). For "Which system?" with 5–20+ sources, use a logo grid or searchable input — same approach Dropbox uses for Industry.
Conditional reveal can feel jumpy Low Brief subtitle on Q3: "Since you picked QBO, we need one more thing." Sets expectation that the question exists because of a prior answer.
Path length not visible up front Low–Medium Progress bar at top. Optional explicit step counter ("Step 2 of 3") if user testing reveals confusion. Don't pre-commit to either — test first.
Long screen at the end Low If all 3 questions are answered + revealed, screen gets tall. Acceptable, but verify on smaller viewports during low-fi sketching.
Power users still feel slowed down Medium Resolved by the express bypass. Watch usage data after launch — if >30% of admins use the bypass, default screen may need rethinking.
Logic vs. presentation: the decision tree (questions, branches, conditions) is what we've agreed on. Progressive disclosure is how it's rendered — if user testing later shows the pattern doesn't work, the underlying logic stays valid and we can swap to a multi-step wizard or a single-screen picker without re-doing this work.

What still needs to be sketched

This document defines logic and interaction model. Visual design comes next. The unresolved UI questions to work through when we move to wireframes:

  • Q1 visual treatment. Big two-up cards with descriptions? Radio with helper text? Segmented control? The choice signals which path is the "default" expectation.
  • Q2 system picker layout. Logo grid: how many visible vs. behind a "More sources" expand? Sort order? Source descriptions inline or on hover?
  • Q3 trigger affordance. Does Q3 fade in below Q2, slide in, or just appear? Subtle motion can soften the "extra question" feel.
  • Express link placement. Top-right of screen? Subdued footer link? In-context "Skip the questions" CTA next to Q1? Discoverability vs. visual noise.
  • Progress indicator style. Continuous bar (Dropbox-style) or stepped dots? Stepped reads as "you have N steps total" which conflicts with conditional questions.
  • Empty-state hand-off. First-time user "Connect your data" hero → this screen. Same screen, different entry framing? Or a dedicated welcome screen first?

How this resolves Alex's SFTP question

Alex: "I'm not clear on how this lines up with SFTP … how does that fit in?"

Rebecca's framing put files and API under "custom" but didn't explicitly call out SFTP. V2 places SFTP as a third sibling under Q2b: which connection type? — same status as file and API. This keeps existing SFTP support intact (per Kristin's "let's keep what's there now") and gives it a clear home in the new framework, so it doesn't get orphaned or treated as a backdoor.

How Kristin's mockup fits

Kristin's "What Are We Connecting Today?" screen does a lot in one view: pick System + pick Data domains. V2 splits those out across the question sequence — but the single-screen pattern doesn't go away. It becomes the express path (Q4): the same compressed picker, repurposed for users who don't want to be walked through.

Two questions to resolve about Kristin's "Which Data?" column:

  • Does data-domain selection belong in selection, or in the wizard? The CDC PRD puts table selection in step 3 of the setup wizard (Provision). If we surface data domains here too, we either duplicate or replace that step. Worth a follow-up with Kristin and Alex.
  • Is "Custom/Non-Standard" (in Kristin's data column) the same as Q1's "custom" branch? The wording overlaps but the meaning differs — Kristin's appears to be a data-domain (a non-standard FQ Model), Rebecca's is a transmission method. We'll want to disambiguate before either ships.

Open questions

  • Naming. "Pre-Built" and "Custom" are working labels and may be jargony. Better candidates: Standard / Custom, Connect a system / Bring your own data, FQ-supported / User-defined. Worth a separate naming pass.
  • Q1 visual treatment. Big two-up cards? Radio with descriptions? Toggle? The choice signals which path is the "default" expectation.
  • Express path discoverability. Where does the "I know what I want" link live? Header link on Q1? A second CTA on the empty state? Part of the user's profile preference?
  • Conditional Q3 logic. How does the system know which sources have multiple tiers? Source registry attribute — needs to be defined as part of the source taxonomy.
  • Custom path scope. Are file, API, and SFTP all genuinely first-class? Or should one (e.g., file) get visual primacy because it's the most common custom path?
