## 🎯 Objective

This sub-PRD covers the final phase before a Model goes live: testing the configured field mappings against actual data to validate correctness, and publishing the first version of the model to make it Active.

It addresses: the test/preview experience (how users validate transformations before committing), publish action mechanics, the Effective Date concept and its operational implications, and publish-time validation (what the system blocks vs. warns on). It does **not** cover creating subsequent versions or lifecycle management of an already-published model (see Sub-PRD 4).

Primary users: FloQast admins and implementation team members.

> **Context:** A field-level Transformation Logic preview already exists in production — it runs an expression against sample records for a single mapping row. The test panel defined in this PRD is a broader, complementary validation step: full model output, all fields together, with entity filter and as-of date selection. Both experiences are intended to coexist.

## 🔤 Definitions

For a complete glossary of terms used across the Model Creation series, see the shared [Definitions & Terms (Data Studio)](https://floqast.atlassian.net/wiki/spaces/Data/pages/4464869409) page.

### 📊 Model States

| **State** | **Description** |
| --- | --- |
| **Draft** | The working, unpublished version of a Model. Changes can be made freely; tests can be run against real source data. Only one Draft can exist at a time per model. |
| **Active** | The live published version. Data is being processed against this version's field mappings. Only one version can be Active at a time. |
| **Archived** | A previously Active version that has been superseded by a newer publish. Read-only; configuration is preserved for reference. *(See Sub-PRD 4.)* |

### 🗺️ Navigation within Data Studio

Testing and Publishing are accessed from the **Field Mappings tab** within a Model's Detail View. The Publish action is available in the model header. After a successful publish, the **Data Preview tab** becomes accessible.

| **Tab / Location** | **What it shows** | **Relevant to this PRD** |
| --- | --- | --- |
| Field Mappings tab | Source-to-target mapping configuration for the current Draft | ✅ Entry point for testing; Publish button is here |
| Test / Preview panel | Run-time preview of transformation output against real source data | ✅ Core of this PRD |
| Data Preview tab | Normalized FQ data post-publish, once the pipeline has processed | ✅ Post-publish terminal state |
| Versions tab | History of all versions (Draft, Active, Archived) | ➡️ Sub-PRD 4 |
| Logs tab | Status and error logs for data processing runs | ➡️ Sub-PRD 4 |

## 🏅 Why This Is Important

Today, users are only able to see how the field mappings will process for a single row (they are unable to select which row for this test.) Likely this means users having to iterate repeatedly before proceeding, potentially having errors and having data rerun multiple times.

Testing before publish is the last line of defense against data quality issues reaching downstream FQ products. Without a robust preview capability, admins are essentially publishing blind — increasing the risk of incorrect data flowing into Close, Flux, or Compliance. The Effective Date mechanic for Version 0 has particularly significant implications: a default of Jan 1, 1900 means all historical data will be re-processed on first publish.

---

## 💡 Key Benefits

* Admins can validate transformation output before data reaches downstream FQ products, reducing post-publish data quality issues.

* As-of date selection and entity filtering let admins test against realistic, targeted data rather than arbitrary sample rows.

* Inline error surfacing with rule-level detail shortens the feedback loop between discovering and fixing a bad mapping.

* Publish-time validation prevents incomplete models (unmapped mandatory fields) from going Active.

* A clear Effective Date UX ensures admins understand the historical data implications of their publish action before committing.

| --- | --- | --- | --- |
| 1 | FQ Admin | Admin has completed field mappings and wants to verify the output looks correct before publishing | Admin opens the test panel, selects an as-of date, optionally filters by entity, inspects transformed rows, confirms output matches expectations, proceeds to publish |
| 2 | FQ Admin | Test output reveals a date field is being formatted incorrectly | Admin sees the error on the affected field row, clicks through to the transformation logic editor, adjusts the rule, re-tests, then publishes |

| 7 | FQ Admin | Admin publishes the model successfully | Model status changes from Draft to Active; data processing begins for the configured source datasets |

## 🤔 Assumptions

### Established

* Field mappings must be defined for required fields (Sub-PRD 2 complete) before publishing is possible.

* A default Effective Date of Jan 1, 1900 triggers a full historical data backfill across all available source data.

* Publishing transitions the model from Draft → Active and makes it visible in the Models Tab as Active.

* "Available dates" for the as-of date picker are determined by the presence of data in the source datasets — not just schema availability.

### Open Items to Confirm

* **G2** — The Effective Date for Version 0 (first publish) defaults to January 1, 1900. *Must be confirmed with the data platform team — this drives the full historical backfill decision.*

* **G3** — At least one mandatory FQ field being unmapped should block publish. *Confirm whether this is a hard block or a warning with override.*

* **Sub-PRD 4** — Only one version can be Active at a time; publishing a new version archives the previous Active version. *Cross-dependency with Sub-PRD 4 lifecycle management.*

## 🗺️ Scope

### 🚗 In Scope

* Test / Preview functionality: running current Draft mappings against source data and displaying the transformed output

* As-of date selection for testing: allowing users to pick a specific date with available data

* Entity filter and row-level filter in the test panel

* Mapping error surfacing per field in test results, with rule-level detail

* Error resolution navigation: path from a test error back to the transformation logic editor

* Publish action and UI (button, confirmation, status change)

* Effective Date selector — default behavior, user override, and explanation of implications

* Publish-time validation: blocking publish if mandatory FQ fields are unmapped

* Effective Date dialog messaging for Scenario A (standard) and Scenario C (initial backfill)

* Post-publish model state: transition to Active, Data Preview tab availability

### 🚦 Out of Scope

* Field mapping logic (see Sub-PRD 2)

* Creating a new version of an already-published model (see Sub-PRD 4)

* Re-publish with past Effective Date on a model that already has an Active version — tear-down/rehydrate (Scenario B) — see Sub-PRD 4 (V8-LC)

* Data Preview tab analytics, reporting, and ongoing monitoring features (initial post-publish availability is in scope; ongoing operational use is a later release)

* Historical backfill orchestration (data platform concern — this PRD defines the trigger, not the implementation)

### TP1-LC — Trigger Test / Preview

**User Story:** As an admin working with a Draft, I can open a test panel and preview how my current source data is transformed based on the field mappings I've defined.

**Importance:** High

**Details:** The test panel must reflect the live draft state of the mappings — not the last published version. It shows source field values alongside their transformed FQ output, row by row. If no data has been loaded (e.g., a brand-new connector), the system must communicate this clearly and provide an alternative path (see G1 — CSV upload is the highest-priority open question in this sub-PRD).

**Notes:** Today, users can only preview a single arbitrary row with no control over which row. This story establishes the core testing surface; as-of date selection (TP2-LC), entity/row filtering (TP3-LC), and error surfacing (TP4-LC) are built on top of it.

**Acceptance Criteria:**

**AC-TP1-01 — Test panel is accessible from the Field Mappings tab**

* **Given** I am on the Field Mappings tab for a Draft model

* **When** I click the "Test" or "Preview" action (button or tab — see design)

* **Then** the test panel opens

* **And** I remain in context of the Draft (I have not navigated away from the mapping workflow)

**AC-TP1-02 — Preview reflects current draft mapping state**

* **Given** I have made changes to one or more field mappings in the current Draft

* **When** I open the test panel

* **Then** the preview uses my current draft mapping configuration

* **And** the preview does not reflect the last published (Active) version's mappings

**AC-TP1-03 — Preview shows source values alongside transformed output**

* **Given** the test panel is open and data is available for the selected as-of date

* **Then** the preview displays a table with at least: source field value, transformation applied, and resulting FQ output value for each mapped field

* **And** I can see multiple rows of data (not limited to a single arbitrary row)

**AC-TP1-04 — No data available state is communicated clearly**

* **Given** no data has been loaded for the model's source datasets (e.g., new connector with no ingested files)

* **When** I open the test panel

* **Then** the system displays a clear message indicating that no data is available for testing

* **And** the message provides guidance on next steps *(see G1 — CSV upload path TBD)*

### TP2-LC — Select As-Of Date for Testing

**User Story:** As an admin, I can select a specific "as-of date" to use when testing my Model, so I can preview how my mappings process data from a known point in time.

**Importance:** High

**Details:** The as-of date determines which slice of source data is fetched for the test preview. Only dates for which data actually exists should be shown as selectable — the picker must not allow selection of dates with no data, to avoid a misleading empty preview. The behavior when only a subset of linked source datasets has data for the selected date is an open question (see G7).

**Acceptance Criteria:**

**AC-TP2-01 — As-of date picker is present in the test panel**

* **Given** the test panel is open

* **Then** an as-of date selector is displayed

* **And** it is clear to the user that this date controls which data will be used in the test preview

**AC-TP2-02 — Only dates with available data are selectable**

* **Given** the as-of date picker is displayed

* **Then** only dates for which source data exists are displayed as selectable options

* **And** dates with no available data are either hidden or visually indicated as unavailable and non-interactive

**AC-TP2-03 — Selecting a date fetches data and updates the preview**

* **Given** I select a valid as-of date in the test panel

* **When** the date is confirmed

* **Then** the system fetches source data for that date

* **And** the test preview updates to reflect the data from the selected date

* **And** a loading state is shown while data is being fetched

**AC-TP2-04 — Default date behavior**

* **Given** I open the test panel for the first time

* **Then** a default as-of date is pre-selected *(most recent date with available data is recommended default — confirm with design/engineering)*

* **And** the default selection is clearly indicated

**AC-TP2-05 — Partial dataset availability (open question)**

* **Given** I select an as-of date

* **And** only one of two linked source datasets has data for that date

* **Then** the system behavior is defined *(see G7 — open question: does the system proceed with available data, or block and warn?)*

### TP3-LC — Filter Test Data by Entity and Row

**User Story:** As an admin in the test panel, I can filter the test data by entity and apply row-level filters, so I can test my mappings against a targeted, realistic subset of data before publishing.

**Importance:** High

**Details:** The test panel should support a progressive filtering workflow: (1) select as-of date (TP2-LC), (2) filter by entity if the entity field is mapped, (3) view the resulting test data and apply additional row-level filters if needed, then (4) run the test against that filtered dataset. If the entity field has not been mapped in Sub-PRD 2, the user should still be able to proceed — either with a "select all" option or with entity filtering simply unavailable.

**Acceptance Criteria:**

**AC-TP3-01 — Entity filter appears when entity field is mapped**

* **Given** the entity field has been mapped in the current Draft's field mapping configuration

* **When** I am in the test panel with a selected as-of date

* **Then** an entity filter is displayed

* **And** the entity filter lists all unique entity values present in the source data for the selected date

**AC-TP3-02 — "Select All" option available when entity field is not mapped**

* **Given** the entity field has not been mapped in the current Draft

* **When** I am in the test panel

* **Then** entity filtering is either unavailable or shows a "Select All" option

* **And** the test proceeds against all available records without entity filtering

* **And** it is clear to the user why entity-level filtering is not available

**AC-TP3-03 — Selecting an entity filters the test data**

* **Given** the entity filter is displayed and I select a specific entity

* **Then** the test preview data is filtered to show only records belonging to that entity

* **And** the record count updates to reflect the filtered dataset

**AC-TP3-04 — Selecting multiple entities filters the test data**

* **Given** the entity filter is displayed and I select multiple entities

* **Then** the test preview data is filtered to show only records belonging to those entities

* **And** the record count updates to reflect the filtered dataset

**AC-TP3-05 — Row-level filters can be applied on the test data grid**

* **Given** I am viewing the test data in the preview grid (after date and entity selection)

* **Then** I can apply additional row-level filters on any visible column

* **And** the preview updates to show only rows matching my filter criteria

* **And** I can clear filters to return to the full filtered dataset

**AC-TP3-06 — Test runs against the filtered dataset**

* **Given** I have applied date, entity, and/or row-level filters

* **When** I run the test

* **Then** the transformation preview is computed only against the filtered records

* **And** the results shown correspond to the filtered dataset, not the full dataset

### TP4-LC — View and Resolve Field Mapping Errors

**User Story:** As an admin, when my test reveals a field mapping error, I can see exactly which rule is failing and why, and I can navigate directly to that rule to fix it — without losing my test context.

**Importance:** High

**Details:** Mapping errors in the test preview should be surfaced at the field level (not as a generic "something went wrong" message). Each error should identify the specific transformation rule that failed and include a human-readable description of why it failed. Ideally, the user can navigate from the error directly to the transformation logic editor for that specific field, make a fix, and re-run the test.

**Acceptance Criteria:**

**AC-TP4-01 — Errors are surfaced per field in the test results**

* **Given** a transformation rule produces an error when applied to one or more source rows

* **When** the test preview is displayed

* **Then** the error is shown inline on the affected field column in the preview grid

* **And** error rows are visually distinguished from successfully transformed rows

**AC-TP4-02 — Error detail identifies the failing rule and reason**

* **Given** a field mapping error is shown in the test preview

* **When** I expand or click on the error indicator

* **Then** I can see which transformation rule failed

* **And** I can see a human-readable description of why it failed (e.g., "Cannot cast 'ABC' to Number", "Null value in required field 'Account ID'")

**AC-TP4-03 — Error summary count is shown in the test results header**

* **Given** one or more field mapping errors occurred in the test run

* **Then** the test panel header or summary area shows the total number of errors

* **And** I can navigate to the list of all errors from the summary

**AC-TP4-04 — User can navigate from an error to the transformation logic editor**

* **Given** I am viewing a field mapping error in the test preview

* **When** I click "Fix this" (or equivalent CTA) on the error

* **Then** I am navigated to the transformation logic editor for the specific field mapping that caused the error *(see OQ-6 — inline modal vs. tab navigation TBD)*

**AC-TP4-05 — User can re-run the test after fixing an error**

* **Given** I have navigated to the transformation logic editor and updated the failing rule

* **When** I return to the test panel

* **Then** I can re-run the test without needing to re-select my date and entity filters

**AC-TP4-06 — Errors do not block access to other rows**

* **Given** some rows produce errors and others transform successfully

* **Then** successfully transformed rows are visible and accessible in the preview

* **And** the presence of errors does not hide or prevent viewing the successful output rows

### TP5-LC — Publish Model

**User Story:** As an admin, I can publish the Draft Model by clicking "Publish," confirm or adjust the Effective Date, and transition the model to Active.

**Importance:** High

**Details:** The publish action is the terminal step of Model creation. The user clicks Publish, is prompted to confirm or adjust the Effective Date, and the system validates that all mandatory FQ fields are mapped before proceeding. On success, the model transitions to Active.

The dialog and pipeline behavior depend on the Effective Date selected. Three scenarios apply across the full publish lifecycle — this PRD covers Scenarios A and C only:

| Scenario | Condition | Behavior | Covered by |
| --- | --- | --- | --- |
| **A** | Today or future date | Standard publish. Data processing begins from the Effective Date forward. No historical reprocessing. | This PRD (AC-TP5-03, AC-TP5-07) |
| **B** | Past date, re-publish (model already has Active version) | Tear down and rehydrate: existing processed data from the Effective Date forward is removed, then reprocessed with new mapping rules. | [Sub-PRD 4 — V8-LC](https://floqast.atlassian.net/wiki/spaces/Data/pages/4443013309) |
| **C** | Past date, initial publish (Version 0, no prior Active version) | Pure historical backfill — pipeline loads data from the Effective Date forward. No existing data is affected. Informational dialog shown before confirm. | This PRD (AC-TP5-04, AC-TP5-08) |

For Version 0, the Effective Date defaults to January 1, 1900, which triggers Scenario C (full historical backfill). This must be communicated clearly to the user before they confirm. See G2 for confirmation needed from the data platform team.

**Acceptance Criteria:**

**AC-TP5-01 — Publish action is accessible from any screen while a draft exists**

* **Given** I am viewing a model that has a draft (from any screen in the Model View)

* **Then** the "Publish" button is visible and accessible from any screen while a draft exists

* **And** the Publish action is disabled when no changes have been made relative to the current live version

**AC-TP5-02 — Publish is blocked if mandatory fields are unmapped**

* **Given** I initiate the Publish action

* **And** one or more mandatory FQ fields do not have a source mapping defined

* **Then** the publish is blocked *(see OQ-2 — confirm whether this is a hard block or a warning with override)*

* **And** the specific unmapped fields are surfaced to the user by name

* **And** I am given a clear path to navigate back to the Field Mappings tab to resolve the issues

**AC-TP5-03 — Effective Date prompt is shown before publish completes**

* **Given** all mandatory fields are mapped and I initiate Publish

* **Then** a confirmation dialog is shown before the publish is executed

* **And** the dialog displays the current Effective Date (defaulting to January 1, 1900 for Version 0)

* **And** I can adjust the Effective Date before confirming *(see OQ-3)*

* **And** the dialog content adapts based on whether the selected date is today/future (Scenario A) or in the past (Scenario C) — see AC-TP5-07 and AC-TP5-08

**AC-TP5-04 — Successful publish transitions model to Active**

* **Given** I confirm the publish action

* **When** the publish completes successfully

* **Then** the model's status transitions from Draft to Active

* **And** the Models Tab reflects the Active status

* **And** the Versions Tab shows the version as Active with the confirmed Effective Date

**AC-TP5-05 — Success confirmation is shown to the user**

* **Given** the publish completes successfully

* **Then** a success confirmation is shown (e.g., a toast or modal)

* **And** the confirmation communicates that data processing has begun (or will begin)

**AC-TP5-06 — Data Preview tab becomes available post-publish**

* **Given** the model has been successfully published and data has been processed

* **Then** the Data Preview tab is available and shows the normalized FQ output

* **And** the Data Preview tab is not available (or shows an appropriate pending state) while data is still being processed

**AC-TP5-07 — Scenario A: Standard confirmation dialog (today or future Effective Date)**

* **Given** I am confirming publish

* **And** the selected Effective Date is today or in the future

* **Then** a standard confirmation dialog is shown

* **And** the dialog clearly states the Effective Date and that data processing will begin from that date forward

* **And** no backfill warning or data unavailability notice is shown

* **When** I confirm

* **Then** the publish proceeds and the model transitions to Active

**AC-TP5-08 — Scenario C: Informational backfill dialog (past Effective Date, initial publish)**

* **Given** I am confirming publish for the first time (Version 0, no prior Active version)

* **And** the selected Effective Date is in the past

* **Then** an informational dialog is shown before the publish is confirmed

* **And** the dialog states: *"Setting an effective date in the past will load historical data from \[Effective Date\] to today. This is a one-time backfill and may take some time to complete."*

* **And** the dialog requires explicit confirmation to proceed (not single-click dismissal)

* **When** I confirm

* **Then** the publish proceeds; the pipeline begins loading historical data from the Effective Date

* **When** I dismiss or cancel the dialog

* **Then** the publish is cancelled and the Draft remains unchanged

## 💻 UX Requirements

### Test Panel

* The test panel must be accessible from the Field Mappings tab without navigating away.

* The as-of date picker should default to the most recent date with available data.

* Dates with no available data must be visually distinguished and non-interactive.

* The entity filter should appear only when the entity field has been mapped.

* Row-level filter controls should feel native to the data grid.

* Error indicators on field columns should be scannable at a glance.

* Each error row must have a visible "Fix this" CTA *(see OQ-6 for navigation pattern)*.

### Publish Action

* The "Publish" button should be positioned in the model header or top-right, visible from any screen while a draft exists.

* Publish is disabled when no changes have been made relative to the current live version.

* Publish validation failure (unmapped mandatory fields) must be surfaced **before** the Effective Date dialog appears.

* The Effective Date dialog must adapt based on scenario:

  * **Scenario A** (today/future): Standard confirmation.

  * **Scenario C** (past date, initial publish): Informational backfill dialog — *"Setting an effective date in the past will load historical data from \[Effective Date\] to today. This is a one-time backfill and may take some time to complete."*

  * **Scenario B** (past date, re-publish on existing Active model): Out of scope for this PRD — see Sub-PRD 4 (V8-LC).

* "Confirm Publish" must be a distinct, deliberate final action.

* The Jan 1, 1900 default must be communicated in plain language. Avoid "backfill" — use "load historical data" instead.

## 😎 Future Considerations

* **Scheduled / automated test runs:** Allow tests to be triggered on a schedule to catch mapping breakage when source data schema changes.

* **Shareable test result snapshots:** Generate a shareable URL or export of a specific test run's output.

* **Test history and run comparison:** Store the history of test runs and allow side-by-side comparison between runs.

* **Bulk error resolution tooling:** When multiple fields fail for the same reason, provide a way to apply a fix across all affected fields at once.

* **Test coverage indicator:** Surface a "coverage score" showing how many target fields have been validated in at least one test run.

* **Publish notifications:** Notify relevant stakeholders when a publish completes or fails.
