## 1. Objective

This sub-PRD defines the notification and logging requirements for a Sage Intacct Direct API connection in Data Studio. It does not redefine platform-level notification or logging behavior — it specifies how the Intacct Direct API connection participates in the patterns already established in the [Data Studio: Notifications PRD](https://floqast.atlassian.net/wiki/spaces/Data/pages/4504551492) and [Data Studio: Logging & Audit PRD](https://floqast.atlassian.net/wiki/spaces/Data/pages/4508254281), and identifies any Intacct-specific extensions to those patterns.

**Notifications** — outbound signals sent to downstream FloQast applications and/or customers when: a sync completes successfully, an error occurs, or a sync request is received and queued.

**Logging** — job log entries written at defined points in the sync lifecycle, following the platform job log schema from the Logging & Audit PRD, with one Intacct-specific extension: data change counts broken down by created, updated, and unchanged per data model.

## 2. Notifications

The Intacct Direct API connection participates in the notification framework defined in the [Data Studio: Notifications PRD](https://floqast.atlassian.net/wiki/spaces/Data/pages/4504551492). The following notification triggers apply.

### 2.1 New Data Available — Downstream Applications

**REQ-01: The system must notify registered downstream FloQast applications (e.g., Close, Reporting) when a sync run completes successfully and new data is available.**

*Functional spec: This applies to both scheduled and on-demand sync completions. The notification must include: TLC ID, connection ID, sync request ID (if triggered on-demand), data model(s) updated (e.g., Accounts, GL Balances), completion timestamp, and status. The delivery mechanism aligns with the eventing pattern referenced in the Logging & Audit PRD — specific mechanism is TBD in coordination with the Eventing PRD. This is distinct from user-facing email notifications; it is a machine-to-machine signal to downstream application systems.*

### 2.2 Error Notifications — Customers and Downstream Applications

**REQ-02: The system must notify customers and downstream applications when a connection error occurs.**

*Functional spec: The Intacct Direct API connection participates in the job failure notification pattern defined in the platform Notifications PRD (NOTIF-1). When a sync fails after all retries are exhausted, or when an authentication failure is detected, an email notification is sent to the configured recipients for that connection's TLC. Notification content follows the platform email template: TLC ID, connection name, error type, failure timestamp, error summary (plain language — no internal technical detail), and a direct link to the connection's Logs tab in Data Studio. Notification throttling applies per NOTIF-1 to prevent repeated failures from producing unbounded emails. Auth failure notification behavior additionally aligns with the Auth Type Support PRD.*

### 2.3 Sync Request Acknowledgement — Queue State

**REQ-03: The system must acknowledge every sync request immediately and communicate the current queue state to the requesting application.**

*Functional spec: Queue state acknowledgement follows the pattern defined in the [On Demand Data PRD](https://floqast.atlassian.net/wiki/spaces/Data/pages/4491214936) (REQ-06, REQ-07). Three cases apply:*

| Queue state | Response to requester |
| --- | --- |
| No active sync | Sync has started; sync request ID returned |
| Active sync running, queue open | Request is queued; queued sync request ID returned |
| Active sync + queue full | Request cannot be queued; ID of the existing queued sync returned — requester should monitor that job for completion |

## 3. Logging

The Intacct Direct API connection follows the job log schema defined in the [Data Studio: Logging & Audit PRD](https://floqast.atlassian.net/wiki/spaces/Data/pages/4508254281) (LA1). All entries are immutable once written.

### 3.1 Job Log Schema

Every sync run generates a job log entry using the platform schema:

| Field | Description |
| --- | --- |
| `run_id` | Unique identifier for the run |
| `connection_id` | The Intacct Direct API connection that ran |
| `trigger_type` | `"scheduled"` (midnight trigger) or `"api"` (on-demand trigger) |
| `triggered_by` | User ID + name (if manual); calling system (if api); `"system"` (if scheduled) |
| `start_time` | UTC timestamp |
| `end_time` | UTC timestamp (null if in progress) |
| `duration_ms` | Run duration in milliseconds |
| `status` | `success` / `failed` / `partial` / `pending` |
| `records_processed` | Total count of records successfully processed across all endpoints |
| `records_failed` | Total count of records that failed across all endpoints |
| `error_message` | User-facing plain-language error summary (if failed) |
| `error_detail` | Internal technical detail — **not surfaced to customers** |

### 3.2 Requirements

**REQ-04: The system must write a connection-level job log entry for every sync run.**

*Functional spec: Applies to both scheduled and on-demand runs. Status reflects the overall outcome:* `success` *if all endpoints completed,* `partial` *if some endpoints failed,* `failed` *if all endpoints failed. The* `error_detail` *field is populated for internal engineering use and is never exposed in the customer-facing UI.*

**REQ-05: The system must write an endpoint-level sub-log entry for each individual endpoint within a sync run.**

*Functional spec: Each endpoint (Accounts, GL Balances) is logged independently as a child of the connection-level run log entry, linked by* `run_id`*. Each sub-log entry records:* `run_id`*, endpoint name, start time, end time, status (*`success` *or* `failed`*), records processed, records failed, and error detail if applicable. An endpoint failure does not fail the entire run — other endpoints continue and the connection-level status reflects* `partial`*.*

**REQ-06: The system must write a data change count log entry per data model per sync run.**

*Functional spec: This is an Intacct Direct API extension to the platform log schema. At the completion of each sync run, a supplementary log entry is written per data model (Accounts, GL Balances) breaking down records_processed into: records created (new records written to the FQ data layer), records updated (existing records modified), and records unchanged (fetched from Intacct but identical to what is already stored). This entry is a child of the connection-level run log, linked by* `run_id`*, and is written at info severity.*

| Field | Description |
| --- | --- |
| `run_id` | FK to parent connection-level run log |
| `data_model` | e.g., `"Accounts"`, `"GL Balances"` |
| `records_created` | New records written to FQ data layer |
| `records_updated` | Existing records modified |
| `records_unchanged` | Records fetched but identical to stored data |
| `timestamp` | UTC timestamp of when this entry was written |

## 4. Assumptions

* The notification delivery mechanism (email for customers, machine-to-machine for downstream apps) is determined by the platform Notifications PRD and Eventing PRD. This sub-PRD does not redefine those mechanisms.

* `error_detail` is always internal-only. The customer-facing `error_message` is a plain-language summary with no stack traces or internal field names.

* An endpoint failure results in `partial` status at the connection level unless all endpoints fail, in which case status is `failed`.

* Change count logging (REQ-06) counts changes relative to what is currently stored in the FQ data layer, not relative to the Intacct source.

* Notification preferences, throttling, and additional recipient configuration are managed at the platform level per the Notifications PRD — no Intacct-specific configuration is required.

## 6. Acceptance Criteria

**Notifications**

| AC-ID | Criterion |
| --- | --- |
| AC-NOT-01 | On successful sync completion, a notification is emitted to registered downstream application consumers with connection ID, sync request ID, data model(s) updated, timestamp, and status. |
| AC-NOT-02 | On connection error (auth failure or sync failure after retries exhausted), an email notification is sent to configured TLC recipients per the platform Notifications PRD (NOTIF-1) pattern. |
| AC-NOT-03 | Error notification emails include connection name, error type, failure timestamp, plain-language error summary, and a direct link to the connection's Logs tab. No internal technical detail is included. |
| AC-NOT-04 | Repeated failures do not produce unbounded emails — throttling applies per the platform notification framework. |
| AC-NOT-05 | Every sync request receives an immediate acknowledgement with the current queue state and the relevant sync request ID or existing queued job ID. |

**Logging**

| AC-ID | Criterion |
| --- | --- |
| AC-LOG-01 | A connection-level job log entry is written for every sync run (scheduled and on-demand), using the platform job log schema. |
| AC-LOG-02 | `trigger_type` is set to `"scheduled"` for midnight-triggered runs and `"api"` for on-demand runs. |
| AC-LOG-03 | An endpoint-level sub-log entry is written for each endpoint within a run, linked to the parent run by `run_id`. |
| AC-LOG-04 | An endpoint failure sets that endpoint's sub-log status to `failed` but does not automatically fail the connection-level run; the connection-level status is set to `partial`. |
| AC-LOG-05 | If all endpoints fail, the connection-level run status is set to `failed`. |
| AC-LOG-06 | `error_detail` is populated on failure and is accessible internally; it is never surfaced in the customer-facing UI. |
| AC-LOG-07 | A data change count log entry is written per data model per run, recording records created, updated, and unchanged. |
| AC-LOG-08 | All log entries are immutable once written. |
