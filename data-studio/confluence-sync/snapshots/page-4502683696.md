# **1. Objective**

This sub-PRD defines the workflow by which customers and FloQast implementation specialists establish a FloQast API (Push) connection within FloQast's existing API connection setup workflow. It covers every step from selecting the connection type through configuring datasets, entity association, authentication, and data frequency - culminating in a handoff to auto-configure, which activates the connection on first successful data submission.

The goal is to make FQ API (Push) a first-class, guided connection type that customers and implementation teams can configure without engineering support, while giving FloQast the metadata it needs to correctly receive, associate, and process incoming data.

# **2. Key Benefits**

* FQ API (Push) is surfaced as a native, discoverable connection type within the existing API setup workflow - no separate onboarding path required.
* Guided step-by-step setup reduces configuration errors and shortens time-to-first-data-push.
* Flexible entity handling supports both pre-selected entity assignment and payload-level entity specification, accommodating different customer data architectures.
* Frequency configuration gives FloQast and customers shared visibility into expected data cadence from the start.
* Edit capabilities allow connections to evolve as customer needs change without requiring a full teardown and rebuild.

# **3. Use Cases**

1. A customer IT team sets up a FloQast API (Push) connection for GL Transactions and Balances, maps the entity field from their payload to FQ entity IDs during setup, and begins pushing data immediately after.
2. A FloQast implementation specialist walks a new customer through connection setup during onboarding, selecting Accounts and Balances as the initial datasets and pre-selecting the relevant FQ entities from a list.
3. A customer with data spanning multiple entities flags "entity specified in data" and maps the entity identifier field in their payload so FloQast can route records to the correct entities automatically.
4. A customer adds SL Transactions to an existing active connection by editing the dataset selection in the connection management UI.
5. A customer rotates their API key and updates the connection's authentication settings without disrupting the rest of the connection configuration.
6. A customer archives a connection that is no longer in use, disabling future pushes while preserving historical data.

# **4. Success Metrics**

* Connection setup completed without manual intervention from the FloQast team (self-serve rate).
* Time from connection setup initiation to first successful data submission (target TBD).
* Percentage of configured connections that reach first successful data push.
* Edit operations completed without errors or requiring FloQast support.
* Setup abandonment rate - percentage of users who start but do not complete connection setup (target TBD).

# **5. Assumptions**

* The FQ API (Push) connection type is integrated into FloQast's existing API connection setup UI, not built as a standalone flow.
* Authentication setup is part of this flow, but implementation details are owned by the Authentication & API Key Management sub-PRD.
* FQ entity IDs are available in the system for the customer's organization at setup time, enabling entity pre-selection.
* Customers know which datasets they intend to push at setup time, or can return to edit the connection later.
* Frequency is informational only in Phase 1 and does not drive alerting or automated system behavior.

# **7. Scope of Data**

The following are in scope for connection setup configuration:

* Connection metadata: name, status (active/archived), data frequency
* Authentication credentials (reference to API key - details in Auth & API Key Management sub-PRD)
* Dataset selection (multi-select): Balances, Accounts, FX Rates, Companies, GL Transactions, SL Transactions
* Entity configuration: pre-selected FQ entities, or payload field mapped to FQ entity identifier

The following are out of scope for connection setup and addressed in other sub-PRDs:

* Field-level payload specifications per dataset (per-model sub-PRDs)
* Auto-configure behavior post first push (Auto-Configure sub-PRD)
* Custom fields and dimensions (details included in model sub-PRDs)
* Bank Transactions dataset (future phase)

# **8. Requirements**

‌

**REQ-CS-01: As a customer or FloQast implementation specialist, I want to select FloQast API (Push) as a connection type within FloQast's API connection setup workflow so that I can configure a data push connection through a consistent, guided experience.**

_**Functional spec:** "FloQast API (Push)" is available as a selectable option within FloQast's existing API connection setup workflow. Selecting it initiates the FQ API connection setup flow defined in this document. The option must be clearly labeled and discoverable alongside other connection types._

‌

**REQ-CS-02: As a customer or FloQast implementation specialist, I want to set a connection name during setup so that I can identify and manage the connection later.**

_**Functional spec:** The setup flow includes a required text field for the connection name. The name must be unique within the customer's organization. Connection names can be updated later via the edit flow._

‌

**REQ-CS-03: As a customer or FloQast implementation specialist, I want to configure authentication during setup so that my API pushes are authenticated by FloQast.**

_**Functional spec:** The setup flow includes an authentication configuration step. Full details on authentication options, API key generation, and credential management are defined in the Authentication & API Key Management sub-PRD. The connection setup flow must integrate with that authentication mechanism._

‌

**REQ-CS-04: As a customer or FloQast implementation specialist, I want to select which datasets I will be pushing so that FloQast knows what data to expect and can configure accordingly.**

_**Functional spec:** The setup flow includes a multi-select step for dataset selection. Available options: Balances, Accounts, FX Rates, Companies, GL Transactions, SL Transactions. At least one dataset must be selected to complete setup. Selections drive which endpoints are activated for the connection. Dataset selections can be updated via the edit flow. Any of these datasets can be configured independently._

‌

**REQ-CS-05: As a customer or FloQast implementation specialist, I want to specify which FQ entities the data applies to, or indicate that entity information will be included in the data payload, so that FloQast can correctly associate incoming data.**

_**Functional spec:** The setup flow includes an entity configuration step with two options: (a) Pre-select one or more FQ entities from a list - FloQast will associate all incoming data for this connection with those entities; (b) Flag "entity specified in data" and map the specific field in the customer's payload that contains the FQ entity identifier. Entity field mapping behavior and downstream requirements are defined in the Entity Lookup sub-PRD and per-model sub-PRDs._

‌

**REQ-CS-06: As a customer or FloQast implementation specialist, I want to specify how often I expect to send data so that FloQast has visibility into the intended data cadence for this connection.**

_**Functional spec:** The setup flow includes a frequency field. This field is informational only in Phase 1 - it is stored against the connection but does not drive automated alerts or system behavior. Frequency options are TBD (examples: daily, weekly, monthly, custom). The value can be updated via the edit flow._

‌

**REQ-CS-07: As a customer or FloQast implementation specialist, I want the connection to be ready for auto-configure after setup is complete so that no manual lineage or mapping configuration is required.**

_**Functional spec:** Completing the connection setup flow positions the connection to trigger auto-configure on first successful data submission. The connection setup flow hands off the necessary configuration context (selected datasets, entity mapping, auth) to the auto-configure process. Auto-configure behavior - including auto-creation of endpoint visibility, connection records, and standard mapping - is defined in the Auto-Configure sub-PRD._

‌

**REQ-CS-08: As a customer or FloQast implementation specialist, I want to edit an existing connection so that I can keep connection settings current as needs change.**

_**Functional spec:** Phase 1 edit capabilities: rename connection, update authentication credentials, add or remove datasets, archive connection. Phase 2 edit capabilities: configure custom fields and dimensions. Archiving a connection disables future data pushes but does not delete historical data; the connection remains visible in a read-only archived state. Removing a dataset from an active connection - including any downstream effects on endpoint visibility or existing data - must be handled gracefully (behavior TBD with Engineering)._

# **9. User Interaction and Design**

Connection setup is a sequential, step-by-step flow. Each step must be completed before proceeding to the next. The flow ends with a save action that creates the connection record and readies it for auto-configure.

‌

## **Setup Flow - Step by Step**

1. User navigates to API connection setup within FloQast and selects "FloQast API (Push)" from the list of available connection types.
2. User enters a connection name (required field, must be unique within the organization).
3. User completes the authentication setup step - generating or linking an API key. See Authentication & API Key Management sub-PRD for full detail.
4. User selects one or more datasets from the multi-select list: Balances, Accounts, FX Rates, Companies, GL Transactions, SL Transactions. At least one selection is required.
5. User configures entity association. Two paths:

* Option A - Pre-select entities: User selects one or more FQ entities from a list. All data pushed through this connection will be associated with the selected entities.
* Option B - Entity in data: User flags that entity will be specified in the payload, then maps the specific field in their data that contains the FQ entity identifier.

6. User specifies data send frequency (informational): e.g., daily, weekly, monthly. Field is required but value does not drive system behavior in Phase 1.
7. User saves the connection. The system creates the connection record, stores all configuration, and triggers the auto-configuration of the source-to-target mapping (details in the auto-configure PRD).

‌

## **Edit Flow**

Users access the edit flow from the connection management UI by selecting an existing connection.

‌

Phase 1 editable fields:

* Connection name
* Authentication credentials (update or rotate API key)
* Dataset selection (add or remove datasets)
* Archive connection

‌

Phase 2 editable fields (future):

* Custom fields - additional fields beyond the standard model spec
* Dimensions - additional dimension data to include in the push

‌

Archiving a connection: disables future data pushes; connection remains visible in a read-only archived state; historical data is preserved. Archiving is reversible - when reactivated, the user is prompted to indicate if data should be processed historically as of a certain date or going forward only (default).

‌

## **Edge Cases and Validation**

* Connection name must be unique within the organization - duplicate names should surface an inline validation error.
* At least one dataset must be selected - the setup flow should not allow progression without a dataset selection.
* If "entity in data" is selected, the entity field mapping must be completed before the connection can be saved.
* If a dataset is removed from an active connection via edit, behavior for any in-flight or previously processed data must be handled gracefully (TBD with Engineering).
