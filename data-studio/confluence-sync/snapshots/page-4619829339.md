## Objective

Make entity tagging in Data Studio **reliable, self-service, and trustworthy across the full lifecycle** — so downstream products (Close, Reporting, and Transform) can safely and reliably expose our data to customers.

Entity is foundational: Close scopes reconciliations by it, Reporting requests data by it, and CAS separates end-clients by it. But today entity setup is narrow (range-only, regex, hard-coded row references), consumes implementation/ATC time that should be self-service, and has **no run-time safety net** — once a model is live, entity values that arrive unmapped silently slip through.

This epic closes that gap across the entity lifecycle, delivered as three sub-PRDs:

| Phase | Sub-PRD | What it owns |
| --- | --- | --- |
| **Config — mapping** | [**Entity Mapping v2**](https://floqast.atlassian.net/wiki/spaces/Data/pages/4600561831) | *How* a source encodes entity — the ten encoding patterns, detect-and-confirm setup, connector-level default + per-source override, the `fq_entity` data contract, and safe live-data corrections (backfill). |
| **Config — grouping** | [**Entity Scope Grouping**](https://floqast.atlassian.net/wiki/spaces/Data/pages/4594303031) | *How compactly that's represented* — when multiple entities share the same file (same headers, period, file), represent them as a **single grouped definition / one source row** instead of one row per entity. Multi-select / "All Entities"; overlap detection. |
| **Run time** | [**Unmapped Entity Identification**](https://floqast.atlassian.net/wiki/spaces/Data/pages/4619731022) | *What happens over time* — catching entity values that arrive with no mapping, surfacing them for review without blocking ingestion, and flagging newly-added entities that existing connectors should consider. |

Together they give an Excel-fluent admin a way to set entity up correctly **and compactly** for the common cases, and keep it trustworthy as data flows — without escalating to Support, without silent gaps, and without redundant source clutter.

### How the three fit together

* **Mapping** (Entity Mapping v2) decides *how* a source encodes entity and which FQ entity each value maps to.

* **Grouping** (Entity Scope Grouping) decides *how compactly* that's represented — when many entities share one file, it's a single grouped definition / one source row, not N. This directly tackles the synthetic-source-row proliferation Entity Mapping v2 calls out as a migration risk.

* **Lifecycle** (Unmapped Entity Identification) keeps it honest over time — and its new-TLC-entity highlight is exactly the prompt that tells an admin to re-save an "All Entities" grouped definition so it picks up a newly-added entity.

* ⚠️ **Reconcile before build:** the grouping PRD is written against today's **"Entity Scope tab / definitions"** surface, while Entity Mapping v2 reorganizes entity config to the **connector level** (its OQ-21). The grouping *behavior* is sound; the *surface and terminology* ("definition" vs "source dataset," the Entity Scope tab) should be aligned as these merge.

## Key Benefits

| Benefit | Where |
| --- | --- |
| **Self-service entity setup** — configure entity without writing regex or escalating to Support | Entity Mapping v2 |
| **Pattern coverage matches real customer files** — ten encoding patterns instead of one range-only mechanism | Entity Mapping v2 |
| **Detect + confirm, not "pick from a list of 10"** — the system proposes the pattern and the admin confirms | Entity Mapping v2 |
| **A reliable** `fq_entity` **contract for downstream** — `array<entity>` with clear NULL / shared / multi-entity semantics | Entity Mapping v2 |
| **Safe corrections on live data** — backfill with a diff preview, required reason, and audit trail | Entity Mapping v2 |
| **One row, not many, for shared files** — when entities share a file, a single grouped definition replaces redundant per-entity source rows, giving admins and end users a cleaner, accurate view | Entity Scope Grouping |
| **"All Entities" is one step** — selecting All Entities creates a single grouped definition (a snapshot; re-save to pick up newly-added entities), reducing setup for the common case | Entity Scope Grouping |
| **Precise targeting + overlap detection** — cover a specific subset of entities, and get flagged when two definitions share the same file structure before they create duplicate sources | Entity Scope Grouping |
| **Nothing slips silently** — entity values that arrive unmapped are surfaced proactively for review | Unmapped Entity Identification |
| **Low-noise signal** — per-value suppression keeps the surface trustworthy | Unmapped Entity Identification |
| **Newly-added entities aren't missed** — connectors that previously covered every entity are flagged to consider a new one | Unmapped Entity Identification |
| **Foundation for adoption** — without dependable entity tagging, Close, Reporting, and CAS can't adopt Data Studio | All three |

## Use Cases

| \# | Persona | Scenario | Outcome | Where |
| --- | --- | --- | --- | --- |
| 1 | Excel-fluent admin | First-time entity setup on a connector where entity is in a column | System detects the Entity Column pattern, admin one-click confirms, source values auto-match for review | Entity Mapping v2 |
| 2 | Admin | A connector has multiple source datasets with different entity semantics (some shared, some entity-specific) | Connector-level default applies to most; admin overrides the outliers per source dataset; entity-specific files each get their own definition (no grouping prompt) | Entity Mapping v2 / Grouping |
| 3 | Admin | Wrong-client correction — records tagged to the wrong entity | Edit the config, backdate `entity_start_time`, review the diff preview, enter a reason, confirm; backfill re-tags and the change is audited | Entity Mapping v2 |
| 4 | Admin | A Chart of Accounts file applies to **all** entities | Selects "All Entities"; the system creates **one grouped definition** — the connector shows one source row, and the model's source-data view shows one row | Entity Scope Grouping |
| 5 | Admin | A dimension file applies to **three specific** entities | Multi-selects the three; the grouped row shows the first three names alphabetically with "+X others" on hover | Entity Scope Grouping |
| 6 | Admin | Two definitions on a connector turn out to share the same file structure | The system flags the overlap (same headers + period + file) and offers to merge them into a grouped definition | Entity Scope Grouping (Phase 2) |
| 7 | Admin | A live model keeps ingesting a value whose entity isn't mapped — and no one's auditing | The value flows through on the configured default and is surfaced in **Unmapped Entities**; admin maps / merges / suppresses it | Unmapped Entity Identification |
| 8 | Admin | A new entity is added to the TLC | Connectors that previously covered every entity are highlighted; admin **re-saves the "All Entities" grouped definition** to include it | Unmapped Entity Identification → Grouping |
| 9 | Controller / Auditor | "What was record X tagged with last quarter?" / "what unmapped values appeared and when?" | Historical configs + audit log reconstruct tagging at any point; the review surface shows each unmapped value, its first-seen run, and disposition | All three |

## High-Level Requirements

Each maps to detailed, testable requirements in the sub-PRDs.

### Config — mapping (Entity Mapping v2)

| \# | High-level requirement | Detailed in |
| --- | --- | --- |
| HL-1 | **Configuration lives on the connector** — a connector-level default that cascades to all source datasets, with a per-source override; no entity step in model setup | EM1, EM2 |
| HL-2 | **Support the ten encoding patterns** — shared/global, entity column, per-sheet, per-file, wide-format, value-substring, connector-level, plus the risky/escape-hatch ones | EM3 |
| HL-3 | **Detect → confirm → side-by-side → manual** — propose the pattern from a sample and let the admin confirm, with graceful fallback; plus an opt-in advanced path | EM5, EM9 |
| HL-4 | **Source-value → FQ-entity mapping** — auto-match, 1-to-many fan-out, and a default for unmapped values | EM4 |
| HL-5 | **A defined** `fq_entity` **data contract** — `array<entity>` with NULL / empty-array (shared) / single / multi semantics and downstream queryability | EM6 |
| HL-6 | **Safe live-data corrections** — `entity_start_time`-driven backfill with diff preview, required reason, destructive gate, and audit log | EM7 |
| HL-7 | **Completeness warning** — warn at save time (warn-and-allow) when a source would land `fq_entity = NULL` | EM8 |

### Config — grouping (Entity Scope Grouping)

| \# | High-level requirement | Detailed in |
| --- | --- | --- |
| HL-8 | **Multi-select entity picker for all file types** — single, subset, or "All Entities" in one step (COA, balance, dimension); each path produces one definition row; entities listed alphabetically | ESG 1 |
| HL-9 | **"All Entities" → a single grouped definition** — one row, not per-entity rows; it's a snapshot (re-save with "All Entities" to capture newly-added entities; no automatic update) | ESG 2 |
| HL-10 | **Grouped row display** — first 3 entity names alphabetically + "+X others" on hover, shown consistently in both the connector source view and the model's source-data view (one row regardless of entity count) | ESG 3, ESG 4 |
| HL-11 | **Edit a grouped definition in place** — add/remove entities without delete-and-recreate; re-saving captures account changes | ESG 5 |
| HL-12 | **Overlap detection** *(Phase 2)* — when definitions share the same file structure (same headers + period + file), flag a non-blocking merge prompt | ESG 6 |

## Out of Scope (epic-level)

* **TLC entity list management** — creating / renaming / archiving the entities themselves is a TLC-level admin function owned elsewhere; this epic consumes the entity list.

* **Grouping across connectors** — grouped definitions are within a single connector; cross-connector grouping is out.

* **Automatic merging or auto-update** — overlap merges require user confirmation, and grouped "All Entities" definitions update only on admin re-save, never automatically.

* **Per-downstream-product entity UX** — how Close / Reporting / CAS / Compliance / Consolidation surface and consume entity is each product's own concern; this epic owns the data contract and the admin-facing config + lifecycle.

* **Aggregate / data-domain modeling** — owned by the Platform team; the `fq_entity` array partially absorbs the multi-tag case but doesn't replace a first-class aggregates concept.
