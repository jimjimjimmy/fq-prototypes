## 🎯 Objective

Enable Data Studio to support multi-file data sources by allowing Models to be built from grouped and linked datasets. This removes the one-file-to-one-model constraint, supports customers whose data providers deliver data across multiple files, and unlocks downstream capabilities — including AI Variance and reporting — that require richer data.

This Idea also introduces self-service dataset definition for file-based connectors: admins and implementation teams can configure filename patterns, define column schemas, and set accounting period rules without FloQast engineering involvement.

This Idea also introduces FloQast-managed global dimensions (initially FX/currency rates), reducing the configuration burden on customers for data that can be centrally maintained.

This Idea also encompasses the Catalog user experience redesign required to support these new capabilities at scale: retiring the Lineage tab and merging it into a unified Catalog tab, and replacing the card-based model list with a searchable, filterable AG Grid table. Together, these changes ensure that as customers configure more and richer datasets, the Catalog experience scales to match.

## 💡 Key Benefits

1. **Broader data provider support** — customers whose providers split data across multiple files can now configure a single Model without needing pre-processing or custom engineering work.

2. **No-code dataset linking** — a guided UI replaces raw SQL join logic, making multi-dataset configuration accessible to admins and implementation teams without technical SQL knowledge.

3. **Richer data for AI** — unlock AI Variance and other downstream capabilities that require transaction-level data enriched across multiple sources.

4. **Self-service file configuration** — clients and implementation teams add and manage file definitions directly in Data Studio, without FloQast integrations team involvement.

5. **FloQast-managed global dimensions** — shared dimensions like FX/currency rates are maintained centrally by FloQast, removing the need for each customer to configure and upload this data themselves.

6. **Unified Catalog navigation** — retiring the Lineage tab and merging it into a single Catalog tab eliminates the confusing dual-entry structure, giving admins one clear home for all model management.

7. **Scalable catalog discoverability** — an AG Grid table with real-time search, column filtering, and sorting replaces the card view, making it practical to manage large model catalogs self-service without FQ support.

## ✅ Use Cases

**Complex Multi-File Provider** A customer's data provider delivers GL transactions in one file and a separate "Transaction Types" file each period. An admin configures a Model in Data Studio that links both datasets — defining the join key (e.g., Transaction_Type_ID) — so FloQast receives a single unified dataset for reporting without any pre-processing.

**Grouped Files** A customer uploads separate GL files for each subsidiary (entity). An admin groups these into a single dataset so they are treated as one continuous source, without needing to manually combine files before upload or without having to define a separate model for each dataset.

**AI Variance Enablement** A customer wants to use AI Variance. Their transaction data lives in one file and additional data located in another file is needed to accurately define the field mapping. By linking the two datasets in Data Studio, AI Variance has the enriched transaction-level data it needs to run.

**Self-Service File Configuration** A new client is onboarding with an SFTP connector. The implementation team adds the file definition directly in Data Studio — uploading a sample filename, confirming the AI-detected pattern as token chips, and saving — without requiring FloQast engineering to write regex.

**Schema Change Detection** A client's data provider updates their GL file format — two columns are renamed. The admin opens the dataset's Schema tab in Edit mode, reviews the detected changes, corrects any type mismatches, and saves without re-running the full Add Dataset wizard.

**FloQast-Managed FX Rates (need to confirm)** A customer operates across multiple currencies. Instead of uploading FX rate files themselves, they activate the FloQast-managed global FX rate dimension, which FloQast maintains centrally. The correct rates are automatically available for their Models without any customer-side configuration.

**Unified Model Navigation** An admin opens Data Studio and lands directly on the Catalog tab — no need to choose between Catalog and Lineage. They click any model and arrive at a single, consistent Model detail view regardless of how they navigated there.

**Finding a Model at Scale** A CAS customer has 20+ models configured across multiple ERP types. An admin types a model name in the search bar and the table filters in real time — no scrolling through cards or navigating across tabs.

## 🤔 Assumptions

1. Multi-file linking and grouping configuration is performed by admins and FloQast implementation teams. Direct configuration by individual end users (without admin permission) is not in scope. Note that in the future we will likely need to expand visibility for ReBAC, but that is out of scope for now.)

2. The linking UI (guided join key definition) is sufficient for the use cases in scope — raw SQL access is not required.

3. Global dimension scope for Q2 is limited to FX/currency rates pending further engineering alignment.

4. Customers using multi-file Models must have their connectors configured and datasets available in Data Studio before linking can be configured.

5. The Catalog/Lineage merge is a prerequisite for the Search & Filter landing page — both ship together as a unified Catalog experience.

6. Self-service file definition (filename pattern, schema, accounting config) is scoped to SFTP connectors for v1. API-based connectors follow the same schema definition step but do not require filename pattern configuration.

**MF1 — Group Schema-Identical Files into a Single Dataset**

*User Story: As an admin, I can group multiple files with identical schemas into a single dataset so they are treated as one continuous source.*

**AC-MF1-01 — Grouped dataset can be created from multiple files** Given I am configuring source datasets for a Model When I select multiple files with identical schemas Then I can group them into a single Grouped Dataset And the group is treated as one dataset in the Model

---

**MF2 — Link Multiple Source Datasets in a Model**

*User Story: As an admin, I can add more than one source dataset to a single Model.*

**AC-MF2-01 — Multiple datasets can be added to a Model** Given I am configuring a Model in Data Studio When I add a second source dataset Then both datasets are associated with the Model And I am prompted to define how they link together

**AC-MF2-02 — One dataset must be designated as Primary** Given a Model has more than one source dataset linked When I attempt to proceed past source configuration Then the system requires exactly one dataset to be designated as Primary And the Primary dataset determines the base schema for field mapping

---

**MF3 — Define How Datasets Join Without Writing SQL**

*User Story: As an admin, I can define the relationship between two linked datasets using a guided UI rather than writing SQL.*

**AC-MF3-01 — Join key can be defined through a guided UI** Given I have two datasets linked in a Model When I open the linking configuration Then I can select the join key field from each dataset using a dropdown And the system shows a preview of how the datasets will be combined

**AC-MF3-02 — Linked dataset output is available to downstream consumers** Given a Model with linked datasets has been published When AI Variance or reporting consumes the Model Then they receive a single unified dataset reflecting the defined join

---

**MF4 — Configure Filename Pattern and Schema Definition Without Writing Regex or Code**

*User Story: As an admin or implementation team member, I can add and configure a file definition in Data Studio — including filename pattern, column schema, and accounting period — without FloQast engineering involvement and without writing regex.*

Details in [File Naming Pattern](https://floqast.atlassian.net/wiki/spaces/Data/pages/4513169493) · [Schema Definition](https://floqast.atlassian.net/wiki/spaces/Data/pages/4523196435) · [Accounting Config](https://floqast.atlassian.net/wiki/spaces/Data/pages/4523163672) sub-PRDs.

**AC-MF4-01 — Filename pattern inferred from sample file** Given I upload or paste a sample filename When the system processes it Then the filename pattern is detected automatically and presented as named token chips (e.g., month_name, year) And the raw regex is generated by the system and never shown to the admin by default

**AC-MF4-02 — Schema detected and confirmed before dataset is published** Given a sample file has been provided When I reach the Schema Definition step Then the system detects column names and data types And I can review, correct, and confirm the schema before the dataset is saved

**MF5 — Activate a FloQast-Managed Global Dimension**

*User Story: As an admin, I can activate a global dimension maintained by FloQast without uploading or configuring the data myself.*

**AC-MF5-01 — Global dimension can be activated from Data Studio** Given a global dimension (e.g., FX rates) is available in Data Studio When I activate it for my workspace Then the dimension is available in my Models without any file upload or mapping required

## ⚠️ Out of Scope

* **End-user dataset linking configuration** — linking and grouping is managed by admins and FloQast implementation teams only. Individual end users (e.g., staff accountants, reviewers) cannot configure source datasets.

* **Raw SQL access** — the linking UI abstracts join logic into a guided interface. Writing raw SQL join conditions is not supported.

* **Customer-managed global dimensions** — customers cannot define or upload their own global dimensions in Q2. Global dimensions are FloQast-managed only.

* **Write-back / bi-directional sync** — FloQast will not push data back to source systems. Read-only ingestion only in this PRD. (Future consideration is bi directional.)

* **Connectors tab redesign** — connector configuration is moved out of Model detail views but the Connectors tab itself is not redesigned in this Idea.

* **Bulk model actions** — bulk publish, archive, or delete is not in scope for the catalog redesign.

* **Non-SFTP file definition** — self-service file definition (filename pattern configuration) is scoped to SFTP connectors for v1.

* **Schema versioning** — behavior when a published dataset's schema changes (new/removed columns, type changes) is a known gap deferred to a future PRD.
