# **1. Objective**

This PRD defines Phase 6 of the API Endpoint Management work within FloQast Data Studio. While the parent PRD establishes patterns for pull-based API data ingestion - where FloQast initiates requests on a schedule - this PRD extends that framework to support push-based (webhook) integrations, where external source systems initiate data delivery to FloQast rather than the other way around.

The primary users are FloQast admins and implementation team members who need to configure incoming webhook connections, provision secure endpoints for source systems to post data to, manage multiple data-type pushes per connection, and surface errors - all without engineering involvement. This work completes the API connection framework established in the parent PRD and enables FloQast to support data-forward customers whose systems prefer event-driven delivery over polling.

# **2. Key Benefits**

* No-engineering webhook setup: admins and implementors can provision and configure push connections directly from Data Studio without opening a support ticket.
* Secure inbound data ingestion: FQ validates all incoming requests via configurable authentication, rejecting unauthorized payloads and logging failures.
* Event-driven data availability: push connections enable near-real-time data delivery without polling overhead, complementing scheduled pull syncs.
* Error visibility: admins have clear visibility into failed push events - auth failures, schema mismatches, processing errors - and can diagnose issues independently.
* Multi-data-model support: a single push connection supports multiple endpoints for different data types, mirroring the pull endpoint pattern from the parent PRD.
* Consistent framework: push is established as a first-class pattern alongside pull within the Data Studio connection model, setting the foundation for future push-capable sources.

# **3. Use Cases**

1. Webhook connection setup: A FloQast implementor is onboarding a customer whose ERP supports outbound webhooks. The implementor navigates to Data Studio, creates a new push API connection, selects an inbound auth method, and receives a unique webhook URL to register in the source system - completing setup without engineering.
2. Multi-model push on one connection: A customer's system pushes both journal entry and account data using the same credentials. An implementor configures two push endpoints on the same connection, each mapped to a different data type, without duplicating the connection setup or auth configuration.
3. Payload sample capture: After the first valid test payload arrives, an admin views the captured sample in Data Studio to understand the schema and support downstream data mapping work handled in a separate workflow.
4. Error investigation: A push connection starts logging auth failures after a source system credential rotation. An admin navigates to the push event log, identifies the failure type, updates the shared secret in the connection edit view, and confirms the next payload is accepted.
5. Connection edit: An implementor needs to update the failure handling behavior for a push connection from "Log and alert" to "Halt." They edit the existing connection configuration from the detail view without recreating the connection.
6. Live connection validation: Before handoff to the customer, an implementor sends a test payload from the source system to the FQ webhook URL and confirms receipt, auth success, and correct parsing in the test view.

# **4. Success Metrics**

| **Metric** | **Target / Description** |
| --- | --- |
| Push connection setup success rate | Greater than 95% of new push connections successfully provision a webhook URL and receive a test payload without error |
| Inbound auth failure rate (post-setup) | Less than 5% of inbound push requests fail authentication due to misconfiguration after initial setup is complete |
| Error surfacing coverage | 100% of failed push payloads (auth or processing) generate a visible log entry accessible to the admin - no silent failures |
| Admin self-service resolution | Admins can identify and resolve broken push connections (e.g., auth update, failure mode change) without engineering support |
| Multi-endpoint configuration success | Admins can configure multiple push endpoints on the same connection without support involvement |
| Time to first valid payload | Target SLA TBD; should align with overall implementation onboarding SLA |

# **5. Assumptions**

* The source system is capable of sending HTTP POST requests to a provisioned URL. FQ does not control or configure the source system's push behavior - the customer is responsible for registering the webhook URL.
* Source systems are responsible for retry logic. FQ will acknowledge receipt with an immediate HTTP 200 and process asynchronously; processing outcome is not communicated in the synchronous response.
* Events may arrive out of order. FQ should not assume payload sequencing unless an explicit ordering mechanism is configured.
* A unique webhook URL is provisioned per connection. Multiple push endpoints on the same connection share the same base connection credentials but are differentiated by path or event type identifier (mechanism TBD - see Open Questions).
* Field mapping from the incoming payload to the FQ data model is handled in a separate PRD and is not in scope here. However, capturing a sample payload to support that downstream work is in scope.
* Push connections do not have a sync frequency setting in the same sense as pull endpoints. Volume expectation configuration is informational, used for FQ's internal rate-limiting and queue planning.
* Inbound auth method selection is an open question. HMAC signature verification and shared secret header are recommended as the baseline for launch (see Open Questions).
* The current FQ API key management framework (used for outbound/pull auth) is a reference, but inbound auth for push requires a distinct configuration model.

# **6. Milestones**

1. Phase 6.1 - Foundation: Core push connection setup. Admins can create a push connection, select an inbound auth method, generate and view the webhook URL, define event types, configure failure handling, and set volume expectations. Webhook URL is provisioned and ready to register in the source system.
2. Phase 6.2 - System Processing: FQ receives, authenticates, and processes incoming push payloads. Includes HTTP 200 acknowledgment, async processing, idempotency/deduplication handling, and handoff to the data pipeline. Sample payload captured on first successful receipt.
3. Phase 6.3 - Observability and Testing: Error surfacing for failed push events (auth, schema, processing). Push event log visible in the connection detail view. Test connection flow allowing admins to validate setup before go-live.
4. Phase 6.4 - Management and Multi-Push: Edit push connection configuration. Support for multiple push endpoints on the same connection with different data models, mirroring the pull endpoint pattern. Connection detail view updated to surface push endpoint list and per-endpoint actions.

# **7. Scope of Data**

The following data objects and entities are in scope:

‌

* Push connection configurations: connection name, source system, inbound auth method, auth credentials (hashed/stored securely), webhook URL, event type definitions, failure handling mode, and volume expectations.
* Push endpoint configurations: per-endpoint settings including endpoint path or routing identifier, event type or data type, activation status, last received timestamp, and error count.
* Inbound payload logs: per-event metadata including receipt timestamp, event ID (if present in payload), auth validation status, processing status, failure type, and error description.
* Sample payloads: the first valid payload received on each push endpoint, stored for use in downstream data mapping work.
* Error events: records of failed push events including failure category (auth, schema validation, processing error), timestamp, payload excerpt, and resolution status.

‌

Explicitly out of scope:

* Field mapping from push payload to FQ data model (covered in separate PRD)
* Outbound/pull API endpoint configuration (covered in parent PRD Phases 1–5)
* Source system configuration (FQ provides the webhook URL; source system setup is the customer's responsibility)

# **8. Requirements**

**REQ-01**

**As an admin or implementor, I want to set up a new push API connection in Data Studio so that I can configure FQ to receive data from an external system that initiates the push.**

_Functional spec:_ The connection setup flow must guide the user through: naming the connection, selecting or entering the source system, confirming the integration type as Push/Webhook, selecting an inbound auth method, completing auth-method-specific configuration, defining event types, configuring failure handling, and setting volume expectations. On completion, FQ provisions a unique webhook URL for the connection.

**REQ-02**

**As an admin or implementor, I want FQ to generate a unique webhook URL for my push connection so that I can register it in the source system as the destination for data delivery.**

_Functional spec:_ On creation of a push connection, FQ must generate and display a unique, connection-scoped webhook URL. The URL must be copyable from the connection detail view. The URL must remain stable for the life of the connection unless explicitly regenerated by the admin. Instructions for registering the URL in a source system must be surfaced alongside the URL.

**REQ-03**

**As an admin or implementor, I want to configure how FQ verifies incoming requests from the source system so that only authorized systems can push data to FQ.**

_Functional spec:_ The connection setup and edit flows must support the selected inbound auth method(s) - see Open Questions for final decision. For each method, the UI must surface the relevant configuration fields (e.g., shared secret value, HMAC signing key, IP ranges) and instructions for what the source system must include in its requests. FQ must reject any inbound request that fails authentication, respond with a 401, and log the failure. Auth credentials must be stored securely and not displayed in plaintext after initial setup.

**REQ-04**

**As an admin or implementor, I want to define which event types or data types a push endpoint will receive so that FQ can route and process incoming payloads correctly.**

_Functional spec:_ When configuring a push endpoint, the user must be able to specify the event type(s) the endpoint will accept (e.g., Journal Entry Posted, GL Balance Updated). For source systems with known event type enumerations, the UI should surface those as options. This configuration is used by FQ for payload routing and downstream processing.

**REQ-05**

**As an admin or implementor, I want to configure how FQ handles payloads that fail processing so that I can control system behavior when errors occur.**

_Functional spec:_ Each push connection must support a configurable failure handling mode with at least three options: (1) Log and alert - record the error and notify the admin; (2) Skip and continue - log the error and discard the payload without halting; (3) Halt - stop processing subsequent payloads until the issue is manually resolved. The selected mode must be visible in the connection detail view.

**REQ-06**

**As an admin or implementor, I want to configure the expected push frequency for a connection so that FQ can plan for rate limiting and queue management.**

_Functional spec:_ During setup and edit, the user must be able to indicate approximate push frequency (e.g., real-time/event-driven, hourly, daily batch, or custom). This value is informational and used for FQ's internal rate-limiting and queuing. It does not restrict or throttle the source system.

**REQ-07**

**As an admin or implementor, I want to send a test payload to my push connection so that I can verify the configuration is correct before going live.**

_Functional spec:_ The connection setup flow and the connection detail view must include a test action. The test view must show: whether the test payload was received, whether auth validation passed, and whether the payload was parseable against the configured event type. A clear pass/fail state must be displayed with sufficient error detail for the admin to diagnose and correct the configuration without engineering.

**REQ-08**

**As an admin or implementor, I want to view a sample of data received on a push endpoint so that it can inform downstream data mapping configuration.**

_Functional spec:_ FQ must capture and store the first valid payload received on each push endpoint as a sample. The sample must be viewable from the connection detail view. The sample must reflect the raw payload structure as received, prior to any transformation. This sample is for reference only; the data mapping workflow is handled separately.

**REQ-09**

**As an admin or implementor, I want to edit an existing push connection configuration so that I can update settings without recreating the connection from scratch.**

_Functional spec:_ Each push connection must have an edit action accessible from the connection detail view. Editable fields must include: inbound auth method and credentials, event type definitions, failure handling mode, and volume expectations. The webhook URL must not change when other settings are edited, unless explicitly regenerated by the admin. Current values must be pre-populated in the edit view.

**REQ-10**

**As FloQast (system), when data is pushed to a configured webhook endpoint, FQ must receive, authenticate, and process that payload so that it flows into the FQ data pipeline.**

_Functional spec:_ FQ must respond to inbound push requests with an immediate HTTP 200 acknowledgment and process the payload asynchronously. Processing must include: auth validation, payload parsing against the configured event type, deduplication using an event ID if present in the payload, and handoff to the data pipeline. Payloads that fail auth must be rejected with a 401 and logged. Payloads that fail parsing must be handled per the configured failure handling mode. Previously stored good data must not be overwritten by partial or failed payloads.

**REQ-11**

**As an admin or implementor, I want to see errors surfaced when incoming push data fails authentication or processing so that I can diagnose and resolve issues without engineering involvement.**

_Functional spec:_ FQ must maintain a push event log per connection, accessible from the connection detail view. Each log entry must include: timestamp, event ID (if present), failure category (auth, schema validation, processing), and a description of the error. Auth failures must be logged even when the payload is rejected before processing. The log must support filtering by status (success / failure) and time range.

**REQ-12**

**As an admin or implementor, I want to configure multiple push endpoints under the same connection when different data models need to be received from the same source system, so that I can handle multiple data types without duplicating connection credentials.**

_Functional spec:_ A single push connection must support multiple push endpoints, each with its own event type definition and endpoint path or routing identifier. All endpoints under the same connection share the same inbound auth configuration. Each endpoint is independently activatable and deactivatable, and each appears in the connection detail view with its own status, last-received timestamp, and error count. This mirrors the pull endpoint model from the parent PRD.

# **9. User Interaction and Design**

**Setup Wizard Flow**

The push connection setup follows a 9-step wizard (data mapping, Step 6, is handled in a separate workflow and is excluded here):

‌

1. Connection Basics: Name the connection and select the source system (or enter a custom source name).
2. Select API Type: Confirm the integration type as Push / Webhook. This branches the setup flow to the push-specific path.
3. Configure Inbound Authentication: Select an auth method and complete the relevant fields. Instructions for what the source system must include in its requests are surfaced inline alongside the configuration fields.
4. Generate Webhook URL: FQ generates a unique webhook URL for the connection. Displayed with a copy action and registration instructions. URL is stable until explicitly regenerated.
5. Define Event Types: Select or enter the event types this endpoint will accept. Source systems with known enumerations surface options in the UI.
6. Configure Failure Handling: Select the failure mode (Log and alert / Skip and continue / Halt). Default: Log and alert.
7. Set Volume Expectations: Indicate expected push frequency (real-time, hourly, daily batch, custom). Informational; used for FQ-side queue planning.
8. Test the Connection: Admin sends a test payload from the source system (or pastes one manually). FQ displays receipt status, auth result, and parse result. Pass/fail shown with actionable error detail.
9. Review and Activate: Summary of all configuration. Admin activates the connection. FQ confirms the webhook is live and listening.

‌

**Connection Detail View - Push Additions**

* Webhook URL displayed prominently at the top of the push connection detail, with a copy action and an option to regenerate (with appropriate confirmation warning).
* Push endpoint list: mirrors the pull endpoint list pattern. Each row shows endpoint name, event type, activation status, last received timestamp, and error count. Actions: Edit, Test, Activate/Deactivate.
* Add Endpoint action: allows adding additional push endpoints to the connection, each with its own event type and path. All share the connection-level auth.
* Push event log panel: filterable log of received push events per connection. Columns: timestamp, event ID, status (success/failed), failure category, error description.
* Sample payload viewer: shows the first valid payload received per endpoint, accessible from the endpoint row. Raw structure, pre-transformation, for use in data mapping.
* Edit action: available at the connection level and per endpoint. Pre-populates current values. Auth credentials shown as masked; re-entry required to update.

# **10. Open Questions**

| **Question** | **Owner** | **Notes** |
| --- | --- | --- |
| What inbound auth methods will FQ support at launch? | PM / Engineering | Recommended: HMAC signature verification (primary) + shared secret in header (secondary). Additional options to consider: API key in header, IP allowlisting as add-on layer. Decision required before setup UI is finalized. Auth method selection drives the configuration fields surfaced in the setup wizard. |
| How are multiple push endpoints on the same connection differentiated? | Engineering | Options: unique URL path suffix per endpoint (e.g., /webhook/conn123/journal-entries), query parameter, or event type identifier in the payload header. Decision affects webhook URL structure and routing logic. |
| How does FQ deduplicate inbound events? | Engineering | Is an event ID expected in the payload? Required or optional? FQ should use this for idempotency - processing the same event ID twice should be a no-op. Need to define behavior when no event ID is present. |
| What happens when inbound push volume exceeds configured expectations? | Engineering | Options: excess payloads are queued, dropped with a 429 response, or accepted but flagged. Behavior should align with the failure handling mode configured for the connection. |
| What is the workflow to rotate or regenerate the webhook URL? | PM / Security | If the URL is suspected to be compromised, the admin needs a way to regenerate it. Should there be a grace period where the old URL continues to work? How is the customer notified to update their source system? |
| How long are push event logs and sample payloads retained? | Engineering / Legal | Retention policy needed for the event log and sample payload store. May vary by data sensitivity and customer tier. |
| Are there OAuth scope implications for push connections from systems that also have pull endpoints? | Engineering | If a connection supports both pull and push, does the push configuration require any additional OAuth scopes or elevated permissions from the source system? |

# **11. Out of Scope**

* Field mapping from push payload to FQ data model - covered in a separate PRD. Sample payload capture (REQ-08) supports this work but the mapping itself is not in scope here.
* Pull / outbound API endpoint configuration - covered in parent PRD Phases 1–5.
* Source system configuration - FQ provides the webhook URL; registering that URL in the source system is the customer's responsibility.
* Auto-provisioning of push endpoints on standard connection setup - push connections require manual configuration. There are no known standard push endpoints equivalent to the auto-provisioned pull endpoints.
* On-demand internal trigger interface - the internal FQ trigger for on-demand data runs is covered in parent PRD Phase 4 and is not in scope here.
* Write-back or bi-directional sync - this PRD covers read-only inbound data ingestion only, consistent with the parent PRD.
* External customer-facing push trigger API - push is initiated by the source system. FQ does not expose a public API for customers to trigger pushes.
* Frequency / scheduling configuration for push endpoints - push delivery timing is controlled by the source system. Volume expectations (REQ-06) are informational only.
