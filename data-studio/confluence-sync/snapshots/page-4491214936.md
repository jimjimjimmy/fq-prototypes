# **1. Objective**

This sub-PRD defines the requirements for on-demand data refresh within FloQast Data Studio for API connections. It covers the trigger interface, sync request processing, audit logging, downstream notification, and the Data Studio user experience for initiating and monitoring manual syncs. The goal is to enable users of downstream FloQast applications -Close and Reporting -as well as Data Studio admins, to request fresh data outside of scheduled sync windows and receive that data with a target latency of under 30 seconds (subject to external API constraints), while continuing their work without interruption during the refresh.

This work establishes the foundational trigger and delivery pattern for on-demand data runs and is designated as Phase 4 of the parent API Endpoint Management PRD. It does not duplicate endpoint configuration, scheduled sync, or endpoint library requirements, which are addressed in the parent PRD and its other sub-PRDs.

# **2. Key Benefits**

* Users can trigger a data refresh and continue working -the application does not stall during the sync.
* Fresh data delivered in under 30 seconds (target, subject to external API constraints).
* Downstream applications (Close, Reporting) are notified when new data is available -no polling required.
* Complete audit trail of all sync requests, including trigger source (user or system) and user identity when applicable.
* Concurrent sync request management prevents system overload and keeps requesting applications informed of sync state.
* Data Studio users have direct visibility into active and recently completed syncs via the connection sync log.

# **3. Use Cases**

1. A Close user triggers a reconciliation refresh. Close sends an on-demand sync trigger to Data Studio with the relevant period and entity parameters. Data Studio acknowledges the request, runs the sync, and notifies Close when new data is available -targeting under 30 seconds where external API constraints permit.
2. A Reporting user needs fresh data for a completeness report. Reporting sends a sync trigger with the relevant scope. The user continues working while the sync processes and receives a notification when updated data is ready.
3. A Data Studio admin opens a connection detail view and clicks "Sync Now" to manually push a refresh. The connection sync log immediately shows the sync as in-progress. The admin can navigate away and continue other work while the sync completes in the background.
4. A sync request arrives while another sync for the same connection is already running. Data Studio returns a "sync in progress" response with the active sync request ID, allowing the downstream application to decide whether to queue a new request or monitor the existing one.
5. A queued sync already exists behind an active sync. A third request arrives. Data Studio rejects the third request and directs the application to monitor the already-queued sync rather than stacking additional requests.
6. A sync request arrives that appears to be a full historical data pull. Data Studio flags the request as long-running, communicates the expected processing time to the requesting application, and does not process it under the standard on-demand SLA.

# **4. Success Metrics**

| **Metric** | **Target** |
| --- | --- |
| On-demand data delivery latency | Under 30 seconds end-to-end from trigger receipt to data-available notification; subject to external API constraints |
| Downstream notification reliability | 100% of successful data runs emit a notification to the requesting application; no silent failures |
| Sync request logging completeness | 100% of sync requests logged with trigger type, source, user identity (if user-triggered), status, and timestamps |
| Concurrent request handling | 100% of duplicate/concurrent sync requests handled gracefully with an appropriate status response and active sync ID returned |
| Historical request detection | 100% of full historical data requests flagged and communicated as long-running before processing |
| Audit trail integrity | All sync log entries are immutable once written; trigger source and user identity preserved for all user-triggered requests |

# **5. Assumptions**

* The trigger interface type (webhook, internal event bus, or direct API call) is TBD and must be defined in collaboration with Close and Reporting engineering teams.
* The downstream notification mechanism (event bus, callback, or polling endpoint) is TBD and must be decided alongside the trigger interface.
* Close and Reporting will define their side of the trigger interface as part of this project; the trigger mechanism does not currently exist.
* On-demand requests are incremental by default -scoped to a period/date range, entity, and other criteria as provided by the requesting application.
* A "full historical request" is any sync request not scoped to a specific recent period; the exact threshold will be defined with engineering (see Open Questions).
* The maximum queue depth is one request behind an active sync; no additional stacking beyond that is permitted.
* Rate limiting interactions between on-demand and scheduled syncs for the same connection must be managed by the system.
* The trigger interface is internal and authenticated; external customer-facing triggers are out of scope.
* Users in Data Studio who trigger a manual sync are authenticated FloQast users; their identity is available for audit logging.

# **6. Milestones**

7. **Phase 1:** Trigger Interface Definition -Define and document the internal trigger interface in collaboration with Close and Reporting teams. Finalize the request schema: connection, endpoint set, period/date range, entity, and other applicable criteria.
8. **Phase 2:** Core On-Demand Processing -Implement trigger receipt, connection identification, data fetch from the external API, pipeline processing, and data store write. System acknowledges trigger immediately and processes asynchronously.
9. **Phase 3:** Logging and Audit Trail -Implement sync request logging (trigger type, user identity, connection, endpoint set, status, timestamps), per-endpoint sub-logging for multi-endpoint syncs, and immutable audit trail.
10. **Phase 4:** Downstream Notification -Implement the notification mechanism to inform downstream applications (Close, Reporting) when a data run completes, including the original sync request ID, connection, data object type(s), and status.
11. **Phase 5:** Data Studio UI -Surface "Sync Now" capability in the connection detail view, active sync state indicator, and sync log with real-time status updates per the design specifications.
12. **Phase 6:** Concurrency and Queue Management -Implement duplicate and concurrent request detection, single-request queue logic, and full historical request detection and flagging.

# **7. Scope of Data**

**In scope:**

* Sync request records: trigger type (user/system), trigger source (application name or "Data Studio"), user ID and display name (if user-triggered), request timestamp, connection ID, endpoint set, request parameters (period/date range, entity, other criteria), status (queued/in-progress/complete/failed), and is_historical flag.
* Sync run logs: per-run metadata including start time, end time, status, records processed, and error details.
* Per-endpoint sub-logs: endpoint name, request timestamp, response status, records processed, and error details -created when a sync covers multiple endpoints.
* Queue state: active sync request ID and queued sync request ID per connection, used to enforce the single-queue-depth limit.
* Downstream notification event payloads: sync request ID, connection ID, data object type(s), status, and notification timestamp.

**Explicitly out of scope for the data layer:**

* Field-level transformation mappings (covered in a separate PRD).
* Fivetran-ingested data objects.
* Full historical data run payloads (flagged and routed separately; not subject to this sub-PRD's latency targets).

# **8. Requirements**

1. **REQ-01  As a downstream FloQast application (e.g., Close, Reporting), I want to trigger an on-demand data run for a specific connection so that I can get fresh data when a user action requires it.**

_**Functional spec:** The system must expose an internal trigger interface (TBD -see Open Questions) that accepts a sync request scoped to a connection, with the relevant request conditions: period/date range, entity, and other criteria as determined by the requesting application and its data needs. The interface must be authenticated and scoped to internal FloQast applications only. The system must acknowledge receipt of the trigger immediately and process asynchronously._

2. **REQ-02  As a Data Studio user, I want to trigger a data refresh from the connection detail view so that I can get updated data without waiting for the next scheduled sync.**

_**Functional spec:** The connection detail view must include a "Sync Now" action. When triggered, a sync record must immediately appear in the connection sync log with "In Progress" status. The user must be able to continue navigating and working in Data Studio while the sync runs in the background. When there is already a request, the user should be able to see that there is already an in progress sync happening._

3. **REQ-03  As a downstream FloQast application, I want to receive a notification when a triggered data run completes so that I can act on new data without polling.**

_**Functional spec:** When a data run completes (success or failure), the system must emit a notification to the requesting application. The notification must include the original sync request ID, connection ID, data object type(s) updated, and status (complete/failed). The target end-to-end latency from trigger receipt to notification is under 30 seconds, subject to external API constraints. The notification mechanism is TBD (see Open Questions)._

4. **REQ-04  As the system, when an on-demand sync is requested, I want to identify the relevant connection, fetch updated data, process it through the pipeline, and write it to the data store so that downstream applications receive normalized, up-to-date data.**

_**Functional spec:** On receipt of a sync trigger, the system must: (1) identify the connection and endpoint set from the request parameters; (2) call the external API for updated data scoped to the requested period/date range, entity, and other criteria; (3) process the data through the pipeline; (4) write the result to the FloQast data store; (5) emit the completion notification. Partial or failed transformations must not overwrite previously stored good data._

5. **REQ-05  As a system admin or auditor, I want every sync request to be logged with full context so that there is a complete, immutable audit trail.**

_**Functional spec:** Every sync request must generate a log entry recording: trigger type (user/system), trigger source (application name or "Data Studio"), user identity (user ID and display name) if user-triggered, request timestamp, connection ID, endpoint set, request parameters, status, start time, end time, and error details if applicable. Log entries must be immutable once written. When a sync covers multiple endpoints, a per-endpoint sub-log entry must be created for each endpoint at the time it is processed. This log entry needs to be surfaced in Data Studio for the connection and lineage, depending on the type of log._

6. **REQ-06  As a downstream FloQast application, I want to know if a sync is already in progress when I submit a request so that I can decide whether to queue my request or monitor the existing sync.**

_**Functional spec:** If a sync request arrives while another sync for the same connection is already active, the system must return a response indicating that a sync is in progress, including the current sync request ID. The requesting application may optionally submit a new queued sync request to run immediately after the active sync completes._

7. **REQ-07  As the system, I want to prevent more than one sync request from being queued behind an active sync so that the connection is not overloaded with concurrent requests.**

_**Functional spec:** If a sync request arrives while an active sync AND a queued sync already exist for the same connection, the system must reject the new request and return the ID of the existing queued sync. The requesting application should monitor that queued sync for updates rather than submitting an additional request._

8. **REQ-08  As the system, I want to detect when an on-demand sync request is for a full historical data range and communicate this to the requesting application so that SLA expectations are properly set.**

_**Functional spec:** If the sync request parameters indicate a full historical pull rather than an incremental or scoped request, the system must flag the request as long-running, respond with a warning that the request will take significantly longer than a standard on-demand sync, and not process it under the sub-30-second SLA. The threshold for "full historical" is TBD (see Open Questions)._

9. **REQ-09  As a Data Studio user, I want to see the real-time status of active and recently completed syncs in the connection sync log so that I have visibility into what is happening.**

_**Functional spec:** The sync log on the connection detail view must display active sync requests with real-time status (queued/in-progress/complete/failed). Each log entry must show: trigger source, triggered-by user display name if user-triggered, start time, end time or in-progress indicator, status, and error summary if applicable. The log must update without requiring a page refresh._

10. **REQ-10  As the system, when processing a sync that covers multiple endpoints, I want to log the outcome for each endpoint individually so that admins can identify exactly where errors occurred.**

_**Functional spec:** When a sync request covers multiple endpoints, the system must create a per-endpoint sub-log entry for each endpoint. Each sub-log must record: endpoint name, request timestamp, response status, records processed, and error details if applicable. Sub-log entries must be written at the time each endpoint is processed, not batched at run completion. Each of these sub-logs should be displayed to the user in Data Studio under the Connection._

11. **REQ-11  As the system, I want on-demand sync requests to be scoped to a specific period or date range so that responses are fast and within the target SLA.**

_**Functional spec:** On-demand sync requests must include a specific date range or period to scope data retrieval. Requests without a defined scope must default to the most recent period as determined by the connection's last successful sync. Full historical requests must follow REQ-08._

# **9. User Interaction and Design**

**On-Demand Trigger (Internal -Downstream Applications)**

The on-demand trigger interface consumed by Close and Reporting is an internal system interface -not a user-facing UI element. The trigger mechanism (webhook, internal event bus, or direct API call) is TBD and must be defined in collaboration with downstream application teams. Key design considerations: the interface must be authenticated and scoped per application; it must accept a FQ entity ID, a connection ID, optional endpoint set, and request conditions (period/date range, entity, other criteria); it must acknowledge the trigger immediately and process asynchronously; and run status must be visible in the sync log.

**Connection Detail View -Sync Now Action**

* A "Sync Now" button is present in the connection detail view header or toolbar.
* Clicking it immediately initiates an on-demand sync and creates a sync log entry with "In Progress" status.
* If a sync is already active: a message displays -"A sync is currently in progress. You can queue a new sync or monitor the existing one." -with options to queue or dismiss.
* If a queued sync already exists: a message displays -"A sync is already queued. Monitor the current sync for updates." -no additional queue option is offered.

**Sync Log**

* Visible in the connection detail view, below or adjacent to the endpoint list.
* Columns: Triggered By (user display name or "System -\[App Name\]"), Trigger Type (User / System), Status, Start Time, End Time, Endpoints, Notes/Errors.
* Active syncs display a spinner or "In Progress" indicator with elapsed time.
* Clicking a sync log row expands to show per-endpoint sub-log entries.
* Log updates in real time without requiring a page refresh (implementation approach TBD -see Open Questions).

**Active Sync Indicator**

* A persistent indicator is visible on the connection summary or header while a sync is in progress.
* Indicator clears automatically when the sync completes or fails.
* Concurrent state (active + queued) is surfaced clearly so users understand the queue state at a glance.

# **11. Out of Scope**

* External customer-facing trigger interface -the on-demand trigger is internal to FloQast applications only.
* Write-back or bi-directional sync -this sub-PRD covers read-only data ingestion.
* Fivetran-connected data sources -separate configuration path, not governed by this sub-PRD.
* Scheduled sync configuration -covered in the parent PRD.
* Endpoint configuration and management -covered in the parent PRD and its related sub-PRDs.
* Full historical data runs -flagged and communicated as out of SLA; processing approach not governed by this sub-PRD's latency targets.
* Data preview and test/sample capability -covered in a separate PRD.
