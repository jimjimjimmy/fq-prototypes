# 1. Objective

This sub-PRD defines the requirements for creating and managing an Intacct direct API connection in Data Studio. An Intacct connection is the foundational object that provides account and balance data from a customer's Intacct instance to FloQast.

This document covers two areas:

* **New connection setup:** credential entry, real-time validation, and auto-setup of the standard connection on success.

* **Connection management:** rename, credential updates, archive, and delete for existing connections.

Intacct's authentication model uses XML-based login credentials. The customer provides their Company ID, User ID, and Password. Multi-entity customers who need to access the top-level company context must also provide a Client ID. FloQast's sender credentials are applied server-side and are never entered or exposed in the setup flow. On validation, FloQast combines the sender credentials with the customer's login credentials to establish a session token; this token is cached and used for all API calls within the sync job.

# 2. Requirements

**REQ-01: As a CS team member or customer IT team, I want to create a new Intacct connection in Data Studio by providing credentials so that FloQast can connect to the customer's Intacct instance and begin pulling account and balance data.**

*Functional spec: The new connection flow collects the customer's Intacct credentials: Company ID, User ID, Password, and optionally Client ID (required for multi-entity customers accessing top-level company context). On submission, the system validates the credentials against Intacct in real time by establishing a session token. If validation fails, an auth error is surfaced immediately without saving the connection. If validation succeeds, the connection is saved and auto-setup is triggered. See REQ-02 and REQ-03.*

**REQ-02: As a CS team member or customer IT team, I want to be immediately notified if the credentials I provided cannot connect to Intacct so that I can correct them before the connection is saved.**

*Functional spec: On credential submission, the system makes a live authentication call to Intacct by attempting to establish a session token. If authentication fails for any reason, an error is displayed inline in the setup flow. The error identifies the failure type and provides clear guidance for correcting it. Specific Intacct error conditions include: authentication failure (session establishment fails), authorization error (code PL04000005 — credentials valid but user lacks required API permissions), and credential error (code XMLGW_JPP0002 — invalid sender or login credentials). The connection is not created until credentials are validated successfully.*

**REQ-03: As a CS team member or customer IT team, I want successful connection setup to automatically trigger the standard connection configuration so that no additional manual setup is required after credentials are validated.**

*Functional spec: On successful credential validation, the system: (1) saves the connection with status ACTIVE, (2) stores the connection details in the connection Settings page, and (3) triggers auto-setup of the standard Intacct connection — including standard field mapping and default book configuration. Auto-setup behavior is defined in Sub-PRD 3: Setup Link & Auto-Connect and Sub-PRD 4: Mapping Configuration.*

**REQ-04: As a CS team member or customer IT team, I want to rename an existing connection so that the display name reflects the customer's preferred naming convention.**

*Functional spec: An authorized user can update the connection's display name from the connection Settings page at any time. Renaming takes effect immediately and is reflected everywhere the connection name appears. It does not affect connection status, credentials, sync schedule, or sync history.*

**REQ-05: As a CS team member or customer IT team, I want to update the credentials on an existing connection so that I can correct invalid credentials or update a password without recreating the connection.**

*Functional spec: An authorized user can update any or all credential fields (Company ID, User ID, Password, Client ID) from the connection Settings page. On save, the updated credentials are validated against Intacct in real time using the same session token establishment logic as new connection setup. If validation fails, the existing credentials are preserved unchanged and an error is surfaced. If validation succeeds, the new credentials are saved and the connection returns to ACTIVE status if it was previously in ERROR.*

**REQ-06: As a CS team member or customer IT team, I want to archive a connection so that existing data is preserved but no new data is processed.**

*Functional spec: Archiving a connection sets its status to ARCHIVED and immediately stops all scheduled and on-demand syncs. All previously synced data, field mappings, and configuration are preserved and remain accessible. The connection remains visible in the Data Studio connection list with an ARCHIVED status indicator. Archiving is reversible — an archived connection can be reactivated to resume sync behavior. No data or configuration is removed on archive.*

**REQ-07: As a CS team member or customer IT team, I want to delete a connection — with a clear warning that all associated field mappings and data models will be permanently removed — so that I can fully remove a connection when needed.**

*Functional spec: Deleting a connection permanently removes the connection record and all associated field mappings and data model configurations. Before deletion executes, the user must confirm a warning dialog that explicitly lists what will be removed and states that this action cannot be undone. The warning dialog must surface archiving as the recommended alternative and offer a direct option to archive instead. Deletion does not affect data already written to the data platform.*

# 3. User Interaction and Design

## New Connection Setup

1. User navigates to Data Studio and initiates a new Intacct connection.

2. User is presented with a credential entry form with four fields: **Company ID**, **User ID**, **Password**, and **Client ID** (optional — labeled as required only for multi-entity accounts accessing top-level company context, with inline help text explaining when it is needed).

3. User submits credentials.

4. System makes a live authentication call to Intacct by establishing a session token using the customer's credentials combined with FloQast's sender credentials.
       

   * **On failure:** An inline error is displayed identifying the failure reason. Error messages map to specific failure types: "Invalid credentials — check your Company ID, User ID, and Password" for XMLGW_JPP0002; "Insufficient permissions — your Intacct user does not have Web Services access" for PL04000005; "Authentication failed — verify your credentials and try again" for general session establishment failure. The connection is not saved. The user can correct fields and resubmit without leaving the flow.

   * **On success:** The connection is saved with status ACTIVE and credentials are stored securely. The established session token is not persisted; a new session is established at the start of each sync job.

5. Auto-setup is triggered automatically in the background: standard field mapping and book configuration are applied.

6. User lands on the connection Settings page showing the active connection.

## Connection Settings Page

The Settings page for an existing connection displays:

* Connection display name (editable via Rename)

* Company ID (masked after initial save)

* User ID (masked after initial save)

* Password (masked after initial save)

* Client ID (masked after initial save, if provided)

* Connection status: **ACTIVE** / **ERROR** / **ARCHIVED**

* Last sync timestamp and outcome

* Available actions: **Rename**, **Update Credentials**, **Archive**, **Delete**

## Rename

1. User selects **Rename** from the Settings page.

2. An editable name field is shown with the current name pre-filled.

3. User updates the name and saves.

4. The new name takes effect immediately across all UI surfaces. No re-validation of credentials occurs.

## Update Credentials

1. User selects **Update Credentials** from the Settings page.

2. Credential fields are shown in an editable state (current values masked).

3. User updates one or more fields and submits.

4. System validates the updated credentials against Intacct in real time by re-establishing a session token.
       

   * **On failure:** Error is surfaced inline with specific guidance based on error code; existing credentials are preserved unchanged.

   * **On success:** New credentials are saved; connection status returns to ACTIVE if it was previously in ERROR.

## Archive

1. User selects **Archive** from the Settings page.

2. A confirmation dialog explains that archiving will stop all new data processing but preserve all existing data and configuration, and that this action is reversible.

3. User confirms.

4. Connection status changes to ARCHIVED; all scheduled syncs stop immediately.

5. Connection remains visible in the connection list with ARCHIVED status. Reactivation is available from the Settings page.

## Delete

1. User selects **Delete** from the Settings page.

2. A warning dialog appears that:
       

   * Lists what will be permanently removed: the connection, all field mappings, and all data model configurations associated with this connection.

   * States that this action **cannot be undone**.

   * Recommends **archiving instead** and surfaces a direct option to archive rather than delete.

3. User must take an explicit destructive confirmation action (e.g., typing the connection name or clicking a clearly labeled irreversible button) to proceed.

4. On confirmed delete, the connection and all associated configuration are permanently removed.

5. Data already written to the data platform is not affected.

# 4. Acceptance Criteria

**REQ-01 — New Connection Setup**

- [ ] User can enter Company ID, User ID, Password, and (optionally) Client ID and submit the form.

- [ ] The system establishes a live session token with Intacct using the submitted credentials before saving any connection record.

- [ ] A connection is not created until credentials are successfully validated.

**REQ-02 — Auth Error Handling**

- [ ] If credentials are invalid (XMLGW_JPP0002), an inline error is displayed with specific guidance on which fields to check.

- [ ] If the user lacks Web Services permissions (PL04000005), an inline error is displayed identifying the permissions issue.

- [ ] The connection is not saved on a failed validation attempt.

- [ ] The user can correct one or more credential fields and resubmit without restarting the flow.

**REQ-03 — Auto-Setup on Success**

- [ ] On successful validation, the connection is saved with status ACTIVE.

- [ ] The connection Settings page is shown immediately after save.

- [ ] Auto-setup of standard field mapping and book configuration is triggered automatically without user action.

**REQ-04 — Rename**

- [ ] User can update the connection display name from the Settings page.

- [ ] The updated name is reflected immediately across all UI surfaces that display the connection name.

- [ ] Rename does not trigger credential re-validation or affect connection status or sync history.

**REQ-05 — Update Credentials**

- [ ] User can update any of the credential fields from the Settings page.

- [ ] Updated credentials are validated against Intacct in real time via session token establishment before being saved.

- [ ] If validation fails, the existing credentials are preserved and an error is surfaced with specific guidance.

- [ ] If validation succeeds and the connection was in ERROR status, it returns to ACTIVE.

**REQ-06 — Archive**

- [ ] Archiving sets the connection to ARCHIVED status and immediately halts all scheduled and on-demand syncs.

- [ ] All existing data, field mappings, and configuration are preserved on archive.

- [ ] The archived connection is visible in the connection list with ARCHIVED status.

- [ ] An archived connection can be reactivated to resume sync behavior.

**REQ-07 — Delete**

- [ ] Deleting a connection requires explicit user confirmation via a warning dialog before any deletion occurs.

- [ ] The warning dialog clearly lists all items that will be permanently removed.

- [ ] The warning dialog surfaces archiving as the recommended alternative and offers a direct path to archive instead.

- [ ] On confirmed deletion, the connection and all associated configuration are permanently removed.

- [ ] Data already written to the data platform is not removed or affected by the deletion.
