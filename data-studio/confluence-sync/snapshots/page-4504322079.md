# **1. Objective**

FloQast's data platform enables customers to configure source data connections spanning multiple ERP types - including Workday, SAP, Yardi, and others - via sFTP and API. Currently, customers cannot self-manage these connections after setup: they cannot create connections independently through a guided flow, rename them, correct configuration mistakes, deactivate unused connections, or permanently remove test configurations without FloQast support involvement. This PRD defines the requirements for end-to-end connection lifecycle management, empowering customers and FloQast implementation specialists to fully self-serve connection configuration - from initial creation through archival and permanent deletion - across all supported connection types.

# **2. Key Benefits**

* Customers and implementation specialists can create, rename, edit, archive, reactivate, and delete connections without FloQast support involvement
* Reduced support ticket volume during implementation and ongoing configuration changes
* Increased configuration accuracy - users can correct mistakes without recreating connections from scratch
* Clear visibility into connection state (active vs. archived) through a filterable list view, defaulting to active connections
* Permanent deletion safeguards (warning modal with cascade impact summary) prevent accidental data loss
* Applies across all connection types (sFTP, API, and future types), establishing a consistent lifecycle pattern

# **3. Use Cases**

1. A customer onboarding FloQast needs to establish a new Workday connection. They navigate to the connections page, select the connection type, and are guided through entering the required credentials and configuration to complete setup - without opening a support ticket.
2. A customer realizes they named their SAP connection incorrectly during onboarding. They rename it directly from the connections list without deleting and recreating it.
3. A customer wants to deactivate a connection to a seasonal ERP system without losing its configuration. They archive the connection and reactivate it when the season resumes - the full configuration is preserved.
4. A FloQast implementation specialist needs to permanently remove a test connection created during onboarding. They select Delete, review the warning listing all associated files and endpoints that will also be removed, confirm the action, and the connection is fully cleaned up.
5. A FloQast implementation specialist needs to review the full history of connections for a customer, including previously archived ones. They toggle the filter to show all connections and see a complete view of active and archived records.

# **4. Success Metrics**

| **Metric** | **Target / Description** |
| --- | --- |
| Support ticket reduction | Measurable reduction in support tickets related to connection configuration (create, rename, edit, archive, delete) within 90 days of release |
| Self-serve completion rate | Customers and implementors complete all connection lifecycle actions without contacting FloQast support, measured via support contact rate for configuration tasks |

# **5. Assumptions**

* Archive / Deactivate is a reversible action: the connection remains in the system but is inactive and not used in data processing
* Delete is a permanent, irreversible hard delete; all associated files, endpoints, and configuration tied to the connection are cascade-deleted upon confirmed removal
* Both customer users and FloQast internal admins / implementation specialists can perform all lifecycle actions, subject to existing permission models
* The connections management UI already exists in some form; these are enhancements to existing screens and action menus
* Editable fields on a connection vary by connection type (e.g., sFTP connections expose different configuration metadata than API connections); what is editable per type will be defined in collaboration with Engineering
* The platform enforces a concept of active vs. inactive connection state for data processing eligibility; this PRD surfaces and extends that state model in the UI
* This PRD covers connection lifecycle management for all connection types - not limited to API or sFTP - and is intended to serve as the foundational pattern for any future connection types added to the platform

# **7. Scope of Data**

* Connection records: name, connection type (sFTP, API, etc.), status (active / archived), creation date, last modified date
* Connection configuration metadata: type-specific fields such as sFTP host, path, and sync frequency, or API base URL and version - excludes raw credential or secret values where sensitive
* Connection status state: active or archived
* Associated files and endpoints: referenced during cascade delete to surface impact in warning modal; permanently removed upon confirmed deletion

‌

Out of scope for this data layer:

* File and source data records (covered in the companion sub-PRD on file/endpoint lifecycle management)
* Raw authentication credentials or secrets beyond what is required for the guided creation flow
* Audit log records of lifecycle actions
* Connection health metrics, sync status, or error logs

# **8. Requirements**

* **REQ-01: As a user, I want to create a new connection by entering the required credentials and configuration so that I can establish a data source connection to FloQast.**

_Functional spec:_ The connection creation flow guides the user through providing all required information for the selected connection type (e.g., sFTP host, path, and credentials; API base URL and authentication details). Required fields are validated before the connection can be saved. Upon successful creation, the new connection appears in the active connections list with Active status.

‌

* **REQ-02: As a user, I want to rename a connection so that I can correct or update its display name without deleting and recreating it.**

_Functional spec:_ A Rename action is exposed in the connection row action menu. It opens an inline edit field or modal with a text input pre-populated with the current name. The updated name is saved immediately and reflected across all references to the connection. Validation prevents blank or duplicate names.

‌

* **REQ-03: As a user, I want to edit a connection's configuration metadata so that I can correct or update settings without recreating the connection from scratch.**

_Functional spec:_ An Edit option in the connection action menu opens a form or modal with pre-populated configurable fields for the connection type. Editable fields vary by connection type (e.g.API base URL or version for API connections). Updated information is saved to the existing connection record. All changes are validated before saving. The edit view clearly displays current values so the user can identify what to correct.

‌

* **REQ-04: As a user, I want to archive (deactivate) a connection so that it is preserved in the system but no longer active in data processing.**

_Functional spec:_ A Deactivate / Archive option is available in the connection action menu for any active connection. A brief confirmation prompt is shown before the action is applied. Archiving prevents the connection from being used in any new data processing runs without deleting its configuration or history. Archived connections are visually distinguished in the list (e.g., an 'Archived' badge) and serve as an audit trail. They are hidden from the default connection list view but remain accessible via the Archived or All filter. When a connection is archived, we log that that the connection is archived as of the datetime.

‌

* **REQ-05: As a user, I want to reactivate an archived connection so that I can resume using it when needed.**

_Functional spec:_ An archived connection exposes a Reactivate option in its action menu. Upon reactivation, the connection returns to active status and becomes eligible for data processing. Reactivated connections appear in the default active connections view and lose the 'Archived' visual indicator. When a connection is reactivated, we log that the connection was reactivated as of the datetime.

‌

* **REQ-06: As a user, I want to permanently delete a connection so that outdated or test connections are fully removed from the system.**

_Functional spec:_ A Delete option is available in the connection action menu for both active and archived connections. This action is permanent and irreversible. Upon selection, a warning modal is displayed before any deletion occurs. Upon confirmed deletion, the connection record and all associated files, endpoints, and configuration are permanently removed from the system via cascade delete. When a connection is deleted, we log that that the connection is deleted as of the datetime.

‌

* **REQ-07: As a user, I want to see a clear warning before permanently deleting a connection so that I understand the full scope and cannot accidentally remove data I still need.**

_Functional spec:_ When a user selects Delete, a confirmation modal displays: (1) a statement that the action is permanent and cannot be undone, and (2) the count of associated files, endpoints, and configuration records that will also be permanently deleted (e.g., 'This connection has 3 associated files and 2 endpoints that will also be permanently deleted'). The modal requires an explicit confirmation action - visually distinct from Cancel and styled as a destructive action - before deletion proceeds.

‌

* **REQ-08: As a user, I want to view all my connections with filtering capabilities so that I can quickly find and manage the connections I need.**

_Functional spec:_ The connections list view supports filtering by connection status. The default filter shows active connections only. Filter options include: Active (default), Archived, and All. The list updates dynamically when the filter is changed. Archived connections display an 'Archived' badge in the row. The filter state persists within the session.

# **9. User Interaction and Design**

All connection lifecycle actions are surfaced via a contextual action menu (three-dot / kebab menu) on each row in the connections list view. This keeps the UI clean while making all management options consistently accessible.

‌

**Connection List View**

The connections list is the primary management surface. Each row displays the connection name, type, status badge, and last modified date. A status filter bar at the top of the list defaults to Active. Filter options are:

* Active - default; shows only active connections
* Archived - shows only archived connections
* All - shows active and archived connections together

‌

**Action Menu - Active Connection**

* Rename: opens an inline edit field or modal with a pre-populated text input for the connection name
* Edit: opens a modal or form with pre-populated configuration fields; editable fields are determined by connection type
* Archive / Deactivate: requires a brief confirmation prompt before applying; connection moves to archived state
* Delete: triggers the permanent deletion warning modal (see REQ-07); requires explicit confirmation before proceeding

‌

**Action Menu - Archived Connection**

* Reactivate: returns the connection to active status without a confirmation prompt
* Delete: same permanent deletion flow as active connections

‌

**Permanent Deletion Warning Modal**

The modal content must include:

* Header: 'Delete Connection - This action cannot be undone'
* Body: A clear statement that the connection and all associated files, endpoints, and configuration will be permanently deleted, with a count of affected records surfaced dynamically
* Actions: Cancel (secondary) and Delete Permanently (primary, styled as a destructive action)

‌

**Archived Connection Indicator**

Archived connections display a visible 'Archived' badge or tag in the connection row. Archived items are not shown in the default Active filter view. The badge is removed upon reactivation.

# **10. Open Questions**

| **Question** | **Owner** | **Notes** |
| --- | --- | --- |
| What specific fields are editable per connection type (sFTP, API, etc.)? Are credential fields re-enterable? | Engineering / PM | Editable fields vary by type; needs per-type definition. The sub-PRD originally listed credentials as out of scope - this PRD expands that to allow metadata edits; credential editability should be confirmed per type. |
| What happens to in-flight data processing if a connection is archived mid-run? | Engineering | May require graceful handling - recommend allowing the current run to complete before archival takes effect. |
| Should the Delete option require the connection to be archived first, or can active connections be deleted directly? | PM / Design | Requiring archival first could serve as a guardrail. Current spec allows deletion from either state. Confirm preferred behavior. |
| Are there permission tiers that restrict who can permanently delete a connection (e.g., admin-only)? | Engineering / PM | Worth defining for enterprise customers with multiple user roles. Recommend admin-only for permanent delete. |
| What is the behavior when a deleted connection has active lineage records linking it to FloQast model fields? | Engineering | Cascade delete should handle cleanup, but the lineage removal process needs confirmation to avoid orphaned model references. |
| Should there be a visual or proactive notification when a connection is in an archived state and a scheduled run would have fired? | PM / Design | Consider surfacing a passive indicator in the archived connection row so admins are aware of missed syncs |

# **11. Out of Scope**

* File and source data lifecycle management - covered in the companion sub-PRD on file/endpoint lifecycle management
* Endpoint lifecycle management - covered in the parent API Endpoint Management PRD
* Bulk archive or bulk delete actions across multiple connections simultaneously
* Automated archiving based on inactivity thresholds
* Connection health monitoring, error alerting, or sync status reporting
* Changes to the lineage mapping UI (how source fields are mapped to FloQast model fields)
* Write-back or bi-directional sync; this PRD covers connection configuration only, not data flow direction
* File content inspection, data preview, or connection testing beyond the guided creation flow
