# **1. Objective**

This sub-PRD defines the requirements for the test and validation capability within FloQast Data Studio's API endpoint configuration workflow. Specifically, it covers how admins and implementors can confirm that a configured API endpoint is functioning correctly - including authentication, parameter construction, and data retrieval - before committing the endpoint to active use or after editing an existing one.

The test capability is split into two distinct flows reflecting fundamentally different execution patterns: pull APIs (where FloQast initiates an outbound request and receives a response) and push APIs (where an external system delivers data inbound to FloQast). Both flows share the goal of surface-level validation without triggering the full data ingestion pipeline. This work is scoped as a sub-component of the parent API Endpoint Management PRD and applies to Phase 1 (Pull APIs) and Phase 6 (Push APIs).

Primary users are FloQast admins and implementation team members who need to validate endpoint configurations without engineering involvement.

# **2. Key Benefits**

* Catch misconfigurations before they cause silent data failures or missed sync windows
* Self-service troubleshooting: admins can identify and resolve broken endpoint configurations without engineering involvement
* Faster implementation confidence: implementors can confirm a new endpoint is working before going live
* Clear error attribution: errors are categorized by component (auth, parameters, endpoint URL, etc.) so admins know exactly what to fix
* Consistent test experience available both during the setup wizard and post-setup from the endpoint detail view

# **3. Use Cases**

1. **Pull API test during setup (new endpoint):** An implementor adds a new QBO Trial Balance endpoint with date range and accounting method parameters. Before saving, they click "Test Request" in the setup wizard. Data Studio executes the request using the configured credentials and parameters, returns a 200 OK status, and displays a preview of the first returned record as key-value pairs (e.g., AccountName: Accounts Receivable | Balance: $45,200 | AccountType: Asset). The implementor saves with confidence.
2. **Pull API re-test after edit (broken endpoint):** An admin sees a Trial Balance endpoint in Error state. They open the endpoint detail, correct a malformed query parameter, and click "Test Now" from the endpoint detail view. The test confirms the fix resolves the error before they save.
3. **Auth failure surfaced during pull test:** An implementor configures a new endpoint, but the OAuth token associated with the connection has expired. The test returns an Auth Failure error flagging the authorization component specifically, so the implementor knows to re-authenticate the connection rather than troubleshoot the endpoint parameters.
4. **Missing required query parameter caught:** An admin adds an endpoint that requires a date range parameter but leaves it blank. Before the request is sent, the system surfaces a "Missing Required Parameter" error identifying the specific parameter.
5. **Push API auth validation:** An admin sets up a new push endpoint. Data Studio displays the generated API key and inbound webhook URL. The admin clicks "Validate API Key" to confirm the key is active and the endpoint is ready to receive data.
6. **Push API inbound data confirmation:** After sharing the webhook URL with the source system operator, the admin uses Data Studio's test flow to confirm an inbound POST is received and parsed. Data Studio displays a single-row key-value preview, confirming the push connection is working end-to-end.

# **4. Success Metrics**

| **Goal** | **Metric / Target** |
| --- | --- |
| Test accuracy for pull APIs | Greater than 95% of test runs correctly identify valid vs. invalid configurations |
| Error categorization accuracy | Errors correctly attributed to the right component in greater than 90% of cases |
| Time to resolve misconfiguration | Admins can identify and correct a misconfigured endpoint without engineering support, measurable by support ticket reduction |
| Reduction in broken endpoints saved | Measurable reduction in endpoints saved in a non-functional state after test capability is introduced |
| Push auth validation reliability | 100% of push API key validations return accurate active/inactive status |

# **5. Assumptions**

1. The test step uses auth credentials and connection configurations already established in the API connection setup workflow. No re-entry of credentials is required during the test.
2. For pull APIs, a test run is a validation-only operation - it does not trigger the scheduled sync pipeline, write data to the FloQast data store, or appear in the endpoint's sync run history.
3. For push APIs, FloQast generates an API key and inbound webhook URL at connection or endpoint setup time (mechanism TBD - see Open Questions).
4. The test UI presents a synchronous experience to the user: they initiate the test and wait for a result before proceeding. Async processing happens under the hood.
5. Nested endpoint resolution during test runs is out of scope for Phase 1. The test validates a single endpoint in isolation.
6. Error messages from external APIs are surfaced as-is, with additional FloQast-applied categorization layered on top.
7. Push API test mechanics (who sends the test payload, what constitutes a valid push test) are partially defined. The two-step model (auth check + inbound data confirmation) is the working assumption and remains subject to revision as push API architecture is finalized.

# **6. Milestones**

1. **Phase 1 - Pull API Test:** Test capability is available within the pull endpoint setup wizard (pre-save) and as a "Test Now" action on saved pull endpoints. Covers auth validation, request construction and parameter validation, request execution, response status display, single-row key-value preview, and categorized error surfacing.
2. **Phase 2 - Push API Test:** Test capability for push endpoints. Covers API key/auth validation (step 1) and inbound sample data confirmation with single-row key-value preview (step 2). Exact mechanics dependent on push API architecture finalized in Phase 6 of the parent PRD.

# **7. Scope of Data**

The following data objects are in scope for the test and validation flow:

* Test request payload: endpoint URL, constructed query parameters, auth headers used for the test request
* Test response (pull): HTTP status code, response latency, first returned record displayed as key-value pairs (up to a defined field count - TBD, recommended: first 10 fields with expand option)
* Test response (push): inbound payload receipt confirmation, first parsed row as key-value pairs
* Error details: error category (see REQ-07 error taxonomy), specific component that failed, raw error message from the API where available
* Test run metadata: timestamp, endpoint config snapshot at test time, pass/fail status - session-only, not persisted to the formal run log (assumed - confirm with engineering)

‌

_The following are explicitly out of scope for this sub-PRD's data layer:_

* Full ingested data records: the test retrieves and previews only the first row and does not write to the data store
* Test run history: test results are not stored as run log entries
* Field mapping or data transformation validation: covered in separate PRDs

# **8. Requirements**

## **Pull API Requirements**

**REQ-01  As an admin or implementor, I want the test step to automatically use the endpoint's saved configuration so that I don't have to re-enter credentials or parameters to run a test.**

_Functional spec:_ When a test is initiated - during the setup wizard or from the endpoint detail view - the system must populate the test request using the auth credentials from the parent connection and the query parameters from the current endpoint configuration. No manual re-entry of credentials or parameters is required. If the endpoint configuration is incomplete (missing required parameters), the system must surface this before attempting the request.

**REQ-02  As an admin or implementor, I want the test to confirm that authentication is working so that I can identify auth issues before they cause sync failures.**

_Functional spec:_ The test must validate that the auth credentials associated with the connection (e.g., OAuth token, API key) are accepted by the external API. If the auth check fails, the system must surface an Auth Failure error (see REQ-07) before attempting to construct or send the full request. Auth failures must be clearly distinguished from other error types.

**REQ-03  As an admin or implementor, I want to see the HTTP status code returned by the API so that I can confirm the endpoint is reachable and responding.**

_Functional spec:_ The test must display the HTTP status code returned by the API endpoint (e.g., 200 OK, 401 Unauthorized, 404 Not Found, 429 Too Many Requests). The system must indicate whether the status represents a success or failure state. Non-2xx responses must trigger error handling per REQ-07.

**REQ-04  As an admin or implementor, I want the system to confirm that a valid request can be constructed from the configured parameters so that I catch parameter errors before the request is sent.**

_Functional spec:_ Before executing the test request, the system must validate that all required query parameters are present and formatted correctly. If a required parameter is missing or malformed, the system must surface a parameter-level error (see REQ-07) identifying the specific parameter without sending a request to the external API. For parameters with known enumerated values, the system must validate that the provided value matches the allowed set.

**REQ-05  As an admin or implementor, I want the system to execute the test request and confirm that a valid response is received so that I know the full request-response cycle works.**

_Functional spec:_ Once auth is confirmed and parameters are valid, the system must execute the test request against the configured API endpoint. The test must confirm that a response is received. The test must complete within a defined timeout window (TBD - recommended: 30 seconds) and surface a Timeout error if no response is received within that window.

**REQ-06  As an admin or implementor, I want to see a preview of the first returned record so that I can confirm the API is returning the expected data.**

_Functional spec:_ On a successful test response, the system must display the first returned record formatted as a key-value pair list (e.g., AccountName: Accounts Receivable | Balance: $45,200 | AccountType: Asset). The preview must show up to a defined field count (TBD - recommended: first 10 fields, with a "Show more" option to expand). The raw response body should not be shown by default; the key-value preview is the primary display. A zero-record response must be surfaced distinctly from an error (see Open Questions).

**REQ-07  As an admin or implementor, I want errors to be categorized by component so that I know exactly what to fix.**

_Functional spec:_ When a test fails, the system must display: (1) the error category from the taxonomy below, (2) the specific component or field that failed, and (3) the raw error message from the API where available. An expandable "Raw Error" section should be available for users who need additional detail.

_Proposed error taxonomy (assumed - please confirm with engineering):_

‌

| **Error Category** | **Description / Examples** |
| --- | --- |
| **Auth Failure** | Token expired, invalid API key, insufficient OAuth scopes. Example next step: re-authenticate this connection. |
| **Invalid Endpoint / URL** | Endpoint path not found (404), base URL unreachable, DNS failure. |
| **Missing Required Parameter** | A required query parameter was not provided. Identifies the specific missing parameter by name. |
| **Invalid Parameter Value** | A parameter value is present but fails format or type validation (e.g., wrong date format, value not in allowed set). |
| **Rate Limit Exceeded** | API returned 429 / rate limit response. May indicate the test request was rejected due to existing API load. |
| **Timeout** | No response received within the timeout window. May indicate network or upstream API availability issue. |
| **Malformed Response** | Response received but could not be parsed (unexpected format, missing required fields in response schema). |
| **Unknown / Other** | Catch-all for unclassified errors. Raw API error message surfaced in full. |

‌

## **Push API Requirements**

**REQ-08  As an admin or implementor, I want to confirm that the FloQast-generated API key for my push endpoint is active and valid so that I can verify the push connection is ready to receive data.**

_Functional spec:_ For push endpoint configurations, the system must display the generated API key and inbound webhook URL. The admin must be able to trigger an API key validation check that confirms the key is active. The validation result must clearly indicate active or inactive status. If the key is inactive, the system must surface next steps (e.g., regenerate key). The API key and webhook URL must be displayed with a copy-to-clipboard action.

**REQ-09  As an admin or implementor, I want to confirm that the push endpoint can receive and parse inbound data so that I know the end-to-end push connection is working before going live.**

_Functional spec:_ The system must support a two-step inbound data confirmation flow. Step 1: Validate the API key is active (REQ-08). Step 2: Confirm an inbound POST is received and parseable - either via a "Send Test Payload" action that simulates or requests a test POST from the source system, or by monitoring for an inbound POST within a defined time window (TBD). On receipt of a valid inbound payload, the system must display a single-row key-value preview of the first parsed record. If the payload cannot be parsed, the system must surface a Malformed Response error.

_(Note: Exact mechanics of push test initiation - whether FloQast triggers the test payload or the source system operator sends one manually - are TBD. See Open Questions.)_

## **General / Cross-Cutting Requirements**

**REQ-10  As an admin or implementor, I want to run a test before saving a new endpoint so that I can validate the configuration is correct before it becomes active.**

_Functional spec:_ The endpoint setup wizard must include a "Test Request" action available after all required fields are filled in. The test step must not be a blocking requirement - the admin can choose to save without testing, but the option must be prominently surfaced. If the test fails, the system must allow the admin to correct the configuration and re-test without losing previously entered values.

**REQ-11  As an admin or implementor, I want to re-test a saved endpoint at any time so that I can validate a fix after editing or investigate an endpoint that has entered an Error state.**

_Functional spec:_ Each saved endpoint in the connection detail view must surface a "Test Now" action alongside Edit, Run Now, and Deactivate. This action must execute the same test flow as the setup wizard test, using the current saved configuration. Test results must be displayed inline without navigating away from the endpoint detail view.

# **9. User Interaction and Design**

## **Test Step in the Setup Wizard**

The test step appears as the final step of the Add/Edit Endpoint flow, after the user has configured all parameters. The panel should include:

* A "Test Request" button (pull) or "Validate API Key" button (push)
* A status indicator cycling through: idle → running → pass/fail
* On pull success: HTTP status code, latency in ms, and the first-record key-value preview
* On push success (step 1 - auth): API key active confirmation; (step 2 - data): inbound payload key-value preview
* On failure: error category badge, component detail, and an expandable raw error message section
* A "Re-Test" button available after any result
* "Save Anyway" and "Save" actions remain available regardless of test result; the test is informational, not a hard gate

‌

## **Test State Display**

The test panel should cycle through the following states:

* **Idle / Not yet tested:** Gray indicator, "Test Request" button available
* **Running:** Spinner with "Testing..." label
* **Pass:** Green checkmark, HTTP status code, latency, first-record key-value preview
* **Fail:** Red X, error category badge, component detail, expandable raw error message, suggested next steps where applicable

‌

## **"Test Now" Action on Saved Endpoints**

The "Test Now" action is accessible from the endpoint row in the Source Data list. Results should be displayed in an inline panel or modal without navigating away from the connection detail view. The pass/fail display mirrors the setup wizard test experience.

‌

## **Push-Specific Test UI**

Push endpoint testing uses a two-step flow:

* Step 1 (Auth): "Validate API Key" button returns an active or inactive status. The API key and webhook URL are displayed with a copy-to-clipboard action.
* Step 2 (Data): A "Waiting for test payload..." state with a timeout indicator is shown. On receipt of an inbound POST, the system transitions to a success state and displays the first parsed row as a key-value preview. On timeout or parse failure, the appropriate error state is shown.

‌

## **Error Display**

When a test fails, the error display should include:

* Error category label as a styled badge (e.g., "Auth Failure", "Missing Parameter", "Timeout")
* Component detail beneath the badge (e.g., "Authorization header rejected", "Parameter: start_date is required")
* Expandable "Raw Error" section showing the API's original error message
* Suggested next steps where applicable - for example, Auth Failure should surface "Re-authenticate this connection" as a direct action link

# **11. Out of Scope**

* Full data ingestion during test: test runs do not write data to the FloQast data store
* Test run history: test results are displayed in-session only and are not stored in the endpoint's formal run log (assumed - see Open Questions)
* Push write-back testing: this sub-PRD covers validation of inbound data receipt only; no data is written back to the source system
* Fivetran endpoint management: Fivetran-connected data sources have a separate configuration path and are not governed by this sub-PRD
* Performance or load testing: this sub-PRD covers functional validation only
