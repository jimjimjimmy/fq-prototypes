## 1. Objective

This document defines the complete set of connection statuses in FloQast Data Studio, the rules that govern transitions between them, and how each status is surfaced to admins. It is a companion to the Connection Lifecycle Management PRD and serves as the authoritative reference for engineering, design, and QA when implementing connection state behavior.

## 2. Status Definitions

Seven statuses define the full lifecycle of a connection. Each represents a distinct, actionable state that an admin can act on or reason about without opening the connection detail view.

| Status | Definition |
| --- | --- |
| **Draft** | Setup is in progress. The connection has been saved but not activated. Configuration is incomplete or untested. |
| **Pending** | The connection has been activated but has not yet completed its first successful sync. Data is not yet available downstream. |
| **Active** | The connection is running normally. At least one sync has completed successfully and the connection is scheduled for future runs. |
| **Warning** | The connection is running, but some — not all — endpoints are failing. Data is partially available. The connection continues to execute scheduled syncs. |
| **Error** | All endpoints on the connection are failing, or a critical failure has occurred. No new data is being ingested. |
| **Auth Expired** | The credentials associated with the connection have expired. No syncs will succeed until credentials are updated and the connection test passes. |
| **Archived** | The connection has been deactivated by an admin. Configuration is preserved but the connection is excluded from all data processing. |

### Notes on Syncing

Syncing is not a connection status. While a sync is actively running, the connection retains its current status (Active, Warning, etc.). An in-progress indicator is surfaced on the connection detail view only. This keeps the connection list stable and avoids status flickering during frequent syncs.

### Notes on Draft

Draft shows as "Draft" in the connection list without a step indicator. The current setup step is visible when the admin reopens the connection. Admins managing multiple in-progress connections can identify them by name and creation date in the list.

There is a difference between a draft state for connectors and a draft state for endpoints.

## 3. Status Rollup from Endpoints

A connection's status reflects the aggregate health of its endpoints. The rollup rules are:

* If **some but not all** endpoints are in Error → connection status is **Warning**
* If **all** endpoints are in Error → connection status is **Error**
* If **all** endpoints are healthy → connection status is **Active**
* Auth expiration is evaluated independently and takes precedence over Warning or Error when credentials have expired
* If **one (or more)** endpoint is active, the connector status is **Active**. There may be endpoints in a draft state as well for the connector.

These rules apply on every sync completion. The system re-evaluates connection status after each run based on the current state of all endpoints.

## 4. State Transitions

### Allowed Transitions

| From | To | Trigger |
| --- | --- | --- |
| Draft | Pending | Admin activates the connection after completing setup |
| Pending | Active | First sync completes successfully |
| Pending | Warning | First sync completes with some endpoints failing |
| Pending | Error | First sync completes with all endpoints failing |
| Pending | Auth Expired | Credentials expire before the first sync runs |
| Active | Warning | A sync completes with some endpoints failing |
| Active | Error | A sync completes with all endpoints failing |
| Active | Auth Expired | Credentials expire (proactively flagged before a sync failure occurs) |
| Active | Archived | Admin archives the connection |
| Warning | Active | A sync completes with all endpoints succeeding (auto-recovery) |
| Warning | Error | A sync completes with all remaining healthy endpoints now failing |
| Warning | Auth Expired | Credentials expire |
| Warning | Archived | Admin archives the connection |
| Error | Active | A sync completes with all endpoints succeeding (auto-recovery) |
| Error | Auth Expired | Underlying cause identified as credential expiration |
| Error | Archived | Admin archives the connection |
| Auth Expired | Active | Admin updates credentials and the connection test passes |
| Auth Expired | Archived | Admin archives the connection without resolving credentials |
| Archived | Pending | Admin reactivates a connection that has never successfully synced |
| Archived | Active | Admin reactivates a connection that previously had successful syncs |

### Blocked Transitions

| Attempted Transition | Block Condition | Behavior |
| --- | --- | --- |
| Archived → Pending or Active | Credentials are expired | Reactivation is blocked. The system surfaces a prompt: "Update credentials before reactivating this connection." Admin must update credentials and pass a connection test before reactivation is permitted. |
| Draft → Pending | Setup is incomplete (required fields missing or connection test not passed) | Activation is blocked. The system routes the admin back to the incomplete or untested step. |

### Auto-Recovery

Warning and Error both auto-recover. When a sync run completes and all endpoints succeed, the connection returns to Active without admin intervention. The previous failure is preserved in the sync log for reference.

This applies equally to scheduled and on-demand syncs. The first successful run after a failure clears the status.

## 5. Auth Expired Behavior

Auth Expired is distinct from Error because the resolution path is known and specific: update credentials. The system does not wait for a failed sync to surface this status — it evaluates credential expiration proactively based on the expiration date captured during connection setup (consistent with Auth Type Support REQ-14 and REQ-15).

When a connection enters Auth Expired:

* No further syncs are attempted until credentials are updated
* A persistent "Credentials expired" banner appears on the connection detail view with a direct link to the auth edit flow
* An email notification is sent to the connection owner (consistent with Auth Type Support REQ-16)
* The status clears to Active once the admin updates credentials and the connection test passes

Auth Expired takes precedence in the status display over Warning or Error. A connection that is both credential-expired and endpoint-failing shows Auth Expired, since fixing credentials is the prerequisite for any other recovery.

## 6. Pending State Behavior

Pending applies only to connections that have never completed a sync. It exists to prevent "Active" from implying data availability when no data has arrived yet.

* A freshly activated connection enters Pending immediately after activation
* The connection detail view surfaces a note: "First sync pending — no data has been ingested yet"
* Pending clears to Active (or Warning/Error) when the first sync run completes
* If a connection is archived and then reactivated, it does not re-enter Pending — it returns to Active, because it already has sync history and data. The next scheduled run proceeds normally.

## 7. Scope of Data

The following fields define connection status in the data model.

**Connection record (additions/updates):**

* `status`: enum — `draft` | `pending` | `active` | `warning` | `error` | `auth_expired` | `archived`
* `status_changed_at`: timestamp — when the status last changed
* `status_changed_by`: string — `system` for auto-transitions, user ID for admin-triggered transitions
* `first_sync_completed_at`: timestamp — used to determine whether reactivation returns to Pending or Active
* `archived_at`: timestamp — when the connection was archived (consistent with Connection Lifecycle Management REQ-04)
* `reactivated_at`: timestamp — when the connection was most recently reactivated (consistent with REQ-05)

**Status display metadata (read-only, derived):**

* `active_endpoint_count`: integer — number of endpoints currently in Active status
* `error_endpoint_count`: integer — number of endpoints currently in Error status
* `has_expired_credentials`: boolean — whether any auth credentials on the connection have passed their expiration date

**Explicitly out of scope:**

* Per-endpoint status fields — defined in the Endpoint Library sub-PRD
* Sync run history records — defined in the Pull API Support sub-PRD
* Auth credential expiration fields — defined in Auth Type Support

## 8. Requirements

**REQ-01 As FloQast (system), I must evaluate and update connection status after every sync run so that the displayed status always reflects the current state of the connection.**

_Functional spec:_ After each sync run completes — scheduled or on-demand — the system must re-evaluate the connection's status based on the rollup rules in Section 3. If the status has changed, the system must update `status`, `status_changed_at`, and `status_changed_by` (set to `system`). Status changes must be reflected in the connection list and detail view without requiring a page refresh where technically feasible.

**REQ-02 As FloQast (system), I must auto-recover a connection from Warning or Error to Active when a sync run completes with all endpoints succeeding.**

_Functional spec:_ When a sync run completes and all endpoints return a success status, the connection must automatically transition to Active. No admin action is required. The previous failure is preserved in the sync log. The transition must follow the rollup rules in Section 3 and must not require manual acknowledgment.

**REQ-03 As FloQast (system), I must set a connection to Auth Expired status when its credentials pass their expiration date, without waiting for a sync failure.**

_Functional spec:_ The system must evaluate credential expiration dates daily and transition any connection whose credentials have expired to Auth Expired status. This evaluation must run independently of the sync schedule. Auth Expired takes precedence over Warning or Error in the displayed status. The transition must trigger the notification and UI prompt behaviors defined in Auth Type Support REQ-15 through REQ-18.

**REQ-04 As FloQast (system), I must block reactivation of an Archived connection when its credentials are expired, and prompt the admin to update credentials first.**

_Functional spec:_ When an admin selects Reactivate on an Archived connection, the system must check whether any credentials on the connection are expired. If they are, the reactivation must be blocked. The system must display a message: "Update credentials before reactivating this connection." with a direct link to the auth edit flow. Reactivation is permitted only after credentials are updated and the connection test passes.

**REQ-05 As FloQast (system), I must set a freshly activated connection to Pending status until its first sync completes successfully.**

_Functional spec:_ On activation of a new connection, the system must set status to Pending. The connection detail view must display a note: "First sync pending — no data has been ingested yet." When the first sync run completes, the system must transition the connection to Active, Warning, or Error based on endpoint outcomes. A reactivated archived connection that has prior sync history must not enter Pending — it must transition directly to Active.

**REQ-06 As an admin, I want to see a connection's current status in the connection list so that I can identify issues without opening each connection individually.**

_Functional spec:_ Each row in the connection list must display a status badge corresponding to the connection's current status. Badge styling must visually distinguish between: healthy states (Active, Pending — neutral), degraded states (Warning — amber), failed states (Error, Auth Expired — red), and inactive states (Draft, Archived — gray). Status badges must reflect the most recently evaluated state. Syncing must not appear as a list-level status badge.

**REQ-07 As an admin, I want to see an in-progress indicator on the connection detail view when a sync is actively running so that I know not to interpret the current status as reflecting a completed run.**

_Functional spec:_ While a sync is actively executing on a connection, the connection detail view must display a visible in-progress indicator (e.g., a spinner or "Sync running" label). This indicator must not change the connection's status badge in the list view. When the sync completes, the indicator must clear and the status must update based on the run outcome.

## 9. User Interaction and Design

### Connection List — Status Badges

Each connection row displays a status badge. Recommended styling:

| Status | Badge color | Label |
| --- | --- | --- |
| Draft | Gray | Draft |
| Pending | Blue | Pending |
| Active | Green | Active |
| Warning | Amber | Warning |
| Error | Red | Error |
| Auth Expired | Red | Auth Expired |
| Archived | Gray | Archived |

The connection list defaults to showing Active, Pending, Warning, Error, and Auth Expired connections. Draft and Archived connections are accessible via filter (consistent with Connection Lifecycle Management REQ-08).

### Warning and Error — Inline Detail

Connections in Warning or Error display a secondary line beneath the connection name in the list: a count of failing endpoints (e.g., "2 of 5 endpoints failing"). This gives admins triage context without opening the connection.

### Auth Expired — Banner

On the connection detail view, Auth Expired surfaces a persistent red banner: "Credentials expired — syncs will not run until credentials are updated." with a direct action link to the auth edit flow. This banner persists until the status clears.

### Pending — First Sync Note

On the connection detail view, Pending connections display a passive note beneath the connection header: "First sync pending — no data has been ingested yet." This note clears when the first sync completes.

### Blocked Reactivation

When reactivation is blocked due to expired credentials, the Reactivate action displays an inline error rather than proceeding: "Credentials expired. Update credentials before reactivating." with a direct link to the auth edit flow.

## 10. Open Questions

| Question | Owner | Notes |
| --- | --- | --- |
| Should the system send an admin notification when a connection auto-recovers from Error or Warning back to Active? | PM | Auto-recovery is silent by default. An optional notification could be useful for high-priority connections, but adds configuration complexity. Decide before M7 of Pull API Support. |
| What is the status of a connection where some endpoints have expired credentials and others do not? | PM / Engineering | Current assumption: Auth Expired takes precedence at the connection level if any credential is expired. Needs confirmation. |
| Should Warning trigger an email notification to the connection owner, or only surface in the UI? | PM | Error and Auth Expired trigger email (per Auth Type Support). Warning is currently UI-only. Consider whether partial failures warrant proactive notification. |
| For the reactivation block on expired credentials: should the system require a full connection test to pass, or just a credential update with a lighter-weight auth check? | Engineering | A full connection test is more thorough but adds friction. An auth-only check is faster but may allow a connection with other configuration issues to reactivate into an Error state immediately. |
