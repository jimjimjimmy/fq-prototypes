# **1. Objective**

The FQ API initiative enables customers to push structured financial data directly into FloQast using FloQast's own object models. It provides a flexible, scalable ingestion path for customers whose data lives outside of traditional ERP integrations, including customers with large transaction volumes that the current infrastructure cannot support.

The existing Lambda-based architecture caps data transmission at approximately 2,000 transactions per API call, which is insufficient for customers with millions of transactions per month. This initiative re-architects that foundation and introduces a standardized ingestion API to support a broader range of customer data architectures, source systems, and implementation patterns.

Success is defined as supporting this ingestion method at scale, with customers, including customer technical teams, the FloQast implementation team, and integration partners, able to reliably push data into FloQast without manual setup or volume constraints.

# **2. Key Benefits**

* Customers can push data directly into FloQast without requiring a pre-built ERP integration.
* The FQ API is surfaced as a first-class connection type within FloQast's existing API connection setup workflow, making it discoverable and consistent with how other connections are established.
* Auto-configuration eliminates manual setup: no lineage configuration or field mapping required from the customer.
* Upsert support enables incremental and corrective data loads across multiple API calls without duplication.
* Re-architected infrastructure removes the current ~2,000 transaction-per-call ceiling, supporting millions to tens of millions of transactions per month.
* Enables FloQast to serve a broader range of customer data architectures and source systems.
* Self-serve API key management in Data Studio gives customers and implementation teams control over authentication without FloQast team involvement.

# **3. Use Cases**

1. A customer's IT team selects the FQ API as their connection type within FloQast's connection setup workflow, generates an API key, and begins pushing GL transactions from an in-house ERP to FloQast on a monthly basis.
2. A FloQast implementation specialist sets up the FQ API connection on behalf of a new customer during onboarding, selecting the FQ API connection type and relying on auto-configure to complete setup without manual mapping.
3. A third-party integration partner builds a connector to FloQast using the FQ API to enable customers in their ecosystem to push financial data automatically.
4. A customer with 10M+ monthly GL transactions batches their data across multiple API calls; the system upserts records correctly across calls without duplication.
5. A customer re-submits corrected balance data mid-month; the system upserts the updated records, overwriting the previously submitted dataset for that period.
6. A customer submits a batch of Accounts data and checks the processing status to confirm row counts and surface errors before the close.

# **4. Success Metrics**

* Successful ingestion at target volumes: millions of transactions per month, per customer.
* Auto-configure completing without manual intervention for standard setups.
* API error rate within acceptable thresholds (specific target TBD with Engineering).
* Processing status accurately reflecting ingestion outcomes for all submissions.

# **5. Assumptions**

* Customers are sending data that already conforms to FQ object models; no transformation layer is required by FloQast.
* The existing FloQast API will continue to operate in parallel. Deprecation of the existing API is out of scope for this initiative.
* Customers or their technical teams are capable of managing API key authentication.
* FQ entity IDs are available and retrievable via the GET /entities endpoint prior to data submission.
* High-volume support will require infrastructure changes beyond the current Lambda-based architecture.
* Data pushed via the FQ API is already period-tagged and entity-associated by the customer.

# **7. Scope of Data**

The following data models are in scope for this initiative:

* Accounts (Phase 1)
* Balances (Phase 1)
* GL Transactions (Phase 1)
* FX Rates (Phase 2)
* Companies (Phase 2)
* SL Transactions (Phase 2)
* Entity Lookup — GET /entities (Phase 1, supporting endpoint)

Each data model endpoint accepts: required fields, optional fields, dimensions and metadata, FQ entity association, and period information. Field-level specifications are defined in per-model sub-PRDs.

Bank Transactions are explicitly out of scope for this PRD and are targeted for a future phase.

**REQ-01: As a customer technical team or FloQast implementation specialist, I want to generate an API key within Data Studio so that I can authenticate my integration without requiring additional FloQast team involvement.**

_**Functional spec:** Customers navigate to the Data Studio area within FloQast to create, view (masked), and revoke API keys scoped to their organization. On key generation, the system displays the full key once; subsequent views show only a masked representation. Key rotation, scoping, and rate limit behavior are defined in the Authentication & API Key Management sub-PRD._

‌

**REQ-02: As a customer technical team, I want to push structured financial data to FloQast using FQ object models so that I can ingest data without building a custom transformation layer.**

_**Functional spec:** The API accepts payloads structured per FQ object model schemas. Each endpoint accepts required fields, optional fields, dimensions and metadata, FQ entity association, and period information. Field-level specs are defined in per-model sub-PRDs._  
_Phase 1 endpoints: Accounts, Balances, GL Transactions._   
_Phase 2 endpoints: FX Rates, Companies, SL Transactions._ 

‌

**REQ-03: As a FloQast implementation specialist or customer technical team, I want the connection, endpoint visibility, and standard mapping to be automatically configured on API connection setup so that setup requires no manual intervention.**

_**Functional spec:** On creating the API connection for a given customer/entity, the system auto-creates: (1) endpoint visibility and (2) a standard mapping. No lineage configuration or manual field mapping is required from the customer. Trigger conditions, sequencing, and failure handling are defined in the Auto-Configure sub-PRD._

‌

**REQ-04: As a customer technical team, I want to make multiple API calls for the same period or dataset so that I can submit data in batches or send corrections without creating duplicate records.**

_**Functional spec:** The API supports upsert behavior - records are inserted on first submission and updated on subsequent calls for the same logical record. Upsert key design (customer-supplied external ID vs. FQ composite key) and conflict handling are defined in the Data Handling sub-PRD._

‌

**REQ-05: As a customer technical team, I want to check the processing status of my data submissions so that I can confirm successful ingestion and identify any errors.**

_**Functional spec:** Each API call returns a response indicating success or failure, the number of rows processed, and error details for failed records. Synchronous response vs. asynchronous polling or webhook pattern is an open decision defined in the Logging sub-PRD._

‌

**REQ-06: As a customer technical team, I want to retrieve FQ entity IDs via a GET /entities endpoint so that I can correctly associate submitted data with the right entities in FloQast.**

_**Functional spec:** The GET /entities endpoint returns the list of FQ entities available for the authenticated customer, with sufficient information to map source-system entities to FQ entity IDs. Response supports filtering and pagination. Full response structure is defined in the Entity endpoint sub-PRD._

‌

**REQ-07: As a customer technical team, I want the API to reliably handle high volumes of transactions so that I can ingest datasets of millions to tens of millions of transactions per month.**

_**Functional spec:** The API infrastructure must be re-architected beyond the current Lambda-based implementation, which caps ingestion at approximately 2,000 rows per call. The new architecture must remove this constraint and support the target volume. Specific infrastructure pattern and batch/chunking strategy are open decisions defined in the High-Volume Data Ingestion sub-PRD._

‌

**REQ-08: As a customer technical team or FloQast implementation specialist, I want the FQ API to be available as a selectable connection type within FloQast's API connection setup workflow so that setting up a data ingestion connection is consistent with how other connections are established.**

_**Functional spec:** The FQ API must be incorporated into FloQast's existing API connection setup workflow as a first-class connection type. When a user selects the FQ API connection type, the system initiates the connection setup process - including API key generation - and positions the connection for auto-configure to fire on first successful data submission. Full UI flow and integration details are defined in the Connection Setup sub-PRD._

# **9. User Interaction and Design**

The end-to-end flow spans three sequential stages: Connection Setup, Data Submission, and Auto-Configure.

## **Stage 1: Connection Setup**

* The FQ API is available as a selectable connection type within FloQast's existing API connection setup workflow.
* When a user selects the FQ API connection type, the system initiates the setup process, including API key generation in Data Studio.
* The Data Studio UI supports: generating a new API key, viewing existing keys in masked form, and revoking keys.
* On key generation, the system displays the full API key once. The customer is responsible for storing it securely; subsequent views show only a masked representation.
* The API key is passed in request headers for all subsequent API calls.
* Full UI flow and integration details are defined in the Connection Setup sub-PRD.

‌

## **Stage 2: Data Submission Flow**

2. Customer authenticates using their API key.

1. Customer optionally calls GET /entities to retrieve FQ entity IDs for data association.
2. Customer constructs a payload conforming to the target endpoint's schema and submits.
3. System processes the payload and returns a status response: success/failure, row counts processed, and error details for any failed records.
4. For large datasets, customer submits data across multiple calls; upsert logic reconciles records across submissions.

‌

## **Stage 3: Auto-Configure**

* On the connection setup for a given customer/entity, FloQast automatically creates: endpoint visibility, the connection, and a standard mapping.
* No user action is required for this stage -  it is triggered automatically by the first successful data submission.
* Auto-configure failure handling to be defined in the Auto-Configure sub-PRD.

# **11. Out of Scope**

* Deprecation of the existing FloQast API.  Planned for a future phase; not part of this initiative.
* Bank Transactions endpoint - targeted for Phase 3; out of scope for this PRD.
* Checklists, reconciliations, audit trail, compliance, users, and folders apis.
* Data transformation or normalization - data must arrive pre-formatted to FQ object model specifications.
* Outbound or read-only APIs - this PRD covers data ingestion only.
* Field-level specifications per data model - covered in separate child PRDs, one per model.
