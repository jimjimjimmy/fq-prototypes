> **Context:** The NetSuite Direct API connection provisions a standard set of endpoints automatically on setup. This sub-PRD defines what those standard endpoints are, how they are auto-provisioned, what additional endpoints are available for customers who need more data, how each endpoint's parameters are configured, and how the full endpoint lifecycle (activate, deactivate, edit, delete) is managed. All NetSuite endpoints use SOAP/XML transport and are limited to SOAP operations for which a parser exists in the FloQast integration layer. This document follows the patterns established in the Direct API Data Platform 2.0 Data Ingestion PRD and its child pages.

---

## 1. Feature Overview

A NetSuite Direct API connection exposes financial data through a defined set of SOAP operations. Two of these — Accounts and Balances — are the core data sources for FloQast Close Management and Reporting workflows and are provisioned automatically on connection creation. Customers who need additional data (transactions, periods, currencies, books, entities) can activate additional endpoints from a supported endpoint library without engineering involvement.

Unlike generic REST API connections, NetSuite Direct API endpoints are not configurable at the SOAP request level by admins. Endpoints are predefined SOAP operations with fixed parsers in the FloQast integration layer. Admin-facing configuration is limited to the parameters those operations natively support.

### 1.1 User Stories

| Story ID | User Story |
| --- | --- |
| US-EP-01 | As a Data Studio admin, I want the standard Accounts and Balances endpoints provisioned automatically when I set up a NetSuite connection so that I don't have to configure them manually. |
| US-EP-02 | As a Data Studio admin, I want to see all active endpoints for my NetSuite connection in one view so that I understand what data is being collected and the health of each endpoint. |
| US-EP-03 | As a Data Studio admin, I want to activate additional supported NetSuite endpoints (e.g., Transactions, Periods) from an endpoint library so that I can bring in more data without filing a support ticket. |
| US-EP-04 | As a Data Studio admin, I want to configure dimensional options on the Balances endpoint (departments, classes, locations, entity) so that balance data is broken down at the right level of granularity for my organization. |
| US-EP-05 | As a Data Studio admin, I want to deactivate an endpoint without deleting it so that I can pause data collection while preserving the configuration and run history. |
| US-EP-06 | As a Data Studio admin, I want to see the status of each endpoint and access logs for every sync operation so that I can monitor health and troubleshoot failures without engineering support. |

## 2. Standard Endpoint Auto-Provisioning

### 2.1 Standard Endpoints

The following endpoints are automatically provisioned when a new NetSuite Direct API connection is created. They are the minimum required data sources for FloQast Close Management and Reconciliations.

| Endpoint Name | SOAP Operation | Data Returned | Default Sync Frequency |
| --- | --- | --- | --- |
| Accounts | AccountSearchAdvanced | Chart of accounts — internal ID, number, name, account type, financial statement classification, normal balance, general rate type, active status | Daily (24h), with full refresh on first sync of each accounting period |
| Balances | getPostingTransactionSummary | Period-level account balances by subsidiary and accounting book, with optional dimensional breakdowns | Daily (24h) |

Additional endpoints, if needed for the configuration, are also auto provisioned.

| Endpoint Name | SOAP Operation / Type | Data Returned | Primary Use Case |
| --- | --- | --- | --- |
| Periods | AccountingPeriodSearch | Accounting period definitions — name, start date, end date, period type, closed status | Period-aware sync scheduling and date resolution |
| Currencies | CurrencySearch | Currency definitions — ISO code, name, exchange rate | Multi-currency balance reporting |
| Books | AccountingBookSearch | Accounting book definitions — internal ID, name, effective period | Multi-book balance configuration |
| Entities | EntitySearch | Entity records (customers, vendors, employees) referenced in balance and transaction data | Dimensional context for entity-coded balances |

### 2.2 Auto-Provisioning Behavior

On creation of a new NetSuite Direct API connection, the system automatically:

1. Creates and activates standard endpoints (Accounts and Balances) for the connection.
2. Applies default parameter configuration to each endpoint (see Section 3 for Balances dimensional options).
3. Sets sync frequency to 24 hours for each.
4. Displays both endpoints in the Source Data section of the connection detail view with Active status.
5. Triggers creation of lineage records for the Accounts and Balances data models as part of the same setup action.

No admin action is required. Both endpoints are available and scheduled immediately after connection creation completes.

### 2.3 Acceptance Criteria — Standard Provisioning

| AC-ID | Criterion |
| --- | --- |
| AC-EP-01 | On creation of a new NetSuite Direct API connection, both Accounts and Balances endpoints are automatically created, activated, and visible in the Source Data section with a default sync frequency of 24 hours and Active status. |
| AC-EP-02 | Standard endpoints are pre-populated with system-defined descriptions and do not require admin input to activate. |
| AC-EP-03 | Lineage records for Accounts and Balances are created as part of the same connection setup action. Failure to create lineage records surfaces an error to the admin and does not silently succeed. |
| AC-EP-04 | Standard endpoints (Accounts, Balances) expose Deactivate but not Delete in the action menu. Permanent deletion is not permitted for standard endpoints. |

## 3. Balances Endpoint Configuration Options

### 3.1 Dimensional Data Options

The Balances endpoint (getPostingTransactionSummary) supports optional dimensional breakdowns that increase the granularity of balance data. These are configured per connection at endpoint setup through the automatic setup or via the Edit action. When a dimension is enabled, the corresponding field is added to both the SOAP request and the response grouping.

| Dimension | Field Returned | Default State | Notes |
| --- | --- | --- | --- |
| Departments | department.internalId | Off | Enable for customers using department-level reporting |
| Classes | class.internalId | Off | Enable for customers using class-level reporting |
| Locations | location.internalId | Off | Enable for customers using location-level reporting |
| Entity | entity.internalId | Off | NetSuite entity (customer/vendor/employee); distinct from FQ subsidiary |

All of the above fields and the following fields are always included in the Balances request regardless of dimensional settings: period, account, book, subsidiary.

> **Not Yet Implemented:** Date range filtering on the Balances endpoint (`withStartAndEnd`) is currently a TODO in the integration layer. Until implemented, balance requests retrieve data for configured periods only — no start/end date parameters are passed to the SOAP service.

### 3.2 Acceptance Criteria — Balances Configuration

| AC-ID | Criterion |
| --- | --- |
| AC-EP-05 | Dimensional options (departments, classes, locations, entity) are on by default. Each can be removed from the field mapping via the Dimensions configuration. |
| AC-EP-06 | When a dimension is enabled, the corresponding field appears in balance records stored in FloQast. When disabled, the field is omitted from the response and the stored record. |
| AC-EP-07 | Enabling a new dimension on the Balances endpoint triggers a re-sync of balance data for the current and prior fiscal year so that the new dimension is populated historically. |
| AC-EP-08 | The default fields (period, account, book, subsidiary) are always included in the Balances request and cannot be removed or disabled by admins. |

## 4. Additional Endpoint Library

### 4.2 Activating an Additional Endpoint

Admins can add a new endpoint from the connection detail view.

1. Admin opens the endpoint library from the Source Data section of the connection detail view.
2. Admin browses available NetSuite endpoints.
3. Admin selects add a custom endpoint. If a matching endpoint already exists for this connection, the system detects the duplicate and prompts the admin to link the existing configuration rather than create a new entry.
4. The admin inputs the relevant details related to the endpoint - endpoint url, query parameters, sync frequency, etc. This follows the Direct Connect API workflow for adding an endpoint to an existing connection.
5. Admin reviews and adjusts configurable parameters where applicable (see Section 4.3).
6. Admin saves. The endpoint is activated and appears in the Source Data list with Active status

### 4.3 Endpoint Parameters

Each additional endpoint supports a defined set of configuration parameters. These are pre-defined options specific to each SOAP operation — not arbitrary query parameters.

### 4.4 Acceptance Criteria — Additional Endpoints

| AC-ID | Criterion |
| --- | --- |
| AC-EP-09 | All supported additional NetSuite endpoints are visible in the endpoint library, showing name, SOAP operation, description, and current activation status for this connection. |
| AC-EP-11 | When an admin attempts to add an endpoint that is already configured for the connection, the system detects the duplicate and presents an option to link the existing endpoint rather than create a new one. |

## 5. Endpoint Lifecycle Management

All NetSuite endpoints — standard and additional — follow the lifecycle pattern established in the platform Endpoint Library PRD. This section documents NS-specific constraints that apply on top of that pattern.

### 5.1 Edit

Admins can edit the configuration of any active endpoint via the Edit action. Editable fields:

* Sync frequency (default 24h; options: 1h, 2h, 4h, 8h, 12h, 24h) in Source Data
* Dimensional options (Balances endpoint only — see Section 3.1) in Field Mappings
* Endpoint-specific parameters as defined in Section 4.3 in Source Data

### 5.2 Deactivate (Archive)

Deactivation stops all scheduled and on-demand sync for an endpoint but preserves configuration and run history. The endpoint remains visible in the Source Data list in an Archived state and can be reactivated.

For standard endpoints (Accounts, Balances): deactivation is permitted only after the admin acknowledges any active lineage records or downstream application dependencies. The system surfaces the affected model fields before the action proceeds.

On reactivation of any endpoint, the admin is prompted to select a data pull start point: from the beginning, from a specific date, from last sync, or going forward only.

### 5.3 Delete

Standard endpoints (Accounts, Balances) cannot be permanently deleted — Deactivate only.

Additional endpoints can be permanently deleted. A confirmation modal is required before deletion proceeds, with explicit language that the action is irreversible and that all configuration and run history will be removed. If the endpoint feeds an active lineage record, the affected model fields are listed in the modal and the admin must acknowledge before deletion is permitted.

### 5.4 Acceptance Criteria — Lifecycle

| AC-ID | Criterion |
| --- | --- |
| AC-EP-13 | Standard endpoints (Accounts, Balances) expose Deactivate but not Delete in the action menu. |
| AC-EP-14 | Deactivating any endpoint that has active lineage records surfaces the affected model fields in a warning before the action is confirmed. The action is permitted after acknowledgment. |
| AC-EP-15 | Deleting an additional endpoint requires a confirmation modal stating the action is permanent and irreversible. The endpoint, its configuration, and its run history are removed on confirmation. |
| AC-EP-16 | On reactivation, the admin is prompted to choose a data pull start point: from the beginning, from a specific date, from last sync, or going forward only. Going forward only is the default. |

## 6. Endpoint Status and Logs

### 6.1 Status Display

Each endpoint in the Source Data section displays a status badge reflecting the most recent known state:

| Status | Color | Meaning |
| --- | --- | --- |
| Active | Green | Endpoint is enabled and running on schedule |
| Archived | Gray | Endpoint is deactivated; no syncs running; configuration preserved |
| Running | Blue | Sync currently in progress |
| Error | Red | Last sync failed; expand to see error detail |

Connectivity errors (SOAP auth failures, network timeouts) and sync errors (parser failures, transformation errors) are tracked and displayed as distinct error categories per endpoint. See Sub-PRD 6 (Notifications & Logging) for the full platform log schema.

### 6.2 Log Requirements

Every sync operation — scheduled or on-demand — generates a log entry scoped to the connection and endpoint, following the platform job log schema defined in Sub-PRD 6. NetSuite-specific extension: each log entry also records data change counts for that endpoint (records created, updated, and unchanged) to support data freshness auditing.

### 6.3 Acceptance Criteria — Status and Logs

| AC-ID | Criterion |
| --- | --- |
| AC-EP-17 | Every endpoint in the Source Data section displays a status badge reflecting the most recent known state (Active, Archived, Running, Error). |
| AC-EP-18 | Every sync operation on any endpoint — scheduled or on-demand — produces a log entry accessible from the connection detail view. |
| AC-EP-19 | Connectivity errors and sync errors are displayed as distinct error categories on the endpoint. Errored endpoints show an inline error summary expandable to full error detail. |
| AC-EP-20 | Each log entry includes NS-specific data change counts: records created, updated, and unchanged for that endpoint run. |

## 8. Edge Cases & Error Handling

| Scenario | Expected Behavior |
| --- | --- |
| Admin enables a dimension on Balances but the NetSuite role lacks access to that record type | Sync runs; dimension field returns empty for affected records. Warning logged: "Dimension \[name\] returned no data. Verify that the connected NetSuite role has access to \[record type\]." |
| Admin activates Transactions endpoint for a large NetSuite account (millions of transaction lines) | Warning shown at activation: "The initial Transactions sync may take an extended period depending on transaction volume." System uses the existing 55-pages-per-batch mechanism and logs progress incrementally. |
| Admin deactivates Accounts endpoint while a balance sync is in progress | The running sync completes. Deactivation takes effect at the start of the next scheduled window. |
| Reactivation of Balances endpoint after extended deactivation | Admin is prompted to choose pull start point. If "from the beginning" is selected and the resulting data volume is large, a warning is shown consistent with initial-sync behavior. |
