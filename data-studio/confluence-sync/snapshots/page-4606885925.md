## 1. Objective

This sub-PRD defines the migration path for existing Intacct customers from the legacy direct connection (outside Data Platform 2.0) to the new Intacct Direct API connection in Data Studio. The migration must preserve customer balance data configurations, populate historical data, run old and new connections in parallel for validation, and execute a controlled cutover — with minimal disruption to customers.

The migration is internal and engineering-led. Customers are not expected to reconfigure their connections manually.

---

## 2. Customer Segmentation

Before migration begins, all existing Intacct customers are segmented into buckets based on the complexity of their current balance data configuration in Recs. Segmentation determines migration sequencing, validation rigor, and the level of manual review required before cutover.

| Segment | Description | Migration Approach |
| --- | --- | --- |
| **Tier 1 — Standard** | Default balance configuration: single reporting book, no dimensional filtering (no location, department, or vendor filters) | Automated migration; lowest risk |
| **Tier 2 — Dimensional** | Custom dimensional filters configured (location, department, vendor, or specific reporting book) but no multi-book complexity | Automated migration with configuration mapping validation step |
| **Tier 3 — Multi-Book** | Multiple reporting or adjustment books configured; adjustment book ID construction must be validated against the new book ID concatenation logic | Semi-automated; requires Engineering review of book ID mapping before cutover |
| **Tier 4 — Complex / Custom** | Non-standard configurations, custom scripts, or unusual setups not covered by Tiers 1–3 | Manual migration; handled case-by-case with Engineering and CS involvement |

> **Open Question:** What is the current count and distribution of customers across these segments? This drives migration timeline and resourcing.

## 3. Phase 1 — Connection Setup

The new Intacct Direct API connection in Data Studio is created for each customer using credentials and configuration data sourced from the existing legacy connection. Customers do not need to re-enter credentials or reconfigure their connection from scratch.

### 3.1 Requirements

**REQ-01: The system must use existing legacy connection credentials to pre-populate the new Data Studio connection.**

*Functional spec: Company ID, User ID, Password, and Client ID (where present) are sourced from the legacy connection record and used to establish the new connection. FloQast sender credentials are applied automatically. Credentials are not exposed to customers during migration.*

**REQ-02: The system must map the customer's existing balance configuration from Recs to the corresponding custom fields on the new GL Balances endpoint.**

*Functional spec: The migration process reads the customer's current balance data configuration (reporting book, location, department, vendor, show zero balances, include child locations) from the legacy system and writes the equivalent values to the new connection's GL Balances endpoint custom fields as defined in Sub-PRD 4. Where a 1:1 mapping exists, it is applied automatically. Where the mapping is ambiguous or unsupported in the new model, the record is flagged for manual review.*

**REQ-03: All standard endpoints must be auto-provisioned on the new connection as part of migration setup.**

*Functional spec: Following the standard auto-provisioning behavior defined in Sub-PRD 7, all standard endpoints (Accounts, GL Balances, Periods, Currencies, Books, Locations) are activated for the migrated connection.*

### 3.2 Acceptance Criteria

| AC-ID | Criterion |
| --- | --- |
| AC-MIG-01 | A new Intacct Direct API connection is created in Data Studio for each migrating customer using credentials sourced from the legacy connection. |
| AC-MIG-02 | Balance configuration fields from the legacy connection are mapped to the equivalent GL Balances endpoint custom fields in the new connection. |
| AC-MIG-03 | Configurations that cannot be automatically mapped are flagged for manual review before the connection is activated. |
| AC-MIG-04 | All standard endpoints are auto-provisioned on the new connection as part of migration setup. |

## 4. Phase 2 — Historical Data Backfill

Once the new connection is set up, historical balance and account data is backfilled into the FQ data layer for the new connection. This ensures customers have continuity of data in Data Studio from day one.

### 4.1 Requirements

**REQ-04: The system must backfill historical data for each migrated connection up to a defined lookback window.**

*Functional spec: The target lookback window is 24 months prior to the migration date, subject to confirmation (see Open Questions). Backfill covers Accounts and GL Balances. The backfill job runs as a one-time operation and is logged as a distinct run type (*`"backfill"`*) in the job log schema defined in Sub-PRD 6.*

**REQ-05: Backfill data must use the same balance configuration as the migrated connection.**

*Functional spec: The GL Balances backfill request uses the same reporting book, location, dimensional filters, and custom field values as the live migrated connection. Backfill data is not pulled with different parameters.*

### 4.2 Acceptance Criteria

| AC-ID | Criterion |
| --- | --- |
| AC-MIG-05 | Historical data is backfilled for each migrated connection covering the agreed lookback window (target: 24 months). |
| AC-MIG-06 | Backfill jobs are logged with `trigger_type: "backfill"` and are visible in the connection's run log. |
| AC-MIG-07 | Backfill failures do not block the parallel running phase — they are logged and queued for retry. |

## 5. Phase 3 — Parallel Running & Validation

After connection setup and backfill, the new Data Studio connection runs in parallel with the legacy connection for a defined validation period. Both old and new pull data independently. This phase exists to validate data parity before customers are cut over.

### 5.1 Requirements

**REQ-06: The new Data Studio connection must run on its standard sync schedule in parallel with the legacy connection for the duration of the validation period.**

*Functional spec: Both connections sync independently during the parallel period. Data from both is stored and available for comparison. The legacy connection is not modified or paused during this phase.*

**REQ-07: A data parity check must be run between the legacy connection output and the new Data Studio connection output at the end of the validation period.**

*Functional spec: Parity is checked at the balance level (account × period × book × location). Discrepancies beyond a defined tolerance threshold are flagged for investigation before cutover is permitted. Tolerance threshold is TBD (see Open Questions).*

**REQ-08: Parity check results must be documented per customer before cutover approval is granted.**

*Functional spec: A parity report is generated per customer showing: total records compared, matched records, discrepancies (with detail), and a pass/fail outcome. Engineering or Product sign-off is required on any customer with a fail outcome before cutover proceeds.*

### 5.2 Validation Period

The parallel running window is TBD (see Open Questions). Suggested starting point: 2–4 weeks for Tier 1 and Tier 2 customers; longer for Tier 3 and Tier 4.

### 5.3 Acceptance Criteria

| AC-ID | Criterion |
| --- | --- |
| AC-MIG-08 | The new connection runs on its standard sync schedule in parallel with the legacy connection for the full validation period without interfering with legacy data. |
| AC-MIG-09 | A parity report is generated per customer at the end of the validation period comparing balance data between old and new connections. |
| AC-MIG-10 | No customer proceeds to cutover with an unresolved parity fail. |

---

## 6. Phase 4 — Customer Cutover

Once parity is confirmed, customers are cut over from the legacy connection to the new Data Studio connection. Cutover is segment-sequenced — Tier 1 customers move first, followed by Tier 2, then Tier 3 and Tier 4.

### 6.1 Requirements

**REQ-09: The legacy connection must be deactivated for a customer only after cutover is complete and the new connection is confirmed active.**

*Functional spec: Cutover is not considered complete until: (1) the new connection has completed at least one successful scheduled sync post-cutover, and (2) the parity report for that customer has a pass outcome. The legacy connection is deactivated (not deleted) at cutover completion. Legacy data is retained for a defined period post-cutover for rollback purposes.*

**REQ-10: Cutover must be sequenced by customer segment.**

*Functional spec: Tier 1 → Tier 2 → Tier 3 → Tier 4. Within each tier, customers are migrated in batches. Batch size is TBD based on engineering capacity and monitoring overhead.*

**REQ-11: A rollback path must exist for each customer for a defined period post-cutover.**

*Functional spec: If issues are discovered after cutover, the legacy connection can be reactivated and the new Data Studio connection deactivated without data loss. Rollback window is TBD (see Open Questions).*

### 6.2 Acceptance Criteria

| AC-ID | Criterion |
| --- | --- |
| AC-MIG-11 | Cutover is only executed for a customer after their parity report shows a pass outcome. |
| AC-MIG-12 | The legacy connection is deactivated (not deleted) after cutover is confirmed complete. |
| AC-MIG-13 | A rollback path exists for each customer for the defined post-cutover window. |
| AC-MIG-14 | Customers are migrated in segment order (Tier 1 → 2 → 3 → 4) in defined batches. |

---

## 7. Assumptions

* Existing legacy connection credentials are accessible and can be read programmatically to pre-populate the new connection.

* The legacy connection's balance configuration in Recs is the source of truth for migration mapping.

* Historical data in Intacct is available for the full lookback window (24 months) and accessible via the same `get_trialbalance` XML API.

* The legacy connection continues to run unmodified during the parallel period — no changes are made to legacy data pipelines during migration.

* Customer-facing disruption is expected to be zero — no action is required from customers as part of this migration.

* CS teams are notified of cutover timing for each customer and are prepared to handle any inbound questions.

---

## 8. Out of Scope

* Migration of non-Intacct legacy connections

* Changes to the legacy connection infrastructure during the migration window

* Customer self-service migration tooling

* Migration of transaction-level data (`gldetail`) — not in scope for initial Data Platform 2.0 release

* Customer-facing communication about the migration (covered by CS / Marketing)
