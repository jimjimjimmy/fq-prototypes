# **1. Objective**

This sub-PRD defines requirements for endpoint nesting within FloQast Data Studio - specifically, the ability to configure API endpoints whose query parameters are dynamically resolved from the output values of other, upstream endpoints. This capability corresponds to Phase 2 of the API Endpoint Management parent PRD.

Many API endpoints require input values - such as account IDs, entity identifiers, or report scope parameters - that are themselves retrieved dynamically from prior API calls and cannot be known in advance or hardcoded. Without nesting support, admins must manually obtain and hardcode these values, which is error-prone, brittle, and unsustainable across diverse customers. This feature enables fully automated, ordered multi-endpoint data retrieval chains, allowing workflows like balance retrieval (which requires account IDs from an accounts endpoint) to run reliably without manual intervention.

# **2. Key Benefits**

* Dynamic parameter resolution - no hardcoded values that break when upstream data changes.
* Automated dependency ordering - the system sequences endpoint calls correctly without admin intervention.
* Circular dependency prevention - invalid configurations are caught at setup time before any data runs occur.
* Frequency guardrails - child endpoints cannot be configured to run more frequently than their ultimate parent, preventing broken or stale data requests.
* Transparent dependency chains - admins can see and understand the full nesting structure from the configuration UI.
* Flexible multi-level nesting - supports complex data hierarchies (e.g., entity → account type → account → balance) across multiple downstream workflows.

# **3. Use Cases**

1. Balances requiring account IDs: An implementor configures a balances endpoint that requires account IDs as a query parameter. Rather than hardcoding values, they configure a dynamic query parameter sourced from the output of the accounts endpoint. Data Studio runs the accounts endpoint first, then passes the retrieved IDs to the balances request automatically.
2. Multi-level nesting for complex hierarchies: An admin configures a three-level chain where a report endpoint requires a department ID (from a departments endpoint), which in turn requires an entity ID (from an entity endpoint). Data Studio resolves the full chain in order on each sync.
3. Circular dependency prevention: An admin attempts to configure endpoint A as a parent of endpoint B, while endpoint B is already a parent of endpoint A. The system detects the circular reference at save time, rejects the configuration, and clearly identifies the endpoints involved in the cycle.
4. Frequency constraint enforcement: An admin tries to set a balances endpoint to sync every 2 hours, but the accounts endpoint it depends on is configured for every 24 hours. The system rejects the 2-hour setting and displays the constraint, naming the limiting parent endpoint.
5. Browsing and selecting available dynamic fields: When configuring a child endpoint's dynamic query parameter, an admin sees a structured list of output fields from the parent endpoint - populated from a prior test run - in dot-notation (e.g., account.accountId, account.accountName). They select the appropriate field to pass as a parameter.
6. Ordered execution on sync: A scheduled or on-demand sync triggers for a connection with nested endpoints. The system computes execution order, runs each endpoint in sequence, passes output values as inputs to the next tier, and completes the full chain within the sync window.

Derived from the parent PRD. Nesting-specific additions are noted.

‌

| **Metric** | **Target / Description** |
| --- | --- |
| Nested endpoint configuration success rate | > 95% of nested endpoint configurations are saved and first-run successfully without error |
| Circular dependency detection rate | 100% of circular dependency configurations (including indirect cycles) are caught and blocked at save time - zero runtime circular failures |
| Frequency constraint enforcement | 100% of save attempts that violate the parent frequency constraint are blocked with a clear error message |

# **5. Assumptions**

* Parent endpoints must be fully configured and have completed at least one successful test run before their output fields can be used as dynamic query parameters. Available fields are sampled from a prior run response, not from a static schema.
* Output field discovery is based on sampling the most recent test run response for the parent endpoint. Fields reflect the actual structure observed at run time.
* Nesting depth limit is TBD (see Open Questions). This PRD does not commit to a specific maximum but recommends a cap of 4–5 levels to balance flexibility with operational complexity.
* Frequency constraints are enforced at configuration save time, not solely at runtime. A child endpoint cannot be saved with a sync frequency more frequent than its ultimate parent in the chain.
* Static and dynamic query parameters are configured in the same endpoint add/edit flow. This PRD covers only dynamic (nested) parameters; static parameter behavior is defined in the parent PRD.
* Multiple dynamic query parameters per endpoint are supported with no defined upper limit.
* A single endpoint may serve as a parent to multiple independent child endpoints simultaneously.
* Circular dependency detection must account for indirect cycles (A → B → C → A), not just direct two-node cycles.

# **6. Milestones**

This work is scoped to Phase 2 of the parent PRD. Phase sub-division is proposed as follows:

‌

1. Phase 2a - Core nesting configuration: Admins can configure a single level of endpoint nesting, selecting a parent endpoint and a dynamic output field for a child endpoint query parameter. Includes circular dependency detection and frequency constraint enforcement at save time.
2. Phase 2b - Multi-level nesting: Support for chains beyond one level (grandparent → parent → child). System correctly resolves dependency chains of arbitrary depth up to the defined maximum. All constraints apply across the full chain.
3. Phase 2c - Ordered execution and error propagation: System executes endpoints in the correct dependency order during both scheduled and on-demand syncs. Failed parent endpoints block child execution and surface a linked error to the admin in the sync log.
4. Phase 2d - Output field discovery UX: Output fields from parent endpoints are discoverable via a structured selector in the child endpoint configuration flow, populated from the parent's most recent test or live run response. Nested field notation (e.g., account.accountType.code) is displayed and selectable.

# **7. Scope of Data**

The following data objects and entities are in scope:

‌

* Endpoint dependency configuration records: per-child-endpoint, per-connection records storing the parent endpoint reference, the selected output field path in dot-notation, and the child query parameter name it maps to.
* Parent endpoint output field samples: the response structure sampled from a parent endpoint's most recent successful test run, stored per endpoint per connection, used to populate the dynamic field selector in the UI.
* Dynamic query parameter values: runtime-resolved values retrieved from parent endpoint responses and passed as inputs to child endpoint requests. These are ephemeral - resolved at sync time and not stored long-term.
* Execution order records: the resolved topological sort order for a connection's endpoint dependency graph, computed at sync initiation and used to sequence calls within each run.
* Sync run log additions: updates to existing per-run metadata to include the execution sequence, which parent outputs were resolved, and which child endpoints were blocked (with reason) if a parent failed.

‌

Explicitly out of scope:

* Long-term storage of resolved dynamic parameter values (these are ephemeral per run).
* Output field samples from endpoints not yet designated as parents in any active configuration.

# **8. Requirements**

‌

1. **REQ-01: As an admin or implementor, I want to configure a query parameter for an endpoint using a value retrieved from a different (parent) endpoint's output, so that I don't need to manually look up or hardcode values that are dynamic.**

_Functional spec:_ When adding or editing an endpoint, for each query parameter the user must be able to choose between Static (manually entered) or Dynamic (sourced from another endpoint). For dynamic parameters, the user selects a parent endpoint from a list of configured, previously-run endpoints for this connection. Upon parent selection, the system displays available output fields from that endpoint (sampled from its most recent test run) in dot-notation (e.g., account.accountId). The user selects the field to use. The configuration must be validated and saved before the endpoint is active.

‌

2. **REQ-02: As an admin or implementor, I want to add more than one dynamic query parameter to a single endpoint, so that I can handle APIs that require multiple upstream-sourced values.**

_Functional spec:_ The query parameter configuration panel must allow any number of query parameters to be configured as dynamic. Each dynamic parameter may reference the same or a different parent endpoint. There is no defined limit on the number of dynamic parameters per endpoint.

‌

3. **REQ-03: As the system, I must detect and reject any endpoint nesting configuration that would create a circular dependency, so that customers cannot create configurations that loop indefinitely at runtime.**

_Functional spec:_ At save time, the system must validate the full dependency graph for the connection to ensure no cycles exist - including indirect cycles (e.g., A → B → C → A). If a circular dependency is detected, the save must be rejected and the user shown a clear error identifying the specific endpoints forming the cycle. Detection must be performed before any changes are persisted. If there is a circular dependency, the user should not be able to move on to the next step in the API connection setup.

‌

4. **REQ-04: As the system, I must prevent a child endpoint from being configured to sync more frequently than its ultimate parent endpoint, so that data retrieval does not fail or produce inconsistent results due to unavailable upstream data.**

_Functional spec:_ When an admin configures or edits the sync frequency for a child endpoint, the system must identify the most restrictive (least frequent) ancestor in the chain and enforce that as the minimum interval. The user is not allowed to select a frequency exceeding the limiting ancestor, and can see an error explaining the limiting parent endpoint. This constraint must be re-evaluated if the parent endpoint's frequency is later changed.

‌

5. **REQ-05: As the system, I must ensure a parent endpoint is fully configured and has at least one successful run before it can be selected as a dynamic parameter source in a child endpoint.**

_Functional spec:_ In the dynamic query parameter selector, only endpoints that are (a) fully configured for this connection and (b) have a sampled output from at least one successful test run are available for selection. Endpoints that have never been run must not appear. If no qualifying parent endpoints exist, the UI must display a message directing the admin to configure and run a parent endpoint first.

‌

6. **REQ-06: As an admin or implementor, I want to configure endpoint chains that span multiple levels (e.g., entity → account type → account → balance), so that I can support complex data hierarchies.**

_Functional spec:_ The system must support nesting chains of at least two intermediate levels (i.e., grandparent → parent → child, and beyond). The maximum supported depth is TBD (see Open Questions) and must be enforced consistently at both configuration and runtime. All constraints - circular dependency detection, frequency enforcement, and ordered execution - must apply across the full depth of any chain.

‌

7. **REQ-07: As the system, during any sync (scheduled or on-demand), I must execute endpoints in the correct order based on their dependency relationships and pass parent output values as inputs to child endpoint requests.**

_Functional spec:_ At the start of each sync run for a connection, the system must compute the execution order for all active endpoints using topological sorting of the dependency graph. Endpoints with no dependencies run first; endpoints with dependencies run after all parents have completed successfully. Output values from parent runs must be captured and passed as query parameter values to child requests. Execution order must be deterministic for a given graph state.

‌

8. **REQ-08: As an admin, when a parent endpoint fails during a sync, I want to see a clear error indicating which child endpoints were blocked as a result, so that I can diagnose and resolve the issue efficiently.**

_Functional spec:_ If a parent endpoint fails during a sync run (after retries per the parent PRD retry policy), all dependent child endpoints must not execute for that run. The sync log must record each blocked child with a status of 'Blocked - parent endpoint \[name\] failed' and link to the parent's error details. No child endpoint should produce a misleading or silent failure when the root cause is an upstream parent failure.

‌

9. **REQ-09: As an admin or implementor, I want to see a clear representation of the endpoint dependency chain in the configuration UI, so that I understand what upstream calls will be made and in what order.**

_Functional spec:_ In the endpoint add/edit panel, any endpoint with dynamic query parameters must display a summary of the full dependency chain - showing which parent endpoints are referenced, what output fields are being used, and the full ancestor hierarchy for multi-level chains. Each item in the chain must link to the referenced endpoint's configuration. The chain summary must be visible without leaving the edit panel.

‌

10. **REQ-10: As an admin or implementor, when selecting a dynamic query parameter source, I want to see a structured list of available output fields from the parent endpoint in dot-notation format, so that I can identify the correct field to pass.**

_Functional spec:_ When a parent endpoint is selected, the system must display available output fields from that endpoint's most recent test run response in dot-notation (e.g., account.accountId, account.accountType.code). The list must be searchable or filterable. For nested response objects, the full field path must be shown. If a previously selected field no longer exists in the latest sample (e.g., schema change), the system must surface a warning prompting the admin to re-validate the configuration.

# **9. User Interaction and Design**

## **Dynamic Query Parameter Configuration (Add / Edit Endpoint Flow)**

Within the query parameter section of the add/edit endpoint panel, each parameter row includes a type toggle: Static or Dynamic.

‌

When Dynamic is selected:

* A parent endpoint selector appears, listing all fully configured endpoints for this connection that have at least one successful prior run. Endpoints without a prior run are excluded with an inline note explaining the prerequisite.
* Upon selecting a parent endpoint, a field selector appears displaying available output fields sampled from the parent's most recent run, in dot-notation (e.g., account.accountId, account.accountName, account.accountType.code). The list is searchable and shows full paths for nested objects.
* The selected parent and field path are displayed as a summary beneath the parameter row (e.g., "Value from: Accounts → account.accountId").
* Multiple dynamic parameters can be added via an 'Add parameter' action; each follows the same flow independently.

‌

## **Dependency Chain Display**

Beneath the query parameter configuration section, a 'Dependency chain' summary shows:

* The current endpoint's position in the chain (e.g., step 3 of 3).
* Each upstream parent endpoint and the specific output field it provides.
* For multi-level chains, the full ancestor hierarchy displayed as a linear sequence (e.g., Entity → Account Type → Accounts → Balances).
* Each item in the chain is a clickable link to that endpoint's configuration panel.

‌

## **Validation and Error States**

* Circular dependency at save time: save is blocked and a banner displays the specific cycle (e.g., "Cannot save: Balances → Accounts → Balances creates a circular dependency").
* Frequency constraint violation: the sync frequency selector shows an inline error (e.g., "Frequency cannot exceed every 24h - limited by parent endpoint: Accounts").
* Missing parent run: if a parent endpoint selected in an existing child config no longer has valid sampled output, the child endpoint's panel shows a warning and blocks re-activation until the parent is re-run.
* Schema drift warning: if a previously selected field path is absent from the parent's latest sampled response, a warning prompts the admin to re-validate the field selection before saving.

‌

## **Sync Log View (Additions to Existing)**

For connections with nested endpoints, the sync log adds:

* Execution order for each run (e.g., Step 1: Entity, Step 2: Accounts, Step 3: Balances).
* For each step: status (completed / failed / blocked), timing, and the parameter field names used as inputs (field names only, not raw values).
* For blocked endpoints: status 'Blocked' with a direct link to the parent endpoint's failure entry.

# **10. Open Questions**

‌

| **Question** | **Owner** | **Notes** |
| --- | --- | --- |
| What is the maximum supported nesting depth? | Engineering | Parent PRD suggests 4–5 levels as a safe range. Engineering input needed on performance and operational complexity before committing to a specific cap. |
| How should the system handle a parent endpoint whose sampled output schema has changed since the child was configured (i.e., a previously selected field path no longer exists)? | Product / Engineering | Current spec surfaces a warning and blocks re-activation. The resolution path - re-select field, auto-remap, or block - is TBD. |
| What is the behavior when a parent endpoint is deactivated after a child is already configured to use it? | Product | Should the child be automatically deactivated or just flagged? Behavior is undefined. Decision needed before Phase 2a ships. |
| How should the system handle a parent endpoint output that returns multiple values (e.g., a list of account IDs)? Does the child run once per value (fan-out) or use only the first value? | Product / Engineering | Significant implications for data volume, API rate limits, and sync duration. Fan out behavior is expected here (a list of accounts requires a balance retrieval for each account). Expect we will need the user to tell us that however, as other scenarios might differ. |
| Should the system cache parent endpoint output within a sync run, or re-execute the parent for each child that depends on it? | Engineering | Caching is likely correct for performance but has implications for data freshness within a run. Architecture decision needed. |
| How is the sampled output from a parent endpoint refreshed over time? Is it updated on every live run, only on explicit re-test, or both? | Engineering | Affects field selector accuracy. If only updated on re-test, schema drift may go undetected for extended periods. |

# **11. Out of Scope**

* Static query parameter configuration - covered in the parent PRD.
* Write-back or bi-directional sync - this PRD covers read-only data ingestion only.
* Push API endpoint nesting - nesting behavior for push APIs is deferred to Phase 6 of the parent PRD and is not defined here.
* Cross-connection endpoint nesting - a child endpoint in connection A cannot reference a parent endpoint from connection B. All nesting is scoped within a single connection.
* Field-level transformation between parent output and child input (e.g., type conversion, formatting) - the selected field value is passed as-is.
* Visual dependency graph diagrams - this phase uses text-based / hierarchical chain display only. A graphical visualization is not in scope.
* Real-time output field discovery - fields are sampled from a prior run, not live-fetched at configuration time.
