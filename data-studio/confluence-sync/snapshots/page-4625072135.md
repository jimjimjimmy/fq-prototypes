## 🎯 Objective

Customers should not have to open Data Studio to discover that something went wrong. When a pipeline fails, the right person should be told — proactively, with enough context to act.

This PRD defines the Q3 notification system: email alerts for job failures, with clear distinction between failures that will self-heal (transient) and failures that require admin action (permanent). In-app notifications, late data alerts, and programmatic webhook delivery are future phases.

Not covered: notification preferences UI (future), in-app notification center (future), webhook/API delivery (see G10 in Logging & Audit PRD), schema change notifications (see Error Patterns PRD).

Primary users: admins.

---

## 🔤 Definitions

For a complete glossary of terms, see [Data Studio: Definitions & Terms](https://floqast.atlassian.net/wiki/spaces/Data/pages/4464869099).

**Transient failure** — A run failure caused by a self-healing condition (e.g., API timeout, temporary service unavailability). The system will retry automatically. No admin action required unless the condition persists.

**Permanent failure** — A run failure that will not self-resolve and requires admin action to remediate (e.g., invalid credentials, schema mismatch, misconfigured field mapping).

**Notification trigger** — The event that causes a notification to be sent.

---

## 🏅 Why This Is Important

The Logging & Audit PRD ensures failures are recorded. Notifications ensures the right people are told.

Today, the only signal that a pipeline failed is an accountant noticing stale data — often at close, after the window to act quietly has passed. Admins have no way to get ahead of failures. FQ support learns about issues reactively, from customer tickets.

This is also a recurring question in enterprise security reviews: "How does FloQast notify us when an integration fails?" The current answer is not acceptable for upmarket customers.

---

## 🔐 Value Unlocked

Admins are no longer dependent on downstream data users to surface pipeline problems. A failure at 2am generates an email before the close team starts work at 8am — with enough context to act without opening a support ticket.

---

## 🗝️ Key Examples

* **Example 1:** A nightly GL transaction job fails at 2am due to an expired credential (permanent failure). The admin receives an email with the model name, connector, failure time, a plain-language description of the issue, and a direct link to the Logs tab. They re-authenticate before the close team starts work.

* **Example 2:** The same job fails due to an API timeout (transient failure). The admin receives an email noting that the system is retrying automatically and no action is needed unless the failure persists. They don't create a support ticket.

* **Example 3:** The same job fails on the 5th consecutive run. The admin receives an escalation notification indicating that retries have been exhausted and action is required — not a fifth copy of the same email.

---

## 💡 Key Benefits

* Admins are alerted to pipeline failures before their close team notices

* Transient vs. permanent distinction reduces noise — admins know at a glance whether they need to act

* Repeated failures escalate rather than flood — no alert storms

* Direct deep links get admins to the right place without hunting

## 🤔 Assumptions

**Established**

* Notifications build on the job log event schema defined in the Logging & Audit PRD. This PRD does not define new event types — only the notification layer on top of existing log events.

* V1 notification channel is email only. In-app notifications are future state.

* Notification emails are scoped to the customer's tenant — admins only receive notifications for their own tenant's jobs.

* Transient vs. permanent failure classification is determined by the run log (as defined in Logging & Audit PRD) and surfaced in the notification content.

* Repeated failures for the same job produce escalation logic, not repeated identical emails.

* Notification preferences (opt in/out per trigger type) are future state — all admins receive job failure notifications in v1 by default.

## 🗺️ Scope

### 🚗 In Scope

* **Job failure email notification** — sent when a scheduled or on-demand run fails

* **Transient vs. permanent failure distinction** — notification content clearly indicates whether the failure is self-healing (system is retrying, no action needed) or requires admin action

### NOTIF-1 — Job Failure Email Notification

**User Story:** As an admin, I want to be notified by email when a scheduled or on-demand data job fails so that I can investigate and resolve the issue before it affects my close process.

**Importance:** High

**Acceptance Criteria:**

**AC-NOTIF-1-01 — Email sent on job failure**

```
Given a data job fails (scheduled or on-demand)
When the failure is recorded in the job log
Then an email notification is sent to the configured recipients within the defined delivery SLA
```

**AC-NOTIF-1-02 — Email contains required context**

```
Given a job failure notification is sent
When the admin receives the email
Then it includes: model name, connector name, failure time, a plain-language description of the failure, and a direct link to the Logs tab for that model or connector
```

**AC-NOTIF-1-03 — Plain language only — no internal terminology**

```
Given a job failure notification is sent
When the admin reads the email
Then the content uses plain language only
And internal system terminology, infrastructure references, or stack traces are not present
```

**AC-NOTIF-1-04 — Email includes reference ID for unknown failures**

```
Given a job fails and the root cause cannot be determined
When the failure notification is sent
Then the email includes a reference ID the admin can provide to support
```

---

### NOTIF-2 — Transient vs. Permanent Failure Distinction

**User Story:** As an admin, I want to know whether a failure is self-healing or requires my action so that I can prioritize my response and avoid unnecessary support tickets for transient issues.

**Importance:** High

**Acceptance Criteria:**

**AC-NOTIF-2-01 — Transient failure notification indicates no action required**

```
Given a job fails with a transient error (system will retry)
When the failure notification is sent
Then the email clearly indicates the failure is transient
And states that the system is retrying automatically
And does not imply that admin action is required
```

**Note — dependency on OQ-5:** AC-NOTIF-2-01 assumes transient failures generate an email (with a "no action needed" message). If OQ-5 resolves to "transient failures are silent," this AC should be removed and NOTIF-2 scoped to permanent failures only.

**AC-NOTIF-2-02 — Permanent failure notification indicates action required**

```
Given a job fails with a permanent error (no further retries)
When the failure notification is sent
Then the email clearly indicates that the failure requires admin action to resolve
And the plain-language description identifies what needs to be done where possible
```

**AC-NOTIF-2-03 — Failure type is consistent with the job log**

```
Given the job log records a failure as transient or permanent
When the notification is generated
Then the failure type in the email matches what is recorded in the log
```

---

### NOTIF-3 — Escalation on Repeated Failures

**User Story:** As an admin, I want repeated failures for the same job to escalate rather than flood my inbox so that I'm made aware of a persistent problem without being overwhelmed by duplicate emails.

**Importance:** High

**Acceptance Criteria:**

**AC-NOTIF-3-01 — Repeated failures do not produce unbounded emails**

```
Given the same job fails on consecutive runs
When each failure is recorded
Then the system does not send a separate failure email for every individual run
```

**AC-NOTIF-3-02 — Escalation notification sent when retries are exhausted**

```
Given a job has failed on consecutive runs and retries are exhausted
When the maximum retry threshold is reached
Then an escalation notification is sent indicating retries are exhausted and action is required
And this escalation is clearly distinguishable from a standard failure notification
```

**AC-NOTIF-3-03 — Escalation includes failure history context**

```
Given an escalation notification is sent
When the admin receives it
Then the email indicates how many consecutive failures have occurred and over what time period
```

## 😎 Future Considerations

* **In-app notification center** — bell icon, badge count, notification feed. V1 is email-only; in-app should be accounted for in the design system for future implementation.

* **Per-user notification preferences** — opt in/out per trigger type, configurable from user account settings without contacting FQ support.

* **Late data notifications** — admin notified when a scheduled job hasn't completed by its expected window. Depends on Scheduling PRD.

* **Unmapped entity alerts** — admin notified when new unmapped entity values appear in a run. See entity mapping gap insights in Logging & Audit PRD Future Considerations.

* **Schema change notifications** — admin notified when a source file's schema changes (new column, type change, removed column). Belongs in Error Patterns PRD.

* **Webhook / programmatic delivery** — enterprise customers want to integrate failure alerts with their own monitoring stacks. See G10 in Logging & Audit PRD.

* **Weekly digest** — scheduled summary of run outcomes and configuration changes for admins who prefer a recap over real-time alerts.

* **Additional recipients** — FQ implementation or support staff added as notification recipients for a customer's tenant so they're alerted without waiting for a ticket.

* **Slack / third-party channel integrations** — future v2 scope.
