## Purpose

This document is a companion to the [Detect User Access Control](https://floqast.atlassian.net/wiki/spaces/~467788746/pages/4677042488) page, which shows the mechanics of each option. This document covers the strategic comparison between options, why this decision is broader than Detect, and the operational implications of each path.

---

## The Core Question

The fundamental decision is: **what FloQast object represents data access control?**

Everything else — whether mapping happens against raw data or the canonical model, where the configuration UI lives — is secondary. The primary choice is the access primitive.

---

## Option Overview

| Option | Access Primitive | Applies To | Sub-options |
| --- | --- | --- | --- |
| **1 — FQ Entities** | Existing FQ Entity concept | All connector types | 1a: ACL against raw data columns; 1b: ACL against canonical `Company` field |
| **2 — New FQ Workspace** | New Subsidiary or Company workspace type | Varies by sub-option | 2a: CDC/Direct Integration only; 2b: all connector types via canonical `Company` |
| **3 — Combination** | Mixed — depends on connector type | Split | e.g. entities for files, subsidiary workspace for CDC |

## Shared Data Layer — Why This Is a Platform Decision, Not Just a Detect Decision

Before evaluating options, it's important to establish which products share the same underlying canonical data. The access control decision affects all of them — not just Detect.

**Key observation:** GL Transactions are consumed by Close AI Matching, Close Amort & Depreciation, Reporting FDM, AI Variance, Report Builder, and Detect. Any change to the access control model for GL Transaction rows affects all of these products — not just Detect.

This means:

* Changing the access primitive for Detect without changing it for AI Matching and FDM creates a situation where users can be scoped differently depending on which product they're in, on the same underlying rows. That is a data consistency and audit risk.

* Whichever option we choose needs to work uniformly across all products consuming each canonical model.

## Why "Entity Is a Close Construct" Understates the Problem

A common framing in recent discussions has been that FQ Entity is primarily a Close construct and we should decouple from it. This is directionally valid but misses an important reality: **Reporting products already scope data by entity today.**

FDM, AI Variance, Report Builder, and Classic Variance all use entity-level data scoping for GL transactions. Replacing the entity access primitive with a new Company/Subsidiary workspace type isn't just a Detect migration — it's a migration for every product in the table above. That's a platform-wide change, not a Detect GA enabler.

The long-term direction may still be correct. But the scope must be understood clearly before committing.

## Option Analysis

### Option 1 — FQ Entities

The existing entity concept remains the access primitive. The change is how entities are scoped to data.

#### Option 1a — Map to raw data columns

Entity ACL references source data directly (e.g. `Transaction.Group = "WK-US"`). See examples doc for mechanics.

**Why this is problematic:** Raw data schemas vary per customer and connector type — `subsidiary_id` in NetSuite, `sub_name` in a file, `CompanyRef` in a custom API. There is no consistent end state. Every implementation is bespoke, making platform-wide validation and auditing unreliable.

#### Option 1b — Map to canonical `Company` field *(preferred near-term)*

A Mapping Expression in the Data Studio model step produces a canonical `Company` field on every row, regardless of source. Entity ACL references `Company` values. See examples doc for mechanics across all connector types including files.

**Why this works:**

* Consistent end state across all connector types — same entity ACL structure whether data comes from NetSuite CDC, SFTP file, or custom API

* For Direct Integration connectors (NetSuite, SAP, Intacct), FloQast owns the recipe and pre-builds the `Company` Mapping Expression — no admin configuration needed

* For files and custom connectors, the admin authors the Mapping Expression in DS model step — same mechanism as passing configuration like accounting period from filename

* Entities already span Close AND Reporting products — extending them with a company ACL is the least disruptive change to the existing access model

---

### Option 2 — New FQ Workspace (Subsidiary or Company)

A new workspace type is the access primitive, decoupled from the FQ Entity concept.

#### Option 2a — New workspace for CDC / Direct Integration only

ERP subsidiaries are auto-discovered from the connector and surfaced as a new workspace type in Admin Settings. Files and custom connectors continue to use entities (Option 1).

**Problems with this approach:**

* Creates a split access model: CDC customers use subsidiary workspace, file customers use entities

* Products sharing the same canonical data (e.g. AI Matching and Detect both reading GL Transactions) would use different access primitives on the same rows — a user could be scoped differently in each product for the same underlying data

* Inconsistency makes auditing and onboarding harder, not easier

#### Option 2b — New workspace for all connector types (tied to canonical `Company`)

The new Company/Subsidiary workspace type is mapped to the canonical `Company` field across all connector types. Same two-step pattern as Option 1b — Mapping Expression produces `Company` in DS model step, then the Company workspace is assigned company values in Admin Settings.

**This is the cleanest long-term architecture:**

* Decouples data access from the FQ Entity concept entirely

* Universal — same model for CDC, files, and custom connectors

* Aligns with the direction Dylan outlined (data-level access with roles/workspaces rather than entity-based scoping)

**However, the scope is much larger than it appears:**

* Requires migrating ALL products that currently use entity-level data scoping: Close AI Matching, Close Amort & Depreciation, Reporting FDM, AI Variance, Report Builder, and Classic Variance — not just Detect

* Close may never migrate (see Close Compatibility section below), meaning both the entity model and the new workspace model may need to coexist permanently

* This is a multi-quarter platform project, not a Detect GA enabler

---

### Option 3 — Combination

Some connector types use entities, others use the new workspace type. For example: CDC uses the subsidiary workspace, files use entities.

**Not recommended.** Creates the same split access model problem as Option 2a, applied more broadly. Admins managing access for a customer with both CDC and file connectors would use two different systems. Products consuming shared canonical data would be scoped differently per product.

---

## Close Compatibility — Permanent Dual Mapping Support

Close relies on `fq_entity` as a written column on canonical model rows today. There is no assumption that Close will migrate away from this — it may need to remain permanently.

This means for any customer running Close alongside Detect or Reporting products, the canonical model must **permanently support both mapping types simultaneously:**

* `fq_entity` on the row — for Close's entity-scoped operations (written at ingest, unchanged)

* Canonical `Company` field + entity ACL — for Detect and Reporting row filtering

This is not a transition state. It is a permanent architectural reality that the data platform must be designed to accommodate. Customers on both products will configure both: entity tag assignment for Close, and entity ACL company values for Detect/Reporting.

The only future scenario where this changes is if Close explicitly chooses to migrate — which is a Close product decision, not a Data Studio decision, and should not be assumed in any near-term planning.

## Operational Implications

### Data reruns

Under Option 1b, changing an entity ACL assignment requires no data rerun. The canonical `Company` value on each row is factual source data — it doesn't change. The entity-company ACL is config — changes take effect on the next query. A rerun is only needed if the Mapping Expression itself changes (i.e. redefining how source data maps to `Company`), which is rare.

### First-run sequencing

Entity ACL configuration cannot happen until the canonical `Company` field exists in the data. The setup sequence is:

1. Connect the ERP or configure the file in Data Studio

2. Define the `Company` Mapping Expression in the model step (or confirm the recipe has done this for Direct Integration)

3. Run the model — `Company` values are now in the data

4. Go to entity configuration — the company picklist is now populated

5. Map company values to FQ entities — access control is live

Entity ACL configuration is not available before step 3 completes. This should be surfaced clearly in setup flows.

### Refresh cadence

When new company values appear in the data (e.g. a new NetSuite subsidiary is created), they must surface as unmapped values in entity config and the admin must be alerted. A refresh mechanism is required.

---

## "Return All Possible Values" Requirement

If entity ACL configuration lives in Admin Settings (outside Data Studio), the UI must surface every distinct `Company` value currently in the canonical model as a **picklist, not a free-text field.** Two reasons:

1. **Error prevention:** Silent mismatches (`"WK-US"` vs `"wk-us"`) cause rows to fall through with no warning. Admins must select from real values.

2. **Coverage validation:** The system must flag any `Company` values in the data with no entity mapping. Without this, data silently becomes inaccessible.

This requires a cross-system dependency: Admin Settings must query Data Studio for the distinct `Company` values in each canonical model. It also requires the refresh mechanism noted above.

---

## Out of Scope

**Raw data access:** Row-level scoping applies to canonical models only. Source datasets (raw ingested data before canonical transformation) are not in scope for this mechanism. Raw data access remains admin-only.

**Custom datasets:** Customer-built models that don't produce a meaningful `Company` field cannot use the entity ACL mechanism. Dataset-level access restrictions for arbitrary custom models are a known gap — not in scope for this phase.
