> **Context:** Scheduling governs when Data Studio automatically pulls data from a connected NetSuite account. On-demand refresh allows authorized users to trigger a sync outside the scheduled cadence — critical during month-end close when real-time data accuracy is essential.

---

## 1. Feature Overview

Once a connection has been set up, sync jobs run according to the configured schedule. The scheduling system must be resilient — handling NetSuite maintenance windows, rate limits, and connection errors gracefully — while giving admins visibility into past and upcoming runs.

On-demand refresh provides a manual override so admins and authorized users can pull fresh data immediately, without waiting for the next scheduled run. Both mechanisms write to FQ and emit downstream notifications.

### 1.1 User Stories

| Story ID | User Story |
| --- | --- |
| US-SCH-01 | As the system, I automatically configure the NS API to run every 24 hours at midnight in the local TLC's timezone. |
| US-SCH-02 | As a Data Studio admin, I can see the standard 24 hour frequency configuration for the NS API. |
| US-SCH-04 | As a Data Studio admin, I want to see when the next scheduled sync is and when the last sync ran so that I can confirm the connection is healthy. |

| US-SCH-08 | As a Data Studio admin, I want to see the status of an in-progress sync in real time so that I know how long it will take. |

## 2. Standard Scheduling Setup (Item 8)

### 2.1 Schedule Configuration

Each connection has one schedule configuration. The schedule applies to all active entities in the connection. Schedules are viewable from the Connection detail page under the "Settings" tab.

#### 2.1.2 Schedule Parameters

| Parameter | Description |
| --- | --- |
| Frequency | Set at every 24 hours. |
| Timezone | Customer timezone based on TLC setting |
| Sync Type | INCREMENTAL - Incremental fetches only changed records since last sync. |

### 2.2 Incremental vs. Full Sync Logic

| Sync Type | When Used | Records Fetched |
| --- | --- | --- |
| Incremental | Standard scheduled runs | Accounts: modifiedDate > lastSyncAt; Balances: current and open periods only |
| Full | First sync after connection creation; Monthly (1st of month); Admin-triggered full refresh; Post-mapping-config-change | All accounts; all periods in current + prior fiscal year for first sync and post mapping config unless date is specified. Monthly sync on the 1st of the month for the prior and current period only. |
| Period-targeted | Period close detected; on-demand with period selection | All accounts; specified periods only |

> **Monthly Full Refresh:** The scheduler automatically escalates the first run of each month to a FULL sync, regardless of the configured frequency.

### 2.4 Schedule Resilience

#### 2.4.1 Missed Runs

If a scheduled run is missed (e.g., scheduler service was down):

* Runs missed by less than 30 minutes: execute immediately on service recovery.
* Runs missed by 30 minutes to 6 hours: execute one catch-up run immediately; skip the individual missed intervals.
* Runs missed by more than 6 hours: skip all missed runs; resume at next scheduled interval; log: "Missed \[N\] scheduled runs during downtime window \[start\]-\[end\]."

#### 2.4.2 NetSuite Maintenance Windows

* NetSuite typically performs maintenance on Saturday/Sunday nights. The scheduler does not have built-in awareness of NetSuite maintenance windows.
* If a scheduled sync fails during a maintenance window, standard retry logic applies (exponential backoff, max 5 retries).
* After 5 retries with no success, the SyncJob is marked FAILED and the next scheduled run proceeds normally.
* Persistent failures (3+ consecutive scheduled jobs failed) trigger a connection-health alert (see Sub-PRD 6 – Notifications).

#### 2.4.3 Concurrent Run Prevention

* Only one SyncJob may run per connection at a time.
* If a scheduled run is triggered while a previous job is still RUNNING, the new trigger is queued with status QUEUED.
* The queued job starts immediately when the running job completes.
* A queued SCHEDULED job is superseded by a subsequent SCHEDULED trigger — only one queued job per type (SCHEDULED) is retained per connection. (ON_DEMAND jobs are added to the queue regardless if there isn't already one in the queue.)

### 2.5 Acceptance Criteria – Scheduling

| AC-ID | Criterion |
| --- | --- |
| AC-SCH-01 | A user can view a sync schedule from the Connection detail page |
| AC-SCH-03 | The next scheduled run time is displayed in the configured timezone. |
| AC-SCH-06 | The first sync of each calendar month automatically runs as a FULL sync regardless of the configured sync type. |
| AC-SCH-07 | If a SyncJob is already RUNNING when the next scheduled trigger fires, the new job is queued as QUEUED; it starts when the running job completes. |
| AC-SCH-08 | After 3 consecutive failed scheduled jobs, a connection-health alert is triggered (see Sub-PRD 6). |

## 3. On-Demand Refresh (Item 9)

### 3.1 Trigger Mechanism

On-demand refresh allows authorized users/applications to start a SyncJob immediately, bypassing the schedule. Accessible from Data Studio API for programmatic triggers only at this time.

### 3.2 On-Demand Sync Options

| Option | Default | Description |
| --- | --- | --- |
| Sync scope | All active entities | User can optionally select specific entities from a multi-select list. |
| Sync type | INCREMENTAL | User can select FULL for a complete re-pull. Full syncs are slower and should be used sparingly. |
| Period range (balances) | Current period | User can extend to "Current + prior period" or "Full fiscal year" for balance data. Account data is always pulled in full or incremental based on sync type. |

### 3.3 Rate Limiting

| Limit | Value |
| --- | --- |
| Per connection per hour | Maximum 4 on-demand syncs per connection per 60-minute rolling window |
| Cooldown after full sync | 30 minutes after a FULL on-demand sync before another FULL on-demand is allowed |
| API rate limit (programmatic) | Same per-connection limits apply to API triggers; API key rate limits also enforced |

When a rate limit is hit, the trigger is rejected with HTTP 429 and the UI shows: "You've reached the sync limit for this connection. You can sync again at \[time\]."

### 3.4 Real-Time Progress

When an on-demand sync is triggered from the UI:

* A progress bar or spinner appears on the Connection detail page.
* Status updates: "Queued" → "Running" → "Complete" (or "Partial" / "Failed").
* Progress is polled via a GET /api/v1/jobs/{jobId}/status endpoint (polling interval: 3 seconds). Server-Sent Events (SSE) preferred if supported by the frontend framework.
* On completion: a toast notification shows "Sync complete — \[N\] records updated" or an error summary.

### 3.5 Concurrency with Scheduled Runs

* If a scheduled SyncJob is RUNNING when an on-demand trigger fires: the on-demand job is queued. It starts immediately when the scheduled job completes.
* If a scheduled SyncJob is QUEUED when an on-demand trigger fires: the on-demand job takes priority and is processed first; the scheduled job remains queued.
* If an identical on-demand request is received while the on-demand job is queued, the first on-demand job should be respected and the later request can be ignored.

### 3.6 Acceptance Criteria – On-Demand Refresh

| AC-ID | Criterion |
| --- | --- |
| AC-SCH-11 | Triggering more than 4 on-demand syncs for the same connection within 60 minutes returns a 429 with a retry-after timestamp. |
| AC-SCH-12 | An on-demand FULL sync has a 30-minute cooldown before another FULL on-demand can be triggered for the same connection. |
| AC-SCH-13 | If a SyncJob is already RUNNING, the on-demand trigger creates a QUEUED job; the QUEUED job starts immediately when the running job completes. |
| AC-SCH-14 | On-demand sync progress is visible in real time in the UI, updating at least every 10 seconds. |
| AC-SCH-15 | The API endpoint for on-demand sync enforces role-based authorization; unauthorized callers receive 403. |
| AC-SCH-16 | On-demand sync respects the rate-limiting. |

## 4. Non-Functional Requirements

| Requirement | Target |
| --- | --- |
| Schedule trigger precision | Scheduled jobs start within 60 seconds of their computed trigger time |
| On-demand trigger acknowledgment | POST /sync returns 202 within 500ms (job is queued; execution may begin asynchronously) |
| Job status polling latency | A status endpoint returns current status within 200ms |
| Scheduler uptime | 99.9% — missed runs must be handled per Section 2.4.1 |
| Max concurrent jobs across all connections | System must support at least 1000 simultaneous SyncJobs without degradation; scale horizontally |

## 5. Edge Cases & Error Handling

| Scenario | Expected Behavior |
| --- | --- |
| Connection enters ERROR state while a SyncJob is RUNNING | The running job completes. Subsequent scheduled jobs are blocked until the connection is repaired. |
| Timezone transition (DST change) | Cron is evaluated in UTC internally. Daily syncs set to a specific local time will shift by 1 hour during DST transitions — this is expected. |
| Admin changes frequency while a job is queued | The queued job runs as-is. The new frequency applies to the next trigger computed after the config change is saved. |
| Full sync on a connection with 500 entities exceeds 30-minute window | Job continues; scheduler logs a warning if duration > 30 minutes. No timeout imposed at the scheduler level. |
| User closes the browser while an on-demand sync is running | The sync continues on the server. User can check status from the Connection detail page on return. |
| On-demand sync triggered for a DISABLED connection | Rejected with 400: "Connection is disabled. Re-enable the connection before syncing." |
