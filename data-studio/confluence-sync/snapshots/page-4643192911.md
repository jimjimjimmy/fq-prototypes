
This master PRD defines the product requirements for FloQast SAP READ integrations for SAP ECC and SAP S/4HANA Private Cloud using the FloQast ABAP connector. It is intended to serve as the parent document for data extraction, scheduling, file delivery, customer setup, and platform integration requirements. This structure mirrors the style of the NetSuite Direct API master PRD, but adapts it to SAP’s customer-managed transport and scheduled extraction model.

> **Executive summary:** Customers install a FloQast-provided SAP transport into SAP ECC or S/4HANA Private Cloud, configure the required output path and scheduling in SAP, and run FloQast extraction programs on their own cadence. These programs generate financial data extracts such as Trial Balance and deliver them to FloQast, primarily via SFTP. An optional HTTP push route may be supported through SAP destination configuration, with any credentials managed by the customer’s Basis team in SM59 and STRUST, never embedded in ABAP source.

# 1. Objective

FloQast is building SAP READ integrations as part of its broader ERP connectivity strategy for Data Platform 2.0 and downstream product use cases including Reconciliations, Flux Analysis, Transaction Matching, Close Management, and Journal Entry Management verification workflows.

For SAP ECC and SAP S/4HANA Private Cloud customers, the primary READ path is a customer-installable ABAP connector delivered as SAP transport files. Once installed, the connector runs natively inside the customer’s SAP environment and extracts required datasets from SAP tables and business structures. Customers schedule these programs using SAP’s native job scheduler at a cadence that fits their operating model, typically nightly or multiple times per day during close.

The goal is to provide a reliable, scalable, low-friction extraction path that avoids inbound firewall complexity, minimizes FloQast-managed credentials, and fits standard SAP Basis change-management practices.

Success is defined as customers being able to install, configure, schedule, and operate SAP data extraction with limited Engineering involvement, while delivering normalized financial data into FloQast on a repeatable schedule.

# 2. Key Benefits

* **Works in the SAP environments that matter most for enterprise customers:** ECC, S/4HANA Private Cloud, and similar private deployments.

* **Runs inside SAP:** avoids the fragility of externally polling customer SAP instances over the public internet.

* **Uses standard SAP operational patterns:** transport import, Basis configuration, SAP scheduler jobs, and customer-controlled execution.

* **Minimizes credential risk:** pure SFTP delivery does not require an API key in SAP code; optional HTTP delivery uses Basis-managed destinations and trust stores.

* **Scales with customer volume:** large extracts run under SAP job control instead of external runtime ceilings.

* **Supports multiple FloQast products:** extracted data can power balances, matching, reconciliation setup, hierarchy rollups, and JE validation.

# 4. Success Metrics

* Customer transport installation completed without custom code modification in the target SAP environment.

* Initial customer setup completed primarily by customer Basis and IT teams using documented configuration steps.

* Scheduled extraction jobs run successfully at customer-defined frequencies with target operational reliability of 99%+ under normal SAP and network conditions.

* Delivery path supports nightly and intra-day refresh patterns for supported datasets.

* No secrets are embedded in FloQast ABAP source code.

* Extracted datasets land in FloQast in a format that supports downstream normalization and product consumption.

# 5. Assumptions

* Customers using this integration are on SAP ECC or SAP S/4HANA Private Cloud, not S/4HANA Public Cloud - thats coming in Q4 and a different integration approach.

* Customers can import SAP transports through their standard change-management process.

* Customer Basis teams are responsible for environment-specific configuration, including output directory setup and job scheduling.

* Customers will typically schedule jobs nightly, with some customers choosing additional intra-day runs during close.

* The default delivery path is FloQast SFTP.

* SFTP authentication method, including whether key-based or password-based access is used, is determined by FloQast endpoint provisioning and customer setup, not by ABAP source logic.

* An optional HTTP push route may be supported through `P_HTTP` and `ZFQ_INGESTION_CLIENT`.

* If HTTP push is used, credentials or certificates are stored and managed by the customer in SAP `SM59` and `STRUST`, not in source code.

* Data Platform 2.0 or equivalent downstream ingestion services will normalize delivered SAP extracts for application use.

> **Security note:** In the optional HTTP delivery path, the only place a token, certificate, or similar secret may appear is in SAP-managed destination and trust configuration. The ABAP source is expected to keep secrets out of code and rely on secure Basis-managed configuration.

# 8. Requirements

**REQ-01:** As a customer Basis team, I want to import a FloQast SAP transport into ECC or S/4HANA Private Cloud so that FloQast extraction programs are available in my SAP environment.

*Functional spec:* FloQast provides transport artifacts and installation guidance. Objects must compile, activate, and be deployable through standard SAP transport procedures.

**REQ-02:** As a customer Basis team, I want to configure the SAP output directory and related runtime settings so that extraction jobs can write files correctly for downstream delivery.

*Functional spec:* Required filesystem or logical path configuration must be documented, including directory expectations, permissions, and any job parameterization needed for file generation.

**REQ-03:** As a customer administrator, I want to schedule FloQast extraction programs in SAP background jobs so that data is refreshed automatically on my preferred cadence.

*Functional spec:* Programs must support recurring background execution through SAP scheduler. Customers should be able to schedule nightly runs and optional multiple daily runs.

**REQ-04:** As a customer, I want extracted files delivered to FloQast’s SFTP endpoint so that no inbound connection into SAP is required.

*Functional spec:* The standard delivery model is outbound delivery to FloQast SFTP. The operational setup must align with customer-managed SAP and file-transfer practices.

**REQ-05:** As a security-conscious customer, I want no API key or secret hard-coded in ABAP source so that the integration meets enterprise security expectations.

*Functional spec:* Pure SFTP delivery must not require application secrets in SAP code. If optional HTTP delivery is used, authentication must be externalized into SAP-managed destination and trust configuration.

**REQ-06:** As a customer Basis team, I want optional HTTP delivery to be configurable using SAP-native destination management so that any secrets are stored in standard SAP security tools.

*Functional spec:* When `P_HTTP` and `ZFQ_INGESTION_CLIENT` are used, the connector references an SAP `SM59` destination such as `FQ_INGESTION` and relies on `STRUST` and destination security configuration for authentication.

**REQ-07:** As a FloQast product and engineering team, I want SAP extract outputs to follow stable contracts so that downstream ingestion and normalization can support multiple products consistently.

*Functional spec:* Each extractor must produce a defined file structure with stable field contracts, sufficient metadata, and environment identification for ingestion into the FloQast data pipeline.

**REQ-08:** As a FloQast implementation or support team member, I want to verify execution and delivery outcomes so that customer issues can be diagnosed quickly.

*Functional spec:* The integration should support operational evidence of job execution, extract completion, and successful or failed delivery, whether through SAP logs, spool output, application logs, or downstream receipt tracking.

**REQ-09:** As a FloQast app team, I want normalized SAP financial data delivered from this connector so that features such as Reconciliations, Flux, Matching, and JEM verification can consume the data without SAP-specific logic.

*Functional spec:* Delivered extracts must map to the target canonical data model and support scheduled refresh expectations for downstream applications.

# 10. User Interaction and Operational Design

The end-to-end SAP READ flow follows a customer-managed operational model rather than a browser-based direct API setup flow.

## Stage 1: Transport Installation

* FloQast provides SAP transport files and installation documentation.

* Customer Basis team imports the transport through standard SAP change management.

* Customer validates object activation and readiness in the target SAP environment.

## Stage 2: Basis Configuration

* Customer configures required output directory and related runtime settings.

* Customer configures the delivery method, typically SFTP.

* If optional HTTP push is enabled, customer configures destination security in `SM59` and trust material in `STRUST`.

## Stage 3: Job Scheduling

* Customer schedules extraction programs in SAP background jobs.

* Typical cadence is nightly, with some customers scheduling two to three runs per day during close.

* Different extractors may have different frequencies depending on business criticality.

## Stage 4: Delivery and Ingestion

* SAP programs generate and deliver files to FloQast.

* FloQast receives the files, ingests them, and normalizes the datasets for downstream product use.

* Internal teams verify receipt and data quality through operational tooling.

# 11. Security and Authentication Model

> **Default model:** Pure SFTP delivery requires no API key in SAP source code. Authentication is handled through the SFTP mechanism provisioned for the endpoint and associated transfer setup.

* **SFTP path:** no application token is embedded in the connector. Authentication method is determined by endpoint provisioning and operational setup.

* **HTTP path:** if used, authentication is supplied through SAP-native destination and trust configuration.

* **Secret management:** tokens, passwords, certificates, or related authentication material must not be hard-coded in ABAP source.

* **Basis ownership:** SAP Basis is responsible for managing secure destinations, trust stores, and environment-specific security settings.

**Implementation context from current SAP strategy**

The ABAP connector is the designated READ path for ECC and S/4HANA Private Cloud, while SAP Public Cloud follows a separate strategy. Current strategy materials indicate that the ABAP connector already covers a broad set of extraction programs and has been tested in live SAP-to-FloQast data flows. This PRD is therefore focused on formalizing the productized customer-operating model rather than inventing a brand-new technical direction.
