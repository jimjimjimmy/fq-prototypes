# **1. Objective**

This sub-PRD defines the field-level specification for the FX Rates endpoint (POST /fx-rates). It covers the required and optional fields of the FX Rate data model, rate precision requirements, the bi-temporal date model governing rate validity and record versioning, submit mode behavior (append, upsert, and replace), custom field passthrough, and the metadata FloQast applies to all incoming records.

The FX Rates endpoint is a Phase 2 core data model endpoint in the FQ APIs initiative. It enables customers to push exchange rate data directly into FloQast, providing the rate values FloQast needs to perform multi-currency translation across GL Transactions, Balances, and other financial data. Rates are defined as currency pair conversions with a designated rate type, an effective validity window, and a full record version history.

A key design consideration for this endpoint is volume. In most implementations, FX rates are a relatively small, static dataset - a few dozen rates updated once per period. However, customers that store transaction-level FX rates (one rate per GL transaction) can generate millions of rate records per period, putting this endpoint in the same volume tier as GL Transactions. The endpoint must be designed to support high-volume ingestion from the outset, even if most customers will never exercise that capacity. Infrastructure requirements are defined in the High-Volume Data Ingestion sub-PRD.

Auto-configure behavior triggered by the first push is defined in the Auto-Configure sub-PRD. Upsert key design and conflict handling are defined in the Data Handling sub-PRD. Authentication is defined in the Authentication & API Key Management sub-PRD.

# **2. Key Benefits**

* Customers can push exchange rates directly into FloQast rather than relying on pre-built ERP connectors, enabling multi-currency translation for API-ingested financial data without manual rate entry.
* The bi-temporal date model separates rate validity (when a rate is effective for conversion) from record versioning (when a particular version of the rate record was current), enabling both accurate translation and full audit history of rate changes.
* High-precision decimal support for rate values and inverse rate values prevents rounding errors in multi-currency calculations, particularly for currency pairs with large exchange rate ratios.
* Rate type classification allows customers to store multiple rate types (e.g., Spot, Average, Historical) for the same currency pair and period without conflict, matching the rate type to the translation methodology used for each account or transaction.
* Nullable end_datetime supports both time-bounded rates (with a defined expiration) and open-ended rates (in effect until superseded), covering the full range of ERP rate management approaches.
* Submit mode (append, upsert, replace) gives customers explicit control over how rate submissions are handled, including the ability to fully refresh a rate table or incrementally correct individual rates.
* Custom field passthrough allows customers to include non-standard rate attributes without rejection; auto-configure captures these fields in the lineage on first push.

# **3. Use Cases**

1. A customer pushes a standard period-end rate table with closing exchange rates for all currency pairs used by their entities. They submit in replace mode, providing one Closing rate per pair. FloQast stores the rates and makes them available for balance translation.
2. A customer maintains Average and Closing rates for each period. They push two separate batches: one for Average rates (for income statement translation) and one for Closing rates (for balance sheet translation). Each batch specifies the appropriate rate_type. Both are available in FloQast for downstream account-level translation.
3. A customer stores transaction-level FX rates in their ERP - one rate per GL transaction, covering millions of records per period. They push the full rate dataset using the batch session model from the High-Volume Data Ingestion sub-PRD, with chunked submissions and idempotency keys.
4. A customer's finance team revises several exchange rates after the initial period-end push. They submit only the corrected records in upsert mode. FloQast updates the matching rate records using the upsert key, increments touch count on each modified record, and advances the effective_start_date on the new version.
5. A rate previously submitted with an open-ended validity (null end_datetime) is superseded by a new rate. The customer submits the updated record with the end_datetime populated to close out the old version, and submits the new rate as a separate record with its own effective_datetime.
6. A FloQast implementation specialist confirms that rate data is available and correctly keyed before enabling multi-currency translation for a customer's entities. They check the ingestion log for the fx-rates endpoint to confirm successful pushes and zero validation errors.

# **4. Success Metrics**

* FX Rates endpoint available and functional at Phase 2 launch.
* Required field validation correctly rejecting payloads with missing required fields or invalid currency IDs, with actionable error messages.
* Rate value and inverse rate value stored at the required decimal precision with no rounding loss.
* Upsert correctly matching on the defined key (source_currency_id + target_currency_id + rate_type + effective_datetime) without creating duplicate rate records.
* Bi-temporal date fields (rate validity window and record version window) correctly stored and queryable independently.
* High-volume rate submissions (transaction-level rates) successfully processed using the batch session model from the High-Volume Data Ingestion sub-PRD.
* FloQast metadata accurately applied to all ingested rate records (target accuracy: 100%).

# **5. Assumptions**

* Customers are responsible for pre-formatting FX rate data to match the field specifications defined in this document. FloQast does not perform transformation or normalization of rate values.
* submit_mode is required on every push. There is no default mode - customers must explicitly specify append, upsert, or replace on each submission.
* In append mode, all submitted records are inserted as new rows unconditionally. No key matching is performed. Submitting the same rate record twice creates duplicate rows.
* In upsert mode, records are matched using the upsert key: source_currency_id + target_currency_id + rate_type + effective_datetime. Matching records are updated; non-matching records are inserted. Records not in the batch are left unchanged. Upsert is idempotent.
* In replace mode, the scope of replacement is TBD - see Open Questions. Options include replacing all rates, replacing all rates for a given currency pair, or replacing all rates within a defined effective date range.
* source_currency_id and target_currency_id are foreign keys to FloQast's internal currency table. Submitted values must match valid ISO 4217 currency codes recognized by FloQast. Records referencing unknown currency IDs are rejected with a 400 error.
* rate_value represents the multiplier to convert a source currency amount to the target currency (target = source × rate_value). inverse_rate_value represents the multiplier to convert in the opposite direction (source = target × inverse_rate_value). Both fields require high decimal precision - exact precision requirements are TBD with Engineering.
* The FX Rate data model uses a bi-temporal structure with two distinct date dimensions: (1) the rate validity window (effective_datetime and end_datetime) defines when the rate is effective for currency conversion; (2) the record version window (effective_start_date and effective_end_date) tracks the history of changes to the rate record itself. effective_end_date = null indicates this is the currently active version. See Section 7 and Section 9 for detailed definitions.
* end_datetime is nullable. A null value means the rate has no defined expiration and is in effect until explicitly superseded or expired.
* effective_end_date (record version) is nullable. A null value means this is the current active version of the rate record.
* Volume can vary significantly: from a handful of period-end rates to millions of transaction-level rates per period. The endpoint must support both patterns. High-volume submissions should use the batch session model defined in the High-Volume Data Ingestion sub-PRD.
* System-applied metadata fields (touch count and FloQast ingestion timestamp) are generated by FloQast at ingestion time and cannot be overridden.

# **7. Scope of Data**

The following table defines the fields accepted by the FX Rates endpoint. Required/Optional and Data Type columns are to be completed by the team where marked. Fields shaded in yellow are system-applied by FloQast at ingestion and are not customer-submitted.

Note on the bi-temporal model: this endpoint uses two distinct date dimensions that are easy to confuse. The rate validity window (effective_datetime / end_datetime) describes when the rate is valid for use in currency conversion - a business-time concept. The record version window (effective_start_date / effective_end_date) describes when this version of the rate record was the current record - a system-time / lineage concept used for point-in-time auditing. Both dimensions can coexist independently on the same record.

| **Field Name** | **Category** | **Required / Optional** | **Data Type** | **Notes** |
| --- | --- | --- | --- | --- |
| _**Currency Pair**_ |
| source_currency_id | Customer-submitted | Required | String (currency code) | ISO 4217 currency code for the source currency (the currency being converted from). Foreign key to FloQast's currency table. Must match a recognized currency code; invalid values are rejected with a 400 error. |
| target_currency_id | Customer-submitted | Required | String (currency code) | ISO 4217 currency code for the target currency (the currency being converted to). Foreign key to FloQast's currency table. Must match a recognized currency code; invalid values are rejected with a 400 error. |
| _**Rate Data**_ |
| rate_type | Customer-submitted | Required | String | The type of exchange rate (e.g., Spot, Average, Period-End, Historical, Budget). Determines which rate is applied for a given translation methodology. A single currency pair may have multiple records with different rate types. Allowable values TBD with Engineering and Data. |
| rate_value | Customer-submitted | Required | Decimal | The exchange rate multiplier from source to target (target amount = source amount × rate_value). Requires high decimal precision - 12 decimal places. Must be a positive value. |
| inverse_rate_value | Customer-submitted | Optional | Decimal | The inverse exchange rate multiplier from target to source (source amount = target amount × inverse_rate_value). Requires the same high decimal precision as rate_value - 12 decimal places. If omitted, FloQast may derive this as 1 / rate_value - see Open Questions. Must be a positive value if supplied. |
| _**Rate Validity Window (when the rate is effective for conversion)**_ |
| effective_datetime | Customer-submitted | Required | Datetime | Date and time from which this rate is effective for use in currency conversion. This is a business-time field - it defines when the rate is valid, not when the record was created. Format: ISO 8601 datetime (e.g., 2025-12-01T00:00:00Z). Part of the upsert key. |
| end_datetime | Customer-submitted | Optional | Datetime | Date and time at which this rate is no longer effective for currency conversion. Nullable - a null value means the rate has no defined expiration and is in effect until explicitly superseded. Format: ISO 8601 datetime. |
| _**System-Applied Metadata (FloQast-generated, not customer-submitted)**_ |
| effective_start_date | Customer-submitted | NA - system generated | Datetime | Date on which this version of the FX rate record became valid. Used for point-in-time lineage: allows FloQast to reconstruct the state of the rate table as it existed on any past date.Distinct from effective_datetime, which governs rate validity for conversion. |
| effective_end_date | Customer-submitted | NA - system generated | Datetime | Date on which this version of the rate record was inactivated. Nullable - a null value indicates this is the current active version of the record. When a rate is revised, the old version's effective_end_date is set to the revision date and a new version is created with a new effective_start_date. |
| created_date | _System-applied_ | _N/A - system-applied_ | _Timestamp_ | _Applied by FloQast at the time of initial ingestion. Not customer-submitted._ |
| created_by | _System-applied_ | _N/A - system-applied_ | _String_ | _Connection and API key identifier associated with the push that created this record. Applied by FloQast._ |
| _touch_count_ | _System-applied_ | _N/A - system-applied_ | _Integer_ | _Number of times this rate record has been updated via subsequent pushes. Starts at 1 on first ingestion; increments on each successful upsert or replace that modifies the record. Indicates whether and how many times a rate has been revised after initial submission._ |

The following are explicitly out of scope for this endpoint:

* Automated rate sourcing or rate feeds from market data providers - FloQast does not source external rate data through Studio today. All rates must be customer-supplied.
* Currency table management (adding or modifying supported currencies) - FloQast maintains its own currency reference table.
* Cross-rate derivation (e.g., deriving EUR/JPY from EUR/USD and USD/JPY) - customers are responsible for supplying all required currency pairs directly.
* GL Transactions, Balances, Accounts - covered in their respective sub-PRDs.

# **8. Requirements**

**REQ-FX-01: As a customer technical team, I want to submit the required FX Rate fields so that FloQast can correctly store and apply exchange rates for multi-currency translation.**

_**Functional spec:** The FX Rates endpoint accepts the required fields defined in Section 7. Every record must include all required fields. Records with missing required fields are rejected with a 400 Bad Request response identifying the specific missing fields and affected records (keyed to source_currency_id + target_currency_id + rate_type + effective_datetime where available). source_currency_id and target_currency_id must match ISO 4217 codes recognized in FloQast's currency table; unrecognized codes are rejected with a 400 error. rate_value must be a positive decimal stored at the required 12 decimal precision. effective_datetime must be a valid ISO 8601 datetime with timezone._

**REQ-FX-02: As a customer technical team, I want to include optional FX Rate fields in my payload so that I can provide richer rate context and lineage data where available without being required to populate every field.**

_**Functional spec:** The FX Rates endpoint accepts the optional fields defined in Section 7. Optional fields may be included or omitted per record. When included, they must conform to the specified data types and formats; a type or format mismatch returns a 422 error identifying the offending field and record. When omitted, the field is treated as absent - the record is accepted without it and no error is raised. end_datetime is optional and nullable; when omitted or null, the rate is treated as open-ended with no defined expiration. effective_end_date is optional and nullable; when omitted or null, the record is treated as the currently active version. Optional fields present in the payload are captured by auto-configure on first push._

**REQ-FX-03: As a customer technical team, I want to specify whether my submission should append to, upsert into, or replace the existing FX rate data so that I have explicit control over how multiple submissions are handled.**

_**Functional spec:** Each push to the FX Rates endpoint must include a submit_mode parameter with one of three values: append, upsert, or replace. Append: all submitted records are inserted as new rows unconditionally. No key matching is performed. Submitting the same record twice across pushes creates duplicate rows. Upsert: each record is matched against existing rate records using the upsert key (source_currency_id + target_currency_id + rate_type + effective_datetime). Matching records are updated; non-matching records are inserted. Records not in the batch are left unchanged. Idempotent. Replace: all existing rate records within the defined scope are removed before the submitted batch is inserted. The scope of replacement for this endpoint is TBD - see Section 10. submit_mode is required on every push - requests without it are rejected with a 400 error._

**REQ-FX-04: As a FloQast system, I want FX rate values stored at sufficient decimal precision so that multi-currency calculations are accurate and rounding errors do not accumulate across large transaction volumes.**

_**Functional spec:** The system stores rate_value and inverse_rate_value at a precision sufficient to represent exchange rates accurately across all supported currency pairs, including pairs with large ratio differences (e.g., USD/JPY, USD/KWD). Exact precision requirements are TBD with Engineering but must be at least 12 decimal places and should be designed to prevent cumulative rounding errors when rates are applied to large transaction sets. Rate values must not be truncated at ingestion. Any precision loss at storage time is a validation failure._

**REQ-FX-05: As a customer technical team, I want to include fields in my FX Rates payload that are not part of the standard model so that I can pass non-standard rate attributes through to FloQast without being rejected.**

_**Functional spec:** Fields present in a push payload that are not defined as required or optional in the standard FX Rates model are treated as custom fields. The API accepts records containing custom fields without error. Custom fields are passed through as-is - FloQast does not validate, transform, or interpret their values. On first push, auto-configure detects and registers custom fields in the lineage per the Auto-Configure sub-PRD._

**REQ-FX-06: As a FloQast system, I want to apply standard metadata to all FX Rate records received via the API so that submissions are traceable, auditable, and correctly attributed to their source.**

_**Functional spec:** FloQast applies the following metadata fields to each FX Rate record at the time of ingestion. These fields are system-generated and cannot be overridden by customer-submitted data: fq_created_at (timestamp of initial ingestion into FloQast), fq_ingested_by (the connection and API key identifier associated with the push that created the record), touch_count (number of times the record has been updated via subsequent pushes, starting at 1 on first ingestion). Metadata fields are visible within FloQast for reporting and audit purposes._

# **9. User Interaction and Design**

The FX Rates endpoint is a developer-facing API. There is no UI component - customers interact with it programmatically through their integration code or API tooling.

## **Endpoint**

POST /fx-rates

## **Authentication**

API key passed in the Authorization: Bearer header, consistent with all other FQ API endpoints. See Authentication & API Key Management sub-PRD.

## **Request Structure**

The request body is a JSON object with the following top-level parameters:

* submit_mode (required): "append", "upsert", or "replace".
* records (required): array of FX Rate objects, each conforming to the field specification in Section 7.

Note: unlike GL Transactions and Balances, the FX Rates endpoint does not take a period parameter at the top level - rate validity is defined per record via effective_datetime. For replace mode, the scope of replacement is defined by the submitted records' currency pairs and effective date ranges (see Open Questions).

## **Bi-Temporal Date Model**

FX Rate records carry two independent date dimensions. Understanding the distinction is important for correct ingestion.

| **Dimension** | **Fields** | **Governs** | **Example** |
| --- | --- | --- | --- |
| **Rate Validity Window** | effective_datetimeend_datetime | When the rate is valid for use in currency conversion - a business-time concept. | A December 2025 period-end USD/EUR rate: effective 2025-12-01, ends 2025-12-31. FloQast uses this rate to translate December balances. |
| **Record Version Window** | effective_start_dateeffective_end_date | When this version of the rate record was the current record in the source system - a lineage concept for point-in-time auditing. | Rate was first loaded on 2026-01-05 (effective_start_date = 2026-01-05). It was revised on 2026-01-10: old version gets effective_end_date = 2026-01-09; new version gets effective_start_date = 2026-01-10. |

## **High-Volume Considerations**

Most customers push a small, static set of period-end rates (tens to hundreds of records). However, customers that store transaction-level FX rates - one rate per GL transaction - can generate millions of rate records per period. Both patterns must be supported.

* For standard period-rate loads (small volume): single-chunk submissions without a batch session are appropriate.
* For transaction-level rate loads (high volume): customers should use the batch session model (POST /batches → chunked POST /fx-rates submissions → POST /batches/{id}/close) as defined in the High-Volume Data Ingestion sub-PRD. Chunk size guidance (10,000–25,000 records per chunk) applies.
* The endpoint infrastructure must be capable of handling high-volume rate ingestion from Phase 2 launch, consistent with the re-architecture targets in the High-Volume Data Ingestion sub-PRD. This is a design requirement, not a Phase 3 consideration.

## **Submit Mode Behavior**

| **submit_mode** | **Behavior** | **When to Use** |
| --- | --- | --- |
| **append** | All submitted records inserted unconditionally. No key matching. Duplicate records possible across pushes. | New rate records with no overlap with existing data. Not idempotent. |
| **upsert** | Records matched on source_currency_id + target_currency_id + rate_type + effective_datetime. Matches updated; non-matches inserted. Unsubmitted records unchanged. Idempotent. | Incremental rate corrections and additions. Most common mode for rate revisions after the initial period-end load. |
| **replace** | Existing rate records within the defined scope (TBD - see Open Questions) are removed before the submitted batch is inserted. | Full rate table refresh. Use when re-publishing all rates for a period or currency pair. |

## **Error Responses**

* 400 Bad Request: missing required fields, missing or invalid submit_mode, unrecognized currency ID, malformed datetime, or negative rate value. Response body identifies the specific issue and affected record(s).
* 401 Unauthorized: API key missing, invalid, or revoked.
* 403 Forbidden: valid key used outside its connection scope.
* 422 Unprocessable Entity: field value present but wrong data type or precision overflow.
* 429 Too Many Requests: rate limit exceeded. Includes Retry-After header.
* 500 Internal Server Error: unexpected system failure.

# **10. Open Questions**

| **Question** | **Owner** | **Notes** |
| --- | --- | --- |
| What are the allowable values for rate_type? | PM / Engineering / Data | Expected values: Spot (or Period-End), Average, Historical, Budget. Customers may use ERP-specific terminology. This also affects how rates are matched to accounts during translation (e.g., income statement accounts use Average; balance sheet accounts use Closing). |
| What is the required decimal precision for rate_value and inverse_rate_value? | Engineering | High precision is explicitly required. Required a minimum of 12 decimal places to handle currency pairs with large ratios (e.g., USD/IDR ≈ 16,000). Engineering to confirm storage type (e.g., DECIMAL(20,10) or equivalent) and whether precision is capped at ingestion or stored as submitted. |
| Should inverse_rate_value be required, or can FloQast derive it as 1 / rate_value? | Engineering / PM | Deriving the inverse removes a customer burden but introduces precision risk (1 / rate_value may not exactly match the ERP's stored inverse, particularly for rounded or adjusted rates). Recommendation: accept inverse_rate_value as optional; derive if omitted, but allow customer-supplied values to override. Flag any significant divergence between supplied and derived values as a warning. |
| What is the scope of replace mode for FX Rates - all rates, rates for a specific currency pair, or rates within a date range? | PM / Engineering | Unlike GL Transactions and Balances, FX Rates are not period-scoped at the top level. Replace mode needs a clear boundary. Options: (1) replace all rates submitted in the batch's currency pairs only; (2) replace all rates for the effective date range spanned by the batch; (3) full table replace. Option 1 is most targeted and least risky.Having the ability to replace for a date range would be preferred. |
| Should FX Rates be entity-scoped, or are rates organization-wide? | PM / Engineering | Most customers use a single rate table across all entities. However, some may have entity-specific rate methodologies. If entity association is not required, the entity_id parameter may be omitted from the request. If entity-specific rates are needed, entity_association should be added to the field spec and the upsert key. Recommendation would be that entity assignment would happen in Studio for the data set overall. |
| How should timezone be handled for effective_datetime and end_datetime? | Engineering | Rate validity windows are often defined in a specific timezone (e.g., local market close). Confirm whether FloQast normalizes to UTC at ingestion or stores the timezone as submitted. Downstream rate lookup behavior (e.g., which rate is valid for a given transaction date) depends on this decision. |
| What is the unique record identifier used in error reports for the FX Rates endpoint in the Ingestion Logging & Status sub-PRD? | PM / Engineering | FX Rate records do not have a single customer-supplied unique ID like unique_transaction_id. The effective key is source_currency_id + target_currency_id + rate_type + effective_datetime. Engineering to confirm what identifier string should appear in the error report table. |
| Should the endpoint support a rate lookup API (GET /fx-rates) for downstream services to query applicable rates by currency pair, rate type, and effective date? | PM / Engineering | Read access to FX rates would allow FloQast workflows (translation jobs, reconciliation) to query rates programmatically rather than relying on internal storage lookups. Likely needed for Phase 2 downstream integration but out of scope for the ingestion endpoint itself. |
