## 🎯 Objective

This PRD defines the requirements for a foreign key alignment validation check that detects zero-overlap between shared dimension keys across ingested datasets. It does not cover automated key remapping, fuzzy matching, or any transformation of the underlying data to reconcile mismatched keys.

The primary users of this feature are FloQast implementors during customer onboarding and integration setup, as well as FloQast's internal data pipeline systems that ingest and process ERP-sourced data. Customers may also encounter the surface-level output of this check in the form of setup warnings.

When two datasets share a dimension — such as a department code, account ID, or company ID — the key values in each dataset must overlap for downstream data linking to work correctly. In practice, the same dimension is often represented differently across source systems (e.g., "R&D" in one dataset and "Research & Development" in another), resulting in a silent zero-overlap join that produces no rows rather than a visible error. This failure mode is difficult to detect without explicit validation and tends to surface late, during reconciliation or reporting, rather than at ingestion time.

This check enables implementors and downstream systems to catch alignment issues early — at setup or as soon as they're detected in the pipeline — so they can be investigated and resolved before they affect close data quality or reporting accuracy.

## 💡 Key Benefits

* **Early detection at setup:** Implementors are warned about key misalignment during onboarding, before the customer ever runs a close cycle with bad data.

* **Prevents silent join failures:** Zero-overlap joins currently fail silently and produce empty result sets with no indication of why. This check makes the failure visible.

* **Applies across all shared dimensions:** Validation covers any shared dimension key (department, class, location, etc.) in addition to account ID and company ID, making it broadly useful across integration types.

* **Non-blocking by design:** Because key misalignment is not always an error (some datasets are intentionally disjoint), the check surfaces as a warning rather than a hard failure, preserving pipeline flexibility.

* **Persistent log signal:** Warning entries in pipeline logs give engineering and support teams a traceable signal for diagnosing downstream data issues tied to key format mismatches.

* **Reduces onboarding support burden:** Catching misalignment at setup rather than post-close reduces back-and-forth between implementation and support teams investigating reconciliation failures.

* **Improves customer trust:** Surfacing a clear, actionable warning at setup gives customers and implementors confidence that the integration has been validated, not just connected.

## ✅ Use Cases

**A FloQast implementor configuring a new customer integration** loads two datasets — a chart of accounts and a transaction file — that both contain a department code column. The system detects zero overlap between the department code values across the two datasets and surfaces a warning during setup, prompting the implementor to confirm whether this is expected or investigate a potential key format mismatch.

**A FloQast implementor reviewing a setup warning** sees that account IDs in the GL balance dataset do not match any account IDs in the trial balance dataset. The warning message identifies the two datasets and the column(s) with zero overlap, along with a sample of non-matching values from each side, giving the implementor enough context to check the source ERP export format and correct the issue before onboarding is complete.

**FloQast (system) ingesting a recurring data file** detects mid-pipeline that a company ID column in a newly received transactions file has zero overlap with the company IDs in the corresponding accounts dataset. The system writes a structured warning to the Logs section of the UI and to the pipeline log, with the dataset names, the shared dimension column, a sample of non-overlapping values, and the overlap count (0), without halting the pipeline run.

**A customer's integration has intentionally disjoint subsidiary datasets** — two subsidiary company files that share a dimension column but are not expected to link. The zero-overlap check fires as a warning, but the implementor dismisses it as expected. The dismissal is logged with a timestamp and user attribution, and the warning is suppressed for that dataset pair until the underlying data changes.

**A FloQast data engineer troubleshooting a reconciliation discrepancy** searches the Logs section for warnings on a specific customer and finds a zero-overlap warning on the account ID column logged at the time of the most recent file ingestion. The sample of non-overlapping values points directly to a key format mismatch, reducing investigation time significantly.

**A new dataset is added to an existing customer integration mid-cycle.** The system validates shared dimension alignment between the new dataset and all existing datasets that share a key column. Any zero-overlap pairs generate setup-time warnings that are surfaced before the new dataset is made active in the pipeline.

## 🤔 Assumptions

1. Each dataset ingested into FloQast has column-level metadata that identifies which columns represent shared dimensions (e.g., account ID, company ID, department code), either via schema configuration or implementor-defined mapping.

2. The alignment check is a read-only validation — it does not modify, remap, or transform any data in the datasets being compared.

3. "Zero overlap" is defined as a 0% intersection between the distinct, non-NULL key values in a given shared dimension column across two datasets. NULL values are excluded from both sides before comparison.

4. The check applies at the column level — two datasets are compared on a specific shared dimension column, not on the dataset as a whole. Comparisons are pairwise (one dataset to another).

5. The pipeline continues execution after a zero-overlap warning is generated. This is not a blocking condition.

6. Implementors have access to a setup interface or review step where warnings can be displayed before onboarding is finalized.

7. The Logs section of the FloQast UI supports structured warning-level entries that can be queried by dataset, column, and run.

8. The check is triggered both at setup (when datasets are first configured or a new dataset is added) and during recurring pipeline runs.

## ⭐ Milestones

1. **Phase 1: Core zero-overlap detection and logging**\
   Implement the foreign key alignment check logic that compares distinct, non-NULL key values across two datasets on a shared dimension column and detects zero overlap. On detection, write a structured warning-level log entry containing the dataset names, column names, a sample of non-overlapping values, and overlap count. This establishes the foundation for all subsequent surfacing.

2. **Phase 2: Setup-time warning surfacing**\
   Integrate the zero-overlap check into the integration setup flow so that misalignment is detected and surfaced to the implementor before onboarding is finalized. The warning should identify the affected datasets and columns, include sample non-overlapping values, and allow acknowledgment without blocking progression.

3. **Phase 3: Coverage expansion to all shared dimensions**\
   Extend the check beyond account ID and company ID to cover any implementor-mapped or system-identified shared dimension column (e.g., department code, cost center, location). Validate that pairwise checks fire correctly across all applicable dataset combinations.

4. **Phase 4: Recurring pipeline detection**\
   Ensure the check runs on each pipeline execution — not just at setup — so that key misalignment introduced by changes to source data exports is detected and surfaced in the Logs section on an ongoing basis. Evaluate performance impact and determine appropriate execution frequency.

## Scope

### In Scope

* Zero-overlap detection on shared dimension columns across any two datasets in an integration (pairwise comparisons)

* Explicit coverage of account ID and company ID as primary shared dimensions, checked across all applicable dataset pairs

* Coverage of any implementor-mapped or system-identified shared dimension column

* NULL value exclusion from key comparisons on both sides

* Structured warning log entry on zero-overlap detection (dataset names, column names, sample non-overlapping values, overlap count)

* Surfacing warnings in the Logs section of the FloQast UI

* Setup-time warning surfacing to implementors when zero overlap is detected during onboarding

* Dismissal / acknowledgment of warnings with audit logging

* Warning generation during recurring pipeline runs (non-blocking)

* Detection logic triggered when a new dataset is added to an existing integration

### Explicitly Out of Scope

* Partial overlap detection or warnings (e.g., 30% key match rates) — only zero-overlap cases are in scope

* Automated key remapping, fuzzy matching, or any transformation to reconcile mismatched keys

* Customer-facing UI warnings directly in the FloQast product (implementor and log surfacing only)

* Root cause analysis or suggested fixes for why keys don't align

* Multi-dataset simultaneous comparison — pairwise only

* Schema inference for automatic shared dimension detection without implementor mapping or convention-based identification

## 🎨 User Interaction and Design

### Setup-Time Warning Display

After an implementor completes field/dimension mapping during integration setup and the system runs the initial alignment check, any zero-overlap conditions are displayed in a warning banner or review step before the integration is activated. Each warning lists the two affected datasets and the column(s) with no overlapping key values, along with the distinct value counts and a sample of up to 5 non-overlapping values from each side. An "Acknowledge and continue" action is available, which logs the acknowledgment and allows the implementor to proceed. The warning does not prevent activation.

### Logs Section of the UI

Zero-overlap warnings are surfaced in the Logs section of the FloQast UI. Each warning entry displays the two dataset names, the shared dimension column names, the distinct value counts (after NULL exclusion), the overlap count (0), and the sample of non-overlapping values from each side. A "Dismiss" or "Mark as Expected" action is available on each warning entry, allowing a user with appropriate permissions to acknowledge that the misalignment is known and intentional. Dismissed warnings are suppressed for that specific dataset pair and column until the underlying data changes. Dismissed warnings remain visible in the log with a "Dismissed by \[user\] on \[date\]" annotation rather than being permanently hidden.

### New Dataset Addition Warning

When a new dataset is added to an existing integration, the system runs the alignment check before the dataset is activated. If zero overlap is detected between the new dataset and any existing dataset, a warning is surfaced in the same setup-time warning interface described above. The implementor must acknowledge before the new dataset is made active.

## ⚠️ Out of Scope

* **Partial overlap warnings:** Only zero-overlap (0 matching keys) is in scope. Cases where some but not all keys match (e.g., 30% overlap) are excluded. A follow-on effort could define thresholds for low-overlap warnings.

* **Automated remediation:** The system will not suggest, apply, or preview any key remapping or normalization. Resolving the mismatch is the implementor's responsibility.

* **Fuzzy or semantic matching:** Detecting that "R&D" and "Research & Development" are likely the same value is out of scope. The check is exact key intersection only.

* **Customer-facing UI warnings:** Warnings are surfaced to FloQast implementors during setup and in the Logs section. Direct customer-facing alerting in the FloQast product UI is out of scope.

* **Root cause diagnosis:** The system flags zero overlap but does not analyze or suggest why keys don't match.

* **Cross-integration validation:** The check compares datasets within a single integration. Comparing shared dimensions across two different customer integrations is out of scope.

* **Schema inference for shared dimension detection:** Automatic detection of shared dimension columns without explicit implementor mapping or convention-based identification is out of scope unless already supported by existing infrastructure.

* **Multi-dataset simultaneous comparison:** All comparisons are pairwise. Evaluating three or more datasets simultaneously in a single comparison is out of scope.
