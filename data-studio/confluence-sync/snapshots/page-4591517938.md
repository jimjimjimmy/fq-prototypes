## 🎯 Objective

This PRD defines the requirements for Data Studio to support Journal Entry Management (JEM) by providing centralized credential management and dimension master data ingestion. Specifically, it covers how Data Studio enables JEM on existing connections, ingests the full set of valid dimension values required for journal entry creation, manages the lifecycle of dimension data including inactivation, and exposes that data to JEM through the Core Data API.

The primary users are FloQast admins and implementation team members who configure data connections and application enablement. The downstream consumer is JEM, which retrieves dimension data through the Core Data API rather than maintaining its own ERP integration layer.

JEM retains ownership of ERP template mapping and the journal entry workflow. Outbound posting of journal entries to ERPs is explicitly out of scope.

## 💡 Key Benefits

* Centralized credential management: JEM leverages the same connection infrastructure as other Studio products, eliminating a parallel ERP integration layer in JEM.

* Full dimension master data: Studio ingests the complete list of valid dimension values per customer — not just values that appear on existing transactions — giving JEM accurate options for JE field population.

* Shared connections across products: a single connection can serve JEM alongside Close and Reporting, reducing setup overhead for customers.

* Dimension lifecycle management: Studio tracks active/inactive status, start dates, and end dates for dimension values, ensuring JEM always works from a current and accurate dataset.

* Consistent data delivery: JEM consumes dimension data through a stable Core Data API with freshness indicators and data availability notifications, replacing direct ERP calls with a governed data layer.

* Platform-standard logging and notifications: dimension data ingestion follows the same logging, audit, and notification patterns as all other Studio data flows, giving admins full visibility and proactive alerting.

## ✅ Use Cases

* **JEM enablement on a new connection:** A FloQast implementor sets up an ERP API connection in Data Studio. During setup, they enable JEM as an application for that connection, tag the relevant dataset as serving JEM, and configure the dimension types required (vendors, departments, cost centers, locations). Studio begins ingesting dimension master data on the configured schedule.

* **sFTP dimension data upload:** A customer on a file-based ERP integration uploads a dimension file to their sFTP folder. Studio processes the file, validates that data is populated for the configured dimension types, and makes the data available through the Core Data API.

* **JEM notified of new dimension data:** Studio completes a scheduled dimension sync and sends a data availability notification to JEM. JEM refreshes its dimension cache without polling.

* **JEM retrieves dimension data:** A JEM user opens the journal entry creation form. JEM calls the Core Data API to retrieve the full list of valid values for each configured dimension type for that customer, receiving only active values by default.

* **Dimension value inactivated:** A customer retires a department in their ERP. On the next sync, Studio sets an end date on that dimension value and marks it inactive. JEM's next API call returns the updated list without the retired department.

* **Admin troubleshoots stale dimension data:** An admin notices that a recently added cost center isn't appearing in JEM. They open the connection in Data Studio, review the run log and last sync timestamp for the dimension type, trigger an on-demand refresh, and receive a notification when it completes.

## 🤔 Assumptions

1. JEM retains ownership of ERP template mapping. Studio provides raw dimension value lists only.

2. Connections are shared across Studio applications. Enabling JEM on a connection does not create a separate connection.

3. Studio ingests all valid dimension values from the ERP, including values that have never appeared on a transaction.

4. Dimension dependency modeling (e.g., valid departments given a specific subsidiary) is not in scope. JEM handles any dependency logic using the raw lists Studio provides.

5. The freshness SLA for dimension data will be defined in collaboration with JEM and may vary by ERP or customer type.

6. For sFTP customers, the customer is responsible for uploading accurate dimension files. Studio validates that data is populated for configured dimension types but cannot validate completeness against an external source of truth.

7. Dimension data ingestion for JEM follows the same logging, audit, and notification standards as all other Studio data flows, per the [Logging & Audit PRD](https://floqast.atlassian.net/wiki/spaces/Data/pages/4508254281) and the [Notifications PRD](https://floqast.atlassian.net/wiki/spaces/Data/pages/4504551492).

8. Source-specific dimension data requirements (which fields, which ERPs, which API calls) will be defined by the JEM team and captured in individual source-specific sub-PRDs.

9. The sFTP file structure and naming convention for dimension data will be defined by the JEM team.

## ⭐ Milestones

1. **Phase 1:** Credential management and JEM connection enablement. Admins can enable JEM on an existing or new connection, tag the relevant dataset as serving JEM, and configure which dimension types are required for that customer.

2. **Phase 2:** Dimension master data ingestion via ERP API. Studio pulls the full list of valid dimension values from supported ERP APIs on a scheduled basis, with on-demand refresh capability. Source-specific requirements to be defined per individual sub-PRD (JEM team to provide).

3. **Phase 3:** Dimension master data ingestion via sFTP. Studio processes customer-uploaded dimension files, validates them against configured dimension types, and surfaces errors to admins. File structure and naming convention to be defined with JEM team.

4. **Phase 4:** Dimension lifecycle management. Studio tracks active/inactive status, start dates, and end dates for dimension values. Inactivation is reflected in the Core Data API on the next sync.

5. **Phase 5:** Core Data API — JEM consumption. Studio exposes dimension data through the Core Data API with support for full value list retrieval, active/inactive filtering, freshness indicators, and JEM data availability notifications. JEM migrates from direct ERP calls to the Core Data API.

## Scope

The following are in scope:

* Connection configuration: enabling JEM as an application on a connection, tagging datasets as serving JEM, and configuring dimension types per customer.

* Dimension master data: all valid values for configured dimension types (vendors, departments, cost centers, projects, locations, and any additional types identified during JEM alignment).

* Dimension lifecycle: active flag, start date, end date, and key/value structure per dimension value.

* Ingestion metadata: per-customer, per-dimension-type sync status, last updated timestamp, and error detail.

* sFTP file processing: ingestion pipeline for customer-uploaded dimension files, including format validation and error notification. File structure TBD with JEM.

* Core Data API: endpoints for JEM to query dimension data by customer and dimension type, with active/inactive filtering, freshness indicators, and data availability notifications.

* Logging and audit: all dimension ingestion runs and configuration changes logged per the [Logging & Audit PRD](https://floqast.atlassian.net/wiki/spaces/Data/pages/4508254281).

* Notifications: admins notified of ingestion failures and late data per the [Notifications PRD](https://floqast.atlassian.net/wiki/spaces/Data/pages/4504551492); JEM notified when new dimension data is available.

Explicitly out of scope:

* ERP template mapping (owned by JEM).

* Outbound posting of journal entries to ERPs (separate workstream, pending Engineering input).

* Dimension dependency modeling.

## ⚠️ Out of Scope

* ERP template mapping and journal entry workflow — owned by JEM.

* Outbound posting of journal entries to ERPs — separate workstream pending Engineering input on a centralized approach.

* Dimension dependency modeling — JEM handles cascading dimension relationships using raw lists from Studio.

* Write-back or bi-directional sync — this PRD covers ingestion only.
