## 🎯 Objective

This sub-PRD covers the first phase of Model creation: initiating a new model, selecting the target FloQast domain, naming the model, and configuring the source dataset(s) that will feed into it — including linked datasets, primary dataset designation, and the grouped dataset pattern for customers with high-volume, schema-identical file sets.

This document does **not** cover field mapping logic, testing, publishing, or versioning. Those are addressed in sub-PRDs 2, 3, and 4 respectively.

The primary users are FloQast admins and implementation team members who need to configure, inspect, and troubleshoot data models without engineering involvement.

## 🏅 Why This Is Important

As our target customer base grows, we need to be able to handle more complex situations (larger enterprise customers) with Self-Service capabilities. This is fundamental for us to scale, and to ensure speed of implementation is fast within the data integrations space.

### 🔐 Value Unlocked

* Mapping auditability, change management of mapping, ability to have multiple mappings per source and data object
* Customers can apply mapping changes when key business events cause data structure changes

### 🗝️ Key examples:

* **Grouped Datasets:** One customer provides 200+ files representing the same dataset split by entity. Without Grouped Dataset support, they would need to manually configure separate model rules for each file.
* **Naming Models**: One customer provides a single file which needs to map to multiple entities and Models. Naming Models reduces clicks and reduces risk of error.

---

## 💡 Key Benefits

* Admins and implementation team members can create and configure Models without engineering involvement.
* Grouped Dataset support eliminates the manual, file-by-file configuration burden.
* A self-service creation flow reduces onboarding time and FQ support overhead.

| # | Persona | Scenario | Expected Outcome |

| 1 | FQ Admin | Customer has a single source file per domain | Admin creates model, links one dataset, designates it as primary |

| 3 | FQ Admin | Customer has two source datasets that must be joined | Admin links both datasets, designates one as primary |
| 4 | Implementation Team | Setting up a new customer environment with no connectors yet configured | System surfaces a zero-state CTA directing user to set up a Connector |

## 🤔 Assumptions

### Established

* At least one Connector must be configured before a user can reach this flow.
* Model names must be unique within a TLC workspace.
* A model can have multiple Linked Datasets but exactly one Primary Dataset.

---

## 🗺️ Scope

### 🚗 In Scope

* Creating a new Model (naming + FQ Model selection)
* Name uniqueness enforcement
* Linking one or more source datasets to a model
* Designating a Primary Dataset (or Primary Grouped Dataset)
* Defining Grouped Datasets (union behavior for schema-identical files)
* Zero-state experience when no Connectors are configured
* Draft state creation upon model save
* Navigation to opening the new draft model after creation

### 🚦 Out of Scope

* Field mapping logic (see Sub-PRD 2)
* Testing / data preview prior to publish (see Sub-PRD 3)
* Publishing and effective dates (see Sub-PRD 3)
* Versioning and lifecycle management (see Sub-PRD 4)
* Entity Mapping tab behavior
* Connector setup (separate product area)
