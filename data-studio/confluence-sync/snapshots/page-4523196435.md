## 🎯 Objective

This PRD defines **Step 3 of the Add Dataset wizard: Define Schema**. It covers how the platform detects a dataset's column structure from a sample file or API response, presents it to the admin for review and confirmation, and allows corrections before the dataset is published.

This PRD covers schema definition at initial setup and schema editing on existing datasets. It does **not** cover what happens when a published dataset's schema changes after the fact — that is addressed in the Schema Versioning PRD. It also does not cover field mapping (how dataset columns map to FloQast's normalized format), which is a separate workflow.

Schema definition applies to all connector types: SFTP file-based sources and API-based sources.

Primary users: Data Studio admins and FloQast implementation team members configuring a new dataset within a Connector.

## 🏅 Why This Is Important

Today, Data Studio infers column data types from incoming files without asking the admin to confirm them. This is a silent assumption that frequently goes wrong — particularly for dates, where format differences (YYYY-MM-DD vs MM/DD/YYYY vs month name) cause incorrect parsing that cascades into failed reconciliations and wrong close data.

Data types and formats are foundational to how the platform reads, transforms, and maps data. Getting them wrong at the source means everything downstream is affected: field mapping, transformation logic, and ultimately the data that reaches FloQast products. Making schema confirmation an explicit, guided step — with AI-assisted detection and clear flagging of uncertain columns — catches these errors before they reach production.

---

## 🔐 Value Unlocked

Admins confirm that the platform has correctly understood their data before it is ever processed. Uncertain columns are surfaced for review rather than silently guessed. Date and number formats are explicitly specified, eliminating a major category of data quality issues downstream.

---

## 🗝️ Key Examples

* **Example 1:** An admin uploads a GL transactions file. The system detects 9 columns and infers data types for each. Two columns — `period_end_date` and `is_active` — are flagged as medium confidence. The admin sees them highlighted, confirms that `period_end_date` is a date in `YYYY-MM-DD` format and that `is_active` is a boolean, and proceeds.
* **Example 2:** An admin connects an API source. The system inspects the API response schema and surfaces the same column review interface — same data types, same confidence flagging, same format specification. The experience is identical regardless of connector type.
* **Example 3:** An admin reviews the detected schema and notices that a column called `amount` was inferred as a string rather than a number. They correct the data type to Number and specify the number format before confirming. The downstream field mapping now receives correctly typed data.

---

## 💡 Key Benefits

* Explicit schema confirmation prevents silent data type mismatches from reaching production
* Confidence flagging directs the admin's attention to the columns most likely to be wrong, without requiring them to review every row
* Data Type Format specification (dates and numbers) eliminates a major source of downstream transformation errors
* Consistent experience across SFTP and API connector types — one schema review pattern for all sources

## 🤔 Assumptions

**Established**

* Schema detection runs against the sample file uploaded in Step 2 (for file-based connectors) or against the API response schema (for API connectors).
* The schema step is the same for all connector types — SFTP and API sources both go through this review.
* Data Type Format is a required specification for date and number columns — the admin must specify the format before the schema can be confirmed.
* Columns can be individually excluded from the schema. Excluded columns are not available for field mapping or any downstream processing.
* Confidence flagging is a mix of AI-based inference and rule-based signals. The specific breakdown of what triggers each confidence level is an open question for engineering.
* Schema definition is for initial setup only. Changes to a published dataset's schema are handled by the Schema Versioning flow (separate PRD).
* **Integer columns should almost never be used.** Columns that appear to be numeric IDs (e.g., `account_id`, `entity_code`) are far safer as String (varchar) — integer typing loses leading zeros, causes join failures, and creates brittle downstream behavior. The system should default ID-like columns to String, and the UI should surface a warning if the admin manually sets an apparent ID column to Integer.

**Open Items to Confirm**

* What is the minimum sample required for reliable schema detection — does a single row suffice, or does the system need multiple rows to detect types confidently?
* Can an admin add columns that weren't detected (e.g., if the sample file was missing a column that appears in production files)?
* What happens if the uploaded sample file has no header row — does schema detection fail, or does the system assign default column names?
* Should excluded columns be permanently excluded or soft-excluded (re-includable later without a schema version change)?

## 🗺️ Scope

### 🚗 In Scope

* Auto-detection of column names and data types from a sample file or API response
* Column-level review: name, detected data type, Data Type Format, include/exclude toggle
* Supported data types: String, Number, Date, Boolean, (others TBD by engineering)
* Data Type Format for date columns: YYYY-MM-DD, MM/DD/YYYY, Month name, YYYY-MM, and others TBD
* Data Type Format for number columns: decimal format, currency handling (TBD with engineering)
* Confidence flagging: medium-confidence columns visually highlighted for admin review
* Schema confirmation as Step 3 of the Add Dataset wizard
* Schema editing as a directly-accessible tab in dataset Edit mode
* Applies to all connector types: SFTP, Manual Upload, API

### 🚦 Out of Scope

* Schema versioning — what happens when a published schema changes (see Schema Versioning PRD)
* Field mapping — how schema columns map to FloQast's normalized format (separate workflow)
* Column-level transformations at the schema step
* Schema inference for CDC connectors (TBD)
* Custom data type definitions beyond the supported set

### SDF1 — Auto-Detect Schema from Sample File or API Response

**User Story:** As an admin, I can see the platform's detected schema when I reach the schema step so that I have a starting point to review rather than entering every column manually.

**Importance:** High

**Details:** For file-based connectors, schema detection runs against the sample file uploaded in Step 2. For API connectors, it runs against the API response schema. The result is a column list pre-populated with detected names and data types. The admin reviews and confirms — they do not start from scratch.

**AC-SDF1-01 — Schema pre-populated from sample**

* Given I have completed Step 2 (Filename Pattern / API connection)
* When I reach Step 3 (Define Schema)
* Then the column list is pre-populated with detected column names and data types
* And I do not need to enter any column information manually to proceed

**AC-SDF1-02 — Detection applies to both file and API sources**

* Given my dataset uses an API connector
* When I reach Step 3
* Then the schema review interface is presented with columns detected from the API response
* And the experience is identical to the file-based schema review

**AC-SDF1-03 — Detection failure is surfaced clearly**

* Given schema detection fails (unreadable file, empty response, etc.)
* When I reach Step 3
* Then a clear error is shown explaining why detection failed and what to do next
* And I am not presented with an empty column list with no guidance

---

### SDF2 — Review and Confirm Column List with Data Types

**User Story:** As an admin, I can review each detected column and its data type so that I can confirm the platform has understood my data correctly before it is processed.

**Importance:** High

**Details:** The column list shows each column with its name and detected data type. The admin scans the list, makes corrections where needed, and confirms. The goal is a fast review — most columns should be correct and require no action.

**AC-SDF2-01 — All detected columns shown**

* Given schema detection has run
* When the schema review step renders
* Then all detected columns are shown in a list
* And each row displays: column name, detected data type, Data Type Format (where applicable), include/exclude toggle

**AC-SDF2-02 — Schema can be confirmed without changes**

* Given all detected types are correct
* When I click "Confirm Schema"
* Then I proceed to Step 4 without being required to make any edits

---

### SDF3 — Confirm Data Type Format for Date and Non-Integer Number Columns

**User Story:** As an admin, I can review and confirm the system's suggested format for date and non-integer number columns so that the platform parses them correctly without me having to select a format from scratch.

**Importance:** High

**Details:** The system pre-selects a suggested Data Type Format based on the sample data. The admin's job is to confirm or correct the suggestion — not to pick a format cold. This applies to date columns and non-integer number columns (e.g., decimal, currency). Integer columns do not require a format specification.

When an admin confirms or changes a format, they are offered the option to apply that same format to other columns of the same type in one action — avoiding the need to manually update each column individually.

The field is labelled "Data Type Format" — not "Date Format" — to make clear it covers both dates and non-integer numbers.

**Notes:** The exact list of supported non-integer number formats is to be confirmed with engineering.

**AC-SDF3-01 — System pre-selects a suggested format for date columns**

* Given a column has a detected type of Date
* When the schema review step renders
* Then the Data Type Format field is pre-populated with the system's best guess at the format
* And the admin can confirm the suggestion as-is or override it

**AC-SDF3-02 — Data Type Format required for date columns before confirming schema**

* Given a column has a detected type of Date
* When I attempt to confirm the schema with no format selected for that column
* Then the schema confirmation is blocked
* And an inline indicator on the date column prompts format selection

**AC-SDF3-03 — Supported date formats shown with plain-language examples**

* Given a column has type Date
* When I open the Data Type Format selector
* Then each format option is shown with a plain-language example alongside the format code:

    * YYYY-MM-DD → e.g. 2026-01-31
    * MM/DD/YYYY → e.g. 01/31/2026
    * Month name + day + year → e.g. January 31, 2026
    * YYYY-MM → e.g. 2026-01
    
* And the admin can identify the correct format by recognising the example rather than reading the format code

**AC-SDF3-04 — System pre-selects a suggested format for non-integer number columns**

* Given a column has a detected type of Number and is non-integer (e.g., decimal, currency)
* When the schema review step renders
* Then the Data Type Format field is pre-populated with the system's best guess
* And the admin can confirm or override

**AC-SDF3-05 — Format not required for integer number columns**

* Given a column has a detected type of Integer
* When the schema review renders
* Then no Data Type Format selector is shown for that column

**AC-SDF3-06 — Format not required for String or Boolean columns**

* Given a column has a detected type of String or Boolean
* When the schema review renders
* Then no Data Type Format selector is shown for that column

**AC-SDF3-07 — Apply format to other columns of the same type**

* Given I confirm or change the Data Type Format for a column
* When other columns of the same type exist in the schema
* Then I am offered the option to apply this format to all other columns of the same type
* And applying it updates all matching columns without requiring individual edits

---

### SDF4 — Flag Medium-Confidence Columns for Review

**User Story:** As an admin, I can see which columns the system is less confident about so that I can focus my review on the most likely errors without checking every row.

**Importance:** High

**Details:** The confidence signal is a mix of AI-based inference and rule-based signals. Medium-confidence columns are visually highlighted in the column list. The admin is not required to take action on flagged columns — the flag is an indicator, not a blocker. However, the intent is that the admin at least reviews the flagged columns before confirming.

**Notes:** The exact criteria for high vs. medium confidence — which signals are AI-based vs. rule-based, and the threshold for each level — is an open question for engineering.

**AC-SDF4-01 — Medium-confidence columns visually flagged**

* Given one or more columns have medium-confidence type detections
* When the schema review step renders
* Then those columns are visually distinguished from high-confidence columns
* And the flagging does not block schema confirmation

**AC-SDF4-02 — Flagged columns are reviewable and correctable**

* Given a column is flagged as medium confidence
* When I review it and correct the data type or format
* Then the flag is resolved and the column no longer appears flagged

**AC-SDF4-03 — No columns flagged when all detections are high confidence**

* Given all columns have high-confidence type detections
* When the schema review step renders
* Then no columns are flagged and no flag-related UI is shown

---

### SDF5 — Include or Exclude Individual Columns

**User Story:** As an admin, I can exclude individual columns from the schema so that columns irrelevant to downstream processing are not included.

**Importance:** High

**Details:** Each column has an include/exclude toggle. Excluded columns are not available for field mapping or any downstream processing for this dataset. By default all detected columns are included.

**AC-SDF5-01 — All columns included by default**

* Given schema detection has run
* When the schema review step renders
* Then all detected columns have their include toggle set to on by default

**AC-SDF5-02 — Columns can be excluded individually**

* Given I toggle a column's include switch to off
* When I confirm the schema
* Then that column is excluded from the dataset's schema
* And it is not available in the field mapping step or any downstream processing

**AC-SDF5-03 — Excluded columns not shown in downstream steps**

* Given a column was excluded during schema definition
* When I reach the field mapping step
* Then that column does not appear in the source column list

---

### SDF6 — Correct a Detected Data Type

**User Story:** As an admin, I can change a column's detected data type if the system inferred it incorrectly so that the correct type is used for all downstream processing.

**Importance:** High

**AC-SDF6-01 — Data type is editable**

* Given a column has a detected data type
* When I click on or interact with the data type selector for that column
* Then I can change it to a different supported type

**AC-SDF6-02 — Changing type to Date or Number reveals format selector**

* Given I change a column's type to Date or Number
* When the type change is applied
* Then the Data Type Format selector appears for that column
* And schema confirmation is blocked until a format is selected

**AC-SDF6-03 — Changing type away from Date or Number hides format selector**

* Given a column has type Date or Number with a format selected
* When I change the type to String or Boolean
* Then the Data Type Format selector is removed for that column

**AC-SDF6-04 — Warning shown when setting an ID-like column to Integer**

* Given a column name suggests it is an identifier (e.g. contains "id", "code", "key", "num")
* When I set that column's type to Integer
* Then an inline warning is shown: "ID and code columns are usually safer as String — integer typing can cause join failures and drop leading zeros."
* And I can dismiss the warning and proceed if I choose

## 😎 Future Considerations

* **Sample value preview:** Show a sample value from the uploaded file next to each column to help admins validate detected types — e.g., showing `2026-03-31` next to a date column makes it easy to confirm the format is correct.
* **Bulk format actions:** Allow admins to apply a format to all columns of the same type at once (e.g., "set all dates to YYYY-MM-DD").
* **Column addition:** Allow admins to manually add columns not detected in the sample (for files where production data may contain additional columns not present in the sample).
* **Schema import/export:** Export a schema definition as JSON or CSV for reuse across similar datasets.
