# **1. Objective**

FloQast's data platform allows customers to configure source data through two primary mechanisms: file uploads mapped to FloQast model fields, and API endpoints that retrieve data on a schedule or on demand. Currently, neither files nor endpoints can be fully self-managed after initial setup - customers cannot correct configuration mistakes, deactivate unused records, test configuration changes, or safely remove stale data without FloQast support involvement. Additionally, there is no mechanism to warn users when an archive or delete action would disrupt an active model field linkage, creating risk for silent misconfigurations.

‌

This PRD defines the requirements for end-to-end lifecycle management of files and endpoints, giving customers and implementation specialists full control over configuration, maintenance, and cleanup of their source data records throughout the platform.

# **2. Key Benefits**

* Customers and implementation specialists can archive, edit, reactivate, and permanently remove files and endpoints without FloQast support involvement
* Reduced support ticket volume during implementation and ongoing configuration
* Increased configuration accuracy - users can correct mistakes (wrong load type, misconfigured endpoint parameters) without re-uploading or recreating from scratch
* Controlled data rehydration on reactivation - users choose whether to restore all historical data, data from a specific point in time, or go forward only
* Proactive lineage warnings prevent accidental disruption to active model field mappings when archiving or deleting
* Clear visibility into source data state (active, archived, unlinked) to reduce silent misconfigurations
* Sample and test capabilities allow users to validate file and endpoint configurations before changes take effect in production

# **3. Use Cases**

1. A customer uploaded a file and selected the wrong load type (full instead of incremental). They edit the file's configuration directly to correct the setting - no re-upload required.
2. A customer wants to deactivate an API endpoint tied to a report they no longer use. Before archiving, the system warns them that the endpoint feeds an active model field. They reassign the lineage, then archive the endpoint.
3. A FloQast implementation specialist needs to permanently remove a test file uploaded during onboarding. They select Remove Entirely, review the warning that the file is linked to a lineage record, confirm the action, and the file is fully removed.
4. A customer reactivates an archived file and is prompted to choose a data hydration strategy: restore all historical data, hydrate from a specific date, or activate going forward only.
5. A customer reactivates an archived API endpoint and specifies that data should be re-fetched from the last 90 days rather than from the beginning of time.
6. A FloQast implementor edits an endpoint's query parameters and uses the inline test view to run a sample call and verify the request and response before saving the configuration.
7. A customer removes a source field from a FloQast model. The previously linked file now appears in the source data list with an 'Unlinked' indicator, prompting the customer to reassign or clean up the orphaned file.
8. A customer uploads a new file and uses the sample preview to confirm field mappings look correct before the file is used in a processing run.

# **5. Assumptions**

* Archive / Deactivate is a reversible action: the file or endpoint remains in the system but is inactive and excluded from data processing
* Delete (Remove Entirely) is permanent and irreversible; all associated configuration and lineage metadata is hard-deleted
* Both customer users and FloQast internal admins / implementation specialists can perform all lifecycle actions, subject to existing permission models
* The lineage structure mapping source fields to FloQast model fields already exists in the data platform; this PRD surfaces its state in the UI but does not change the underlying mapping logic
* A file or source data record is considered 'Unlinked' when no active lineage record connects it to a FloQast model field
* The files and endpoints management UI already exists in some form; these are enhancements to existing screens and action menus
* File creation / endpoint creation flows already exist and are in scope per existing platform functionality; this PRD focuses on lifecycle management of existing records and does not redefine the creation flow
* For file reactivation, data hydration options (all time, from a point in time, going forward only) require Engineering confirmation that retroactive hydration is technically supported
* For endpoint reactivation, the system supports a configurable pull-from date to re-fetch historical data, subject to API-side data retention and rate limit constraints
* Load type and configuration changes apply to future processing runs only; retroactive application is not assumed

# **7. Scope of Data**

**Files / Source Data**

* File records: name, load type (full / incremental / historical), entities assigned, active/inactive status, lineage linkage state (linked / unlinked)
* File configuration metadata: name, load type, entity assignments, load behavior (append vs. replace vs. historical)
* File sample/preview data: representative row sample surfaced during configuration review

‌

**Endpoints**

* Endpoint records: name, API path, description, query parameters, sync frequency, activation status, last run metadata
* Endpoint configuration metadata: name, API path, query parameters, sync frequency, activation status
* Endpoint test/sample data: raw request and response captured during configuration test

‌

**Lineage**

* Active lineage records linking files or endpoints to FloQast model fields, used to derive linked/unlinked state and to surface warnings on archive and delete actions

‌

**Out of Scope for This Data Layer**

* Connection lifecycle records - covered in the companion Connection Lifecycle Management PRD
* File content beyond sample preview capability
* Fivetran-managed endpoint configurations

# **8. Requirements**

## **Files / Source Data**

‌

* **REQ-01: As a user, I want to archive (deactivate) a file so that it is preserved in the system but no longer active in data processing.**

_Functional spec:_ A Deactivate / Archive option is available in the file action menu for any active file. If the file is linked to an active lineage record, a lineage warning is surfaced before the confirmation prompt (see REQ-12). A brief confirmation prompt is shown before archival is applied. Archived files retain their configuration and lineage metadata but are excluded from active data processing. They display an 'Archived' visual tag in the source data list and are hidden from the default view, accessible via filter. The action to archive the file is logged in the source data logs.

‌

* **REQ-02: As a user, I want to permanently remove a file from the system so that outdated or incorrect files are cleaned up entirely.**

_Functional spec:_ A Remove Entirely option is available in the file action menu. This action is permanent and irreversible. Selecting it triggers a warning modal (see REQ-03). If the file is linked to active lineage records, the modal surfaces this impact per REQ-12. Upon confirmed deletion, the file and all associated configuration are permanently removed from the system.The action to delete the file is logged in the source data logs.

‌

* **REQ-03: As a user, I want to see a clear warning before permanently removing a file so that I do not accidentally delete data I still need.**

_Functional spec:_ When a user selects Remove Entirely, a confirmation modal displays: (1) a statement that the action is permanent and cannot be undone, and (2) any active lineage records that will also be removed, listed by model field name. The user must take an explicit confirmation action - visually styled as destructive and distinct from Cancel - before deletion proceeds.

‌

* **REQ-04: As a user, I want to reactivate an archived file and choose how to handle historical data so that I have control over data completeness when restoring a file to active status.**

_Functional spec:_

Upon selecting Reactivate on an archived file, the user is prompted to choose a data hydration strategy before the reactivation is confirmed:

* All time: hydrate all available historical data for this file
* From a specific date: user selects a date; data is hydrated from that point forward
* Going forward only: no historical hydration; the file becomes active for new data only. This is the default option.

Upon confirmation of the selected option, the file returns to active status and is included in future data processing runs per its configuration.

‌

* **REQ-05: As a user, I want to edit a file's configuration so that I can correct mistakes or update settings without re-uploading the file.**

_Functional spec:_

An Edit option in the file action menu opens a modal or form with pre-populated configurable fields including:

* File name
* Entities assigned
* Load type and behavior: full / incremental / historical (mapping to append vs. replace vs. historical load behavior)

Current values are pre-populated so the user can identify what to correct. A Sample / Preview action is available within the edit modal to validate the configuration before saving (see REQ-11). Changes take effect on the next processing run.

‌

## **Endpoints**

‌

* **REQ-06: As a user, I want to archive (deactivate) an endpoint so that it is preserved in the system but no longer active in data processing.**

_Functional spec:_ A Deactivate / Archive option is available in the endpoint action menu for any active endpoint. If the endpoint is linked to an active lineage record, a lineage warning is surfaced before the confirmation prompt (see REQ-12). A brief confirmation prompt is shown before archival is applied. Archived endpoints retain their configuration and run history but are excluded from scheduling and new data processing runs. They display an 'Archived' visual tag and are hidden from the default view, accessible via filter. The action to archive the endpoint is logged in the source data logs.

‌

‌

* **REQ-07: As a user, I want to permanently delete an endpoint so that stale or misconfigured endpoints are fully removed from the system.**

_Functional spec:_ A Delete option is available in the endpoint action menu. This action is permanent and irreversible. Selecting it triggers a warning modal. If the endpoint has active lineage records, the modal surfaces this impact per REQ-12. If the endpoint is referenced as a parent in a nested endpoint call chain, a dependency warning is also surfaced. Upon confirmed deletion, the endpoint and all associated configuration, run history, and query parameter definitions are permanently removed. The action to delete the endpoint is logged in the source data logs.

‌

‌

* **REQ-08: As a user, I want to reactivate an archived endpoint and specify when data retrieval should resume so that I have control over how much historical data is re-fetched.**

_Functional spec:_

Upon selecting Reactivate on an archived endpoint, the user is prompted to choose a pull-from date/time before the reactivation is confirmed. Options include:

* From the beginning: re-fetch all available data from the earliest supported date for this endpoint
* From a specific date: user selects a date; data is pulled from that point forward
* From last sync: resume from where the endpoint last successfully ran
* Going forward only: no historical re-fetch; the endpoint begins fresh from the reactivation date

Upon confirmation, the endpoint returns to active status and is scheduled for its next run per its configured sync frequency. Historical re-fetch options are subject to API-side data retention windows and rate limit constraints.

‌

* **REQ-09: As a user, I want to edit an existing endpoint's configuration so that I can correct errors, update parameters, or adjust scheduling without recreating the endpoint.**

_Functional spec:_

An Edit option in the endpoint action menu opens a configuration panel pre-populated with current settings. Editable fields include:

* Endpoint name
* API path (for manually entered endpoints)
* Query parameters (required and optional), with descriptions and enumerated values where applicable
* Sync frequency (default 24h; options: 1h, 2h, 4h, 8h, 12h, 24h, Custom)
* Activation status

All changes are validated before saving. A Test / Run Sample action is available within the edit panel to validate the configuration before the save is committed (see REQ-11). For nested endpoints, the UI exposes the dependency chain so the user understands which upstream endpoints will be called.

‌

## **Shared: Testing, Indicators, and Warnings**

‌

* **REQ-10: As a user, I want to create a new file or endpoint so that I can establish a new source data record within an existing connection.**

_Functional spec:_

File and endpoint creation flows are already in place. This requirement confirms that creation is in scope for this surface and that the sample/test capability (REQ-11) is available as part of the creation flow, not only during edits. No changes to the existing creation flow are required unless driven by other requirements in this PRD.

‌

* **REQ-11: As a user, I want to see a sample of data or run a test call for a file or endpoint so that I can validate configuration before changes take effect in production.**

_Functional spec:_

For files: a Sample / Preview action available within the file row action menu and within the edit modal displays a representative row sample showing field mappings and data values. This allows the user to confirm the configuration is correct before saving.

‌

For endpoints: a Test / Run Sample action available within the add and edit flows executes the endpoint with the current configuration and displays the raw request and response in a Swagger-style view. The user can inspect the response payload to confirm the endpoint returns expected data before saving.

‌

Both sample actions are non-destructive and do not write data to the production data store. Results are visible for the current session only.

‌

* **REQ-12: As a user, I want to be warned when I attempt to archive or delete a file or endpoint that is actively linked to a FloQast model field so that I can reassign or remediate before taking the action.**

_Functional spec:_

Before an archive or delete action is applied to a file or endpoint with active lineage records, the system surfaces a warning that includes:

* A statement that the file or endpoint is actively linked to one or more FloQast model fields
* The names of the affected model fields
* For delete: an additional statement that the action is permanent and the lineage record will also be removed

For archive: the user must acknowledge the warning before proceeding; the action is permitted after acknowledgment. For delete: the user must provide explicit confirmation (styled as destructive, distinct from Cancel) before the file or endpoint is permanently removed. For endpoints that are parent nodes in a nested call chain, an additional dependency warning is surfaced alongside the lineage warning.

‌

* **REQ-13: As a user, I want to see a visual indicator on files and source data that are not linked to any FloQast model so that I can identify and address orphaned data.**

_Functional spec:_ Files and source data records with no active lineage record display an 'Unlinked' badge or indicator directly in the source data list row. This indicator is passive and informational only - it does not block other actions. The badge updates dynamically when a linkage is added or removed. No user action is required, but the indicator makes orphaned data immediately visible so the user can reassign or remove it.

# **9. User Interaction and Design**

All file and endpoint lifecycle actions are surfaced via a contextual action menu (three-dot / kebab menu) on each row in the respective list views. This keeps the UI clean while making all management options consistently accessible.

‌

**File / Source Data Action Menu - Active**

* Edit: opens a modal with pre-populated configuration fields (name, entities, load type/behavior); includes Sample / Preview action inline
* Archive / Deactivate: surfaces lineage warning if applicable; requires brief confirmation before applying
* Remove Entirely: triggers warning modal with lineage impact detail; requires explicit destructive confirmation before proceeding

‌

**File / Source Data Action Menu - Archived**

* Reactivate: opens data hydration selection modal; options are All time / From a specific date / Going forward only; returns file to active status after confirmation
* Remove Entirely: same permanent removal flow as active files

‌

**Endpoint Action Menu - Active**

* Edit: opens a configuration panel pre-populated with current settings; includes inline Test / Run Sample action; covers name, API path, query parameters, sync frequency
* Archive / Deactivate: surfaces lineage warning if applicable; requires brief confirmation before applying
* Delete: triggers warning modal with lineage impact and (if applicable) nested dependency warning; requires explicit destructive confirmation before proceeding

‌

**Endpoint Action Menu - Archived**

* Reactivate: opens pull-from date selection modal; options are From the beginning / From a specific date / From last sync / Going forward only(default); returns endpoint to active status after confirmation
* Delete: same permanent deletion flow as active endpoints

‌

**Reactivation Modal - Files**

Title: 'Reactivate File - Choose Data Hydration'

* Option 1: All time - hydrate all available historical data
* Option 2: From a specific date - date picker
* Option 3: Going forward only - no historical hydration (default)

Actions: Confirm | Cancel

‌

**Reactivation Modal - Endpoints**

Title: 'Reactivate Endpoint - Choose Data Pull Start'

* Option 1: From the beginning - re-fetch all available data
* Option 2: From a specific date - date picker
* Option 3: From last sync - resume from last successful run
* Option 4: Going forward only - no historical re-fetch (default)

Actions: Confirm | Cancel

‌

**Lineage Warning (Archive)**

Displayed inline above the confirmation prompt. Content includes the names of affected model fields. User must acknowledge before the archive action proceeds. The action is permitted after acknowledgment.

‌

**Lineage Warning (Delete / Remove Entirely)**

Displayed in the warning modal alongside the permanent action statement. Content includes affected model field names and a statement that lineage records will also be removed. User must provide explicit destructive confirmation before deletion proceeds.

‌

**Unlinked Indicator**

An 'Unlinked' badge (gray or yellow tag) is displayed directly in the file or source data row for records with no active model linkage. The indicator is passive and informational only, requires no user action, and updates dynamically when a linkage is added or removed.

‌

**Default List View Filter**

Active files and endpoints are shown by default. Filter options are: Active (default) | Archived | All. Archived items are not visible in the default view but are accessible via the filter.

# **10. Open Questions**

| **Question** | **Owner** | **Notes** |
| --- | --- | --- |
| What is the maximum lookback window for endpoint reactivation data re-fetch? | Engineering | API-side data retention and rate limit windows may cap how far back a re-fetch can go. Needs per-source definition. |
| Should the lineage warning hard-block the archive action, or just require acknowledgment before proceeding? | PM / Design | Current spec allows archive after acknowledgment. Confirm if a hard block is preferred for any scenarios. |
| What happens when a deleted endpoint was a parent node in a nested endpoint call chain? | Engineering | Deleting a parent endpoint breaks downstream nested calls. A dependency warning is specified in REQ-12, but the exact blocking behavior needs confirmation. |
| Can load type changes (full vs. incremental / append vs. replace) be applied retroactively? | Engineering | Recommend applying to future runs only to protect historical data integrity. |
| Are there permission tiers that should restrict who can permanently delete files or endpoints (e.g., admin-only for Remove Entirely)? | Engineering / PM | Worth defining for enterprise customers with multiple user roles. |
| Should the 'Unlinked' indicator trigger a proactive notification (e.g., in onboarding checklist or setup dashboard), or remain a passive visual cue only? | PM / Design | Consider surfacing unlinked records in an implementation checklist for higher visibility during onboarding. |
| For endpoints with nested dependencies, should reactivation require the parent endpoint to also be active before the child can be reactivated? | Engineering | Dependency sequencing for nested endpoints may need to be enforced at the reactivation step. |

# **11. Out of Scope**

* Connection lifecycle management - covered in the companion Connection Lifecycle Management PRD
* File and endpoint creation flows - already in place; this PRD does not redefine creation, only lifecycle management of existing records
* Bulk archive or bulk delete actions across multiple files or endpoints simultaneously
* Automated archiving based on inactivity thresholds
* Changes to the lineage mapping UI (how source fields are mapped to FloQast model fields)
* Fivetran endpoint management - Fivetran-connected sources have a separate configuration path
* Write-back or bi-directional sync; this PRD covers read-only data ingestion configurations
* File content inspection beyond the sample preview capability (e.g., full file download or row-level browsing)
* External customer-facing on-demand trigger interface - covered in the parent API Endpoint Management PRD
* Connection health monitoring, error alerting, or sync status reporting
