## 1. Objective

This sub-PRD defines the requirements for scheduling Data Studio model runs. It covers how admins configure when a model executes — including time-based and accounting-aware scheduling, run monitoring, skipped execution handling, and the controls required when schedule configurations are changed in production environments.

**Primary users:** FloQast admins, implementation team members, compliance/audit reviewers.

**This PRD does not cover:**

* Connector-level sync scheduling (when raw data is pulled from source systems via Pull API). That is defined in the [Pull API Support](https://floqast.atlassian.net/wiki/spaces/Data/pages/4491214866) PRD. Model run schedules operate downstream of connector sync schedules and must be configured in coordination with them.
* On-demand / manual run triggers. Covered in the On-demand Refresh PRD.
* Internal FQ engineering alerting on failed runs. Covered in Logging & Audit.
* Customer-facing failure notifications. Covered in Notifications.
* Scheduling for other FloQast job types (AI Matching, Apply All Rules, Reconciliations). Tim's scheduling spec covers a broader cross-product job framework; this PRD is scoped to Data Studio model runs only. The broader job scheduler is a future platform consideration.

## 2. Definitions

See the shared [Definitions & Terms glossary](https://floqast.atlassian.net/wiki/spaces/Data/pages/4464869099).

Key terms for this PRD:

* **Model run** — A single execution of a Data Studio model, during which all configured transformations and joins are applied to the current state of the source datasets and output is written downstream.
* **Schedule** — A recurring configuration that defines when a model run is triggered automatically (e.g., daily at 5:00 AM UTC, or on Workday 1 of each month).
* **Time-based schedule** — A schedule defined by a fixed clock interval (e.g., hourly, daily at 5:00 AM UTC).
* **Accounting-aware schedule** — A schedule defined relative to the accounting calendar rather than a fixed clock time (e.g., Workday 1, End of Month, T-2 before close). These schedules require FloQast to resolve the actual run date using the customer's configured business calendar.
* **Workday N** — The Nth business day of the accounting period, as defined by the customer's business calendar (excluding weekends and holidays).
* **Close-relative day** — A run date expressed relative to the close date (e.g., T-2 = two workdays before close, T+1 = one workday after close).
* **Skipped execution** — A scheduled run that was not executed because the calculated run date fell on a company or regional holiday. The skip is logged and the admin is notified.
* **Run history** — A log of past model executions for a given model, including timestamp, duration, status (including skipped), and error detail.
* **Connector sync** — The process by which raw data is pulled from a source system (e.g., via Pull API or Fivetran). Defined in Pull API Support. Connector sync schedules are configured in the connector setup flow, not here.

## 3. Why This Is Important

Currently, Data Studio models do not run on a schedule — execution must be triggered manually. This means:

* Customers cannot rely on data being fresh at a predictable time each day (e.g., before close begins in the morning).
* Time-based scheduling alone (e.g., "run daily at 6am") doesn't serve accounting workflows — accountants think in workdays, close deadlines, and business calendars, not UTC timestamps.
* FloQast cannot meet the data freshness expectations implied by selling Data Studio as a production-grade platform.
* There is no audit trail for when or why a scheduled job configuration was changed, which is required for SOC 1 compliance (control 6.18).

Scheduling is a prerequisite for Data Studio Beta launch. Without it, every data refresh requires manual intervention, which is not viable for live customer use.

### Commercial Urgency — EMEA Pipeline

In a March 2026 conversation with Josh Lewis (Senior Sales Manager, EMEA) and John Phillips (GM, EMEA), Steve Raedar surfaced a concrete, time-bound commercial requirement that scheduling directly addresses:

**Enemotics deal (Germany, \~€500K ARR):** The prospect has issued a formal commitment requirement for "the ability to call SAP from the application, trigger a job, run a report" — needed by **H2 2027**. This is a written blocker to close the deal.

Beyond Enemotics, Josh Lewis framed scheduling's broader sales impact:

> _"It takes a ton of friction out for my sales team — faster sales, not getting DQ'd, not pulled into escalations."_

EMEA prospects are frequently evaluating FloQast against alternatives that already have automated data collection. Without scheduling, deals either require extended evaluation periods, go to escalation, or are lost outright. Scheduling removes that objection class entirely.

The broader market framing: **45% of accountant time is spent on data preparation.** Scheduling automates the data collection layer — not just saving time, but eliminating a class of errors that come from stale or mistimed data entering the close process.

## 4. Key Benefits

* Admins can configure a model to run automatically on a recurring schedule, eliminating manual intervention for routine data refreshes.
* **Accounting-aware scheduling** lets admins define schedules in terms accounting teams understand — Workday 1, End of Month, T-2 before close — rather than requiring them to translate business deadlines into UTC timestamps.
* Holiday and business calendar support means models automatically skip or defer runs on non-business days, without manual intervention.
* Skipped executions are logged and admins are notified, so no run silently disappears.
* The job monitoring dashboard gives admins a real-time view of upcoming, running, completed, and failed jobs across all scheduled models — a single place to assess pipeline health.
* Schedule configuration is informed by connector sync timing — the UI surfaces the relevant connector sync schedule so admins can set an appropriate model run time with confidence.
* API and Fivetran connections default to a 24-hour sync cadence out of the box — no configuration required to get a baseline refresh cycle.
* Pausing a schedule (e.g., during year-end freeze or a data migration) is a self-service action that does not require engineering involvement.
* All changes to production schedules are logged with full before/after state and user attribution, meeting SOC 1 control 6.18 requirements.

## 7. Assumptions

* Model runs are stateless with respect to scheduling — each run reads from the current state of source datasets at execution time. There is no incremental logic within the model run itself (that belongs to the connector sync layer).
* All scheduled times are configured and displayed in UTC for time-based schedules in V1. Accounting-aware schedules are resolved by date (workday/close-relative), not a specific time of day — a default run time (e.g., 2:00 AM UTC) is applied unless the admin specifies otherwise. Timezone configuration for clock-based times is deferred (see OQ-1).
* FloQast holiday calendar support uses the customer's existing business calendar configuration. The specific source of truth for the business calendar (whether it lives in FloQast today, or needs to be configured as part of this feature) is an open question — see OQ-7.
* Connector sync scheduling (when raw data is pulled) is configured separately in the connector setup flow. The model scheduling UI surfaces the connector's configured sync schedule as read-only reference to help admins set an appropriate model run time.
* Only admins can create, edit, pause, resume, or delete schedules. Non-admin users have view-only access to schedule status and run history.
* SOC 1 6.18 applies to all changes to scheduled job configurations in production environments, including: frequency changes, trigger type changes, time changes, pausing, and unpausing. New schedule creation, deletion, and manual overrides are also logged per SOC 1 6.8 (covered in Logging & Audit).
* Default sync frequency for API and Fivetran connections is once every 24 hours; this is fixed in v1 and not configurable per connection.

## 9. Scope

**In Scope:**

* Default sync frequency for API and Fivetran connections: once every 24 hours (fixed in v1, not configurable per connection)
* Time-based recurring schedule configuration for individual Data Studio models (hourly, daily, weekly, custom interval)
* Accounting-aware schedule types: Workday N, End of Month, close-relative days (T-2, T+1, etc.)
* Holiday calendar integration: company-specific and region-specific calendars
* Skipped execution handling: log, notify admin, do not silently drop
* Job monitoring dashboard: upcoming, running, completed, and failed jobs across all scheduled models
* Model run history per model (last 30 days by default, exportable with custom date range)
* Pause and resume a schedule
* Edit and delete a schedule
* View-only access to schedule status and run history for non-admin users
* Display of connector sync schedule as reference context when configuring model run time
* SOC 1 6.18 audit log integration for all schedule config changes and manual overrides in production (depends on Logging & Audit PRD)

**Out of Scope:**

* Configurable sync frequency per connection (v1 fixed at 24 hours; flexibility is a future iteration)
* Trigger-based scheduling (model runs automatically when a connector sync completes) — deferred to Phase 2
* On-demand / manual run triggers — covered in On-demand Refresh PRD
* Cross-model scheduling dependencies (Model A waits for Model B to complete before running)
* Sub-hourly scheduling — minimum frequency is hourly for V1
* Per-customer timezone display for clock-based schedules — UTC only for V1 (see OQ-1)
* Internal FQ engineering alerting on scheduled run failures — covered in Logging & Audit PRD
* Customer-facing email/in-app notifications on scheduled run failures — covered in Notifications PRD
* Scheduling for other FloQast job types (AI Matching, Apply All Rules, Reconciliations, Variance Analysis)

### SCHED-0 — Default 24-hour sync frequency for API and Fivetran connections

**User Story:** As an admin, I want my API and Fivetran connections to automatically sync data every 24 hours so that my models stay current without any manual configuration of a schedule.

**Importance:** Must Have

**Details:**

* When an API or Fivetran connection is configured and saved, a default sync frequency of once every 24 hours is applied automatically — no additional setup required.
* This fires a data run for all published models using that connection every 24 hours.
* Admins can see the sync frequency in connection settings but cannot change it in v1.
* Additional frequency flexibility (e.g., hourly, custom intervals) is explicitly deferred to a future iteration.

**Acceptance Criteria:**

_Given_ I configure an API or Fivetran connection in Data Studio,
_When_ the connection is saved,
_Then_ a default sync frequency of once every 24 hours is automatically applied.

_Given_ a connection has a 24-hour sync frequency,
_When_ 24 hours have elapsed since the last sync,
_Then_ a data run is triggered automatically for all published models using that connection.

_Given_ I view a connection's settings,
_When_ I look at the sync frequency,
_Then_ I see "Every 24 hours" displayed and I cannot modify it in v1.

### SCHED-1 — Configure a time-based recurring schedule for a model

**User Story:** As an admin, I want to configure a time-based recurring schedule for a model so that it runs automatically at a predictable clock time without manual intervention.

**Importance:** Must Have

**Details:**

* Schedule is configured from the model detail view (not during model creation).
* Required fields: frequency (hourly, every 2 hours, every 4 hours, every 8 hours, every 12 hours, daily, weekly, custom) and time of day (UTC).
* Optional: start date (defaults to today).
* The UI surfaces the connector sync schedule(s) feeding this model as read-only reference context, so the admin can set an appropriate buffer after the sync completes. See [Pull API Support REQ-17 and REQ-18](https://floqast.atlassian.net/wiki/spaces/Data/pages/4491214866) for connector sync schedule definition.
* A model can have only one active schedule at a time.
* Weekly scheduling requires day-of-week selection in addition to time-of-day.
* Only admins can create or edit schedules. Non-admin users can view schedule status and run history but cannot modify the schedule.

**Acceptance Criteria:**

_Given_ an admin is on the model detail view for a model with no schedule configured,
_When_ they click "Add schedule" and select "Time-based",
_Then_ a schedule configuration panel opens showing: frequency selector, time-of-day picker (UTC), start date field (defaulting to today), and a read-only display of the connector sync schedule(s) for this model's source datasets.

_Given_ an admin has selected a frequency and time and clicked "Save schedule",
_When_ the save is confirmed,
_Then_ the schedule is saved, the next run time is calculated and displayed on the model detail view, and a creation event is written to the audit log per Logging & Audit PRD.

_Given_ a non-admin user views a model with an active schedule,
_When_ they view the schedule section,
_Then_ the schedule configuration is visible in read-only mode with no edit, pause, or remove actions shown.

_Given_ an admin attempts to save a schedule without selecting a frequency or time,
_When_ they click "Save",
_Then_ an inline validation error is displayed on the missing field(s) and the schedule is not saved.

### SCHED-2 — Configure an accounting-aware schedule for a model

**User Story:** As an admin, I want to schedule a model to run on accounting-calendar-relative dates — like Workday 1 or T-2 before close — so that data is ready at the right point in the accounting cycle without me having to calculate the exact calendar date each period.

**Importance:** Must Have

**Details:**

* Accounting-aware schedules are a separate schedule type from time-based schedules. The admin selects the type first, then configures the trigger.
* Supported accounting-aware trigger types for V1:

    * **Workday N** — Run on the Nth business day of the accounting period (e.g., Workday 1 = first business day after period close). Admin specifies N.
    * **End of Month** — Run on the last business day of the month, as defined by the customer's business calendar.
    * **Close-relative (T-N / T+N)** — Run N workdays before or after the close date for the period. Admin specifies the offset (e.g., T-2, T+1).

* FloQast resolves the actual run date each period using the customer's configured business calendar (company-specific and region-specific calendars supported).
* A default run time (e.g., 2:00 AM UTC) is applied to accounting-aware schedules. Admins can optionally specify a different time of day.
* Only admins can create or edit accounting-aware schedules.

**Notes:** The specific source of the business calendar is an open question — see OQ-7. The engineering feasibility of close-relative scheduling (T-N/T+N) depends on whether the close date is a known data point per customer per period — see OQ-8.

**Acceptance Criteria:**

_Given_ an admin selects "Accounting-aware" as the schedule type,
_When_ the configuration panel opens,
_Then_ the admin sees: a trigger type selector (Workday N / End of Month / Close-relative), fields specific to the selected type, an optional time-of-day picker, and a reference display showing the customer's configured business calendar.

_Given_ an admin selects "Workday N" and enters N = 1,
_When_ the schedule is saved,
_Then_ FloQast resolves the run date each period as the first business day of the period using the customer's business calendar, excluding weekends and configured holidays.

_Given_ an admin selects "Close-relative" and enters T-2,
_When_ the schedule is saved,
_Then_ FloQast resolves the run date each period as two business days before the configured close date.

_Given_ the resolved run date falls on a configured holiday,
_When_ FloQast calculates the next execution,
_Then_ the run is skipped per SCHED-6 (logged, admin notified, no silent drop).

### SCHED-3 — Job monitoring dashboard: view all scheduled jobs by status

**User Story:** As an admin, I want a single view showing the status of all scheduled model runs — upcoming, running, completed, and failed — so I can quickly confirm pipeline health before the finance team starts work.

**Importance:** Must Have

**Details:**

* The job monitoring dashboard is a cross-model view (not per-model), accessible from Data Studio navigation.
* Status categories: **Upcoming**, **Running**, **Completed** (last 24 hours), **Failed** (last 24 hours).
* Skipped runs (holiday/calendar conflict) are shown as a distinct status — not conflated with failures.
* Admins can click into any run to view full run detail.
* Default lookback for completed/failed: last 24 hours. Configurable date range for historical review.

**Acceptance Criteria:**

_Given_ an admin opens the job monitoring dashboard,
_When_ the page loads,
_Then_ they see four distinct sections: Upcoming, Running, Completed (last 24 hours), and Failed (last 24 hours), each populated with the relevant scheduled model runs.

_Given_ a model run has failed,
_When_ the admin views the Failed section,
_Then_ the failed run row shows: model name, scheduled run time, actual start time, status "Failed", and a brief error summary. Clicking the row opens the full run detail.

_Given_ a run was skipped due to a holiday,
_When_ the admin views the dashboard,
_Then_ the skipped run appears with a "Skipped — holiday" status, not as a failure.

_Given_ a non-admin user opens the dashboard,
_When_ the page loads,
_Then_ they see the same four status sections but only for models they have access to. No schedule management actions are shown.

### SCHED-4 — Edit or remove a model schedule

**User Story:** As an admin, I want to edit or remove a model's schedule so that I can adjust run timing when connector sync windows change, or stop runs permanently when a model is decommissioned.

**Importance:** Must Have

**Details:**

* Edit: opens the schedule configuration panel with current values pre-populated; all fields are editable.
* Delete: requires a confirmation prompt; is permanent; stops all future runs and logs the deletion.
* In production environments, edits must be logged per SCHED-7 (SOC 1 6.18).

**Acceptance Criteria:**

_Given_ an admin clicks "Edit schedule" on a model with an active schedule,
_When_ the panel opens,
_Then_ all current schedule values are pre-populated and editable, including the schedule type.

_Given_ an admin saves an edited schedule,
_When_ the save is confirmed,
_Then_ the updated schedule is applied, the next run time is recalculated, and the change is written to the audit log with before/after state.

_Given_ an admin clicks "Remove schedule" and confirms the prompt,
_When_ the deletion is processed,
_Then_ the schedule is removed, no future runs are queued, and a deletion event is written to the audit log.

### SCHED-5 — Pause and resume a model schedule

**User Story:** As an admin, I want to temporarily pause a model's schedule without deleting it, so that I can prevent runs during data adjustments or maintenance windows and easily resume afterward.

**Importance:** Must Have

**Acceptance Criteria:**

_Given_ an admin clicks "Pause schedule" and confirms,
_When_ the action is processed,
_Then_ the schedule status changes to "Paused", no future runs are queued, and the pause event is logged with user and timestamp.

_Given_ an admin clicks "Resume schedule" on a paused model and confirms,
_When_ the resume is processed,
_Then_ the schedule status changes to "Active", the next run is calculated forward from current time (no backfill of missed runs), and the resume event is logged.

_Given_ a model's schedule is paused,
_When_ an admin views the model detail,
_Then_ the status clearly shows "Paused" and the "next run" field is empty.

### SCHED-6 — Skipped execution: holiday and calendar conflict handling

**User Story:** As an admin, I want to know when a scheduled run was skipped because it fell on a holiday or non-business day, so I'm not left wondering whether a model ran or silently failed.

**Importance:** Must Have

**Notes:** Whether "skip and notify" is the correct behavior for all calendar conflicts, or whether the system should "run on next eligible workday" instead, is an open question — see OQ-9.

**Acceptance Criteria:**

_Given_ a model's accounting-aware schedule resolves to a date that is a configured company holiday,
_When_ the scheduled run time arrives,
_Then_ the run is not executed; a "Skipped — holiday" log entry is created with: model name, intended run date, holiday name, and calendar source; and the admin is notified per the Notifications PRD.

_Given_ a run has been skipped,
_When_ the admin views the run history or job monitoring dashboard,
_Then_ the skipped run appears with status "Skipped — holiday" and is visually distinct from "Failed" runs.

_Given_ a run was skipped and the next scheduled date is not a holiday,
_When_ the next scheduled run time arrives,
_Then_ the run executes normally with no admin intervention required.

### SCHED-7 — SOC 1 6.18: Audit log for production schedule changes and manual overrides

**User Story:** As a compliance officer, I need all changes to scheduled job configurations in production — including manual overrides — to be logged with full before/after state and user attribution so that FloQast meets SOC 1 control 6.18.

**Importance:** Must Have

**Details:**

* Applies to all schedule events in production: creation, edits, pause, resume, deletion, and manual overrides.
* Required fields per log entry: user (name + ID), timestamp, action type, before state, after state.
* All log entries surfaced in the audit log defined in the Logging & Audit PRD (LOG-1).

**Acceptance Criteria:**

_Given_ an admin edits a model schedule in production,
_When_ the change is saved,
_Then_ the following is written to the audit log: user (name + ID), timestamp, action type ("Schedule edited"), before state, and after state.

_Given_ an admin pauses or resumes a schedule in production,
_When_ the action is confirmed,
_Then_ a log entry is created with: user, timestamp, action type ("Schedule paused" or "Schedule resumed"), and the schedule configuration at time of action.

_Given_ an admin triggers a manual run outside the schedule (via On-demand Refresh),
_When_ the run is initiated,
_Then_ a log entry is created with: user, timestamp, action type ("Manual override"), and model name.

_Given_ a compliance reviewer queries the audit log filtered to schedule events,
_When_ the results are returned,
_Then_ all schedule creation, edit, pause, resume, deletion, and manual override events are present, each with full before/after state and user attribution.

## 11. User Flow Reference

Schedule configuration sits within the model detail view, after model creation and activation. It is not part of the model creation wizard.

* Model detail view → Schedule section → "Add schedule" → select schedule type (time-based or accounting-aware) → configure → Save
* Editing: model detail → Schedule → "Edit" → configuration panel → Save (with SOC 1 audit log in production)
* Run history: model detail → Run History section (per-model view)
* Cross-model status: Data Studio navigation → Job Dashboard (upcoming, running, completed, failed)

## 14. Future Considerations

* **Configurable connection sync frequency:** v1 fixes API and Fivetran connections at 24 hours. Future iteration allows per-connection custom intervals.
* **Trigger-based scheduling:** Model run triggered automatically when a connector sync completes, rather than at a fixed time. Eliminates the need for admins to manually coordinate schedules. Deferred to Phase 2.
* **Cross-model scheduling dependencies:** Model B waits for Model A to complete before starting its run. Needed for multi-model pipelines.
* **Timezone display:** Show schedule times in the customer's local timezone rather than UTC only.
* **Sub-hourly scheduling:** Minimum frequency of hourly for V1; sub-hourly may be needed for high-frequency connector customers.
* **Formal two-party approval for SOC 1 6.18:** If self-attestation is insufficient (see OQ-2), a second-approver flow would be a follow-on release.
* **Cross-product job scheduler:** Tim's functional requirements describe a broader scheduling framework covering AI Matching, Apply All Rules, Reconciliations, and other FloQast job types. Data Studio scheduling should be designed with this future platform in mind.
* **"Skip to next workday" vs. "skip and wait":** Option for admins to configure whether a holiday-conflicted run should fire on the next eligible workday. Not in scope for V1.
* **Event-based / SAP triggers:** The Enemotics commitment may require event-based triggering where SAP signals job completion. Deferred pending clarification on whether time-based scheduling satisfies their requirement.
