## 🎯 Objective

Enable downstream products — starting with Transform — to respond intelligently to changes in Data Studio models and data, without polling or custom integration work.

Today, there is no mechanism for Transform (or any other FloQast product) to know when a DS model's data has refreshed, when its schema has changed, or when the model has been archived. Subscribers either run against potentially stale data or build one-off integrations that are brittle and hard to maintain.

This PRD defines a standard event contract that Data Studio publishes through FloQast's Scheduling Service. Any downstream product can opt in by registering a dependency. The contract is designed to be general-purpose — not Transform-specific — so that Report Builder, analytics surfaces, and future consumers can adopt it without custom work.

---

## 🔤 Definitions

| Term | Meaning |
| --- | --- |
| **Subscriber** | A downstream product or system that consumes DS events (e.g., Transform, Report Builder) |
| **Event contract** | The agreed-upon structure and semantics of events DS publishes — field names, types, and guaranteed presence |
| **Canonical model** | A FloQast-standardized schema (e.g., Bank Transactions) with a known field set |
| **Custom model** | A user-defined schema; field definitions vary but are always known at the time the model is published |
| **TLC (Top Level Client)** | The primary tenant partition key; always present to prevent data leakage between tenants |
| **Dependency registration** | A subscriber's declaration of which model, source, entities, and field filters it depends on |
| **Mapping rule** | The transformation expression applied to a source field to produce a standardized output field |
| **Scheduling Service** | FloQast's central event bus for cross-product notifications; owned by SOMIA (core platform) |
| **Run ID** | A unique identifier for a single data processing job; correlates DATA_PROCESSING, DATA_AVAILABLE, and DATA_FAILED events |

---

## 🏅 Why This Is Important

Without a standard event contract:

* **Transform blocks run against stale data.** There is no signal that a data run is in progress, so agents execute against whatever was last available — potentially yesterday's numbers.

* **Breaking changes are invisible.** When a model's mapping rules or field definitions change, downstream blocks have no way to know until they fail at runtime.

* **Every integration is custom.** Each new subscriber (Report Builder, analytics) builds its own polling or coupling strategy, creating maintenance burden and inconsistent behavior.

A shared event contract solves all three problems in a single implementation. It also unlocks future capabilities — like surfacing active dependencies before a destructive model change — that would be impossible without structured subscriber data.

## 🗝️ Key Examples

**Example 1 — Data run completes, Transform agent fires**\
An admin's daily sync completes for the Bank Transactions model. DS emits `DATA_AVAILABLE`. Transform receives the event and triggers all blocks registered against that model's `run_id`. Users see fresh results in their Transform output without manual intervention.

**Example 2 — Mapping rule changes, Transform block warned**\
A DS admin publishes a new version of Bank Transactions that changes the `transaction_type` mapping rule. DS emits `MODEL_VERSION_PUBLISHED` with a `mapping_rule_changes` diff. Transform matches the affected field against registered blocks and surfaces: "A mapping rule used by this block has changed — review before running."

**Example 3 — Model archived, dependent block flagged**\
A DS admin archives a model. DS emits `MODEL_ARCHIVED`. Transform receives the event and marks any block depending on that model with a warning state, preventing silent failure on the next scheduled run.

**Example 4 — New subsidiary added, entity scope expands**\
An entity is added to a model's scope. DS emits `MODEL_ENTITIES_UPDATED`. Subscribers with entity-scoped registrations receive the update and can decide whether to expand their block's entity scope or keep it narrow.

---

## 💡 Key Benefits

* **Proactive, not reactive** — subscribers are notified of changes before they cause silent failures

* **General-purpose** — one contract serves Transform, Report Builder, and any future consumer

* **Change-diff aware** — mapping rule changes include before/after detail, enabling targeted warnings rather than generic "something changed" alerts

* **Audit-ready** — `MODEL_VERSION_PUBLISHED` events with `mapping_rule_changes` double as the data source for the DS Change Log view

* **Tenant-safe** — `tlc_id` is required on every event; environment scoping prevents cross-environment event handling

## 🤔 Assumptions

**Established**

* FloQast's Scheduling Service (owned by SOMIA) is the event bus; DS publishes to it and subscribers consume from it

* TLC is always present on every event — this is non-negotiable for tenant safety

* IDs are the stable contract; names travel in the payload for display purposes only and are never used as keys

* `entities` is nullable — some models (particularly custom) may not be scoped to specific entities; when null, the event is TLC-scoped only

* Field definitions are always available when a model is published; custom model fields are not "unknown" at publish time

* `MODEL_VERSION_PUBLISHED` mapping rule changes are additive to the payload — versioning is never destructive (no `fields_removed` in v1)

* Event names, field names, and structure in the schema reference are a starting point — engineering should rename or restructure as needed during implementation

**Open Items to Confirm**

* Should `DATA_FAILED` be its own event type (cleaner subscriber contracts) or a status update on the `DATA_PROCESSING` event? Recommendation: own event type, but deferring to engineering

* How does a subscriber deregister when a block is deleted? Needs a deregistration mechanism or TTL — otherwise registrations go stale

* Who on the DS side owns the Scheduling Service integration? John pointed to SOMIA on the Transform side; DS counterpart TBD

* Should `fields_removed` be enforced at the API level (DS rejects destructive schema changes) or remain a convention?

* How does a new downstream product opt in to receiving DS events? The subscriber opt-in mechanism via the Scheduling Service is not yet defined

## 🗺️ Scope

### 🚗 In Scope

* Base event envelope (event_id, event_type, occurred_at, tlc_id, environment, publisher, model, source, entities)

* Eight event types: MODEL_PUBLISHED, DATA_PROCESSING, DATA_AVAILABLE, DATA_FAILED, MODEL_VERSION_PUBLISHED, MODEL_ENTITIES_UPDATED, MODEL_ARCHIVED, MODEL_DELETED

* Mapping rule change diff in MODEL_VERSION_PUBLISHED (field-level before/after, powering the Change Log)

* Dependency registration endpoint (subscriber, subscriber_ref, model_id, source_id, entity_ids, filters)

* Two dependency registration implementation options for engineering to evaluate: manifest-based (Option A) vs. event-driven (Option B)

* Transform as the first subscriber

### 🚦 Out of Scope

* DS UI surfacing active subscribers before destructive actions (future)

* Bidirectional contract (Transform publishing usage signal back to DS) — proposed, deferred to future iteration

* Estimated completion time or run metadata in DATA_PROCESSING (future)

* Scheduled run metadata in events (future)

* Email / Slack / SMS notifications to end users — event contract is system-to-system only; user-facing notifications are a separate surface

* Deregistration / TTL mechanism — dependency cleanup TBD with engineering

### EC1 — Data Processing Started

**User Story:** As a Transform block, I receive a signal when a DS data run starts so I can pause or queue until data is ready.

**Importance:** High

**Details:** DS emits `DATA_PROCESSING` as soon as a data run begins. The event includes a `run_id` that correlates with the subsequent `DATA_AVAILABLE` or `DATA_FAILED` event. All base envelope fields are present.

**Acceptance Criteria:**

**AC-EC1-01 — Event emitted on run start**

```
Given a data run is triggered for a published model (scheduled or on-demand)
When the run begins processing
Then DS emits a DATA_PROCESSING event containing run_id and all base envelope fields
```

**AC-EC1-02 — run_id is unique per run**

```
Given multiple data runs for the same model
When each run starts
Then each DATA_PROCESSING event carries a distinct run_id
```

---

### EC2 — Data Available

**User Story:** As a Transform block, I receive a signal when a DS data run completes successfully so I can execute against fresh data.

**Importance:** High

**Details:** DS emits `DATA_AVAILABLE` when a run completes with no errors. The event includes the `run_id` from the preceding `DATA_PROCESSING` event and `rows_processed` for observability.

**Acceptance Criteria:**

**AC-EC2-01 — Event emitted on successful run completion**

```
Given a data run completes successfully
When all data is processed and written
Then DS emits a DATA_AVAILABLE event containing run_id and rows_processed
```

**AC-EC2-02 — run_id matches preceding DATA_PROCESSING**

```
Given a DATA_PROCESSING event was emitted for run_id X
When the run completes successfully
Then the DATA_AVAILABLE event for that run carries the same run_id X
```

---

### EC3 — Data Failed

**User Story:** As a Transform block, I receive a signal when a DS data run fails — with enough detail to show the user a meaningful message — so I do not execute against stale data.

**Importance:** High

**Details:** DS emits `DATA_FAILED` when a run cannot complete. The event includes `error_type` (`processing_error | connector_unavailable | timeout`) so subscribers can tailor the user-facing message, and `error_message` for human-readable context.

**Acceptance Criteria:**

**AC-EC3-01 — Event emitted on run failure**

```
Given a data run fails for any reason
When the failure is detected
Then DS emits a DATA_FAILED event containing run_id, error_type, and error_message
```

**AC-EC3-02 — error_type is one of the defined values**

```
Given a DATA_FAILED event is emitted
When a subscriber reads error_type
Then the value is one of: processing_error, connector_unavailable, timeout
```

**AC-EC3-03 — DATA_FAILED does not follow DATA_AVAILABLE for the same run_id**

```
Given a run_id that has already produced DATA_AVAILABLE
When DS evaluates the run state
Then DS does not emit DATA_FAILED for that same run_id
```

---

### EC4 — Model Published

**User Story:** As a downstream subscriber, I receive a signal when a new DS model becomes available — with its field definitions — so I can present it to users without making additional API calls.

**Importance:** High

**Details:** DS emits `MODEL_PUBLISHED` when a model is first published and available for subscription. The event includes `version` (starting at 1.0.0) and `field_definitions` with the full field set. This is especially important for custom models, where subscribers cannot assume a known schema.

**Acceptance Criteria:**

**AC-EC4-01 — Event emitted when a model is first published**

```
Given a model (canonical or custom) transitions from Draft to Published state
When the publish is confirmed
Then DS emits a MODEL_PUBLISHED event containing version and field_definitions
```

**AC-EC4-02 — field_definitions includes all fields at publish time**

```
Given a model is published
When the MODEL_PUBLISHED event is received
Then field_definitions.fields contains every field available on the model at that point in time
```

---

### EC5 — Model Version Published

**User Story:** As a Transform block, I receive a detailed diff when a DS model's mapping rules or field definitions change so I can warn the user before a breaking change causes a silent failure.

**Importance:** High

**Details:** DS emits `MODEL_VERSION_PUBLISHED` whenever a new version of an existing model is published. The event includes previous and current version strings, a `mapping_rule_changes` array with field-level before/after rule diffs, and a `field_changes` summary. `mapping_rule_changes` also powers the DS Change Log view.

**Acceptance Criteria:**

**AC-EC5-01 — Event emitted on new version publish**

```
Given an existing published model has a new version published
When the new version is confirmed
Then DS emits a MODEL_VERSION_PUBLISHED event with version.previous and version.current populated
```

**AC-EC5-02 — Mapping rule changes include field-level diff**

```
Given a new version changes one or more mapping rules
When the MODEL_VERSION_PUBLISHED event is emitted
Then mapping_rule_changes contains one entry per changed field with field_id, field_name, change_type, previous_rule, and current_rule
```

**AC-EC5-03 — mapping_rules_changed flag is accurate**

```
Given a new version is published with no mapping rule changes
When the MODEL_VERSION_PUBLISHED event is emitted
Then mapping_rules_changed is false and mapping_rule_changes is an empty array
```

**AC-EC5-04 — fields_added is populated when new fields are added**

```
Given a new version adds one or more fields
When the MODEL_VERSION_PUBLISHED event is emitted
Then field_changes.fields_added contains each new field's id and name
```

### EC6 — Model Entities Updated

**User Story:** As a subscriber with entity-scoped registrations, I receive a signal when entities are added to or removed from a model so I can decide whether to expand or maintain my coverage.

**Importance:** Medium

**Details:** DS emits `MODEL_ENTITIES_UPDATED` when the set of entities mapped to a model changes. The event includes arrays of entities added and removed, each with id and name.

**Acceptance Criteria:**

**AC-EC6-01 — Event emitted when entity scope changes**

```
Given an admin adds or removes entities from a model's mapping
When the change is saved
Then DS emits a MODEL_ENTITIES_UPDATED event with entities_added and entities_removed arrays populated
```

**AC-EC6-02 — Arrays are empty (not null) when there are no additions or removals**

```
Given only additions occur (no removals)
When the MODEL_ENTITIES_UPDATED event is emitted
Then entities_removed is an empty array, not null
```

### EC9 — Dependency Registration

**User Story:** As a subscriber, I can register which model, source, entities, and field filters I depend on so that DS can surface targeted warnings when relevant changes occur.

**Importance:** High

**Details:** Subscribers POST a dependency registration to DS when a block or configuration is saved. Registration includes subscriber identity, subscriber_ref (the consuming artifact's ID), model_id, source_id, optional entity_ids, and optional field filters. DS stores this for future dependency-surface features. The specific registration mechanism (manifest-based vs. event-driven) is an engineering decision; both options are presented in the schema reference.

**Acceptance Criteria:**

**AC-EC9-01 — Registration is accepted with required fields**

```
Given a subscriber POSTs a dependency registration with subscriber, model_id, source_id, and registered_at
When DS receives the registration
Then DS stores the registration and returns a success response
```

**AC-EC9-02 — entity_ids and filters are optional**

```
Given a subscriber POSTs a registration without entity_ids or filters
When DS receives the registration
Then DS accepts and stores the registration with entity_ids as null and filters as an empty array
```

**AC-EC9-03 — MODEL_VERSION_PUBLISHED warnings are targeted by registration**

```
Given a subscriber has registered with a specific field filter (e.g. transaction_type = ACH)
When DS emits MODEL_VERSION_PUBLISHED with a mapping rule change on transaction_type
Then DS identifies this subscriber as affected and includes it in the targeted notification
```
