## 🎯 Objective

This PRD defines the behavior and requirements for editing source data files and model definitions within FloQast's Data Platform. Specifically, it covers the lifecycle of modifying a linked source file, applying those changes to active models with an effective date, surfacing breaking changes, and allowing models to exist in a draft state without any source data attached. It does not cover the initial setup of file-to-model linking, ERP integration connection management, or downstream product behaviors triggered by model output changes.

The primary users are FloQast implementors and platform admins who configure and maintain data models on behalf of customers. These users manage the ongoing relationship between source data (files delivered via sFTP or other ingestion mechanisms) and the model definitions built on top of them.

Today, if a source file is linked to an active model, that file is locked from modification. At the same time, the model cannot be saved if its linked file is not providing valid data. This creates a deadlock: the user cannot fix the data without breaking the model, and cannot fix the model without valid data. The only escape is deleting the model entirely and starting over, which is disruptive and error-prone.

This PRD enables implementors to edit source files in place, apply those changes with an effective date to preserve historical integrity, and receive clear, actionable feedback when a change would break a dependent model. It also allows models to be staged in a draft state without any source data, giving implementors flexibility during setup and iteration.

## 💡 Key Benefits

* **Unblocks the edit loop:** Implementors can modify source files without needing to delete and recreate models, reducing setup time and support burden.

* **Historical integrity via effective dating:** Changes to in-use files are applied from a specified date forward, enabling accurate rehydration without corrupting prior-period data.

* **Clear breaking change communication:** When a file edit would break an existing model, the user receives an explicit error identifying which models are affected before any change is committed.

* **Controlled error state:** Affected models are placed in a defined error state, making it easy to identify and prioritize remediation without silently corrupting model outputs.

* **Draft models without data:** Models can exist and be configured in draft without a linked source, supporting more flexible and iterative implementation workflows.

* **Reduced implementation risk:** Clear guardrails reduce the chance of accidental data corruption during active close periods.

* **Shorter time-to-resolution:** Implementors can resolve data quality issues directly rather than escalating to engineering or support to manually unlock records.

## ✅ Use Cases

**A FloQast implementor corrects a non-breaking file change.** A source file linked to an active model has an extra column added that does not conflict with any existing model field mappings. The implementor edits the file, sets an effective date, and saves. The system accepts the change, marks rehydration as needed from that date, and the model continues operating normally with updated data going forward.

**A FloQast implementor attempts a breaking file change.** An implementor renames a column in a source file that a model's field mappings depend on. When they attempt to save, the system surfaces a breaking change error listing each affected model and the specific field mappings that would be invalidated. No changes are committed until the implementor acknowledges and resolves the conflict.

**A FloQast implementor resolves a broken model after a breaking change.** After a breaking change is applied or detected, one or more models are placed in an error state. The implementor navigates to each affected model, updates the field mappings or configuration to reflect the new file structure, and saves. The model exits the error state and rehydration is triggered from the effective date of the file change.

**A FloQast admin removes a source file from a model.** A customer's data source changes and the current file is no longer valid. The admin removes the file from the model, placing the model in draft state. The model retains its configuration and field mapping definitions but produces no output until a new source is linked.

**A FloQast implementor stages a new model without source data.** During initial implementation, an implementor creates a model definition and configures all field mappings before the customer's file delivery is set up. The model is saved in draft state without any linked source. Once the file arrives and is linked, the model can be activated and data processed from the effective date.

**A FloQast implementor edits a file in use during an active close period.** A source file is actively feeding a model in use for the current period close. The implementor needs to correct erroneous data. They edit the file, set an effective date that falls within the current period, and the system triggers rehydration from that date. The model reflects corrected data without requiring the close to be restarted.

**FloQast (system) detects a structural mismatch after a file update.** A file is updated and upon processing, the system detects that required fields referenced by a dependent model are no longer present. The system automatically transitions the affected model(s) to an error state, logs the mismatch, and surfaces it in the model management UI without requiring a manual re-check by the implementor.

## 🤔 Assumptions

1. "File" refers to source data files ingested via sFTP or equivalent pipeline; the same patterns should apply to API-sourced data but API-specific handling is out of scope for this PRD.

2. Models have a defined set of field mappings that reference named columns or fields from a linked source file — breaking change detection relies on this mapping being machine-readable and stored.

3. "Rehydration" means re-processing model calculations or derivations from a given effective date forward using the updated source data; the rehydration mechanism itself exists or is being built separately.

4. A model in "draft" state does not produce output and is not visible to end users of downstream FloQast products.

5. A model in "error" state retains its last valid output (does not wipe historical data) but halts new processing until the error is resolved.

6. Effective date is required when editing a file that is actively linked to a model; it is not required for files in draft or unlinked state.

7. A single file may be linked to multiple models; a breaking change must surface all affected models, not just the first one encountered.

8. The current lock preventing file edits when linked to an active model is an application-level constraint, not a storage-level constraint, and can be modified.

## ⭐ Milestones

1. **Phase 1: Unlock file editing and effective dating.** Remove the application-level lock that prevents editing a source file linked to an active model. Implement effective date requirement for edits to in-use files. Trigger rehydration from the effective date on save. Implementors can modify non-breaking file changes without deleting models.

2. **Phase 2: Breaking change detection and model error state.** Implement diff-based detection of breaking changes at save time (before commit). Surface a blocking error listing affected models and impacted field mappings. Define and implement the model "error" state — models transition to error on breaking change, halt processing, and are surfaced in the management UI. Implementors can resolve error state by updating model configuration.

3. **Phase 3: Draft model without source data.** Allow models to be created, configured, and saved in draft state without a linked source file. Remove any validation that blocks saving a model definition without data attached. Define the draft-to-active transition behavior when a source is linked.

4. **Phase 4: System-side mismatch detection (post-ingestion).** Implement automated detection of structural mismatches when a file is processed post-update. Automatically place affected models in error state and surface alerts. Covers cases where a file changes upstream without going through the platform edit flow.

## 🎨 User Interaction and Design

### Editing a linked source file

When an implementor opens a source file that is linked to one or more active models, the file detail view is no longer read-only. All editable fields (column definitions, mappings, file format settings) are accessible. There is no lock indicator or disabled state.

When the implementor makes changes and clicks Save, the system runs a pre-commit breaking change check. If no breaking change is detected, a confirmation dialog appears asking the implementor to set an effective date. The dialog shows the default of today's date, a date picker, and a summary of what will be updated. On confirm, the save completes and a rehydration job is enqueued.

### Breaking change error flow

If the pre-commit check detects a breaking change, the Save action does not proceed. Instead, an error state appears inline (or in a modal) reading something like: "This change will break \[N\] model(s). Review the affected models below before continuing." The list shows each model name (linked to the model configuration view) and the specific field(s) that would be invalidated. The implementor can dismiss this view and return to editing, or navigate to the affected models directly to resolve.

### Model error state in the management UI

In the model list view, models in error state display a red or warning-colored status badge. A filter option allows implementors to view only errored models. The error badge includes a short label such as "Source mismatch" or "Configuration error."

When an implementor opens an errored model, a banner at the top of the configuration view explains the error: which file changed, on what date, and which field mappings are no longer valid. The affected mappings are highlighted in the field mapping table. The implementor can update the mappings directly in this view and save to resolve.

### Removing a source file from a model

On the model configuration view, a "Remove source" or "Unlink file" action is available in the source data section. Clicking it opens a confirmation dialog warning the implementor the model will stop producing output and be placed in draft. On confirm, the file is unlinked and the model enters draft state. The model name, field mapping configuration, and history are preserved.

### Draft model setup

When creating a new model, the implementor can complete all configuration steps (name, field mappings, output settings) without being required to link a source file. A "Save as draft" option is always available. The model card in the list view shows a "Draft" status badge. When a source file is later linked and configuration is validated, an "Activate" button becomes available.

### Rehydration status

While a rehydration job is running, the model card and detail view display a status indicator such as "Rehydrating — data current through \[date\]." Once complete, the indicator clears. If rehydration fails, the model surfaces a distinct error state with a message indicating the rehydration failure (separate from a configuration error).

## ⚠️ Out of Scope

* **Rehydration engine implementation:** This PRD assumes rehydration capability exists or is being built under a separate effort. The trigger and status visibility are in scope; the engine itself is not.

* **ERP API source editing:** This PRD focuses on file-based sources (sFTP and similar). API-sourced data has different mutability constraints and will be handled separately.

* **Downstream product behavior on rehydration:** What happens in Close, Reconciliations, or other FloQast products when model output changes as a result of rehydration is out of scope. Downstream impact should be addressed in those products' respective PRDs.

* **File versioning or history:** Full file version history and rollback capability are not covered here. The audit log (Req 15) covers edit tracking only.

* **Customer-facing file editing:** This workflow is for FloQast implementors and admins only. End customers do not have access to source file configuration.

* **Bulk model remediation:** Resolving multiple errored models simultaneously is not in scope for initial release.

* **Permission model changes:** Any changes to role-based access for who can edit files or models are not addressed here.
