# 1. Objective

FloQast is building Data Platform 2.0 as a centralized, ERP-agnostic data layer that will serve all FloQast products — Close Management, Reconciliations, JEM, and Transform — with normalized financial data from a single platform. NetSuite is the largest ERP in FloQast's customer base and the most critical integration to bring onto this platform.

Today, FloQast's NetSuite integration operates outside of Data Platform 2.0 as a legacy SOAP-based direct connection. Customers on NetSuite cannot be onboarded through Data Studio and are served by a separate integration path that creates ongoing operational overhead for Engineering and Customer Success.

This project brings the NetSuite direct API connection into Data Platform 2.0 — enabling new customer self-serve onboarding through Data Studio, providing a structured migration path for all existing NetSuite SOAP customers, and delivering normalized financial data to all downstream app teams.

Success is defined as new NetSuite customers being onboarded through Data Studio without manual Engineering or CS intervention, and all existing NetSuite customers having a clear, low-risk path to the new platform.

Bringing NetSuite onto Data Platform 2.0 also requires transitioning the underlying API protocol from SOAP/SuiteTalk to the NetSuite REST API (v1). This migration is required to continue NetSuite support in the medium term as NetSuite continues to invest in REST and deprioritize SOAP.

# 2. Key Benefits

* New NetSuite customers can be onboarded self-serve through Data Studio — no manual Engineering or CS setup required.

* Existing SOAP customers have a structured, low-risk migration path to the new platform.

* All NetSuite data is normalized, giving app teams (Close, Reconciliations, JEM, Transform) a consistent, ERP-agnostic data feed.

* REST API replaces brittle SOAP/SuiteTalk — standard TBA or OAuth 2.0 auth, SuiteQL for reliable balance queries, JSON over HTTPS instead of XML.

* Platform-native integration means NetSuite customers benefit from all Data Platform 2.0 capabilities as the platform evolves.

* A single integration codebase replaces two separate paths, reducing long-term maintenance burden.

# 3. Use Cases

1. A new NetSuite customer is set up by their CS team, who navigates to Data Studio, selects NetSuite as the ERP source, and completes the connection wizard — entering credentials, selecting subsidiaries, and confirming mapping — in under 30 minutes, without Engineering involvement.

2. A CS team generates a setup link for a customer's IT team, who clicks the link, lands in a pre-populated connection wizard, and completes setup independently.

3. A customer's IT team completes onboarding via the setup link and immediately triggers an on-demand sync to validate that data is flowing into FloQast correctly.

4. A Close Management or Reconciliations user accesses balance data that has been refreshed from NetSuite within the last 5 minutes, with no manual action required.

5. An existing NetSuite SOAP customer is migrated to the new platform during a scheduled migration window; their scheduled sync continues without interruption and their data is validated for parity before cutover.

6. An app team engineer subscribes to the `netsuite.data.available` event and their service receives a notification when new data is ready, without polling the database.

# 4. Success Metrics

* New NetSuite customers onboarded via Data Studio without Engineering intervention (target volume TBD with CS).

* Time-to-connect for a new customer under 30 minutes end-to-end.

* Data latency from NetSuite to CDA under 5 minutes for scheduled syncs.

* Sync success rate of 99%+ under normal NetSuite API availability.

* Zero data loss during SOAP-to-REST migration for all migrated customers.

# 5. Assumptions

* NetSuite customers have or can create TBA or OAuth 2.0 credentials in their NetSuite account.

* Data Platform 2.0 is available and supports the NetSuite account and balance schema required by this integration.

* The existing SOAP integration remains live in parallel throughout the transition period; no hard cutover until all customers are successfully migrated.

* NetSuite REST API (v1) is available on all NetSuite editions used by FloQast customers (Standard, OneWorld, PE).

* SuiteQL is available on all relevant NetSuite editions for balance queries.

* Customers are responsible for configuring the correct roles and permissions in their NetSuite account prior to connection setup.

* Existing SOAP customers will be migrated automatically (opt-out model); customers will not need to take action to initiate migration.

* Historical sync data from the SOAP integration must be preserved through migration; a re-sync will not be acceptable. This will require coordination with application teams.

* Customers may have multiple active Direct API connections per NetSuite account.

* Schema changes required to support NetSuite-specific fields will include standard dimensions at minimum; full scope to be confirmed with the Data Platform team.

# 7. Scope

The following capabilities and data types are in scope for this initiative:

**Connection & Auth**

* Direct API connection creation and management (TBA and OAuth 2.0)

* Multiple active connections per NetSuite account supported

* Credential storage, validation, and lifecycle management

* Setup link generation and auto-connect flow

**Data**

* Chart of Accounts

* GL Balances (via SuiteQL)

* Subsidiaries / Entities

* Currencies and Accounting Periods

**Platform**

* Normalization for all ingested data

* Scheduling (preset frequencies) and on-demand sync

* App-team event notifications (pub/sub)

* Audit logging and sync job observability

* Custom endpoint configuration for non-standard data needs

* Migration path from SOAP integration to new platform

# 8. Requirements

‌

**REQ-01: As a CS team member or customer IT team, I want to create a NetSuite direct API connection in Data Studio so that I can connect a customer's NetSuite account to FloQast without Engineering involvement.**

*Functional spec: The connection wizard collects NetSuite account credentials (TBA or OAuth 2.0), validates them against NetSuite in real time, and creates an active connection on successful validation. Credential storage, validation behavior, edit flow, and error states are defined in Sub-PRD 1: Connection Management.*

‌

**REQ-02: As a CS team member, I want to capture the information from the setup link for a customer so that their IT team can complete the initial connection setup independently.**

*Functional spec: The first FQ user can set up an initial connection to their NetSuite instance using the existing setup link. A successful connection setup in the setup link creates a connector in Data Studio and triggers the setup of a standard NetSuite mapping. An admin user generates a time-limited, JWT-signed setup link scoped to a customer. Auto-connect flow is defined in Sub-PRD 3: Setup Link & Auto-Connect.*

‌

**REQ-03: As a CS team member or customer IT team, I want to select which FQ entities to sync so that only the relevant entities are connected to the data feed.**

*Functional spec: After connection setup, an admin user can assign the relevant FQ entities to the connection. Data stored in the data platform is tagged with the appropriate entities. Selected entities become the active entities for all sync jobs. Entity assignment and change flow are defined in Sub-PRD 2: Entity Management.*

‌

**REQ-04: As a CS team member or customer IT team, I want field mappings to be automatically configured from NetSuite fields to FQ fields so that no manual mapping is required for standard setups.**

*Functional spec: A standard mapping configuration is applied at connection creation, covering all required fields for accounts and balances. Entity-level overrides are supported for non-standard account structures. Mapping logic is defined in Sub-PRD 4: Mapping Configuration.*

‌

**REQ-05: As a CS team member or customer IT team, I want to configure a sync schedule for a connection so that NetSuite data is refreshed automatically at a defined frequency.**

*Functional spec: The connection setup includes a scheduling step with preset frequency options. On-demand sync is also available at any time. Frequency options, timezone handling, missed run behavior, and on-demand API spec are defined in Sub-PRD 5: Scheduling & On-Demand Refresh.*

‌

**REQ-06: As an app team engineer, I want to receive a notification when new NetSuite data is available so that my service can consume updated data without polling.**

*Functional spec: The integration publishes events to a pub/sub topic when sync jobs complete. App teams subscribe to receive data-available and failure notifications. Event types, payload schema, SNS/SQS architecture, and failure notifications are defined in Sub-PRD 6: Notifications & Logging.*

‌

**REQ-07: As a CS team member or Engineering team, I want sync job outcomes and API call history to be logged so that I can diagnose issues and confirm data delivery.**

*Functional spec: All sync jobs produce structured log entries including job ID, connection, entity, status, record counts, and error details. Logs are retained per defined policy and accessible via internal tooling. Log schema and retention policy are defined in Sub-PRD 6: Notifications & Logging.*

‌

**REQ-08: As an Engineering or CS team member, I want to configure additional or non-standard NetSuite endpoints for a connection so that customers with custom record types or RESTlet-based data can be supported.**

*Functional spec: Endpoint configuration supports standard record, SuiteQL, custom record, and RESTlet endpoint types. Each endpoint has its own enable/disable state and failure isolation. Full endpoint model and approval workflow are defined in Sub-PRD 7: Additional Endpoint Configuration.*

‌

**REQ-09: As a CS or Engineering team member, I want existing NetSuite SOAP customers to be migrated to the new Data Platform 2.0 integration so that all NetSuite customers are served from a single platform.**

*Functional spec: A structured migration path allows SOAP customers to be transitioned to the REST-based platform with parallel validation to confirm data parity before cutover. Migration is automatic (opt-out). Historical data is preserved through migration in coordination with application teams. Migration phases, rollback strategy, and SOAP sunset plan are defined in Sub-PRD 8: REST API Transition.*

# 9. User Interaction and Design

The end-to-end flow spans four stages: Connection Setup, Entity & Mapping Configuration, Ongoing Sync, and (for existing customers) Migration.

**Stage 1: Connection Setup**

* User navigates to Data Studio and selects NetSuite as an ERP source, or clicks a CS-generated setup link.

* User selects authentication method (TBA or OAuth 2.0) and enters credentials.

* System validates credentials against NetSuite in real time and surfaces clear error messages on failure.

* On success, the connection is created and the user proceeds to entity selection.

**Stage 2: Entity & Mapping Configuration**

* System retrieves available FQ entities from FQ and presents them for selection.

* User selects one or more entities to include in the sync.

* Standard field mapping is applied automatically; entity-level overrides are available if needed.

**Stage 3: Ongoing Sync**

* Scheduler triggers sync jobs per the configured frequency.

* On-demand sync is available via UI or API at any time.

* App teams receive event notifications when new data is available.

* Sync job status and logs are visible in Data Studio.

**Stage 4: Migration (Existing SOAP Customers)**

* Existing SOAP customers are migrated automatically in a phased approach with parallel validation.

* Data parity is confirmed before SOAP cutover for each customer.

* Historical data is preserved; scheduled syncs continue without interruption post-migration.

* See Sub-PRD 8 for full migration design.

# 11. Out of Scope

* Write-back from FloQast to NetSuite (e.g., posting journal entries).

* NetSuite SuiteScript customizations or SuiteApp delivery.

* Non-financial data domains (CRM, inventory, HR).

* sFTP-based data ingestion (separate pipeline; not in scope for this project).

* Real-time event streaming from NetSuite (webhook-push model).
