# **1. Objective**

The Entity Lookup endpoint (GET /entities) enables customers to programmatically retrieve FloQast entity IDs and associated metadata. Because all data pushed to FloQast through the FQ API must be associated with a FQ entity in order for customers to see the data, customers need a reliable, automated way to look up entity IDs from their own systems and use those IDs to tag each row of data before or during a push.

This endpoint exists today in the legacy FloQast API framework. This sub-PRD defines the requirements to rebuild it within the new FQ API framework, with consistent authentication, pagination support, and flexible query options - including retrieving all entities, filtering by entity name, or filtering by entity ID.

# **2. Key Benefits**

* Customers can programmatically retrieve FQ entity IDs without manual lookup in the FloQast UI, enabling fully automated integration workflows.
* Flexible query options - all entities, by name, or by ID - support a range of integration patterns from bulk mapping to targeted lookups.
* Pagination ensures reliable performance for organizations with large numbers of entities, removing the risk of timeouts or oversized responses.
* Rebuilt in the new FQ API framework with consistent authentication (API key) and endpoint conventions, removing the dependency on the legacy API.
* Entity status field allows integrations to filter out inactive entities before tagging data, reducing downstream association errors.

# **3. Use Cases**

1. At the start of each monthly close cycle, a customer's integration script calls GET /entities with no filters to retrieve all active FQ entities and builds a local mapping table of source system entity identifiers to FQ entity IDs. This mapping is then used to tag all data rows in subsequent GL Transaction and Balance pushes.
2. A customer queries GET /entities?entity_name=US+Operations to retrieve the FQ entity ID for a specific entity before tagging a batch of journal entries, avoiding the need to maintain a local cache.
3. A customer queries GET /entities?entity_id=fq-ent-00123 to confirm that a specific entity is still active in FloQast before including it in a data push.
4. A customer with hundreds of entities calls the endpoint with pagination parameters to retrieve entities in manageable batches rather than attempting a single large response.

# **4. Success Metrics**

* Endpoint is available and functional in the new API framework at Phase 1 launch.
* Customers are able to retrieve entity IDs programmatically without requiring manual FloQast UI access.
* Response time within acceptable thresholds under expected load (targets TBD with Engineering).
* Endpoint error rate within acceptable thresholds (TBD with Engineering).
* Old API framework entity endpoint usage declines as customers migrate to the new endpoint (tracked post-launch).

# **5. Assumptions**

* This endpoint exists today in the legacy FloQast API framework and must be rebuilt - not net-new - in the new FQ API framework. The legacy endpoint will continue to operate in parallel during transition; its deprecation is out of scope for this initiative.
* Authentication uses the same API key mechanism as the data push endpoints, defined in the Authentication & API Key Management sub-PRD.
* The endpoint returns only entities scoped to the authenticated customer's organization - customers cannot retrieve entities from other organizations.
* FQ entity IDs are stable identifiers and do not change over time, allowing customers to safely cache results between calls.
* The endpoint is read-only - customers can retrieve entities but cannot create, update, or delete them through this endpoint.
* Entity type values and hierarchy level definitions are defined by FloQast's existing entity model and are not configurable per customer.

# **7. Scope of Data**

The following data is returned by the entity endpoint:

| **Field** | **Type** | **Required in Response** | **Description** |
| --- | --- | --- | --- |
| `entity_id` | `string` | Yes | The unique FQ identifier for the entity. Used to tag data rows in subsequent pushes. |
| `entity_name` | `string` | Yes | The human-readable name of the entity as configured in FloQast. |
| `entity_type` | `string` | Yes | The entity type (e.g TBU, QBO, Workday, etc.). Specific values TBD. |
| `status` | `string` | Yes | Whether the entity is currently active or inactive in FloQast. Values: "active", "inactive". Need to determine this is available from the entities team |

‌

The following are explicitly out of scope for this endpoint:

* Parent entity / hierarchy relationships - not included in the response for this phase.
* Entity creation, updates, or deletion - this is a read-only endpoint.
* Cross-organization entity access - results are always scoped to the authenticated customer's organization.

# **8. Requirements**

‌

**REQ-EL-01: As a customer technical team, I want a GET /entities endpoint in the new FQ API framework so that I can retrieve FQ entity information using the same authentication and conventions as the data push endpoints.**

_**Functional spec:** The entity lookup endpoint must be implemented in the new FQ API framework, consistent with the authentication (API key), versioning, and endpoint conventions of the broader FQ API initiative. It must not depend on the legacy API framework. The endpoint path is GET /entities._

‌

**REQ-EL-02: As a customer technical team, I want to retrieve all entities for my organization when no filter is provided, so that I can build a complete local mapping of FQ entity IDs.**

_**Functional spec:** When called with no query parameters (other than pagination), the endpoint returns all entities belonging to the authenticated customer's organization. Both active and inactive entities are returned unless filtered by status. Results are paginated per REQ-EL-05._

‌

**REQ-EL-03: As a customer technical team, I want to filter the entity list by entity name so that I can retrieve the FQ entity ID for a specific entity without pulling the full list.**

_**Functional spec:** The endpoint accepts an entity_name query parameter. When provided, results are filtered to entities whose name matches the supplied value. Match behavior (exact vs. partial/fuzzy) is an open decision - see Section 10. If no entities match, the response behavior is TBD (see Open Questions)._

‌

**REQ-EL-04: As a customer technical team, I want to retrieve a specific entity by its FQ entity ID so that I can confirm entity details - such as active status - before including it in a data push.**

_**Functional spec:** The endpoint accepts an entity_id query parameter. When provided, results are filtered to the entity matching the supplied ID. entity_name and entity_id parameters may not be combined in the same request - behavior when both are supplied is TBD (see Open Questions). If no entity matches, the response behavior is TBD (see Open Questions)._

‌

**REQ-EL-05: As a customer technical team, I want the entity endpoint to support pagination so that I can retrieve entities in manageable batches without risking timeouts or oversized responses.**

_**Functional spec:** The endpoint supports paginated responses. Customers can specify the number of results per page and navigate through pages using the appropriate pagination parameters. Pagination type (cursor-based vs. offset/limit), default page size, and maximum page size are open decisions to be determined by Engineering - see Section 10._

‌

**REQ-EL-06: As a customer technical team, I want the entity endpoint response to include entity ID, entity name, entity type, and status so that I have enough information to correctly map and tag my data without needing additional lookups.**

_**Functional spec:** Each entity record in the response must include: entity_id (string), entity_name (string), entity_type (string), and status (string: "active" or "inactive"). Specific valid values for entity_type are defined by FloQast's existing entity model. No additional fields are required in Phase 1._

‌

**REQ-EL-07: As a FloQast system, I want the entity endpoint to return only entities scoped to the authenticated customer's organization so that customers cannot access entity data belonging to other organizations.**

_**Functional spec:** All responses from the entity endpoint are automatically scoped to the organization associated with the authenticated API key. No additional filtering or parameter is required from the customer. Requests authenticated with an invalid or revoked API key must be rejected with an appropriate authentication error._

‌

**REQ-EL-08: As a customer technical team, I want to retrieve all active entities for my organization, so that I can build a complete local mapping of active FQ entity IDs.**

_**Functional spec:** The endpoint accepts an active query parameter. When provided, results are filtered to entities whose status matches the supplied value. If no entities match, the response behavior is TBD (see Open Questions)._

# **9. User Interaction and Design**

This is a developer-facing API endpoint. There is no UI component - customers interact with it programmatically through their integration code or API tooling. The design considerations below cover endpoint behavior, request/response shape, and expected usage patterns.

## **Endpoint**

`GET /entities`

‌

## **Authentication**

API key passed in the request header, consistent with all other FQ API endpoints. See Authentication & API Key Management sub-PRD for full detail.

‌

## **Query Parameters**

‌

| **Parameter** | **Type** | **Required** | **Description** |
| --- | --- | --- | --- |
| `entity_name` | `string` | No | Filter results to entities matching the provided name. Match behavior (exact vs. partial) TBD. |
| `entity_id` | `string` | No | Filter results to the entity with the provided FQ entity ID. |
| `status` | `string` | No | Filter the results to the entities with the provided status |
| `limit` | `integer` | No | Number of results to return per page. Default and max TBD with Engineering. |
| `offset / cursor` | `string / integer` | No | Pagination parameter. Type (cursor vs. offset) TBD with Engineering. |

‌

## **Response Structure**

Successful response (HTTP 200) returns a paginated list of entity objects. Each object contains:

‌

* `entity_id - the FQ entity identifier to use when tagging data rows in push payloads`
* `entity_name - human-readable entity name`
* `entity_type - entity type`
* `status - "active" or "inactive"`

‌

The response envelope also includes pagination metadata (total count, next page token or offset) - exact structure TBD with Engineering.

‌

## **Expected Usage Pattern**

The most common integration pattern is:

‌

1. Call GET /entities (paginated if needed) at the start of an integration run to build or refresh a local entity mapping.
2. Map source system entity identifiers to FQ entity IDs using the local mapping.
3. Tag each row of data with the corresponding entity_id before pushing to the relevant data endpoint (GL Transactions, Balances, etc.).

‌

Customers with stable entity structures may cache the response and refresh periodically rather than calling the endpoint on every push cycle.

‌

## **Error Responses**

* 401 Unauthorized - API key missing, invalid, or revoked.
* 400 Bad Request - invalid query parameter combination (e.g., entity_name and entity_id both provided - TBD).
* No match behavior (empty 200 vs. 404) - TBD with Engineering; see Open Questions.
* 500 Internal Server Error - unexpected system failure.

# **10. Open Questions**

| **Question** | **Owner** | **Notes** |
| --- | --- | --- |
| What pagination type should be used - cursor-based or offset/limit? | Engineering | Cursor-based is better for large or frequently changing datasets. Offset/limit is simpler for customers. Engineering to recommend based on expected entity volumes and data change frequency. |
| What is the behavior when a query by entity_name or entity_id returns no matching results? | Engineering | Options: empty array with HTTP 200 (consistent with list conventions) or HTTP 404. Decision affects how customer integrations handle the no-match case. |
| Is entity_name matching exact, case-insensitive, or partial/fuzzy? | Engineering / Product | Exact match is simpler to implement and predictable. Partial/fuzzy matching is more forgiving but adds complexity. Decision affects how customers construct name queries. |
| What happens if both entity_name and entity_id are provided in the same request? | Engineering | Options: reject with 400 Bad Request, or honor entity_id and ignore entity_name (ID is more specific). Needs a defined behavior to avoid ambiguity. |
| What are the valid values for entity_type? | Engineering / Data | Entity type values are defined by FloQast's existing entity model. These need to be enumerated and documented so customers know what to expect in responses. |
| What are the default and maximum page sizes for paginated responses? | Engineering | Determines how many entities are returned per call by default and the ceiling a customer can request. Relevant for customers with very large entity lists. |

# **11. Out of Scope**

* Entity creation, update, or deletion - this is a read-only endpoint. Entity management is handled within FloQast, not through the FQ API.
* Parent entity hierarchy relationships - not included in the response for Phase 1.
* Cross-organization entity access - results are always scoped to the authenticated customer's organization.
* Deprecation of the legacy API framework entity endpoint - out of scope for this initiative; timing to be determined separately.
* Entity-to-entity mapping or hierarchy traversal - not supported in Phase 1.
* Write operations of any kind (POST, PUT, PATCH, DELETE) against the /entities path.
