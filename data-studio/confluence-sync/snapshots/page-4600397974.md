## 🎯 Objective

This PRD defines the work required to onboard customers to FloQast Data Studio at scale in Q3 2026, with a target of 1,000 customers actively using Data Studio by end of quarter. It covers the rollout process for DP2.0-connected applications, new customer onboarding across NetSuite, Workday, and Intacct, and the engineering-led migration of existing direct and enhanced data connections. It does not cover the underlying product development of Data Studio itself, nor does it address ERPs outside the scope listed below.

The primary users of this work are FloQast implementors and the Data/Integrations team, who are responsible for onboarding net-new customers, and Engineering, who will execute connection migrations and build the infrastructure to support DP2.0 application awareness. Customers themselves are the end beneficiaries — their data pipelines must be live and healthy for them to count toward the 1,000 target.

The core problem this PRD addresses is that there is no coordinated plan to move customers onto Data Studio at the volume required. Existing connections exist in legacy configurations (direct API, enhanced data), new ERP onboarding pilots are untested at scale, and DP2.0-powered applications lack a clear rollout trigger mechanism. Without explicit ownership and sequencing of these workstreams, the 1,000-customer target will not be met.

This initiative enables downstream activation across FloQast products — once customer data is flowing through Data Studio, it unlocks Close, Reconciliations, Flux Analysis, and other DP2.0-powered features. The migration work also retires technical debt in legacy connection paths, improving data reliability and reducing support burden going forward.

## 💡 Key Benefits

* **Scaled customer activation:** A coordinated onboarding plan across ERP types gets customers live faster and with less one-off effort per customer.

* **Legacy connection retirement:** Migrating NetSuite direct API, Intacct direct, and enhanced data connections to DP2.0 eliminates maintenance burden and inconsistent data delivery.

* **ERP pilot validation:** Onboarding 3–5 customers per ERP type (NS, Workday, Intacct) stress-tests the DP2.0 pipeline before broad rollout, surfacing issues early.

* **Application readiness signal:** The DP2.0 rollout process gives applications a reliable mechanism to detect when customer data is available, reducing manual coordination between integrations and product teams.

* **Historical data continuity:** A defined historical migration plan ensures customers transitioning from legacy connections do not lose access to prior period data.

* **Repeatable onboarding playbook:** Pilots across ERP types produce documented processes that can be handed off or scaled with additional implementors.

* **Progress toward Q3 goal:** The combined output of new onboardings and migrated connections directly drives the 1,000-customer activation target.

## ✅ Use Cases

**1. DP2.0 Application Rollout Signal**\
A FloQast application (e.g., Close, Reconciliations) needs to know when a customer's data is available in DP2.0 before enabling DP2.0-powered features. The system detects that a customer's pipeline is active and triggers the appropriate application configuration or feature enablement without manual intervention from an implementor.

**2. Define NetSuite Onboarding Playbook via Direct API**\
The product and implementation team works through onboarding 3–5 NetSuite customers via the DP2.0 direct API path to define a repeatable playbook. Each customer is fully configured, data is validated end-to-end, and gaps or deviations from the expected flow are documented. The output is a written playbook that can be used for scaled NetSuite direct API onboarding.

**3. Define NetSuite Onboarding Playbook via CDC**\
The product and implementation team works through onboarding 3–5 NetSuite customers via Change Data Capture to define the incremental data path playbook. CDC-specific configuration steps are documented, incremental data is confirmed to arrive on schedule, and the output is a written playbook distinct from the direct API path.

**4. Define Workday Onboarding Playbook**\
The product and implementation team works through onboarding 3–5 Workday customers to define a repeatable Workday playbook. Known Workday-specific considerations — authentication, data shape, multi-ledger configurations — are tested and documented. The output is a written playbook for future Workday onboarding.

**5. Define Intacct Onboarding Playbook via Direct API and CDC**\
The product and implementation team works through onboarding 3–5 Intacct customers across both direct API and CDC paths to define playbooks for each. Intacct-specific configuration and any edge cases are documented. The output is two written playbooks — one per connection type — ready for scaled Intacct onboarding.

**6. Engineering Migrates Legacy NetSuite Direct API Connection**\
Engineering migrates an existing NetSuite direct API customer from the legacy connection path to DP2.0. The customer's data continues to flow without interruption, historical data is preserved per the migration plan, and the legacy connection is decommissioned.

**7. Engineering Migrates Enhanced Data Connection**\
Engineering migrates a customer on an enhanced data connection (NetSuite, Workday, or Intacct) to DP2.0. The migration plan accounts for any custom configuration or non-standard data fields present in the Fivetran-managed connection, and the customer's pipeline is validated post-migration before the legacy path is retired.

**8. Historical Data Migration for Transitioning Customer**\
A customer being migrated from a legacy connection requires historical data going back multiple periods. Engineering applies the historical data migration plan to backfill prior period data into Data Studio, and the customer confirms data continuity before the migration is marked complete.

## 🤔 Assumptions

1. Data Platform 2.0 infrastructure is stable and production-ready prior to the start of Q3 onboarding and migration work.

2. NetSuite, Workday, and Intacct DP2.0 integration paths are built and validated before pilot onboardings begin.

3. Engineering has capacity to execute all three migration workstreams (NS direct API, Intacct direct, enhanced data) within Q3.

4. The mechanism by which applications detect DP2.0 data availability will be managed via feature flags and does not require customer-facing configuration.

5. Historical data migration scope and approach will be defined by Engineering prior to any customer migration beginning.

6. The 1,000-customer target includes both newly onboarded customers and customers migrated from legacy connections — both count toward the goal.

7. Pilot customers (3–5 per ERP type) will be identified and committed by customer success or implementation teams before pilot onboarding begins.

8. CDC availability for NetSuite and Intacct is assumed to be production-ready for pilot use in Q3.

## ⭐ Milestones

1. **Phase 1: DP2.0 Rollout Process & Historical Migration Plan** — Engineering defines and builds the mechanism that signals to FloQast applications when a customer's DP2.0 data is available and ready (managed via feature flags). In parallel, Engineering produces a historical data migration plan defining scope, approach, and sequencing for customers transitioning from legacy connections. Both are prerequisites for all downstream migration and onboarding work.

2. **Phase 2: ERP Pilot Onboardings** — The product and implementation team onboards 3–5 customers each for NetSuite (direct API and CDC), Workday, and Intacct (direct API and CDC). Pilots validate the DP2.0 onboarding path end-to-end for each ERP type, surface gaps in tooling or process, and produce repeatable playbooks for scaled onboarding.

3. **Phase 3: Legacy Connection Migrations** — Engineering migrates existing customers from NetSuite direct API, Intacct direct, and enhanced data connections to DP2.0. Historical data migration plan is applied as needed. Migrated customers are validated post-migration and legacy connections are decommissioned. This phase drives the bulk of the 1,000-customer activation count.

4. **Phase 4: Scaled Onboarding** — With pilot playbooks validated and migration infrastructure in place, the implementation team onboards additional customers across all ERP types to reach the 1,000-customer target. Any gaps identified in Phases 1–3 are resolved before this phase begins.

## Scope

**In scope:**

* DP2.0 rollout process / application awareness mechanism (via feature flags)

* Historical data migration plan and execution

* NetSuite pilot onboardings — direct API and CDC (3–5 customers), with the goal of producing repeatable playbooks

* Workday pilot onboardings (3–5 customers), with the goal of producing a repeatable playbook

* Intacct pilot onboardings — direct API and CDC (3–5 customers), with the goal of producing repeatable playbooks

* Migration of existing NetSuite direct API connections to DP2.0

* Migration of existing Intacct direct connections to DP2.0

* Migration of existing enhanced data connections (NetSuite, Workday, Intacct) to DP2.0

**Explicitly out of scope:**

* Net-new product development for Data Studio features

* ERPs not listed above (SAP, Yardi, and others are not in scope for Q3 onboarding)

* Post-Q3 scaled onboarding beyond the 1,000-customer target

## ⚠️ Out of Scope

* **SAP, Yardi, and other ERPs:** Not included in Q3 onboarding targets. These will be addressed in a future initiative.

* **Net-new Data Studio feature development:** This PRD assumes Data Studio is feature-complete for the connection types in scope. New feature work is not tracked here.

* **Post-Q3 scaled onboarding:** Work beyond the 1,000-customer target is out of scope. A follow-on initiative will address Q4 and beyond.
