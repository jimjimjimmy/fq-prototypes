## Overview

The **Source Data Management** tab is a new configuration surface inside Data Studio's Connectors section, available at the individual file level for file-based connections (sFTP, manual upload, etc.). It sits alongside the existing File Config, Accounting Config, and Entity Scope tabs.

This tab gives customers and admins the tools to describe what a file contains, how to identify rows uniquely, how to type each field, and how to handle structural quirks like non-standard headers, fixed values, and cell-level metadata. Together, these configurations allow the Data Platform to ingest raw file data and route it correctly into one or more FQ domain models.

## Background

The Data Platform 2.0 strategy requires that any source of data — not just native ERP integrations — can be normalized into FQ domain models (GL Balances, GL Transactions, GL Accounts, JEM dimensions, etc.). File-based connections are a primary mechanism for customers whose data lives outside a directly integrated ERP.

Today, file ingestion lacks a standardized way to describe the contents of a file before transformation rules are applied. Without that metadata layer, the platform cannot:

* Route a file's data to the correct domain model pipeline

* Validate or deduplicate records reliably

* Surface the file as an available source when a customer is building transformation rules for a specific model in Accounting Config

* Support JEM dimension population from file-sourced data

The Source Data Management tab is the configuration layer that closes this gap.

## Goals

* Allow users to declare what a file is intended to populate (data purpose), with support for multiple use cases per file.

* Enable customers to define how records in a file are uniquely identified — primary key, single or composite.

* Provide per-field data type configuration so the platform can validate and transform correctly.

* Support fixed-value fields that apply to every row (e.g., a single FQ entity applied to all rows in the file).

* Allow users to indicate where headers appear in the file, including files with non-standard header positions.

* Support reference to data from specific cells (e.g., a period date or entity code stored in a header cell rather than a data row).

* Ensure that files configured for a specific domain model appear as available sources when building transformation rules for that model.

## Non-Goals / Out of Scope

* **Transformation rule authoring** — this tab configures the source, not the mapping to FQ fields. Mapping rules live in field mappings.

* **Non-file-based connections** — API and data share connections have separate configuration flows; this tab is file-only.

* **Data preview / validation UI** — viewing sample rows or running full validation is a separate feature (data quality visibility, per the Data Platform roadmap).

* **Automated field type inference** — the system may suggest types, but enforced inference is out of scope for this phase.

* **Multi-file join / relationship definition** — relating two files to each other is out of scope for this tab.

* **Version history / change tracking** for source configuration changes.

## Feature Requirements

### 1. Data Purpose Configuration

Users declare what the file is intended to populate. This drives downstream routing, model availability, and conditional configuration (e.g., JEM dimension setup).

#### Requirements

* Users can assign one or more data purposes to a file (multi-select).

* Available purposes align to FQ domain models and data sets:

| Purpose | Description | Tier |
| --- | --- | --- |
| GL Balances | Trial balance amounts by account and period | Tier 1 |
| GL Accounts | Chart of accounts structure | Tier 1 |
| GL Transactions | General ledger transaction detail | Tier 2 |
| Companies / Entities | Legal entity definitions and relationships | Tier 1 |
| FX Rates | Foreign exchange rates between currencies | Tier 1 |
| Subledger | Subledger transaction detail (AR, AP, bank, etc.) | Tier 3 |
| JEM Field Dimensions | Dimension values used when creating journal entries | Tier 3 |

* At least one purpose must be selected before the tab configuration can be saved.

* Purpose selection is shown prominently at the top of the tab, above all other configuration sections.

#### Conditional: Domain Model Availability

* When a file is configured for any domain model purpose, it becomes available as a selectable source in the Source Data sectio of field mapping when building transformation rules for that model.

* Files in an Incomplete state (no purpose saved, or required conditional config missing) do not appear as available sources.

### 2. Primary Key Configuration

Users define how rows in the file are uniquely identified. This is required for deduplication, upsert logic, and change detection during ingestion.

#### Requirements

* Users can define a primary key using either a **single field** or a **composite key** (2 or more fields).

* The field selector is populated from the columns detected in the file based on header configuration (see Section 5).

* For composite keys, users select fields and define their order. A preview of the resulting key is shown (e.g., entity_id + account_number + period).

* Primary key fields should have a type assigned (Section 3); the system warns if a selected key field is untyped.

* Primary key configuration is required before the file can be used as a source in a domain model mapping.

> **Engineering note — key storage:** The composite key should be stored as an ordered array of field references, not a pre-concatenated string. This allows individual field types to be validated independently and key construction logic to evolve without requiring a config migration.

### 3. Field Type Configuration

Users define the data type for each field (column) detected in the file. This drives validation, transformation, and type-safe downstream consumption.

#### Requirements

* The system detects and lists all fields present in the file based on header configuration (Section 5).

* For each field, the user assigns one of the following data types:

| Type | Description |
| --- | --- |
| String | Free-form text |
| Decimal | Numeric value |
| Currency | Numeric monetary amount; should be paired with a currency code field |
| Date | Calendar date; user specifies format (e.g., YYYY-MM-DD, MM/DD/YYYY) |
| DateTime | Date and time; user specifies format |
| Boolean | True/false or equivalent (Y/N, 1/0) |
| Identifier | A reference key used for joins or lookups; treated as a string but flagged semantically |

* For Date and DateTime types, the user must specify the format string.

* Fields with no type assigned are treated as untyped strings at ingestion time. The UI surfaces a warning on save if untyped fields exist.

* The system may suggest a type based on sample values from the most recently uploaded file (optional enhancement for a later iteration). User can always override.

* Field names are shown as detected from the file. Renaming and aliasing is handled in Accounting Config transformation rules, not here.

### 4. Fixed Fields

Some fields required by a domain model may not exist as columns in the file — they are constant values that apply to every row. Fixed fields let users define these inline without requiring the source file to be modified.

#### Requirements

* Users can define one or more fixed fields on a source file.

* Each fixed field has:
      

  * A **field name** — selected from a list of known FQ domain fields (e.g., FQ Entity, Currency, Data Source Label) or entered as a custom name.

  * A **static value** — a string entered by the user, applied to every row at ingestion time.

  * A **data type** — from the same type list as Section 3.

* Fixed fields are distinct from file columns — they do not appear in the detected field list in Section 3 and cannot be selected as primary key fields.

> **Example:** A customer uploads a monthly GL balance extract scoped to a single entity. The file has no entity column. The user defines a fixed field: fq_entity = "us-operations-001" (Identifier). Every ingested row is stamped with this entity reference without a column being present in the file.

### 5. Header Configuration

Users indicate where column headers appear in the file. Finance system exports frequently include report titles, metadata rows, or multi-row headers above the actual data.

#### Requirements

* Default assumption: row 1 is the header row. Users can override this.

* Users specify the **header row number** (1-indexed). Rows above the header are treated as pre-header metadata and excluded from ingestion.

* Users can indicate the file has **no header row**, in which case fields are identified by column index (Column 1, Column 2, etc.) and the user must assign a label to each column in Section 3.

* Users can indicate **multiple header rows** (e.g., a primary header and a sub-header). In this case:
      

  * The user specifies which row is the primary (field-name) header.

  * Additional header rows are excluded from data ingestion but remain accessible for cell-level data references (Section 6).

* A file preview (first N rows) should be displayed alongside header configuration so the user can visually confirm their selection.

### 6. Cell-Level Data References

Some files embed metadata in fixed cell positions outside the main data grid — a pattern common in finance report exports where a period, entity code, or report title appears in a specific cell (e.g., A2 = "Report Period: Jan-2026"). Cell-level references capture this data and apply it as a field value to every ingested row.

#### Requirements

* Users can define one or more cell references on a source file.

* Each cell reference has:
      

  * A **cell address** — row and column position (spreadsheet-style, e.g., A2, or Row 2 / Column A).

  * A **field name** — what this value should be named when applied to ingested rows (from known FQ domain fields or a custom name).

  * A **data type** — from the same type list as Section 3.

  * An optional **parsing pattern** — a prefix/suffix strip rule or regex to extract just the value from a cell that contains a label (e.g., strip "Report Period: " from "Report Period: 2026-01").

* Cell references behave like fixed fields at ingestion time — the resolved value is stamped on all rows — but the value is sourced from file content, not user-entered text.

* Cell references must be validated at ingestion time. If the referenced cell is empty or missing, ingestion fails with a descriptive error.

* Users can preview the current resolved value of a cell reference based on the most recently uploaded version of the file.

> **Example:** A Yardi export places the reporting period in cell B3 as "Report Period: Jan-2026". The user defines a cell reference: cell B3, field name reporting_period, type Date, parse pattern: strip prefix "Report Period: ". At ingestion, the platform reads B3, strips the prefix, parses the date, and stamps every row with reporting_period = 2026-01-01.

### 7. Sheet Identification

Some files will have multiple sheets associated with them if they are Excel files. In some cases, each sheet will represent the same pattern with different data and in others each sheet will represent different data. Users need a way to identify the sheets and the usage of the data with in the sheets.

#### Requirements

* Users can indicate which sheet or sheets to use for an Excel file

* Users can indicate different data patterns for different sheets

  * For example, sheet 1 contains the chart of accounts and sheet 2 contains the balances information. In sheet 2, there is a static cell for a period, which can be retrieved from sheet 2 but is not present in shet one.

  * Another example is that each sheet represents a different FQ entity but the data pattern across sheets is the same. This allows for the definition of the different entity but the same data ingestion otherwise.

## Tab State and Validation

| State | Condition | Effect on Downstream Use |
| --- | --- | --- |
| `Incomplete` | No data purpose selected, or required conditional config (e.g., JEM dimension mapping) is missing | File does not appear as an available source in model mapping. Save is blocked. |
| `Configured (warnings)` | Required fields are saved, but some fields are untyped or key fields have warnings | File is available as a source, but ingestion may produce warnings at runtime. |
| `Configured` | All required config complete, no warnings | File is available as a source. Ingestion proceeds normally. |

## Data Model Notes

The following entities need to be created or extended to support Source Data Management configuration. Names are conceptual and subject to change during technical design.

* **SourceFileConfig** — top-level record per file connector; stores purpose selection, primary key definition, header row config.

* **SourceFieldConfig** — per-field records linked to a SourceFileConfig; stores field name, detected type, user-assigned type, date format string.

* **FixedFieldConfig** — user-defined fixed fields per source file; stores field name, static value, type.

* **CellReferenceConfig** — stores cell address, field name, type, and parsing pattern per source file.

> Exact schema, storage layer, and API contract will be defined in an RFC/ADR during technical discovery. The entity names above are conceptual.

## Out of Scope

* Transformation rule authoring (mapping file fields to FQ domain model fields) — handled in field mappings.

* Non-file-based connectors (API, data share).

* Data preview and validation UI beyond what is needed to confirm header and cell configuration selections.

* Automated enforcement of field type inference without user override.

* Multi-file relationship or join definitions between source files.

* Version history or audit log for source configuration changes.
