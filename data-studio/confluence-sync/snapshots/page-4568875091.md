## Objective

This PRD defines FloQast's framework for CDC (Change Data Capture) connectors in Data Studio. It establishes the foundational concepts, shared definitions, and product scope that govern all CDC connector work and serves as the entry point for the sub-PRDs that specify individual capability areas.

CDC connectors allow FloQast to ingest data from source systems (NetSuite, Intacct, Workday, and others) via change data capture, rather than relying on scheduled batch file transfers. This framework describes how those connections are set up, how data is structured and mapped, how it moves through the pipeline, and how the system behaves when things go wrong.

Source-specific implementation details (NetSuite, Intacct, Workday) are covered in separate related PRDs linked at the bottom of this document.

---

## Why This Matters

Today, CDC connections exist in Data Platform 1.0 but are limited: the available tables per connection are fixed and there is no self-serve path for customers who need additional data. As reporting and analytics demand grows, particularly from the Reporting Business Unit, this bottleneck slows time-to-value and increases implementation cost.

The CDC Connector Framework addresses this by establishing a scalable, self-serve model: FloQast defines the rules once (supported tables, Source-to-Target mappings, standard dimensions), and customers configure and expand their own connections without opening a support ticket. The result is faster onboarding, lower implementation overhead, and a data foundation that supports both standard FloQast models and customer-specific use cases.

To fully transition off of the legacy platform, the CDC connectors that are supported today mush also be supported by DP2.0.

## Guiding Principles

**Customer-controlled, FloQast-governed.** Admins configure and expand their own connections. FloQast controls what is available - which tables, which mappings, which dimensions - so quality and consistency are maintained at scale.

**Source-agnostic where possible.** The framework is designed to work across CDC sources. Source-specific behavior (credential fields, standard table sets, mapping rules) is a configuration concern handled in source-specific PRDs - not a reason to build separate product flows.

**No engineering required for standard setups.** An admin should be able to set up a CDC connection, select tables, and have fully mapped models ready for review without opening a ticket.

**Fivetran is an implementation detail.** CDC connections are powered by Fivetran. User-facing language refers to the data source (e.g., "NetSuite"), not to the underlying integration platform.

**Transparency at every layer.** Admins should be able to see what data is flowing, what tables are active, what errors have occurred, and what the system is doing at any point in the process.

## Scope

### In Scope

* Connection setup wizard for CDC sources (source selection, credentials, table provisioning, validation)

* Self-serve table selection from a FloQast-controlled list of supported tables along with standard table selection

* Standard Source-to-Target mapping and dimension provisioning per source for FQ models

* Entity assignment for CDC connection data

* Table linking (primary/foreign key relationships between connected tables)

* Scheduling and frequency configuration for data syncs

* On-demand data refresh

* Data pipeline visibility (raw data preview, sync progress)

* Connection and data processing error states

* Data quality error surfacing (type mismatches, missing keys, schema drift)

* Data run logging

* Notifications when data stops flowing or errors occur

* Related/companion connector type configuration (e.g., Workday RaaS linked to a Workday CDC connection)

### Out of Scope

* Source-specific implementation details. Table lists, credential fields, mapping rules, and dimension definitions for NetSuite, Intacct, and Workday are covered in their respective source-specific PRDs

* Authoring or maintaining Source-to-Target mapping definitions (assumed to exist as a dependency)

* Retroactive updates to existing customer models when FloQast updates a standard mapping

* Batch connector setup

* User-defined custom model creation from connected tables (deferred)

* Administration of connector type taxonomy (e.g., how FloQast names and surfaces connector options in the product)

## Shared Definitions

| Term | Definition |
| --- | --- |
| **CDC (Change Data Capture)** | A data integration method that captures row-level changes in a source system in near real-time and streams them to a destination. Contrasts with batch/file-based sync. |
| **Fivetran** | The underlying integration platform powering FloQast's CDC connections. Not exposed in user-facing language. |
| **Source** | The external system being connected (e.g., NetSuite, Intacct, Workday). |
| **Table** | A discrete dataset available from a source via Fivetran (e.g., Transactions, Accounts, GL Lines). |
| **Standard tables** | The default set of tables FloQast pre-selects for a given source. Required for FloQast standard models. Cannot be deselected. |
| **Additional tables** | Tables from the FloQast-supported list that admins may optionally add during or after setup. |
| **FQ-supported table list** | The FloQast-controlled set of tables for which Source-to-Target mappings exist. Only these tables are surfaced to admins during setup. |
| **Source-to-Target mapping** | A pre-defined rule set that transforms raw source table fields into the FloQast model schema. |
| **Standard dimensions** | A FloQast-defined set of dimension fields for a given source, derived from connected table data and applied consistently across all customers using that source. |
| **Initial data load** | The one-time full historical sync that runs after a CDC connection is configured, before incremental streaming begins. |
| **Draft model** | A model auto-created after the initial data load completes, with Source-to-Target mappings pre-applied. Must be reviewed and published before going live. |
| **Active model** | A published model available for use across FloQast. |
| **Entity assignment** | The process of associating a CDC connection's data with one or more FloQast entities (e.g., subsidiaries, business units). |
| **Table linking** | Defining primary/foreign key relationships between connected tables to support multi-table models and joins. |
| **Companion connector** | A related connection type that works alongside a primary CDC connection (e.g., a Workday RaaS connector linked to a Workday CDC connection). |

## Assumptions

* CDC connections are powered by Fivetran; this is not surfaced to users.

* The FQ-supported table list per source is a prerequisite to shipping any self-serve table selection. This list must be defined and maintained by FloQast (PM + Engineering ownership).

* Source-to-Target mappings are assumed to exist as a dependency for each supported table. Authoring mappings is a separate workstream.

* Connections cannot be changed to a different type after setup. A new connection is required if the type needs to change.

* Standard tables for a given source cannot be deselected by admins. They are required for FloQast standard models.

* User-facing language refers to the data source (e.g., "NetSuite"), never to Fivetran.
