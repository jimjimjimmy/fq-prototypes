# **1. Objective**

This sub-PRD defines the field-level specification for the SL Transactions endpoint (POST /sl-transactions). It covers the required and optional fields of the Subledger Transaction data model, account type classification, submit mode behavior (append, upsert, and replace), SCD Type 2 versioning for record lineage, custom field passthrough, and the metadata FloQast applies to all incoming records.

The SL Transactions endpoint is a Phase 2 core data model endpoint in the FQ APIs initiative. It enables customers to push subledger transaction detail directly into FloQast, providing the transaction-level source data that supports reconciliation, flux analysis, and close management workflows across accounts receivable, accounts payable, fixed assets, inventory, payroll, and other subledger categories.

SL Transactions are structurally similar to GL Transactions but serve a different purpose: where GL Transactions represent the summarized general ledger view of financial activity, SL Transactions represent the underlying detail that rolls up to the GL. FloQast uses SL Transaction data to support detailed reconciliation workflows - for example, reconciling an AR subledger to the GL accounts receivable balance, or tying a fixed assets schedule to the GL.

Like GL Transactions, SL Transactions can be high volume depending on account type. AR and AP subledgers in particular can carry millions of transaction records per period for large enterprises. The endpoint must support high-volume ingestion from Phase 2 launch. Infrastructure requirements are defined in the High-Volume Data Ingestion sub-PRD.

Auto-configure behavior triggered on first push is defined in the Auto-Configure sub-PRD. Upsert key design and conflict handling are defined in the Data Handling sub-PRD. Authentication is defined in the Authentication & API Key Management sub-PRD.

# **2. Key Benefits**

* account_type classification (Accounts Receivable, Accounts Payable, Fixed Assets, etc.) allows FloQast to correctly categorize subledger data without requiring customers to map transactions to chart of accounts entries, and enables subledger-type-specific reconciliation workflows.
* Transaction-level detail supports detailed reconciliation: customers can push the full AR or AP subledger and reconcile it line-by-line to the GL balance, rather than relying on aggregate summaries alone.
* Local and functional currency fields follow the same dual-currency pattern as GL Transactions, enabling multi-currency subledger reconciliation without additional transformation.
* transaction_id provides a source-system-traceable unique identifier for every subledger record, enabling error reports, audit trails, and record-level drill-down in the Ingestion Logging & Status sub-PRD.
* FQ internal transaction ID (fq_transaction_id) gives FloQast a stable internal key to link subledger records to other data types - GL Transactions, Balances, or future reconciliation artifacts - independent of source system IDs.
* SCD Type 2 versioning via effective_start_date and effective_end_date preserves the full version history of each subledger transaction record, enabling point-in-time reconstruction for audit and compliance purposes.
* Submit mode (append, upsert, replace) gives customers the same explicit control over data submission behavior used across all FQ API endpoints, with consistent semantics.

# **3. Use Cases**

1. A customer pushes their full AR subledger for December 2025 in replace mode. FloQast ingests all open and closed invoice transactions, makes them available for reconciliation against the GL accounts receivable balance, and returns a success response.
2. A customer pushes their AP subledger incrementally throughout the month as new vendor invoices are posted. Each daily push uses upsert mode with transaction_id as the key. FloQast adds new transactions and updates any previously submitted records that have been modified (e.g., payment applied against an invoice).
3. A customer reconciles their fixed assets subledger to their GL fixed assets account. They push both the SL Transactions (POST /sl-transactions with account_type = Fixed Assets) and the GL Transactions (POST /gl-transactions) for the period. FloQast uses both datasets to support the reconciliation workflow.
4. A customer's payroll system generates a large volume of payroll transaction detail at period end. They push the full payroll subledger using the batch session model from the High-Volume Data Ingestion sub-PRD, with chunked submissions and idempotency keys.
5. A transaction in the AR subledger is subsequently reversed in the source system. The customer re-submits the updated record in upsert mode. FloQast updates the existing record, sets the previous version's effective_end_date, and creates a new version reflecting the reversal.
6. A customer pushes intercompany subledger transactions with account_type = Intercompany. FloQast stores the detail and makes it available for intercompany matching and elimination workflows in conjunction with company hierarchy data from the Companies endpoint.

# **4. Success Metrics**

* SL Transactions endpoint available and functional at Phase 2 launch.
* account_type validation correctly rejecting records with values outside the defined allowable set, with actionable error messages.
* Required field validation correctly rejecting payloads with missing required fields, with errors keyed to transaction_id.
* Upsert correctly matching on transaction_id and updating existing records without creating duplicates.
* High-volume subledger submissions (AR, AP, Payroll) successfully processed using the batch session model from the High-Volume Data Ingestion sub-PRD.
* fq_transaction_id correctly assigned to every ingested record and stable across subsequent upserts.
* FloQast metadata accurately applied to all ingested SL Transaction records (target accuracy: 100%).

    **5. Assumptions**


* Customers are responsible for pre-formatting subledger transaction data to match the field specifications defined in this document. FloQast does not perform transformation or normalization.
* submit_mode is required on every push. There is no default mode - customers must explicitly specify append, upsert, or replace.
* In append mode, all submitted records are inserted unconditionally. No key matching is performed. Submitting the same transaction_id twice creates duplicate rows.
* In upsert mode, records are matched using transaction_id as the upsert key. Matching records are updated; non-matching records are inserted. Records not in the batch are left unchanged. Upsert is idempotent. When a record is updated, FloQast advances the SCD Type 2 version: the previous record's effective_end_date is set and the updated record becomes the new active version.
* In replace mode, all existing SL Transaction records for the specified period, entity, and account_type are removed before the submitted batch is inserted. Replace scope is period + entity + account_type. Customers replacing an AR subledger do not affect AP or other subledger types for the same period.
* transaction_id is the customer-supplied unique identifier for the subledger transaction in the source system. It is the upsert key and the identifier used in error reports. It must be unique within the combination of entity, period, and account_type.
* fq_transaction_id is the FloQast-assigned internal unique identifier for the SL Transaction record. It is system-generated at first ingestion and stable across subsequent upserts. It is not customer-supplied.
* account_type is required on every record. Allowable values are defined in Section 7 and Section 8. Records with an account_type outside the allowable set are rejected with a 422 error.
* functional_amount and functional_currency are optional, particularly for single-currency customers. When provided, functional_currency must match an ISO 4217 code recognized in FloQast's currency table.
* effective_start_date and effective_end_date follow the SCD Type 2 versioning model: null effective_end_date means this is the currently active version of the record.
* SL Transactions can be high volume. AR and AP subledgers for large enterprises can contain millions of records per period. High-volume submissions should use the batch session model from the High-Volume Data Ingestion sub-PRD.
* System-applied metadata fields (fq_transaction_id, touch_count, and FloQast ingestion timestamp) are generated by FloQast at ingestion time and cannot be overridden.

# **7. Account Type Reference**

account_type is a required field on every SL Transaction record. It classifies the subledger to which the transaction belongs and determines which FloQast workflows the transaction is available for. The following are the allowable values:

‌

| **account_type Value** | **Subledger Context** |
| --- | --- |
| **Accounts Receivable** | Customer invoices, payments received, and outstanding receivable balances. |
| **Accounts Payable** | Vendor invoices, payments made, and outstanding payable balances. |
| **Fixed Assets** | Capital asset acquisitions, disposals, and carrying value transactions. |
| **Accumulated Depreciation** | Depreciation charges applied against fixed assets. |
| **Inventory** | Inventory movements: receipts, issues, adjustments, and valuation changes. |
| **Cash** | Cash receipts, disbursements, and bank-level transaction detail. |
| **Sales** | Revenue transactions, sales order activity, and customer billing detail. |
| **Purchase** | Purchase order activity, vendor transactions, and procurement detail. |
| **Payroll** | Payroll transactions, salary accruals, tax withholdings, and benefit costs. |
| **Intercompany** | Transactions between related entities or subsidiaries that require elimination in consolidation. |
| **Leases** | Lease liability and right-of-use asset transactions, including ASC 842 / IFRS 16 entries. |
| **Other** | Subledger transactions that do not fit the categories above. Use sparingly - customers should use a more specific type where available. |

‌

account_type values are case-sensitive and must match the values listed above exactly. Records submitted with values outside this set are rejected with a 422 error identifying the offending record (keyed to transaction_id) and the invalid value. The "Other" value is available as a catch-all but customers are encouraged to use the most specific applicable type.

# **9. Requirements**

**REQ-SL-01: As a customer technical team, I want to submit the required set of SL Transaction fields so that FloQast can correctly ingest and classify subledger transaction data by entity, period, and account type.**

_**Functional spec:** The SL Transactions endpoint accepts the required fields defined in Section 8. Every record must include all required fields. Records with missing required fields are rejected with a 400 Bad Request response identifying the specific missing fields, keyed to transaction_id where present. account_type must match one of the allowable values defined in Section 7 - records with invalid values are rejected with a 422 error. local_currency must match an ISO 4217 code recognized in FloQast's currency table. Required field values must conform to the specified data types and formats defined in Section 8._

‌

**REQ-SL-02: As a customer technical team, I want to include optional SL Transaction fields in my payload so that I can provide richer transaction context where available without being required to populate every field.**

_**Functional spec:** The SL Transactions endpoint accepts the optional fields defined in Section 8. Optional fields may be included or omitted per record. When included, they must conform to the specified data types; a mismatch returns a 422 error identifying the offending field and record. functional_currency, when provided, must match an ISO 4217 code recognized in FloQast's currency table. When omitted, optional fields are treated as absent - the record is accepted without them. Optional fields present in the payload are captured by auto-configure on first push._

‌

**REQ-SL-03: As a customer technical team, I want to specify whether my submission should append to, upsert into, or replace the existing subledger data for the target period, entity, and account type so that I have explicit control over how multiple submissions are handled.**

_**Functional spec:** Each push must include a submit_mode parameter: append, upsert, or replace. Append: all submitted records are inserted unconditionally. No key matching. Submitting the same transaction_id twice creates duplicate rows. Upsert: records matched on transaction_id. Matches updated; non-matches inserted. Records not in the batch are unchanged. SCD Type 2 version advanced on update: the previous record's effective_end_date is set and the updated record becomes the new active version. Idempotent. Replace: all existing SL Transaction records for the specified period + entity + account_type are removed before the submitted batch is inserted. Replace is scoped to the period + entity + account_type combination - replacing an AR subledger does not affect AP or other account types for the same period. submit_mode is required on every push._

‌

**REQ-SL-04: As a customer technical team, I want to include fields in my SL Transactions payload that are not part of the standard model so that I can pass non-standard subledger attributes through to FloQast without being rejected.**

_**Functional spec:** Fields present in a push payload not defined as required or optional in the standard SL Transactions model are treated as custom fields. The API accepts records containing custom fields without error. Custom fields are passed through as-is. On first push, auto-configure detects and registers custom fields in the lineage per the Auto-Configure sub-PRD. Custom fields introduced after the initial auto-configure run are flagged as unregistered schema additions._

‌

**REQ-SL-05: As a FloQast system, I want to apply standard metadata to all SL Transaction records received via the API so that submissions are traceable, auditable, and correctly attributed to their source.**

_**Functional spec:** FloQast applies the following metadata to each SL Transaction record at ingestion. These fields are system-generated and cannot be overridden: fq_transaction_id (FloQast-assigned internal unique identifier, generated at first ingestion and stable across subsequent upserts), fq_created_at (timestamp of initial ingestion into FloQast), fq_ingested_by (connection and API key identifier associated with the push that created the record), touch_count (number of times the record has been updated via subsequent pushes, starting at 1). Metadata fields are visible within FloQast for reporting and audit purposes. fq_transaction_id may be used by FloQast internally to link SL Transaction records to GL Transactions, reconciliation artifacts, and other data types._

‌

# **10. User Interaction and Design**

The SL Transactions endpoint is a developer-facing API. There is no UI component - customers interact with it programmatically through their integration code or API tooling.

‌

## **Endpoint**

POST /sl-transactions

‌

## **Authentication**

API key passed in the Authorization: Bearer header, consistent with all other FQ API endpoints. See Authentication & API Key Management sub-PRD.

‌

## **Request Structure**

The request body is a JSON object with the following top-level parameters:

‌

* submit_mode (required): "append", "upsert", or "replace".
* period (required): the target period for the submission. Format TBD with Engineering (likely YYYY-MM for monthly periods). Used to scope replace mode.
* account_type (required for replace mode): the account_type being replaced. For replace mode, all existing SL Transaction records for the specified period + entity + account_type are removed. Must match one of the allowable values in Section 7.
* entity_id (conditional): the FQ entity ID for the submission. Required if entity association is not pre-configured at the connection level. See Connection Setup sub-PRD.
* records (required): array of SL Transaction objects, each conforming to the field specification in Section 8.

‌

## **Submit Mode Behavior**

| **submit_mode** | **Behavior** | **When to Use** |
| --- | --- | --- |
| **append** | All submitted records inserted unconditionally. No key matching. Duplicate transaction_id values across pushes create duplicate rows. | New subledger transactions with no overlap with existing data. Not idempotent. |
| **upsert** | Records matched on transaction_id. Matches updated (with SCD2 version advance); non-matches inserted. Unsubmitted records unchanged. Idempotent. | Incremental subledger loads and corrections. Most common mode for daily or intraperiod AR/AP updates where some records already exist. |
| **replace** | All existing SL Transaction records for the period + entity + account_type are removed before the submitted batch is inserted. Scoped to account_type - does not affect other subledger types. | Full subledger refresh for a specific account type and period. Use when the source system re-generates all subledger detail. |

‌

## **High-Volume Considerations**

AR and AP subledgers for large enterprises can contain millions of transaction records per period. Payroll subledgers can similarly be high volume at companies with large workforces. Customers with high-volume subledgers should use the batch session model (POST /batches → chunked POST /sl-transactions submissions → POST /batches/{id}/close) as defined in the High-Volume Data Ingestion sub-PRD. Chunk size guidance (10,000–25,000 records per chunk) applies. The endpoint infrastructure must support high-volume ingestion from Phase 2 launch.

‌

## **GL Transaction Relationship**

SL Transactions and GL Transactions are complementary datasets in FloQast. SL Transactions provide the subledger detail (e.g., individual AR invoices); GL Transactions provide the summarized general ledger view (e.g., the AR account movement). FloQast uses both to support subledger-to-GL reconciliation: the sum of SL Transactions for a given account_type should tie to the corresponding GL account balance.

‌

## **Error Responses**

* 400 Bad Request: missing required fields, missing or invalid submit_mode, missing period, unrecognized currency code, malformed payload.
* 401 Unauthorized: API key missing, invalid, or revoked.
* 403 Forbidden: valid key used outside its connection scope.
* 422 Unprocessable Entity: account_type value outside allowable set, field value wrong data type.
* 429 Too Many Requests: rate limit exceeded. Includes Retry-After header.
* 500 Internal Server Error: unexpected system failure.
