## Objective

Today, Data Studio has no dedicated surface for managing dimensions. Admins who want to understand which sources feed a dimension, which models depend on it, or whether its values are consistent must trace that context manually across individual models. This becomes increasingly difficult as more sources are configured and dimension-type models accumulate.

The Dimensions tab introduces a centralized management and catalog view for all dimension objects in a TLC. Specifically, it provides:

1. A single table of all dimensions — with status, linked model count, value count, and last updated

2. A detail view per dimension — showing its member values and data quality signals

3. A Data Flow view — visualizing how sources, the dimension, and dependent models interrelate at both node and field level

When this ships, an FQ Admin can immediately understand the health and dependency map of any dimension without opening a single model.

## Why This Is Important

Dimensions are fundamentally different from other model types in Data Studio. Where most models have a single source and a clear owner, dimensions can be written to by multiple sources simultaneously — and they serve as shared reference tables that many models depend on. This creates two compounding risks that have no current mitigation:

**1. Dependency opacity.** As a TLC grows, admins lose visibility into which models depend on a given dimension. A configuration change to a dimension's source — or a silent data quality issue — can cascade across multiple downstream models without the admin knowing what's affected.

**2. Data quality drift.** Because dimensions standardize categorization (e.g., Department, Region, Cost Center), inconsistent values in a dimension — such as "US of A" alongside "United States" — propagate errors into every model that references it. Without a dedicated surface to inspect dimension values and surface duplicates, these errors go undetected until they surface in downstream FloQast products.

**Why now:** IDEA-2487 (Multi-File Handling) makes it possible for multiple source files to contribute to a single dimension, materially increasing both dependency complexity and data quality risk. But the broader opportunity is larger than risk mitigation: while the Financial Data Model (FDM) provides some dimensional management today, it operates post-normalization, is scoped to reporting, and is not integrated across business units. No part of the current platform gives admins visibility into how dimensional data is structured at the source, where it originates, and what depends on it — before it reaches downstream products. The Dimensions tab introduces that transparency for the first time. We believe this level of clarity is a meaningful lever for driving adoption of the new platform, and the Close business unit has already identified dimensional support as a priority.

## Use Cases

**Use Case 1: Reviewing dimension health across the TLC**\
An FQ Admin navigates to the Dimensions tab to get a high-level view of all dimensions. They scan the Status column and immediately spot two dimensions flagged with warnings — one with a data quality issue, one orphaned with no models using it. They now know which dimensions need attention without opening a single model.

**Use Case 2: Investigating a specific dimension's values**\
An FQ Admin notices the Department dimension has a data quality warning. They click into the dimension and open the Values tab, where they see "Eng" flagged as a possible duplicate of "Engineering" with 23 records. They now have the information they need to address the inconsistency at the source.

**Use Case 3: Tracing a dimension's data flow before making a change**\
An FQ Admin needs to update the Department dimension — perhaps adjusting how values are mapped or changing a source field. Before making the change, they open the Dimensions tab and navigate to Department's Data Flow view. The Overview shows them that three models — GL Transactions, Trial Balance, and Accounts — all depend on this dimension. They switch to Fields view to confirm exactly which model fields are joined on the dimension key, so they can anticipate the downstream impact before proceeding.

## Assumptions — Established

1. **Dimensions have two creation paths with different underlying structures.** A dimension can be created as a standalone model in Catalog (Type: Dimension), in which case it has its own source file(s) and the full Sources → Mapping → Versions structure. Alternatively, a dimension can be defined from within an existing model's Dimensions sub-tab — in this case, no separate dimension file is required; the dimension values are derived from the parent model's source data. Both paths produce a dimension object that appears in the Dimensions tab.

2. **Dimensions are entity-agnostic.** Even when source data is entity-scoped, the dimension produced from it applies globally across all entities. The Dimensions tab does not include entity filtering.

3. **Entity is not a dimension.** Entity is managed separately via FloQast's org structure and permissioning system and does not appear in this tab.

4. **No dimensions are required.** There is no FQ-prescribed list of dimensions that must exist. The tab is entirely user-driven and accumulates over time as users build models.

5. **Two creation paths exist, both via Catalog.** Dimensions are created either by building a new model (Type: Dimension) in Catalog, or by defining a dimension from within an existing model's Dimensions sub-tab. The Dimensions tab is a management surface only — it does not introduce a third creation path.

6. **Access is FQ Admin only in V1.** Broader role access is expected in a future iteration but is explicitly out of scope here.

7. **"Stale" is not a valid status.** Dimensions change slowly enough that source sync recency is not a meaningful health signal. It is intentionally excluded from the status model.

8. **Entity and Chart of Accounts are not managed in this tab.** Both are special dimension types with their own dedicated management surfaces. The Dimensions tab covers user-defined dimensions only.

9. **Dimension creation and editing follows existing model permissions.** No new permission model is required for this tab — creating and modifying dimensions uses the same role-based access controls as creating and modifying models.

## Scope

**In Scope**

* Dimensions tab: management table showing all dimensions in the TLC (Name, Linked Models, Unique Values, Last Updated, Status)

* Four status states: Draft, Active, Data Quality warning, Orphaned

* Empty state for TLCs with no dimensions configured

* Dimension detail view with Values tab, Data Flow tab, and Logs tab

* Data Flow tab: Overview (node-level) and Fields (field-level) display modes

* Health indicators: Orphaned (0 linked models) and Data Quality (duplicate keys, blank values)

* Warning detail drawer on the Values tab for data quality issues

**Out of Scope — V1**

* Dimension deletion (safety story not yet defined — see Open Items)

* Broader role access beyond FQ Admin (expected in a future iteration)

* Entity-specific dimensional data scoping

* Data quality as a model-level health signal (promising but not yet scoped — see Open Items)

* "Show orphaned" filtered view (candidate for a future iteration)

* Upstream data correction workflows (identified as a future use case)

* Entity Mappings tab alignment (pending decision on whether it merges here — see Open Items)

* "Stale" status state

* Draft version indicator when an Active version and in-progress Draft coexist

## Requirements

**Story 1: Viewing the Dimensions tab**

*As an FQ Admin, I want to see all dimensions in my TLC in a single table so that I can assess their health and dependencies at a glance.*

* **Given** I am an FQ Admin and navigate to the Dimensions tab, **When** dimensions exist in my TLC, **Then** I see a table with one row per dimension showing: Name, Linked Models (first model name + overflow count), Unique Values count, Last Updated date, and Status badge.

* **Given** I am an FQ Admin and navigate to the Dimensions tab, **When** no dimensions exist in my TLC, **Then** I see the empty state with the headline "No dimensions yet", explanatory body copy, and an inline text link to Catalog.

* **Given** the Dimensions tab is loaded, **When** multiple dimensions exist, **Then** rows are sorted alphabetically by Name by default.

* **Given** I am viewing the Dimensions table, **When** a dimension has linked models, **Then** each model name in the Linked Models column is a hyperlink that navigates to that model's detail view.

* **Given** a dimension has more linked models than are shown inline, **When** I click the "+N more" overflow count, **Then** a list of all remaining linked models appears, each as a hyperlink to that model's detail view.

---

**Story 2: Dimension status states**

*As an FQ Admin, I want each dimension to show a clear status so that I know which ones need attention.*

* **Given** a dimension's own model is in Draft state (not yet published), **When** I view it in the table, **Then** its Status shows **Draft** — the publish state of models that reference this dimension has no effect on its status.

* **Given** a dimension is live and referenced by at least one model, **When** I view it in the table, **Then** its Status shows **Active**.

* **Given** a dimension has duplicate key values or blank name/value fields in its source data, **When** I view it in the table, **Then** its Status shows a **Data Quality** warning badge.

* **Given** a dimension has no models referencing it, **When** I view it in the table, **Then** its Status shows an **Orphaned** warning badge.

* **Given** a dimension's source has not synced recently, **When** I view it in the table, **Then** no "Stale" status is shown — sync recency is not surfaced as a status signal.

* **Given** a dimension has a published (Active) version and a Draft version simultaneously, **When** I view it in the table, **Then** its Status shows **Active** — the presence of an in-progress draft version does not change the displayed status.

---

**Story 3: Viewing a dimension's values**

*As an FQ Admin, I want to inspect the member values of a dimension so that I can verify its contents and identify data quality issues.*

* **Given** I am viewing the Dimensions table, **When** I click a dimension row, **Then** I am taken to the dimension's detail view, defaulting to the Values tab.

* **Given** I am on the Values tab, **When** values exist, **Then** I see a table of all dimension member values sorted alphabetically by default, with a record count for each value and a relative bar chart scaled to the highest count.

* **Given** a dimension value has a data quality issue (e.g., duplicate key, possible duplicate name), **When** I view the Values tab, **Then** a warning icon appears on that row.

* **Given** warning icons are present on the Values tab, **When** I click a warning icon, **Then** a detail drawer expands below the grid describing the specific issue.

* **Given** data quality issues exist on the Values tab, **When** I view the tab, **Then** a "Show issues only" toggle is visible and filters the table to flagged rows only.

* **Given** I want to find a specific value, **When** I use the search field on the Values tab, **Then** the table filters to matching values in real time.

---

**Story 4: Data Flow — Overview mode**

*As an FQ Admin, I want to see a visual map of a dimension's sources and dependent models so that I can understand its full dependency picture at a glance.*

* **Given** I am on a dimension's detail view, **When** I select the Data Flow tab, **Then** I see the Overview mode by default — source cards on the left, the dimension card in the center, and model cards on the right, connected by bezier curves with directional arrowheads.

* **Given** I am in Overview mode, **When** I view a model card, **Then** it displays a role badge indicating whether the model is **Primary** (where the dimension's values originate) or **Linked** (references the dimension as a lookup).

* **Given** I am in Overview mode, **When** I click a model card, **Then** I am navigated to that model's detail view.

* **Given** a dimension has multiple sources, **When** I view the Overview, **Then** all contributing sources are shown as separate cards on the left side.

---

**Story 5: Data Flow — Fields mode**

*As an FQ Admin, I want to see the field-level connections between sources, a dimension, and its dependent models so that I can understand exactly how data flows before making a change.*

* **Given** I am on the Data Flow tab, **When** I toggle to Fields mode, **Then** each card expands to show its field-level connections — source fields mapping to the dimension label on the left, and the dimension key mapping to model fields on the right.

* **Given** I am in Fields mode, **When** I view the source-to-dimension connections, **Then** I see: `source field → dimension label` for each contributing source.

* **Given** I am in Fields mode, **When** I view the dimension-to-model connections, **Then** I see: `dimension key → model field` for each dependent model.

* **Given** I am in Fields mode, **When** I view a model card, **Then** it still displays its Primary or Linked role badge.

* **Given** I am in Fields mode, **When** I click a model card, **Then** I am navigated to that model's detail view (same behavior as Overview mode).

---

**Story 6: Dimension detail header and navigation**

*As an FQ Admin, I want clear context and easy navigation when I'm inside a dimension's detail view so that I always know what I'm looking at and can move between sections efficiently.*

* **Given** I am on a dimension's detail view, **When** the page loads, **Then** the header displays: dimension name, status badge, source connector chip(s), and last updated date.

* **Given** a dimension has multiple source connectors, **When** I view the header, **Then** each source is shown as a separate chip.

* **Given** I am on the detail view, **When** I view the left sidebar nav, **Then** I see three items: **Values**, **Data Flow**, and **Logs** — with the active section highlighted.

* **Given** I am on the detail view, **When** I click Values, Data Flow, or Logs in the sidebar, **Then** the main content area updates to show that section without a full page reload.

---

**Story 7: Viewing a dimension's logs**

*As an FQ Admin, I want to see a log of changes and runs for a dimension so that I can audit its history and understand when its data last changed.*

* **Given** I am on a dimension's detail view, **When** I navigate to the Logs tab, **Then** I see a chronological list of configuration changes and run events, each referencing the underlying model.

* **Given** I navigate to the Logs tab, **When** no log entries exist yet, **Then** I see an appropriate empty state.

## UX Requirements

**Key screens and states:**

1. **Dimensions tab — populated** — management table with status badges, linked model chips, and value counts

2. **Dimensions tab — empty state** — headline, body copy, and inline Catalog link

3. **Dimension detail — Values tab** — sortable value table with record count bars, warning icons, detail drawer, search, and "Show issues only" toggle

4. **Dimension detail — Data Flow tab (Overview)** — node-level lineage graph with source, dimension, and model cards; Primary/Linked role badges; clickable model cards

5. **Dimension detail — Data Flow tab (Fields)** — field-level expansion of the same graph

6. **Dimension detail — Logs tab** — chronological run and change log referencing the underlying model

**Prototype references:**

* React prototype built April 24, 2026 in the data-studio project — covers all six screens above, can be used as a Figma reference for detailed interaction design

* [Claude Design Prototype — Dimensions](https://claude.ai/design/p/019dd045-909f-75d1-9452-b43d8772f6cd?file=Dimensions.html&via=share)

**Model hyperlinking** — Wherever a model is referenced in the Dimensions tab (Linked Models column in the management table, model cards in Data Flow, log entries), the model name should be a hyperlink that navigates directly to that model's detail view. This is a key affordance for admin usability.

**Left for the designer:**

* Exact visual treatment of the Data Flow graph (card sizing, curve routing, spacing at scale)

* Behavior of the warning detail drawer (animation, positioning relative to the grid)

* Empty state illustration or iconography

* Responsive behavior at smaller viewport widths

* Visual differentiation between Primary and Linked role badges

* Pattern for the "+N more" overflow expansion (tooltip, popover, inline expand, or other) — should follow an established Data Studio convention if one exists
