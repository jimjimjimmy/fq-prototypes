## 🎯 Objective

This PRD defines the H2 2026 expansion of the API Endpoint Management initiative within FloQast Data Studio, encompassing three parallel workstreams: Push API Support (Phase 6), the AI Setup Assistant (Phase A), and the onboarding of a new pull API source using the framework delivered in Q2.

The Q2 work (Phases 1–5) established the foundational pattern for pull-based API data ingestion — where FloQast initiates scheduled requests to external systems. That work is complete and in production. This parent PRD does not redefine those phases; it extends them. Phase 6 adds push/webhook support as a first-class connection type. Phase A adds an AI-powered setup assistant that reduces manual configuration effort for both pull and push flows. The new source onboarding applies the existing pull framework to an additional ERP without requiring new engineering, and is expected to be driven primarily by PM and implementation.

Primary users across all three workstreams are FloQast admins and implementation team members who configure and manage API connections in Data Studio. Secondary stakeholders include Engineering (for Phase 6 and Phase A infrastructure) and the FloQast implementation team responsible for customer onboarding.

Together, these workstreams complete the API connection framework for the current product cycle: bidirectional integration support (pull and push), faster and more accessible setup via AI assistance, and expanded source coverage using the generic pull connection wizard.

## 💡 Key Benefits

* **Bidirectional ingestion:** FloQast can now receive data both by polling external systems (pull) and by accepting data delivered by external systems on their own schedule (push/webhook), covering the full range of customer ERP integration patterns.

* **No-engineering connection setup:** Admins and implementors can configure push connections, provision webhook URLs, manage auth, and handle errors entirely within Data Studio — no support tickets required.

* **AI-reduced setup friction:** The AI Setup Assistant reads API documentation and pre-populates wizard fields, cutting manual research time for both pull and push connections and reducing configuration errors from transcription mistakes.

* **Guided experience for non-technical users:** The conversational AI interface lets less technical admins ask plain-language questions about setup steps without leaving the wizard.

* **Expanded source coverage:** New pull API sources can be onboarded using the generic API setup wizard without requiring new engineering work, leveraging the Q2 framework directly.

* **Consistent connection model:** Push joins pull as a fully supported, first-class connection type within Data Studio, using a shared wizard pattern and configuration paradigm.

* **Transparent error handling:** Both push and pull connections surface failure logs, auth errors, and processing issues directly to admins, enabling self-service troubleshooting.

## ✅ Use Cases

1. **Push connection onboarding:** A FloQast implementor is onboarding a customer whose ERP sends webhook events on journal entry posting. The implementor creates a push connection in Data Studio, selects HMAC signature verification as the inbound auth method, receives a provisioned webhook URL, and registers it in the source system — completing setup without opening a support ticket.

2. **AI-assisted pull setup:** An implementor is configuring a pull API connection for an ERP they haven't worked with before. They paste the vendor's developer documentation into the AI Setup Assistant. The assistant pre-populates the base URL, auth method, endpoint paths, pagination type, and rate limits. The implementor reviews flagged fields, confirms values, and reaches the test step in a fraction of the time manual configuration would have required.

3. **Generic pull source configuration:** A PM or implementor needs to onboard a new ERP customer using the pull API framework built in Q2. No new engineering is required; the implementor completes the standard generic pull connection wizard (aided by the AI assistant or manual entry) and validates connectivity with a test run. The connection goes live without an engineering ticket.

4. **Multi-model push from a single source:** A customer's ERP sends both journal entry and GL balance data via webhook using the same credentials. An implementor configures two push endpoints on the same push connection, each mapped to a different data type, without duplicating auth configuration.

5. **Push error investigation:** A push connection begins logging auth failures after the source system rotates its signing secret. An admin opens the push event log in Data Studio, identifies the failure type, updates the shared secret in the connection edit view, and confirms the next inbound payload is accepted — without engineering involvement.

6. **AI clarifying question exchange:** An implementor provides API documentation that describes endpoint paths but omits the pagination method. The AI assistant pre-fills what it can and asks: "I wasn't able to determine the pagination method from the documentation provided. Does this API use cursor-based, offset/limit, or page-number pagination?" The implementor answers, the assistant fills in the field, and setup continues.

7. **Skipping AI setup:** An experienced implementor opens the AI setup step, already knows all configuration values, and clicks Skip. They complete setup manually with no friction. For a subsequent connection they're less familiar with, they use the AI step to reduce research time.

## 🤔 Assumptions

1. The Q2 pull API framework (Phases 1–5) is stable and in production. This PRD assumes those features require no rework as a dependency for Phase 6 or new source onboarding.

2. New pull API sources support the generic pull pattern (FloQast-initiated scheduled requests) and do not require custom connectors or schema transforms beyond what the existing pull framework handles. If a source requires net-new engineering, that work is out of scope and must be scoped separately.

3. Source systems sending push data are responsible for retry logic. FloQast acknowledges inbound payloads with an HTTP 200 and processes asynchronously; processing outcomes are not communicated in the synchronous response.

4. The AI Setup Assistant does not pre-populate or store credential values (API keys, secrets, tokens, passwords) under any circumstances.

5. The AI assistant is powered by an LLM (Anthropic Claude API or internal equivalent). The specific model, infrastructure, and data handling posture are to be confirmed by Engineering and Security before Phase A.1 begins.

6. New source onboarding will be handled by PM/implementation using the existing pull wizard. No new Data Studio UI surfaces are required for individual sources.

7. Field mapping from inbound push payloads (or pull responses) to the FloQast data model is handled in a separate PRD and is not in scope here. Sample payload capture for push connections is in scope as a prerequisite for that downstream work.

8. The push URL provisioned per connection is stable for the life of the connection unless explicitly regenerated. URL rotation workflows are to be designed with Security input (see Open Questions).

## ⭐ Milestones

1. **Phases 1–5 — Pull API Framework (Q2, Complete):** Core pull-based API data ingestion is live. FloQast admins and implementors can configure pull connections, define endpoints, schedule syncs, and manage connections in Data Studio. This is the foundation for all work in this PRD.

2. **Phase 6.1 — Push Connection Foundation:** Admins can create a push connection in Data Studio, select an inbound auth method, provision a webhook URL, define event types, configure failure handling, and set volume expectations. Webhook URL is live and ready to register in the source system. Sub-PRD: [Push API Support](https://floqast.atlassian.net/wiki/spaces/Data/pages/4491247622).

3. **Phase 6.2 — Push System Processing:** FloQast receives, authenticates, and processes inbound payloads asynchronously. Includes HTTP 200 acknowledgment, deduplication, error handling per configured failure mode, and handoff to the data pipeline. Sample payload captured on first successful receipt per endpoint.

4. **Phase 6.3 — Push Observability and Testing:** Push event log visible in the connection detail view. Error surfacing for auth, schema, and processing failures. Test connection flow allows admins to validate push setup before go-live.

5. **Phase 6.4 — Push Multi-Endpoint and Management:** Edit push connection configuration. Multiple push endpoints supported per connection with independent event types, mirroring the pull endpoint pattern. Connection detail view updated with full push endpoint list and per-endpoint actions.

6. **Phase A.1 — AI Setup Assistant (Pull):** AI step added as Step 0 of the Pull API setup wizard. Users can paste documentation text, provide URLs, or write a freeform description. AI pre-populates pull wizard fields. Flagged fields displayed with confidence indicator. Skip option available at all times. Sub-PRD: [AI Assistant Setup](https://floqast.atlassian.net/wiki/spaces/Data/pages/4491214880).

7. **Phase A.2 — AI Q&A and URL Ingestion:** Conversational chat panel added to the AI step. AI can ask clarifying questions; users can ask plain-language setup questions. URL input added with server-side fetch.

8. **Phase A.3 — AI Push Support:** AI step integrated into the Push API setup wizard. AI maps ingested documentation to push-specific fields: inbound auth suggestion, event type definitions, failure handling recommendations, volume expectations.

9. **New Source Onboarding:** New ERP source configured as a pull API connection using the existing generic pull connection wizard. No new engineering required. PM/implementation-driven configuration validated through standard connection test and activation flow.

## Scope

### In scope

* Push/webhook connection creation, configuration, and management in Data Studio (Phase 6)

* Inbound authentication configuration for push connections (HMAC signature verification and shared secret, at minimum)

* Webhook URL provisioning and management (including regeneration workflow)

* Push event type definition and multi-endpoint configuration

* Failure handling mode selection (Log and alert / Skip and continue / Halt)

* Push event logging, error surfacing, and sample payload capture

* AI Setup Assistant embedded in Pull and Push API setup wizards (Phase A)

* AI-driven field pre-population from pasted documentation, freeform description, uploaded files, and documentation URLs

* Conversational Q&A interface within the AI step

* Flagged field confidence indicators and review panel

* New ERP source onboarding as a pull API connection using the Q2 generic framework (PM-configured, no new build)

### Explicitly out of scope

* Pull API framework (Phases 1–5) — complete and not redefined here

* Field mapping from push payloads or pull responses to the FloQast data model — separate PRD

* Source system configuration — FloQast provides the webhook URL; registering it in the source system is the customer's responsibility

* AI credential pre-population — the AI step never generates or pre-fills API keys, secrets, tokens, or passwords

* Persistent AI memory across separate setup sessions or connections

* Standard connector setup flows (e.g., QBO direct connector) — AI step applies to custom API connections only

* Write-back or bi-directional sync — this initiative covers inbound data ingestion only

* Net-new engineering for individual source systems — if a source requires a custom connector or schema transform beyond the existing pull framework, that work is out of scope and must be separately scoped and resourced

## 🎨 User Interaction and Design

**Prototype (Push API):** [Pull pattern reference](https://www.figma.com/make/Q7A2kkXSSDBehr7aG2Nxsf/QBO-Fivetran-Connection-with-Table-Library) (push-specific prototype TBD, to be built on this foundation)

**Prototype (AI Assistant):** [AI API setup workflow](https://www.figma.com/make/3c2VXFNTKrtHJWu6Cs4kra/AI-API-setup-workflow)

### Push Connection Setup Wizard

The push setup wizard is triggered when a user selects Push/Webhook as the integration type during new connection creation. It follows a 9-step flow: Connection Basics → API Type Selection → Inbound Auth Configuration → Webhook URL Generation → Event Type Definition → Failure Handling → Volume Expectations → Test Connection → Review and Activate. The webhook URL is generated and displayed with a copy action at Step 4. The test step allows the admin to send a real or sample payload and see receipt, auth, and parse results in real time.

### Push Connection Detail View

The connection detail view for push connections prominently displays the webhook URL with a copy action and a regenerate option (with confirmation warning). Below the URL, a push endpoint list mirrors the pull endpoint list pattern — each row shows endpoint name, event type, activation status, last-received timestamp, and error count. An Add Endpoint action allows additional push endpoints to be added. A push event log panel shows filterable inbound event history per connection. A sample payload viewer is accessible per endpoint from the endpoint row.

### AI Setup Assistant (Step 0)

The AI assistant step is the first screen displayed after the user selects API type (Pull or Push). It presents a text input area for pasting documentation or describing the API in freeform, a URL input field with an Add URL option for multiple links, and a file upload option for PDF or Word documentation. A Submit / Analyze button triggers AI processing with a loading state. A conversational chat panel displays AI clarifying questions proactively and accepts user-typed questions. A Skip button is always visible and labeled "Skip and set up manually."

After analysis, the AI step transitions to a review panel listing all AI-suggested field values grouped by wizard section. Confident fields are shown in standard styling. Flagged fields appear with a yellow highlight and caution icon; hovering reveals the AI's confidence note. Blank fields (AI could not determine) include a note directing the user to fill them in on the next step. A Confirm and Continue button advances the wizard with pre-filled values applied as editable defaults.

### Generic Pull Source Setup

New source onboarding follows the standard pull connection wizard with no custom UI. The implementor selects the source system (or enters a custom name), optionally uses the AI setup assistant with the source's API documentation, completes connection configuration, runs a test connection, and activates. No source-specific screen or workflow exists.

## ⚠️ Out of Scope

* **Pull API framework (Phases 1–5):** Complete as of Q2. Not redefined here. The push and AI work extend this foundation but do not modify it.

* **Field mapping from push payloads or pull responses to the FloQast data model:** Covered in a separate PRD. Sample payload capture (push) and AI pre-population (pull/push) are in scope here as prerequisites for that work.

* **Source system configuration:** FloQast provides the webhook URL; registering it in the source system is the customer's responsibility.

* **AI credential pre-population:** The AI Setup Assistant never generates, suggests, or pre-fills credential values. Credential fields are always completed manually.

* **Persistent AI memory across separate connections or sessions:** AI context is scoped to the active setup session or saved draft. No cross-connection learning.

* **Standard connector flows:** The AI setup step applies to custom API connections only. Standard connectors follow their existing setup paths.

* **Write-back or bi-directional sync:** This initiative covers inbound data ingestion only.

* **Net-new engineering for individual source systems:** If a source requires a custom connector, schema transform, or any build beyond the existing pull framework, that work is out of scope and must be separately scoped and resourced.

* **On-demand internal trigger interface:** Covered in parent PRD Phase 4; not in scope here.

* **External customer-facing push trigger API:** Push is always initiated by the source system. FloQast does not expose a public API for customers to trigger pushes on demand.
