## 🎯 Objective

This PRD defines the requirements for adding hierarchical data support to Data Studio's core data models. It covers three distinct but related capabilities: (1) within-field hierarchy, where objects belonging to a single field (such as accounts or companies) can be arranged into one or more parent-child trees; (2) company-scoped account hierarchy, where the account tree for a specific company can be captured and queried as it existed at a given point in time; and (3) cross-field hierarchy dependencies, where ordered relationships between different fields (e.g., Location → Department → Team) encode how those fields relate structurally to one another. This PRD does not cover UI for end-user hierarchy management, downstream consumption patterns in Close or Flux, or ERP-specific hierarchy ingestion pipelines.

The primary users are FloQast implementors configuring Data Studio for customers, Data Studio admins maintaining hierarchy definitions post-go-live, and end customers who need to query or validate their own hierarchical data. Internal engineering teams building features on top of Data Studio are a secondary audience — the data structures defined here must be queryable and extensible enough to support downstream product surfaces without redesign.

Accounting data is inherently hierarchical. Accounts roll up into parent accounts, companies sit within ownership structures, and dimensional fields like Cost Center or Location only carry meaning in relation to other fields. Today, Data Studio stores these as flat lists with no structural context, which means downstream features cannot perform accurate roll-up calculations, variance analysis across hierarchy levels, or cross-dimensional filtering. This capability closes that gap.

Once in place, hierarchical data support unblocks accurate consolidation reporting, period-over-period comparisons at any level of a tree, and richer cross-dimensional filtering across FloQast products.

## 💡 Key Benefits

* **Accurate roll-up calculations:** Aggregating balances or metrics up a parent-child account tree becomes possible without custom logic per customer.

* **Point-in-time account structure:** Capturing the account tree for a specific company at a moment in time supports historical comparisons even when the structure changes.

* **Flexible dimensional relationships:** Cross-field dependency chains (e.g., Location → Department → Team) can be defined once and reused across any product consuming Data Studio.

* **Multiple root trees per field:** A field can support multiple independent trees, accommodating customers with multi-entity or multi-book structures under one configuration.

* **Tree-level placement integrity:** Enforcing that an object belongs to at most one location within any single tree prevents ambiguous hierarchy states that would corrupt roll-up logic, while still allowing the same object to appear across multiple trees.

* **Extensible to dimensions:** While companies and accounts require hierarchy support, the same data model can be optionally applied to dimension fields, reducing future engineering rework.

* **Foundation for consolidation:** Cross-company and cross-entity hierarchy support provides the structural layer needed for intercompany and consolidation features.

## ✅ Use Cases

**A FloQast implementor sets up an account hierarchy for a new customer.** During implementation, the implementor loads a customer's chart of accounts and arranges them into a parent-child tree within Data Studio. The customer uses multiple account groups (e.g., Operating Expenses, Capital Expenditures), so the implementor creates two separate root trees under the Accounts field. The system ensures no account appears more than once within any single tree, though an account may appear in both trees if needed.

**An admin updates the account tree mid-year after a restructure.** A customer reorganizes its chart of accounts in Q3. An admin modifies the hierarchy in Data Studio, moving several accounts to new parent nodes. The system captures the updated structure while preserving the prior state so that Q1/Q2 reports still reflect the original tree at the time of those periods.

**A downstream system queries the account tree for a specific company as of a given date.** A FloQast service (e.g., Flux or Close) requests the account hierarchy for Company X as it existed on March 31. Data Studio returns the tree structure — parent-child relationships, depth, and leaf nodes — reflecting the state of the hierarchy on that date rather than the current state.

**A FloQast implementor defines a cross-field dependency chain for dimensions.** The customer tracks expenses by Location, and within each Location by Department, and within each Department by Team. The implementor defines this dependency chain in Data Studio. The system enforces that when querying at the Team level, the parent Department and grandparent Location are always resolvable.

**An admin validates hierarchy integrity before a close period.** Prior to month-end close, an admin runs a check against the account hierarchy to confirm no accounts have duplicate placements within a tree, no circular references exist, and cross-field dependency references are intact. The system surfaces any violations with enough context to resolve them.

**A FloQast implementor configures company hierarchy for a multi-entity customer.** A customer with 12 legal entities needs them organized into a reporting structure: a US holding company with regional subs, and a separate international holding company. The implementor creates two root trees under the Companies field. The system validates the structure and confirms no entity appears twice within the same tree.

**A customer queries which accounts are direct children of a given parent.** Using a Data Studio API or export, a customer wants to see all accounts that roll directly into a specific summary account. The system returns the immediate children in the tree, along with metadata indicating whether those children have further descendants.

## 🤔 Assumptions

1. Data Studio is the system of record for hierarchy definitions — ERPs may be the source of hierarchy data, but Data Studio owns the structured representation.

2. An object (account, company, or dimension value) can exist in at most one location within any single tree — this is a hard constraint, not a configurable option. The same object may appear in multiple trees within the same field.

3. Multiple root trees per field are supported, but cycles (circular parent-child references) are never valid and must be rejected at write time.

4. Point-in-time hierarchy state means Data Studio must store hierarchy history — a change to the tree does not overwrite the prior state.

5. Cross-field dependency hierarchy is ordered and directional — if Location → Department is defined, Department is a child of Location, not the reverse. The chain is not bidirectional.

6. The initial implementation targets Accounts and Companies as required hierarchy-capable fields. Extension to dimension fields is in scope but may ship in a later phase.

7. Hierarchy configurations are scoped per organization — one customer's hierarchy does not affect another's.

8. Downstream consumers (Close, Flux, etc.) will query hierarchy via Data Studio APIs; this PRD does not define those API contracts, but the data model must support them.

## ⭐ Milestones

1. **Phase 1: Within-field hierarchy model (Accounts & Companies)** — Define and implement the core data model for parent-child hierarchies within a single field. Covers multiple-tree support, tree-level single-placement enforcement, and cycle detection at write time. Implementors can configure account and company hierarchy structures in Data Studio.

2. **Phase 2: Point-in-time company-scoped account hierarchy** — Extend the hierarchy model to capture temporal state — when a hierarchy changes, the prior structure is preserved and queryable by date. Downstream systems can request "the account tree for Company X as of \[date\]" and receive an accurate historical snapshot.

3. **Phase 3: Cross-field dependency hierarchy** — Implement support for ordered dependency chains across distinct fields (e.g., Location → Department → Team). Allow implementors to define the chain, enforce referential integrity across the fields, and expose the chain for downstream querying.

4. **Phase 4: Extension to dimension fields (optional)** — Apply the within-field hierarchy model to dimension fields beyond Accounts and Companies. This phase is contingent on customer demand and downstream product readiness.

5. **Phase 5: Hierarchy integrity tooling** — Build validation and reporting tools that allow admins and implementors to detect and resolve hierarchy violations (orphaned nodes, duplicate within-tree placements, broken cross-field chains) before or during close periods.

## Scope

### In scope

* Within-field parent-child hierarchy for Account and Company fields

* Multiple independent root trees per field

* Tree-level single-placement constraint enforcement (an object can exist in at most one node within any single tree)

* Cycle detection and rejection at write time

* Point-in-time hierarchy snapshots for company-scoped account hierarchies

* Cross-field dependency chains with ordered directionality

* Optional within-field hierarchy for dimension fields

* Integrity validation for hierarchy configurations (orphan detection, duplicate within-tree placement, cycle detection)

### Explicitly out of scope

* UI for end-user hierarchy management (separate design effort)

* ERP-specific ingestion pipelines for hierarchy data (covered under integration PRDs)

* Downstream API contracts for Close, Flux, or other consuming products

* Hierarchy-based roll-up calculations or aggregation logic (consuming products own this)

* Multi-organization or cross-tenant hierarchy sharing

### Dimension Nesting in Mapping

When configuring field mappings in Data Studio, an implementor can define how dimension fields relate to one another by nesting them in an ordered chain. In the mapping interface, dimensions can be designated as parent or child of another dimension field. This produces the cross-field dependency chain that drives how dimension values are associated at ingestion time. The implementor selects from available dimension fields for the organization, arranges them in order, and saves the chain. The canonical data model receives the dependency definition as structured metadata, which downstream hierarchy logic can consume.

### Hierarchy Fields in Mapping

In the field mapping configuration, implementors can designate specific fields as hierarchy-contributing. For fields flagged as hierarchy-capable (Accounts, Companies, and opted-in dimensions), the mapping interface surfaces options to define the parent field — the column or attribute in the source data that carries the parent reference for each record. For example, if a customer's account export includes a `parent_account_id` column, the implementor maps that column to the parent reference slot in Data Studio's account hierarchy data model. This drives how the canonical model is populated with parent-child relationships at ingestion.

### Account Sets Tied to a Company

In the Data Studio mapping and configuration surface, an implementor can define an account set: a named grouping of accounts associated with a specific company. An account set represents the subset of the account field relevant to a given company, and serves as the input for constructing that company's account hierarchy. The implementor selects the company, names the account set, and identifies which accounts (or account ranges) belong to it. An account can belong to multiple account sets across different companies. The account set, once defined, feeds into the company-scoped account hierarchy as the population of nodes available for that tree.

### System / API Interface

Downstream systems and ingestion pipelines interact with hierarchy data through Data Studio's canonical data models. At ingestion, source data carrying parent references (e.g., `parent_account_id`) is mapped and loaded into the hierarchy data model via the configured field mappings. The resulting structure — parent-child node relationships, cross-field dependency chains, and company-scoped account sets — is stored in the canonical models and exposed via read APIs. Downstream consumers request hierarchy data by field, company, chain, or as-of date; Data Studio returns the structured data without requiring those consumers to understand the ingestion source.

## ⚠️ Out of Scope

* **End-user hierarchy management UI:** The visual interfaces for building and editing hierarchy trees are a separate design and engineering effort. This PRD defines the data model and API requirements; UI design is deferred.

* **ERP-specific ingestion for hierarchy data:** How hierarchy structure is extracted from Workday, SAP, Yardi, or other ERPs and loaded into Data Studio is handled by integration-specific PRDs.

* **Roll-up calculation and aggregation logic:** Downstream products (e.g., Flux) are responsible for defining how they consume hierarchy structure to perform aggregations. Data Studio provides the structural layer; calculation logic is out of scope here.

* **Cross-tenant hierarchy sharing:** No hierarchy construct defined here crosses organizational boundaries.

* **Downstream API contract definitions:** The specific request/response schemas for Close, Flux, or other consuming services will be defined in those products' respective PRDs or API specs.

* **Soft-delete / archive for hierarchy nodes:** Policies around archiving or tombstoning obsolete hierarchy nodes (beyond the point-in-time versioning requirement) are deferred pending input from engineering and data governance teams.
