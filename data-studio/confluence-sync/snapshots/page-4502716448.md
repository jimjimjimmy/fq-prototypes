# **1. Objective**

Auto-configure is the process by which FloQast automatically builds the source data linkage, field mappings, and lineage in Data Studio immediately following a customer's first successful data push through the FQ API. The goal is zero manual configuration required for standard fields - a customer completes connection setup, pushes data, and finds their lineage and catalog fully populated and ready to use.

Auto-configure handles four categories of fields: required fields and optional fields (mapped one-to-one from source to target based on the FQ data model spec), dimension fields (detected from the push payload and captured as dimensions), and custom fields (any non-standard fields detected in the push, added automatically to the lineage). The specific data model schemas are defined in the per-model sub-PRDs.

Auto-configure also handles incremental updates: when a new dataset is added to an existing connection, auto-configure runs specifically for that dataset on its first push, without affecting the already-configured lineages for existing datasets.

# **2. Key Benefits**

* No manual lineage or field mapping setup required for standard required and optional fields - configuration is fully automated from the first data push.
* Dimension fields and custom fields are automatically detected from the push payload and added to the lineage, eliminating the need for customers to pre-declare their full schema.
* Data Studio stays current without manual catalog administration - models, lineages, and source data linkages are created and populated automatically.
* Incremental re-configuration for new datasets means customers can expand their connection over time without disrupting existing, already-configured lineages.
* Error surfacing on failure gives the FloQast team and customers clear visibility when auto-configure does not complete, enabling fast resolution.

# **3. Use Cases**

1. A customer completes connection setup for GL Transactions and Balances, then pushes data for the first time. Auto-configure creates the source data linkage entries for both endpoints, builds one-to-one field mappings for all required and optional fields, captures any dimension fields, and creates the GL Transaction and Balance models with their lineages in Data Studio - all without any manual action from the customer or FloQast team.
2. A customer pushes GL Transaction data that includes non-standard fields not in the required or optional model spec. Auto-configure detects these fields in the push payload and automatically adds them as custom fields in the GL Transaction lineage.
3. A customer pushes data that includes fields flagged as dimensions. Auto-configure captures these as dimension entries in the lineage rather than as standard field mappings.
4. An existing customer adds SL Transactions to their connection via the edit flow. On the first SL Transaction push, auto-configure runs for that dataset only, building its source data linkage and lineage without modifying the already-configured GL Transaction or Balance lineages.
5. Auto-configure fails for a dataset due to an unexpected payload structure. An error state is surfaced in the connection management UI so the customer or FloQast implementation team can investigate and resolve.

# **4. Success Metrics**

* Percentage of first data pushes that result in successful auto-configure completion without manual intervention.
* Time from first successful data push to completed lineage configuration in Data Studio (target TBD with Engineering).
* Percentage of connections where no manual lineage edits are required after auto-configure runs for standard fields.

# **5. Assumptions**

* Auto-configure is triggered by the first successful data push for a given dataset, not by connection setup completion. Connection setup prepares the connection; auto-configure fires when data arrives.
* Required and optional field schemas for each data model are known at the time auto-configure runs, as defined in the per-model sub-PRDs.
* Dimension fields and custom fields can only be detected from an actual data push - their presence cannot be inferred from the connection setup configuration alone. (Whether a dedicated sample push is required or if the first real push suffices is an open question - see Section 10.)
* When a new dataset is added to an existing connection, auto-configure for that dataset runs on its first push and does not affect existing dataset lineages.
* Custom fields added after the initial auto-configure has run must be manually configured by the customer. Auto-configure does not re-run retroactively for manual field additions.
* Auto-configure populates Data Studio - specifically the source data linkage, mapping areas of the catalog, and the model and lineage records.

# **7. Scope of Data**

The following are created or populated by auto-configure:

‌

* Source data linkage entries - one per selected dataset/endpoint, representing the FQ API as a data source in Data Studio
* Source-to-target field mappings - required fields (always) and optional fields (if present in the push payload), mapped one-to-one per the FQ data model spec
* Dimension field entries - fields flagged as dimensions in the push payload, captured as dimensions in the lineage
* Custom field entries - any fields in the push payload not in the standard required or optional model spec, added as custom fields in the lineage
* FQ data model instances in Data Studio - the specific model records created with their lineages populated

‌

Field-level specifications for each data model (which fields are required, optional, or dimension-eligible) are defined in the per-model sub-PRDs, not in this document.

# **8. Requirements**

‌

**REQ-AC-01: As a FloQast system, I want to create a source data linkage entry for each endpoint selected in the connection setup when the first data push is received, so that the FQ API connection is represented as a data source in Data Studio.**

_**Functional spec:** On first successful push for a given dataset, the system creates a link between the endpoint and it's corresponding data model in Data Studio. Each endpoint corresponds to a FQ data model type (e.g., the GL Transactions endpoint maps to the GL Transaction model type). The linkage entry must be visible in the source data area of the Data Studio catalog under linked data, categorized under the Connection Name._

‌

**REQ-AC-02: As a FloQast system, I want to automatically create source-to-target field mappings for all required and optional fields when the first data push is received, so that standard field lineage is configured without manual intervention.**

_**Functional spec:** For each dataset endpoint, auto-configure creates a source-to-target field mapping for every required field defined in the FQ data model spec, and for every optional field that is present in the incoming push payload. Mappings are one-to-one: each source field maps directly to its corresponding target field in the FQ model. Field-level specs are defined in the per-model sub-PRDs. If required fields are not provided, an error is flagged indicating that for the push, not all required fields were provided and what the missing required fields are._

‌

**REQ-AC-03: As a FloQast system, I want to detect fields flagged as dimensions in the push payload and capture them as dimensions in the lineage, so that dimension data is correctly classified without requiring manual configuration.**

_**Functional spec:** When a push payload includes fields identified as dimensions (flagged mechanism TBD - see Open Questions), auto-configure captures those fields as dimension entries in the lineage rather than as standard field mappings. Dimension detection requires an actual data push. The specific mechanism by which dimension fields are identified in the payload must be resolved before implementation (see Open Questions)._

‌

**REQ-AC-04: As a FloQast system, I want to detect fields in the push payload that are not part of the standard required or optional model spec and add them as custom fields in the lineage, so that non-standard customer data is captured automatically.**

_**Functional spec:** Any field present in a push payload that is not defined as a required or optional field in the FQ data model spec for that endpoint is treated as a custom field. Auto-configure adds these fields to the lineage automatically on first push with their designated label. Custom fields added after the initial auto-configure has run are not automatically detected - customers must configure those manually via the Data Studio edit flow._

‌

**REQ-AC-05: As a FloQast system, I want to create the FQ data model instances and their lineages in Data Studio when auto-configure runs, so that the full catalog representation is available immediately after the first push.**

_**Functional spec:** Auto-configure creates the specific model instances in Data Studio for each configured dataset endpoint, populated with the source data linkage, field mappings, dimension entries, and custom fields built in REQ-AC-01 through REQ-AC-04. The resulting models and lineages must be visible in both the source data and mapping areas of the Data Studio catalog._

‌

**REQ-AC-06: As a FloQast system, I want to run auto-configure incrementally for new datasets added to an existing connection, so that expanding a connection does not disrupt already-configured lineages.**

_**Functional spec:** When a customer adds a new dataset to an existing connection via the connection edit flow, auto-configure runs for that dataset only when its first push is received. Existing dataset lineages are not modified or re-run. The new dataset follows the same auto-configure process as a first-time setup. New datasets of the same type can be added (for example, a new set of GL transactions tagged to a different entity from the existing GL transactions)._

‌

**REQ-AC-07: As a customer or FloQast implementation specialist, I want to see an error state when auto-configure fails, so that I can identify and resolve configuration issues before they affect data processing.**

_**Functional spec:** If auto-configure fails for any reason - unexpected payload structure, missing required fields, system error - an error state is surfaced in the connection management UI against the affected dataset. Silent failure is not acceptable. The error state must be visible without requiring the user to proactively check; it should surface where the connection is managed. Success states do not require a notification or indicator._

# **9. User Interaction and Design**

‌

Auto-configure is a fully automated, background process. No user action is required when it runs successfully. The user experience is entirely defined by what appears in Data Studio after completion, and by the error state if it fails.

‌

## **Happy Path - What the User Sees After Auto-Configure**

* Data Studio source data: a new source data linkage entry is visible for each configured endpoint, labeled with the connection name and dataset type.
* Data Studio mapping area: one-to-one field mappings are populated for all required and optional fields. Dimension fields appear as dimension entries. Custom fields appear as custom field entries.
* Data Studio models in the catalog: the FQ data model instances are created with lineages fully populated and ready for use.
* No notification or status indicator is shown to the user on success - the populated catalog is the confirmation.

‌

## **Error State**

* If auto-configure fails, an error indicator is surfaced in the connection management UI against the affected dataset/connection.
* The error state is visible without requiring the user to navigate to Data Studio - it should be surfaced where the user manages their connection.
* Error details should provide enough information for the customer or FloQast implementation team to diagnose the issue (e.g., missing required field, unrecognized payload structure).
* Specific error UI design and messaging are TBD with Design and Engineering.

‌

## **Field Classification Logic - Summary**

‌

| **Field Type** | **How Identified** | **Auto-Configure Behavior** |
| --- | --- | --- |
| **Required fields** | Defined in FQ data model spec (per-model sub-PRDs) | One-to-one source-to-target mapping created automatically |
| **Optional fields** | Defined in FQ data model spec (per-model sub-PRDs) | One-to-one source-to-target mapping created if field is present in the push |
| **Dimension fields** | Flagged in the API payload (mechanism TBD - see Open Questions) | Captured as dimensions in the lineage; requires a data push to detect |
| **Custom fields** | Any field present in the push not in the standard required or optional model spec | Detected from data push and added as custom fields in the lineage; requires a data push to detect |

‌

## **Incremental Re-Configure (New Dataset Added)**

* When a customer adds a new dataset to an existing connection, no immediate action is required.
* Auto-configure for the new dataset fires automatically on its first push, following the same process as the initial setup.
* The connection management UI should reflect that the new dataset is pending its first push / auto-configure (status indicator TBD).

# **10. Open Questions**

| **Question** | **Owner** | **Notes** |
| --- | --- | --- |
| Is a dedicated sample push required to detect dimensions and custom fields, or does the first real data push serve this purpose? | PM / Engineering | Most likely a push is required. Key question is whether it needs to be a separate "sample" push or whether the first production push triggers detection. Decision affects the connection setup and onboarding experience. |
| How are dimension fields identified in the push payload - is there an explicit flag/tag in the API spec, or is it inferred? | Engineering / Data | The mechanism by which dimension fields are marked in the payload must be defined before REQ-AC-03 can be implemented. Options include: a dedicated field attribute, a payload wrapper, or a separate field list in the connection setup. |
| What constitutes an auto-configure failure - partial failure (some fields mapped, others not) vs. complete failure? | Engineering | Determines whether the system attempts a partial auto-configure and surfaces warnings, or rolls back entirely and surfaces a hard error state. |
| What does the error state UI look like in the connection management view? | Design / Engineering | Needs design spec - where exactly it surfaces, what information is shown, and whether there is a retry or manual resolution path. |
| What happens to the lineage if a dataset is removed from a connection - is the lineage archived, deleted, or preserved? | Engineering / Data | Downstream impact on existing data and reporting must be considered. Likely the lineage is auto-archived if the changes are saved. If in an active editing state, the final state at the time of save would determine this. |
| How does auto-configure handle schema changes in a subsequent push - e.g., a new custom field appears in a later push? | Engineering | Detection of schema drift would be useful here, though not an initial requirement. We should flag a warning here that there is an additional column that is being sent but not mapped. |

* Authentication and API key management - covered in the Authentication & API Key Management sub-PRD.
* Data ingestion processing and upsert logic - covered in the Upsert & Data Reconciliation sub-PRD.
* Status and observability of data pushes (success/failure of data ingestion) - covered in the Status & Observability sub-PRD.
* Bank Transactions endpoint - future phase.
