## 🎯 Objective

The Draft concept exists in Data Studio today, but the current publish workflow is destructive: publishing a model removes all processed data, requiring a full re-upload. There is no effective date, no bounded reprocessing, and no way to make a configuration change without losing historical data.

This PRD replaces that behavior with a non-destructive publish workflow. Admins set an effective date when publishing, and only the runs within that version's effective range are reprocessed — historical data outside that range is preserved. The current "publish and re-upload everything" pattern is eliminated.

Q3 scope covers the core lifecycle controls that enable this: draft creation, publish with effective date, discard, autosave, and dimension version interactions. Automatic draft creation on structural changes, version history view, manual archive, data preview, and pipeline run logs (see Logging & Audit PRD) are future phases.

Primary users: Data Studio admins.

---

## 🔤 Definitions

For a complete glossary of terms, see the shared [Data Studio: Definitions & Terms](https://floqast.atlassian.net/wiki/spaces/Data/pages/4464869099) page.

**Draft** — An editable, unpublished version of a model. Not processing data. Only one Draft may exist per model at any time.

**Active** — The live, published version of a model. Currently processing data. Only one Active version may exist per model at any time.

**Archived** — A previous Active version that has been superseded by a newer publish. Read-only, preserved for audit. Cannot be re-activated directly — a new Draft must be created from it.

**Effective Date** — The date from which a published version's configuration applies. Can be set to a past date, which triggers reprocessing of historical runs.

---

## 🏅 Why This Is Important

Today, publishing a model in Data Studio wipes all processed data. Every configuration change — no matter how small — requires a full data re-upload to restore what was there before. This is a significant barrier to iteration: admins are disincentivized from making legitimate corrections because the recovery cost is too high.

For a platform that sits upstream of the financial close, this is a serious risk. A mapping that needs a small fix can't be corrected safely mid-period. The publish workflow as it exists today is not compatible with a production-grade data platform.

The Q3 versioning work eliminates this by introducing effective date-based, non-destructive publishing. Configuration changes go live from the effective date forward; historical data outside that range is untouched. Admins can iterate confidently without fear of data loss.

---

## 🔐 Value Unlocked

Admins can confidently iterate on model configurations without fear of breaking live data processing. Changes happen in a draft, reviewed before publish, and the previous configuration is always preserved. The publish workflow enforces intentionality — nothing goes live by accident.

---

## 🗝️ Key Examples

* **Example 1:** An admin needs to correct a field mapping mid-period. Today this would require publishing and re-uploading all data. With Q3 versioning, they update the Draft and publish with today's effective date — only runs from today forward use the new mapping, and nothing historical is touched.

* **Example 2:** An admin starts editing a Draft and navigates away. When they return, their changes are exactly where they left them — autosave means nothing is lost.

* **Example 3:** An admin accidentally starts making changes and realizes they want to start over. They discard the Draft, reverting to the Active version as the baseline, and create a fresh Draft when ready.

* **Example 4:** An admin tries to create a second Draft while one already exists. The system blocks the action and links them to the existing Draft so they don't lose work.

---

## 💡 Key Benefits

* Changes to live model configurations are always intentional — nothing goes live without a publish action

* Autosave means admins never lose work in progress

* One Draft at a time prevents conflicting parallel changes

* The Active version is never disrupted while a Draft is in progress

* Every publish creates an auditable record of what changed and when it took effect

## 🤔 Assumptions

**Established**

* Only one Draft per model at any time

* Only one Active version per model at any time

* Opening a model opens the most recent version (highest version number)

* Changes to a Draft are autosaved — there is no manual Save button

* Archived versions are read-only and cannot be directly re-activated; a new Draft must be created from them

* Discarding a Draft is permanent — it cannot be recovered

* The version number increments on Draft creation, not on each individual save

* Pipeline run logs are not in scope for this PRD — see Logging & Audit PRD

* Dimension changes are **additive only** — new keys are inserted, existing keys are never modified or deleted by the system. Publishing a dimension version never automatically re-runs linked models; that decision always belongs to the admin

**Open Items to Confirm**

* When both a Draft and an Active version exist, which opens by default? (OQ-1)

* Is publishing gated on valid field mappings — i.e., can an admin publish a model with incomplete or invalid mappings? (OQ-2)

* When a past effective date is set on publish, what exactly triggers the historical reprocessing — is it immediate or queued? (OQ-3)

* Is autosave server-side or client-side persistence? (OQ-4)

## 🗺️ Scope

### 🚗 In Scope

* **Draft creation** from an Active version (manual)

* **Block second Draft** — only one Draft permitted per model at a time; clear warning with link to existing Draft

* **Discard Draft** — permanent, with confirmation; Active version is unchanged

* **Publish Draft** — set effective date (current or past), Draft becomes Active, previous Active becomes Archived

* **Autosave** — all Draft changes saved automatically; no Save button; "Saved" / "Saving…" indicator

* **Dimension version interactions** — additive-only key insertion on dimension publish; auto-insert of unknown keys surfaced by linked models; key removal warning before publish confirmation; no automatic re-run of linked models

### 🚦 Out of Scope (Q3)

* Auto-draft creation on structural changes (source dataset added/removed, field mapping edited) — future

* Draft creation from an Archived version — future

* Delete Draft-only model — future

* Version history view (table of all versions with metadata) — future

* Manual archive — future

* View Archived field mappings (read-only audit access) — future

* Data preview from Active version — future

* Pipeline run logs — see Logging & Audit PRD

### V1 — Create Draft from Active Version

**User Story:** As an admin, I can create a new Draft from the current Active version of a model so that I have a safe workspace to make configuration changes without affecting live data processing.

**Importance:** High

**Acceptance Criteria:**

**AC-V1-01 — Draft created as a copy of Active**

```
Given a model has an Active version and no existing Draft
When I initiate creating a new Draft
Then a Draft is created with all configuration copied from the Active version
And it is assigned the next version number
And the Active version continues processing data unchanged
```

**AC-V1-02 — Draft is editable; Active is not**

```
Given a Draft and an Active version both exist
When I view the model
Then the Draft is editable
And the Active version is read-only
```

---

### V3 — Block Second Draft

**User Story:** As an admin, I am prevented from creating a second Draft when one already exists so that I don't accidentally create conflicting parallel changes.

**Importance:** High

**Acceptance Criteria:**

**AC-V3-01 — Second Draft creation is blocked**

```
Given a Draft already exists for a model
When I attempt to create a new Draft
Then the action is blocked
And I am shown a message indicating a Draft already exists with a link to navigate to it
```

---

### V4 — Discard Draft

**User Story:** As an admin, I can discard a Draft so that I can abandon in-progress changes and return to the Active version as the baseline.

**Importance:** High

**Acceptance Criteria:**

**AC-V4-01 — Discard requires confirmation**

```
Given I am on a model with an existing Draft
When I choose to discard the Draft
Then a confirmation dialog appears making clear the action is permanent and cannot be undone
```

**AC-V4-02 — Draft is permanently deleted on confirm**

```
Given I confirm the discard action
When the action completes
Then the Draft is permanently deleted
And the Active version is unchanged
And I can create a new Draft when ready
```

**AC-V4-03 — Discard is not available if no Draft exists**

```
Given a model has no Draft
When I view the model
Then no Discard action is visible or accessible
```

---

### V8 — Publish Draft

**User Story:** As an admin, I can publish a Draft with an effective date so that my configuration changes go live in a controlled, auditable way.

**Importance:** High

**⚠️ Engineering note — bounded reprocessing:** When a past effective date is set, the system must reprocess only the runs that fall within the new version's effective range — specifically, from the new version's effective date up to the date the next version (if any) became effective. The system must **never trigger unbounded reprocessing across all historical data**. Reprocessing scope is always bounded by the version timeline. Engineering must define and enforce this boundary explicitly — it is not acceptable to default to "reprocess everything." See OQ-3 and G3.

**Acceptance Criteria:**

**AC-V8-01 — Publish requires an effective date**

```
Given I initiate publishing a Draft
When the publish dialog appears
Then I am required to set an effective date before confirming
And today's date is pre-populated as the default
```

**AC-V8-02 — Past effective date surfaces a warning before confirmation**

```
Given I set an effective date in the past
When I attempt to confirm the publish
Then a clear warning is shown before the action completes explaining:
  - which date range will be reprocessed
  - how many historical runs are affected
  - that this action cannot be undone
And I must explicitly confirm before reprocessing begins
```

**AC-V8-03 — Reprocessing is bounded to the version's effective range**

```
Given I publish a Draft with an effective date in the past
When reprocessing is triggered
Then only runs that fall within the new version's effective range are reprocessed
And runs outside that range (belonging to a prior version's effective period) are not affected
And reprocessing does not extend back to the beginning of all data
```

**AC-V8-04 — Draft becomes Active on publish**

```
Given I confirm the publish action
When publish completes
Then the Draft becomes the new Active version
And the previous Active version transitions to Archived
And the new Active version begins processing data
```

**AC-V8-05 — Publish is recorded in the Change Log**

```
Given a Draft is published
When publish completes
Then a Change Log entry is created capturing: who published, when, the effective date, the version number, and the number of historical runs reprocessed (if applicable)
```

---

### V9 — Autosave to Draft

**User Story:** As an admin, my changes to a Draft are saved automatically so that I never lose work in progress when navigating away or closing the browser.

**Importance:** High

**Acceptance Criteria:**

**AC-V9-01 — Changes saved without manual action**

```
Given I am editing a Draft
When I make a change to any configuration field
Then the change is saved automatically without requiring me to click a Save button
```

**AC-V9-02 — Save state is visible**

```
Given a Draft is being edited
When a save is in progress
Then a "Saving…" indicator is visible
And it transitions to "Saved" once the save is complete
```

**AC-V9-03 — Changes persist across sessions**

```
Given I have made changes to a Draft and navigated away
When I return to the model
Then all previously made changes are present exactly as I left them
```

### V10 — Dimension Version Interactions

**User Story:** As an admin, when a dimension changes — either through a new version publish or because a linked model surfaces an unknown key — the dimension table is updated additively and linked models are never automatically re-run.

**Importance:** High

**Background:** Dimensions can be linked to by one or more models via a key pair. When a dimension's version changes, the impact is not isolated — every model linked to that dimension potentially depends on its key set. The system must handle dimension version changes in a way that preserves data integrity without triggering unintended re-runs.

**Guiding principle: dimension changes are additive only.** When a new dimension version adds keys, those keys are inserted. When a linked model surfaces a key that doesn't exist in the dimension, that key is auto-inserted. The system never automatically re-runs linked models as a result of a dimension change — that decision belongs to the admin.

**Acceptance Criteria:**

**AC-V10-01 — New dimension version inserts new keys, does not cascade re-runs**

```
Given a new dimension version is published that includes keys not present in the previous version
When publish completes
Then the new keys are inserted into the dimension table
And no linked models are automatically triggered to re-run
And linked models continue operating on their current data until the admin chooses to re-run them
```

**AC-V10-02 — Unknown keys surfaced by linked models are auto-inserted**

```
Given a linked model processes a record whose key has no match in the dimension
When the run completes
Then the new key is automatically inserted into the dimension table
And the record is not dropped from the linked model's output
And the admin is notified that a new dimension entry was added
```

**AC-V10-03 — Admin is warned when a dimension version removes keys linked models depend on**

```
Given a new dimension version would remove one or more keys currently used by linked models
When the admin initiates the publish
Then a warning is shown identifying which keys would be removed and which linked models depend on them
And the admin must explicitly confirm before the publish proceeds
```

**AC-V10-04 — Dimension version publish is recorded in the Change Log**

```
Given a new dimension version is published
When publish completes
Then a Change Log entry is created capturing: who published, when, and what keys were added or removed
```

## 😎 Future Considerations

* **Auto-draft on structural changes:** When a source dataset is added or removed, a custom field is added or removed, or a field mapping is edited on an Active version, the system automatically creates a Draft. Reduces risk of accidental changes to Active configurations.

* **Draft from Archived version:** Allow admins to create a new Draft starting from any Archived version, not just the current Active. Useful for reverting to a prior configuration as a starting point.

* **Delete Draft-only model:** Allow admins to permanently delete a model that has never been published (Draft-only state). Scope and confirmation behavior TBD.

* **Version history view:** A table of all versions for a model showing version number, state, effective date, published by, and published date. Navigation to any version's configuration.

* **Manual archive:** Allow admins to manually archive the Active version without publishing a new one. Blocked if it is the only Active version.

* **View Archived field mappings:** Read-only access to Archived version configurations for audit purposes.

* **Data preview from Active version:** A read-only preview of the data the Active version is producing. Reflects Active only — not Draft.
