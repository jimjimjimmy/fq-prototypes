## Objective

This sub-PRD defines the requirements for the Endpoint Library within FloQast Data Studio, scoped specifically to how individual API endpoints are provisioned, displayed, managed, and monitored within an API connection. It covers the auto-setup of standard endpoints on connection creation, deduplication and auto-linking of existing library entries, connection validation, endpoint descriptions, status display, push/pull logging, error surfacing, and the full endpoint lifecycle — archive, edit, and delete.

‌

This document is a child of the parent PRD: API Endpoint Management in FloQast Data Studio. It focuses on library-level behaviors that power the endpoint experience in the Source Data section of the connection detail view. The primary users are FloQast admins and implementation team members who configure, inspect, and troubleshoot API data endpoints without engineering involvement.

## Key Benefits

* Standard endpoints auto-provisioned on connection creation, eliminating manual setup for common workflows.
* Duplicate prevention via auto-linking keeps the endpoint library clean and consistent.
* Built-in connection validation on endpoint add reduces misconfiguration before data runs begin.
* Required descriptions on every endpoint improve admin understanding and discoverability.
* Full push/pull logs per endpoint enable data auditing and targeted troubleshooting.
* Real-time status indicators let admins quickly identify endpoint health at a glance.
* Distinct connectivity vs. sync error display speeds up root-cause analysis.
* Archive, edit, and delete lifecycle management gives admins full control without engineering support.

## Use Cases

* A FloQast implementor sets up a new QBO connection. The system automatically provisions the standard TrialBalance and Accounts endpoints and displays them under the Source Data tab — no manual steps required.
* An admin attempts to add an endpoint that already exists in the library. The system detects the match and auto-links the existing endpoint to the connection, activating it without creating a duplicate entry.
* An implementor creates a new custom endpoint and is prompted to enter a description. After saving, the description is visible on the Source Data tab in the connection detail view.
* An admin adds a new endpoint and uses the built-in validation to confirm the connection responds correctly before saving.
* An admin reviews the connection logs and identifies a connectivity error on an endpoint (auth failure). They correct the configuration, re-run the endpoint, and confirm the error is resolved.
* An admin sees a sync error on an endpoint — the API responded but the transformation failed. They edit the query parameters, retest, and save.
* An admin wants to stop running an endpoint temporarily but keep its configuration intact. They archive it — the endpoint is deactivated but remains visible in the Source Data list.
* An admin permanently removes an outdated endpoint. A confirmation modal warns them the action is irreversible before proceeding with deletion.

## Assumptions

1. "Archive" means deactivation — the endpoint is stopped but remains visible in the Source Data list in an Archived/Inactive state. It is not removed from the library or the connection view.
2. Connectivity errors (auth/network failures) and sync errors (data retrieval/transformation failures) are tracked and displayed as distinct error categories.
3. Endpoint descriptions are required when creating a new custom endpoint. For auto-provisioned standard endpoints, descriptions are pre-defined by the system and do not require admin input.
4. Logs are scoped per connection and per endpoint. Each push and pull operation generates its own log entry.
5. Standard endpoint definitions (name, API path, description) for supported connection types (e.g., QBO) are maintained in the system. No admin input is required to provision them.
6. Auto-link logic is triggered by matching on endpoint name and/or API path within the library.
7. Archived endpoints can be re-activated by an admin

## Scope

The following data objects and fields are in scope for the Endpoint Library:

‌

* Endpoint records: endpoint name, API path, description, activation status (Active / Archived), last run timestamp, next scheduled run, sync frequency, query parameters, and push/pull type.
* Endpoint statuses: Active, Archived, Running, Error.
* Endpoint logs: per push/pull entry including timestamp, endpoint name, trigger source (scheduled vs. on-demand vs. manual), operation type (push / pull), status (success / failure), records processed, and error detail if applicable.
* Connectivity errors: auth or network failures associated with an endpoint — stored and surfaced per endpoint.
* Sync errors: data retrieval or transformation failures — stored and surfaced per endpoint, not overwriting previously stored good data.
* Standard endpoint definitions: predefined per supported connection type, including name, API path, and description.
* Auto-link mapping: record associating an existing library endpoint with a given connection.

‌

**Explicitly out of scope for this sub-PRD:**

* Field-level mapping configuration (covered in separate PRDs).
* Fivetran endpoint data objects and configurations.
* On-demand trigger interface payloads and notification events (covered in parent PRD).
* Nested endpoint query parameter resolution (covered in parent PRD).

## Requirements

**REQ-01 — Display Endpoints on the Connection Screen**

As an admin or implementor, I want to see all endpoints for a connection displayed under the Source Data tab so that I can quickly understand what data is being collected and the health of each endpoint.

Functional spec: The Source Data tab of the connection detail view must list all endpoints associated with the connection, including active, archived, and errored endpoints. Each row must display endpoint name, API path, short description, status badge, last successful run timestamp, and an action menu (Edit, Archive, Delete). The list must load without navigating away from the connection screen.

**REQ-02 — Auto-Populate Standard Endpoints on Connection Creation**

As FloQast (system), when a new standard API connection is created, the standard endpoints for that connection type must be automatically provisioned and displayed in the Source Data section without any admin action.

Functional spec: On creation of a new API connection for a supported connection type (e.g., QBO), the system must automatically create and activate the predefined standard endpoints, including their names, API paths, and descriptions. These endpoints must appear in the Source Data tab immediately after connection setup with a default sync frequency of 24 hours and an Active status.

**REQ-03 — Endpoint Description Required on Creation**

As an admin or implementor, when I create a new custom endpoint I must provide a description, and that description must be displayed on the Source Data tab.

Functional spec: The add endpoint flow must include a required description field. The system must not allow a new custom endpoint to be saved without a description. For auto-provisioned standard endpoints, descriptions are pre-populated by the system and visible to admins. Descriptions must be displayed in the endpoint list on the Source Data tab.

**REQ-04 — Duplicate Detection and Auto-Link**

As an admin or implementor, when I add a new endpoint the system must check whether it already exists in the library and, if so, automatically link and activate the existing endpoint for this connection rather than creating a duplicate.

Functional spec: When an admin inputs an endpoint name or API path during the add flow, the system must check the endpoint library for an existing match. If a match is found, the system must notify the admin, confirm the auto-link, and activate the existing endpoint for this connection without creating a new library entry. No duplicate endpoint entries should be created as a result of this flow.

**REQ-05 — Connection Validation When Adding an Endpoint**

As an admin or implementor, when I add a new endpoint I want to validate that the connection works before saving so that I can confirm the endpoint is correctly configured.

Functional spec: The add endpoint flow must include a 'Test Connection' or 'Validate' action that sends a test request to the configured endpoint and displays the response status (success or failure). The admin must be able to view the result before saving. Saving a failed endpoint must be permitted but must surface a clear warning. Validation must not require the endpoint to be saved first.

**REQ-06 — Display Endpoint Status**

As an admin or implementor, I want to see a status indicator for each endpoint so that I can immediately identify which endpoints are healthy, running, errored, or archived.

Functional spec: Each endpoint in the Source Data list must display a status badge. Supported statuses are: Active (green), Archived (gray), Running (blue), and Error (red). Status must reflect the most recent known state. For errored endpoints, the status badge must link to or expand to show an inline error detail panel.

**REQ-07 — Logs for Every Push and Pull**

As an admin or implementor, I want a log entry generated for every push or pull operation on each endpoint so that I can audit data retrieval history and troubleshoot failures.

Functional spec: Every push or pull operation — whether scheduled, on-demand, or manually triggered — must generate a log entry scoped to the connection and endpoint. Each log entry must include: timestamp, endpoint name, trigger source (scheduled / on-demand / manual), operation type (push / pull), status (success / failure), records processed, and error details if applicable. Logs must be accessible from the connection detail view and filterable by endpoint, status, and date range.

**REQ-08 — Display Connectivity Errors**

As an admin or implementor, I want connectivity errors surfaced on the endpoint so that I can quickly diagnose and resolve authentication or network failures.

Functional spec: When an endpoint fails due to an auth or network issue (connectivity error), the error must be surfaced on that endpoint in the Source Data list and must be visually distinct from sync errors. The error display must include the error type, timestamp, and a summary of the failure reason. Connectivity errors must be stored per endpoint and must persist until resolved by a successful run.

**REQ-09 — Display Sync Errors**

As an admin or implementor, I want sync errors surfaced on the endpoint so that I can identify and resolve data retrieval or transformation failures.

Functional spec: When an endpoint fails during data retrieval or transformation (sync error), the error must be surfaced on that endpoint in the Source Data list and must be visually distinct from connectivity errors. The error display must include the error type, timestamp, failure step (retrieval vs. transform), and a summary of the failure reason. Sync errors must not overwrite previously stored good data.

**REQ-10 — Archive an Endpoint**

As an admin or implementor, I want to archive an endpoint so that I can deactivate it without removing its configuration or history.

Functional spec: Each endpoint must have an 'Archive' action accessible from the Source Data list. Archiving an endpoint sets its status to Archived and stops all scheduled and on-demand runs for that endpoint. The endpoint must remain visible in the Source Data list in an Archived state. Archived endpoints are assumed to be re-activatable by an admin (confirm before building). Archived endpoints should be listed last on the list of endpoints in Source Data.

**REQ-11 — Edit an Endpoint**

As an admin or implementor, I want to edit an existing endpoint's configuration so that I can correct errors or update parameters without creating a new endpoint from scratch.

Functional spec: Each endpoint must have an 'Edit' action accessible from the Source Data list. Editable fields include: description, query parameters, sync frequency, and activation status. Current values must be pre-populated when the edit panel opens. Changes must be validated before saving. A test/validate action must be surfaced in the edit view so the admin can confirm the updated configuration before leaving.

**REQ-12 — Delete an Endpoint (Permanent)**

As an admin or implementor, I want to permanently delete an endpoint, with a clear warning that the action is irreversible, so that I can remove endpoints that are no longer needed.

Functional spec: Each endpoint must have a 'Delete' action accessible from the Source Data action list. Selecting delete must trigger a confirmation modal with explicit language stating that the action is permanent and cannot be undone, and that all endpoint configuration and log history will be permanently removed. The deletion must not proceed without explicit admin confirmation. Deletion removes the endpoint from the library and all associated connection configurations.

The Source Data tab of the connection detail view is the primary surface for endpoint management. Each endpoint row displays:

* Endpoint name, API path, and short description
* Status badge: Active (green), Archived (gray), Running (blue), Error (red)
* Last successful run timestamp and next scheduled run
* Action menu: Edit, Archive, Delete
* For errored endpoints: an inline error summary expandable to show error type (Connectivity or Sync), timestamp, failure reason, and a link to the full log entry

‌

## **Add Endpoint Flow**

When an admin adds a new endpoint, the flow proceeds as follows:

1. Admin enters the endpoint name or API path.
2. System checks the library for a matching endpoint. If a match is found, the system notifies the admin and confirms auto-link to the existing endpoint — activating it for this connection without creating a duplicate. If no match, creation proceeds.
3. Admin enters a required description (cannot be blank for custom endpoints).
4. Admin configures the API settings and query parameters as needed.
5. Admin runs 'Test Connection' / 'Validate' to confirm the endpoint responds correctly.
6. Admin saves. The endpoint appears immediately in the Source Data list with an Active status.

‌

## **Delete Confirmation Modal**

When an admin selects Delete on an endpoint, a confirmation modal must appear with:

* Header: Delete endpoint?
* Body: This action is permanent and cannot be undone. All endpoint configuration and log history will be permanently deleted.
* Actions: 'Delete permanently' (destructive/red) and 'Cancel'

‌

## **Logs View**

A Logs section accessible from the connection detail view displays all push/pull log entries for the connection. The log list must be filterable by endpoint name, status (success / failure), date range, and operation type (push / pull). Each log entry displays: timestamp, endpoint name, trigger source, operation type, status, records processed, and error detail if applicable.

## Open Questions

| **Question** | **Owner** | **Notes** |
| --- | --- | --- |
| Where are logs surfaced — a dedicated Logs tab on the connection, or inline under each endpoint? | **Engineering / Design** | Both views may be needed: inline for quick status, full tab for history and filtering. |
| Can archived endpoints be re-activated? Or is archive a one-way deactivation? | **Product** | Assumed re-activatable — confirm before building. Archive is currently defined as deactivation only. |
| Are connectivity errors surfaced at the connection level or only at the endpoint level? | **Engineering / Design** | Auth/network failures may be connection-wide rather than per-endpoint. Display ownership needs to be defined. |
| What triggers a 'Running' status update — real-time or on page refresh? | **Engineering** | Real-time preferred. Clarify whether WebSocket or polling approach is used. |
| Are log entries retained indefinitely, or is there a retention policy? | **Engineering** | High-volume connections could generate significant log volume. Retention period TBD. |
