## Overview

Customers building on the FQ Data Platform can create multiple models of the same domain type — for example, two Balances models representing two different legal entities. When multiple models of compatible types exist, the platform currently has no way to know which models should be used together when resolving relationships (e.g., which Accounts model a given Balances model should link to).

Model Groups give customers a way to explicitly define which models belong together, so FloQast can correctly resolve cross-model relationships when serving data to downstream applications.

## Background

The FQ Data Platform supports a set of core domain models — Balances, Chart of Accounts, Entities, GL Transactions, and others. Each model is built by a customer through transformation rules that map raw source data into the FQ domain model schema.

For customers with multi-entity structures or multiple data sources, it is common to have more than one model of a given type. Without a grouping mechanism, the platform cannot determine, for instance, which of two Accounts models should be used to resolve account references in a specific Balances model. This creates an ambiguity that blocks downstream features — including Reconciliations, AI Variance, AI Matching, and Reporting — from functioning correctly when multiple models are present.

## Goals

* Allow customers to create named groups of models, where each group represents a coherent set of models that should be used together.

* Each group contains at most one model per domain type.

* A model may belong to any number of groups with no restriction.

* Surface grouping as a first-class concept in Data Studio with a dedicated UI.

* Proactively recommend groupings to customers as models are created, reducing manual configuration burden.

* Auto-recommend a single group when only one model of each relevant type exists.

* Automatically pre-group models that are created via pre-built integration setups (standard mappings).

* Validate key linkages within a group to surface bad groupings or data quality issues early.

## Non-Goals

* This PRD does not cover how downstream applications consume group membership — that is a separate integration concern for each consuming team (Reconciliations, AI Variance, etc.).

* This PRD does not cover model versioning or model archiving.

* Groups are not a mechanism for entity scoping — a group is not implicitly tied to a single legal entity.

## User Stories

* **As a customer with multiple entity-level Balances models**, I need to specify which Accounts model each Balances model links to, so that FloQast can correctly resolve account references per entity.

* **As a customer setting up models for the first time via a pre-built integration**, I want my models to be automatically grouped according to the standard mapping so I don't need to configure groupings manually.

* **As a customer setting up models manually**, I want FloQast to recommend how my models should be grouped so I don't have to figure out the correct combinations on my own.

* **As a customer with only one model of each type**, I want FloQast to automatically suggest grouping all my models together so there is no unnecessary configuration overhead.

* **As a Data Studio admin**, I need a clear UI for creating, naming, editing, and deleting model groups, so I can manage groupings as our data structure evolves.

* **As the Reporting application**, I need to understand which models belong together within a group so I can correctly join datasets and return accurate results to customers.

## Functional Requirements

### Model Groups

1. A **Model Group** is a named collection of models, with at most one model per domain type per group.

2. A model may belong to **any number of groups** with no restriction (e.g., a single Accounts model can be shared across multiple groups, each pairing it with a different Balances model).

3. Groups must have a customer-defined name (e.g., "Entity A – US GAAP", "Entity B – IFRS"). Group names must be unique within a customer's account.

4. There is no enforced minimum or maximum number of groups per customer.

5. A group does not need to contain a model of every domain type — partial groups are valid.

6. Groups must be persistable and editable after creation.

7. Models that are not assigned to any group must be surfaced as **ungrouped** within Data Studio, so customers are aware of unlinked models.

### Pre-Built Integration Auto-Grouping

8. When a customer completes setup of a pre-built integration (e.g., NetSuite, Workday, Intacct) using a standard mapping, any models created as part of that setup must be **automatically pre-grouped** according to the standard mapping definition.

9. Auto-generated groups created from pre-built integrations should be named based on the integration source and mapping (e.g., "NetSuite – Primary") and remain editable by the customer after creation.

### Auto-Recommendation Logic

10. When a customer creates a new model, the system evaluates existing models and generates grouping recommendations.

11. If only **one model of each relevant domain type** exists, the system recommends a single group containing all of them, with no user action required beyond confirmation.

12. If **multiple models of any type** exist and the new model could pair with more than one existing model of another type, the system surfaces a recommendation prompt asking the customer to confirm or adjust the suggested groupings.

13. Recommendation logic should prioritize matches based on available metadata — data source, naming patterns, entity references — and fall back to prompting the user when confidence is low.

14. Recommendations are non-binding; customers can always override or manually configure groups.

15. Dismissed recommendations must remain accessible from the Model Groups page so customers can revisit them.

### Key Validation

16. When models are added to a group, the system must validate that the **foreign and primary keys** used to link models to one another resolve to matching values (e.g., account IDs in a Balances model match account IDs in the associated Accounts model).

17. If validation finds **no matching keys** between linked models in a group, the system must surface an error or warning indicating that the grouping may be incorrect or the underlying data may have quality issues.

18. Validation must run: at group creation, when a model is added to an existing group, and on demand from the Model Groups UI.

19. Validation results (pass/fail/warning) must be visible within the Model Groups UI alongside each group.

## UI/UX Requirements

### Model Groups Management Page

* A dedicated **Model Groups** section within Data Studio, accessible from the main navigation.

* Displays a list of all existing groups, each showing: group name, member models (by type and name), validation status, and last modified date.

* Displays a separate **Ungrouped Models** section listing all models not currently assigned to any group.

* Allows customers to **create** a new group by naming it and selecting one model per domain type from a picker.

* Allows customers to **edit** an existing group (rename, add/remove individual models).

* Allows customers to **delete** a group (with a confirmation step; deleting a group does not delete the underlying models and does not auto-dissolve — models are simply removed from the group).

* Allows customers to **remove an individual model** from a group without deleting the group.

* Displays key validation results inline, with the ability to re-run validation manually.

### Recommendation Surface

* When a new model is saved, if the system has a grouping recommendation, display a **non-blocking prompt** (e.g., a banner or modal) in Data Studio suggesting the recommended group(s).

* The prompt must show the proposed group composition clearly and allow the customer to: accept as-is, modify before saving, or dismiss and configure manually later.

* Dismissed recommendations must be accessible from the Model Groups page.

## Technical Considerations

* Group membership needs to be stored in a way that is queryable by downstream application teams (Reconciliations, AI Variance, AI Matching, Reporting, JEM) so they can resolve which models to use for a given customer context.

* When requests are made for data, the platform must respect group context. The Reporting application specifically requires awareness of group membership to correctly join datasets. Other consuming applications may resolve data without group-level context — this contract should be defined per integration.

* The recommendation engine requires access to model metadata — at minimum: domain type, source system, entity association (if available), and creation timestamp.

* Consider whether group resolution should be synchronous (query at request time) or precomputed and cached, given the performance sensitivity of downstream consumers like Reconciliations.

* Key validation logic must be able to compare join keys across models, which may require access to a sample or full index of model data — consider the performance implications of validation at group creation time for large datasets.

* The data model for groups should be flexible enough to support future group-level configuration (e.g., group-scoped transformation overrides) without requiring a schema migration.

## Success Metrics

| Goal | Metric |
| --- | --- |
| Customers adopt groupings | % of customers with 2+ models of the same type who have at least one group configured |
| Recommendations reduce manual effort | % of groups created via accepted recommendation vs. manually configured |
| Pre-built integrations drive adoption | % of pre-built integration setups resulting in a valid auto-generated group |
| Data quality issues surfaced early | Number of key validation warnings caught at group creation vs. surfaced downstream by consuming apps |

## Open Questions

1. **Group behavior when a model is deleted:** Groups should *not* auto-dissolve when a model is deleted. The model should be removable from the group individually, leaving the group intact with remaining members. UI should surface incomplete groups clearly.

2. **Default group:** There will be no system-designated default group. Ungrouped models will be surfaced explicitly in the Model Groups UI so customers are aware of models that have not been assigned to any group.

3. **Downstream group consumption:** When data requests are made, the platform must respect groupings. For the Reporting application, group membership must be surfaced so it can correctly join datasets. Other consuming applications (Reconciliations, AI Matching, etc.) may not require group-level context — the integration contract for each app should be defined separately.

4. **Entity scoping of groups:** Groups are not inherently tied to a legal entity. A group is a logical collection of models that belong together for data resolution purposes, regardless of entity structure.

5. **Group name uniqueness:** Group names must be unique within a customer's account.

6. **Model Groups as catalog view:** There is an open question about whether the Model Groups page should serve as the *primary catalog view* in Data Studio — replacing or augmenting the current model list. *To discuss with Natasha and Kris before finalizing the UI approach.*
