## 1. Objective

This sub-PRD defines the migration path for existing NetSuite customers from the legacy direct connection (gl-service, outside Data Platform 2.0) to the new NetSuite Direct API connection in Data Studio. The migration must map existing balance data configurations to the new connection model, populate historical data, run old and new connections in parallel for validation, and execute a controlled cutover — with minimal disruption to customers.

The migration is internal and engineering-led. Customers are not expected to reconfigure their connections manually, with one exception: NetSuite's Token-Based Authentication (TBA) model may require customers or implementation teams to provision new integration credentials in NetSuite, depending on whether existing TBA tokens can be reused for the new connection. This is a key open question that must be resolved before migration planning is finalized.

---

## 2. Customer Segmentation

Before migration begins, all existing NetSuite customers are segmented based on the complexity of their current balance data configuration. Segmentation determines migration sequencing, validation rigor, and the level of manual review required before cutover.

| Segment | Description | Migration Approach |
| --- | --- | --- |
| **Tier 1 — Standard** | Single subsidiary, primary accounting book only, no dimensional breakdowns (no departments, classes, locations, or entity filters) | Automated migration; lowest risk |
| **Tier 2 — Dimensional** | One or more optional dimensions enabled (departments, classes, locations, entity), or non-primary book configured, but single subsidiary group | Automated migration with configuration mapping validation step |
| **Tier 3 — Multi-Entity or Multi-Book** | NetSuite OneWorld customers with multiple subsidiaries, or multiple accounting books (e.g., primary + statutory + tax) configured | Semi-automated; requires Engineering review of subsidiary and book mapping before cutover |
| **Tier 4 — Complex / Custom** | Non-standard configurations, custom NetSuite scripts or saved searches, intercompany elimination configurations, or setups not covered by Tiers 1–3 | Manual migration; handled case-by-case with Engineering and CS involvement |

**Open Question:** What is the current count and distribution of NetSuite customers across these segments? This drives migration timeline and resourcing.

## 3. Phase 1 — Connection Setup

The new NetSuite Direct API connection in Data Studio is created for each customer using configuration data sourced from the existing legacy connection. The key complexity for NetSuite relative to other connectors is TBA credential handling — NetSuite does not use simple username/password authentication, and existing tokens may or may not be directly portable.

### 3.1 TBA Credential Handling

The legacy gl-service NetSuite integration uses Token-Based Authentication (TBA), which consists of four components: consumer key, consumer secret, token key, and token secret. These are tied to a specific Integration record created in the customer's NetSuite account.

Two migration paths exist for TBA credentials. The correct path depends on how the legacy credentials are stored and whether a new Integration record is required for Data Studio.

| Path | Condition | Approach |
| --- | --- | --- |
| **Credential reuse** | Legacy TBA tokens are stored in a format accessible to the migration process AND the same integration record can serve the new Data Studio connection | Credentials are programmatically sourced from the legacy connection record and applied to the new connection. No customer action required. |
| **New credential provisioning** | A new Integration record must be created in NetSuite for the Data Studio connection, OR legacy credentials are not accessible in a reusable format | CS or implementation team works with the customer to create a new Integration record and generate new TBA tokens. This is the higher-friction path and must be planned for at a segment level. |

**Open Question:** Can existing TBA credentials stored in the legacy gl-service connection be accessed and reused for the new Data Studio connection, or does the new connection require a new NetSuite Integration record with freshly issued tokens? This is the most significant migration dependency and must be resolved before migration tooling is built.

### 3.2 Requirements

**REQ-01: The system must map the customer's existing balance configuration from the legacy connection to the equivalent configuration on the new NetSuite Direct API connection.**

*Functional spec: The migration process reads the customer's current balance data configuration from the legacy gl-service connection (subsidiary assignments, book configuration, dimensional flags for departments/classes/locations/entity) and writes the equivalent values to the new connection's Balances endpoint configuration as defined in Sub-PRD 7. Where a 1:1 mapping exists, it is applied automatically. Where the mapping is ambiguous or unsupported in the new model, the record is flagged for manual review before the connection is activated.*

**REQ-02: All standard endpoints must be auto-provisioned on the new connection as part of migration setup.**

*Functional spec: Following the standard auto-provisioning behavior defined in Sub-PRD 7, the Accounts and Balances endpoints are activated for the migrated connection with default sync frequency of 24 hours. Lineage records are created for both as part of the same setup action.*

**REQ-03: TBA credentials must be sourced for each migrated connection before the connection can be activated.**

*Functional spec: If credential reuse is confirmed feasible (see Open Question above), credentials are read from the legacy connection record and applied programmatically. If new credentials are required, the migration workflow must surface a clear action item to the CS or implementation team and block activation until credentials are provided and validated. The new connection must not be activated without a successful TBA authentication test.*

### 3.3 Acceptance Criteria

| AC-ID | Criterion |
| --- | --- |
| AC-MIG-01 | A new NetSuite Direct API connection is created in Data Studio for each migrating customer. |
| AC-MIG-02 | Balance configuration from the legacy connection (subsidiary, book, dimensional options) is mapped to the equivalent Balances endpoint configuration on the new connection. |
| AC-MIG-03 | Configurations that cannot be automatically mapped are flagged for manual review before the connection is activated. |
| AC-MIG-04 | All standard endpoints (Accounts and Balances) are auto-provisioned on the new connection with default sync frequency as part of migration setup. |
| AC-MIG-05 | The new connection is not activated without a successful TBA authentication test confirming credentials are valid. |

## 4. Phase 2 — Historical Data Backfill

Once the new connection is set up and authenticated, historical account and balance data is backfilled into the FQ data layer for the new connection. This ensures continuity of data in Data Studio from day one.

### 4.1 Requirements

**REQ-04: The system must backfill historical data for each migrated connection up to a defined lookback window.**

*Functional spec: The target lookback window is 24 months prior to the migration date, subject to confirmation (see Open Questions). Backfill covers Accounts and Balances. The backfill job runs as a one-time operation and is logged with* `trigger_type: "backfill"` in the job log schema defined in Sub-PRD 6. Backfill jobs use the same batching mechanism as live syncs — 55 pages per batch for the Balances endpoint — and must respect the same SOAP rate limit constraints.

**REQ-05: Backfill data must use the same balance configuration as the migrated connection.**

*Functional spec: The Balances backfill request uses the same subsidiary assignment, book configuration, and dimensional filter settings as the live migrated connection. Backfill data is not pulled with different parameters.*

**REQ-06: The withStartAndEnd implementation gap must be resolved before the backfill phase begins.**

*Functional spec: The Balances endpoint's* `withStartAndEnd` method is currently a TODO in the integration layer (see Sub-PRD 7, Section 3.1 open questions). Historical backfill by date range requires this to be implemented. If it is not available by the time backfill is scheduled, an alternative backfill mechanism (e.g., period-by-period iteration using the Periods endpoint data) must be defined and agreed with Engineering before migration proceeds.

### 4.2 Acceptance Criteria

| AC-ID | Criterion |
| --- | --- |
| AC-MIG-06 | Historical data is backfilled for each migrated connection covering the agreed lookback window (target: 24 months). |
| AC-MIG-07 | Backfill jobs are logged with `trigger_type: "backfill"` and are visible in the connection's run log. |
| AC-MIG-08 | Backfill failures do not block the parallel running phase — they are logged and queued for retry. |
| AC-MIG-09 | Backfill for large NetSuite accounts (high account × period combinations) completes within an agreed SLA. Accounts exceeding expected backfill duration are flagged proactively. |

## 5. Phase 3 — Parallel Running & Validation

After connection setup and backfill, the new Data Studio connection runs in parallel with the legacy gl-service connection for a defined validation period. Both connections pull data independently. This phase validates data parity before customers are cut over.

### 5.1 Requirements

**REQ-07: The new Data Studio connection must run on its standard sync schedule in parallel with the legacy connection for the duration of the validation period.**

*Functional spec: Both connections sync independently during the parallel period. Data from both is stored and available for comparison. The legacy gl-service connection is not modified or paused during this phase.*

**REQ-08: A data parity check must be run between the legacy connection output and the new Data Studio connection output at the end of the validation period.**

*Functional spec: Parity is checked at the balance level (account × period × book × subsidiary). Where dimensional data is configured (departments, classes, locations), parity is checked at the dimensional granularity level as well. Discrepancies beyond a defined tolerance threshold are flagged for investigation before cutover is permitted. Tolerance threshold is TBD (see Open Questions).*

**REQ-09: Parity check results must be documented per customer before cutover approval is granted.**

*Functional spec: A parity report is generated per customer showing: total records compared, matched records, discrepancies (with detail), and a pass/fail outcome. Engineering or Product sign-off is required on any customer with a fail outcome before cutover proceeds. Known acceptable divergences — such as differences attributable to the* `withStartAndEnd` gap or known rounding differences — must be documented and explicitly accepted, not silently excluded.

### 5.2 Validation Period

The parallel running window is TBD (see Open Questions). Suggested starting point: 2–4 weeks for Tier 1 and Tier 2 customers; longer for Tier 3 and Tier 4. For OneWorld customers (Tier 3) with complex multi-subsidiary configurations, a full close cycle (one month) is the recommended minimum before cutover.

### 5.3 Acceptance Criteria

| AC-ID | Criterion |
| --- | --- |
| AC-MIG-10 | The new connection runs on its standard sync schedule in parallel with the legacy connection for the full validation period without interfering with legacy data. |
| AC-MIG-11 | A parity report is generated per customer at the end of the validation period comparing balance data between old and new connections at the account × period × book × subsidiary level. |
| AC-MIG-12 | No customer proceeds to cutover with an unresolved parity fail. |

---

## 6. Phase 4 — Customer Cutover

Once parity is confirmed, customers are cut over from the legacy gl-service connection to the new Data Studio connection. Cutover is segment-sequenced — Tier 1 customers move first, followed by Tier 2, then Tier 3 and Tier 4.

### 6.1 Requirements

**REQ-10: The legacy connection must be deactivated for a customer only after cutover is complete and the new connection is confirmed active.**

*Functional spec: Cutover is not considered complete until: (1) the new connection has completed at least one successful scheduled sync post-cutover, and (2) the parity report for that customer has a pass outcome. The legacy gl-service connection is deactivated (not deleted) at cutover completion. Legacy data and connection configuration are retained for a defined period post-cutover for rollback purposes.*

**REQ-11: Cutover must be sequenced by customer segment.**

*Functional spec: Tier 1 → Tier 2 → Tier 3 → Tier 4. Within each tier, customers are migrated in batches. Batch size is TBD based on engineering capacity and monitoring overhead. OneWorld customers (typically Tier 3) must be migrated as a complete unit — partial subsidiary migration is not permitted.*

**REQ-12: A rollback path must exist for each customer for a defined period post-cutover.**

*Functional spec: If issues are discovered after cutover, the legacy gl-service connection can be reactivated and the new Data Studio connection deactivated without data loss. Rollback window is TBD (see Open Questions). Rollback does not require customer credential re-entry — the legacy connection configuration must be preserved intact until the rollback window closes.*

### 6.2 Acceptance Criteria

| AC-ID | Criterion |
| --- | --- |
| AC-MIG-13 | Cutover is only executed for a customer after their parity report shows a pass outcome. |
| AC-MIG-14 | The legacy gl-service connection is deactivated (not deleted) after cutover is confirmed complete. |
| AC-MIG-15 | A rollback path exists for each customer for the defined post-cutover window. |
| AC-MIG-16 | Customers are migrated in segment order (Tier 1 → 2 → 3 → 4) in defined batches. OneWorld customers are migrated as a complete unit. |

## 7. Assumptions

* The legacy gl-service NetSuite connection configuration is accessible and can be read programmatically to source subsidiary assignments, book configuration, and dimensional settings for the migration mapping.

* The legacy connection's balance configuration is the source of truth for migration mapping — no customer input is required to determine what data they were pulling.

* Historical balance data in NetSuite is available for the full lookback window (24 months) and accessible via the same `getPostingTransactionSummary` SOAP operation.

* The legacy connection continues to run unmodified during the parallel period — no changes are made to gl-service pipelines during migration.

* The `withStartAndEnd` gap in the Balances endpoint is resolved before the backfill phase begins. If it is not, an alternative backfill approach is agreed with Engineering before migration starts.

* For Tier 1 and Tier 2 customers, customer-facing disruption is expected to be zero. Tier 3 and Tier 4 customers may require CS communication about TBA credential provisioning if new Integration records are needed.

* CS teams are notified of cutover timing for each customer and are prepared to handle any inbound questions.

---

## 8. Out of Scope

* Migration of non-NetSuite legacy connections

* Changes to the legacy gl-service NetSuite infrastructure during the migration window

* Customer self-service migration tooling

* Migration of transaction-level data — not in scope for the initial Data Platform 2.0 release

* Customer-facing communication about the migration (owned by CS / Marketing)

* Migration of NetSuite customizations (custom fields, saved searches, custom segments) beyond those already supported in the new integration layer
