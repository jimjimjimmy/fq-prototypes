## Objective

 

Today, DP 2.0 APIs do not use the entity access information already present in the user's JWT token to filter data responses. As a result, data is returned for all entities within a TLC — regardless of which entities a given user is authorized to see. This is a security and compliance risk and a blocker for Detect reaching GA.

 

This PRD defines the Q3 requirements for DP 2.0 APIs to:

 

1. Read the authorized entity list from the requesting user's JWT token and apply it as a default filter on all canonical model data responses

2. Accept an optional entity ID filter parameter so consuming products can narrow results to a subset of their JWT-authorized entities

 

When this ships, downstream consumers — beginning with Detect (a product within the Reporting business unit) — will receive data scoped to only the entities the requesting user is authorized to access. No Platform RBAC service call is required; the JWT already carries this information.

 

> **Note:** A second, related piece of work — expanding entity mapping support to CDC/Fivetran connections (currently SFTP only) — is tracked separately under Entity Mapping v2 (IDEA-2618). Both are required for Detect GA.

 

> **Open flag:** How entity-level filtering intersects with Q3 Transform Integration work (IDEA-2628) is an open question that may affect assumptions in that PRD.

## Why This Is Important

 

RBAC exists in FloQast today because customers — particularly those in regulated or audit-sensitive environments — need to restrict what individual users can see and do within the application. This isn't just a permissions convenience; it's frequently a compliance requirement. Auditors and internal controls teams expect that a user's access to financial data is scoped appropriately, and that this scoping can be demonstrated and enforced consistently.

 

At the entity level specifically, this matters because a single FloQast account can span multiple legal entities or subsidiaries with different ownership, different finance teams, and different audit boundaries. A user authorized to see Entity A's financials should not be able to see Entity B's — regardless of which product or surface they're using. Where that boundary is enforced inconsistently across the application, it becomes an audit finding and a customer trust issue, not just a product gap.

 

For DP 2.0 specifically, the entity access information needed for filtering is already embedded in the JWT — but the APIs are not currently using it. This means a user with restricted entity access can still retrieve data for entities they should not be able to see. This is a hard GA blocker for Detect: a user who can only see certain entities in the rest of the FloQast application must not be able to see more data than that in Detect.

 

The fix is contained and well-scoped — the infrastructure is already there. This work closes a meaningful security gap and unblocks a Q3 GA milestone for the Reporting business unit.

## Key Benefits

 

**For Customers**

 

* **Entity-level data precision:** Users accessing Detect receive data scoped to the entities they are authorized to see — consistent with their access in the rest of FloQast.

* **Security assurance:** Financial data is never returned beyond a user's authorized entity scope — no over-sharing, no manual workarounds.

* **Detect GA unblocked:** Customers can move to GA on Detect with confidence that data access is correctly enforced.

 

**For FloQast**

 

* **Detect reaches GA:** This is a hard blocker for Detect GA. Shipping it unblocks the Reporting business unit's Q3 milestone.

* **DP 2.0 as a trusted data layer:** Enforcing entity-level access in the API layer means every consuming product inherits correct behavior rather than building its own filtering logic.

* **No new platform dependencies:** The JWT already carries entity access — this is an integration of existing infrastructure, not net-new platform work.

## Use Cases

 

**Use Case 1: End user queries a Reporting product — canonical model data**

 

A user with access to Detect (or another Reporting product) requests financial data. Today, DP 2.0 returns all rows across all entities for that TLC, regardless of the user's entity permissions. This means a user restricted to certain entities in the rest of FloQast may see data they shouldn't in Detect — a GA blocker.

 

When this ships:

 

1. The consuming product sends a data request to the DP 2.0 API, including the user's JWT

2. DP 2.0 reads the authorized entity list from the JWT — this is the **maximum set of entities** the user can access (and that the request can return)

3. DP 2.0 applies that entity list as a default filter; only rows matching authorized entities are returned

4. Optionally, the consuming product may pass one or more specific entity IDs to narrow the result further — but the response can never exceed the JWT-authorized set (AND logic)

 

The user experiences no UI change — they simply receive the correct, scoped dataset.

 

---

 

**Use Case 2: Custom data models and dimensions**

 

A user requests data from a custom data model or a dimension. Unlike canonical models — which have a direct FQ Entity ID association — custom data models and dimensions do not map cleanly to entities. Dimensions in particular may span entities by design. Whether and how JWT-based entity filtering should apply to these dataset types is not yet established.

 

*This use case is a placeholder. Behavior is TBD — see Open Questions.*

## Assumptions — Established

 

1. Entity access is encoded in the user's JWT token — DP 2.0 can read the authorized entity list from the JWT without calling an external service

2. The JWT-derived entity list represents the **maximum** set of entities a user is authorized to access — DP 2.0 applies this as a ceiling; consuming products may narrow further but cannot exceed it

3. Consuming products are responsible for passing the user's JWT with each API request

4. Canonical models have FQ Entity IDs — row-level filtering by entity ID is the established mechanism

5. Row-level filtering is the access control mechanism in scope — column-level obfuscation (e.g., hiding specific fields) is out of scope for this PRD

6. No Platform RBAC service call is required for Q3 — the platform team confirmed no gaps; the JWT carries the needed information

7. Entity access configuration is managed outside of Data Studio, in the platform's RBAC system

## Scope

 

**In Scope**

 

* Reading authorized entity list from JWT and applying it as a default filter on canonical model API responses

* Accepting an optional entity ID filter parameter to allow consuming products to narrow results within their JWT-authorized set

* Defining the entity filtering pattern for canonical models

 

**Out of Scope**

 

* Calling the Platform RBAC service at query time — the JWT provides the needed information for Q3

* Full RBAC enforcement where DP 2.0 integrates with the Platform RBAC service — deferred to Q4

## Requirements

 

**Story 1: JWT entity list applied as default filter on canonical model responses**

 

*As a consuming product, I want DP 2.0 to automatically scope canonical model data to the requesting user's authorized entities (from their JWT), so that users never receive data beyond their authorized entity set.*

 

Acceptance Criteria:

 

* Given an API request with a valid JWT, DP 2.0 reads the authorized entity list from the JWT

* DP 2.0 applies a row-level filter, returning only rows where the FQ Entity ID matches an entity in the JWT-authorized list

* If the JWT contains no authorized entities, DP 2.0 returns an empty dataset with a message indicating no entities are available

* The filtered response is returned to the consuming product without requiring the consumer to pass entity IDs explicitly

 

---

 

**Story 2: Optional entity ID filter parameter for narrowing results**

 

*As a consuming product, I want to pass one or more FQ Entity IDs as an optional filter parameter, so that I can request data for a specific subset of my JWT-authorized entities.*

 

Acceptance Criteria:

 

* Canonical model API endpoints accept one or more FQ Entity IDs as an optional filter parameter

* When entity IDs are passed, DP 2.0 returns only rows matching those entity IDs — AND-filtered against the JWT-authorized set (a passed entity ID not in the JWT-authorized set returns no data for that entity)

* When no entity ID parameter is passed, the JWT-authorized entity list is used as the default filter

* An invalid or malformed entity ID parameter returns a clear error response

 

---

 

**Story 3: No user JWT passed in request**

 

*As DP 2.0, I need to handle requests that arrive without a JWT, so that unscoped data is never returned by default.*

 

Acceptance Criteria:

 

* Given an API request with no JWT, DP 2.0 returns an error response indicating that credentials were not passed

* DP 2.0 does not return any data when a JWT is absent

## UX Requirements

 

This PRD defines API behavior only. There are no Data Studio UI changes in scope.

 

Consuming products are responsible for passing a valid JWT with each request. DP 2.0 handles entity scoping automatically from that JWT. The following response states must be handled by each consumer:

 

| Response state | Expected consumer behavior |
| --- | --- |
| Filtered dataset returned | Render data normally |
| Empty dataset — no authorized entities in JWT | Surface a message indicating no data is available for the user's access level |
| Error — no JWT passed | Handle as an authentication error |
| Error — invalid entity ID filter parameter | Handle as a request error |

 

*Data Studio UI enforcement of entity-level access for Data Studio users is covered in a separate PRD.*

## Gaps

 

* **Full RBAC enforcement (Q4):** DP 2.0 integrating with the Platform RBAC service at query time — enforcing permissions beyond what the JWT carries — is deferred to Q4. A new IDEA ticket is needed.

* **Custom data models and dimensions:** JWT-based entity filtering behavior for these dataset types is unresolved. Deferred until Open Questions 1 and 2 are answered.

* **Entity mapping for CDC/Fivetran:** Currently entity mapping only exists for SFTP connections. Expanding to CDC is required for Detect GA and is tracked under Entity Mapping v2 (IDEA-2618) — not in this PRD.

* **Close BU filtering interaction:** How the Close business unit's existing filtering layer interacts with DP 2.0 entity scoping needs evaluation before rollout.

* **Data Studio UI RBAC enforcement:** Whether and how Data Studio's own UI enforces entity-level access for Data Studio users is covered in a separate PRD (Data Studio UI RBAC Enforcement, to be created — Q4).
