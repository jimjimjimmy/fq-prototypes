# **1. Objective**

This sub-PRD defines the requirements for authentication configuration in FloQast Data Studio for custom API connections. It covers three authentication patterns - API Key, OAuth 2.0 / Bearer Token, and Basic Auth - including field capture, secure credential storage, sandbox vs. production credential management, expiration tracking, proactive expiration alerts, and re-authentication flows when credentials fail.

Authentication is a discrete, required step in the API connection setup wizard and is a shared dependency for both the Pull API sub-PRD and the future Push API sub-PRD. The primary users are FloQast admins and implementation team members who configure, maintain, and troubleshoot API connections. A key design goal is that the authentication configuration experience is clear enough for less technical users to complete without engineering assistance.

# **2. Key Benefits**

* Secure, structured credential capture across three common API auth patterns, with all sensitive fields masked and encrypted at rest.
* Separate sandbox and production credential management reduces misconfiguration risk during implementation and testing.
* Proactive expiration alerts - via UI warnings and email notifications - prevent unexpected sync failures due to stale credentials.
* Guided re-authentication flow when credentials fail mid-operation reduces time to resolution and keeps syncs recoverable without engineering support.
* Service account enforcement guidance reduces connection disruptions caused by personal credential changes or offboarding.
* IP allowlist tracking ensures customers complete network configuration steps before going live, reducing day-one connectivity failures.
* An extensible auth framework makes it straightforward to add new auth types in future phases without rearchitecting the credential management layer.

# **3. Use Cases**

1. An implementor sets up a new pull API connection. During the authentication step, they select API Key, enter the vendor-provided key (masked), specify the header name as Authorization and a header prefix of Token. They indicate the key expires in 90 days. The system stores the key encrypted and the expiration date displays as a badge on the connection detail view.
2. An admin configures OAuth 2.0 credentials for a production ERP connection. The grant type defaults to client_credentials. They enter the token endpoint URL, client ID, and client secret. They also expand the sandbox section and enter separate sandbox credentials. The system groups production and sandbox fields into collapsible sections to keep the form manageable.
3. An admin sets up Basic Auth using what they believe is a personal user account. The is_service_account field is set to false and the system immediately surfaces a warning: 'We recommend a dedicated service account to avoid disruption if this user's access changes.' The admin checks with their IT team, creates a service account, and re-enters credentials with is_service_account = true.
4. An admin's API key is set to expire in 30 days. They receive a proactive email notification with a direct link to the connection's auth edit flow. They update the key before it expires and the connection continues syncing without interruption.
5. A nightly sync fails because an OAuth token endpoint returns a 401. The sync is logged as an authentication failure. On the connection detail view, a 'Credentials need updating' prompt appears with a direct link to the auth edit step. The admin also receives an email notification. They click the link, update the client secret, and manually trigger a re-run of the failed sync.
6. An implementor is setting up a new connection and is unsure whether they need to allowlist FloQast's IP addresses with their API provider. The ip_allowlist_required field in the auth step prompts them to confirm, and if yes, the system provides FloQast's IP ranges so the implementor can share them with the customer's IT team.
7. An admin edits the client secret for an OAuth 2.0 connection that has multiple endpoints configured. The system prompts: 'Apply this change to this endpoint only, or to the entire connection?' The admin selects 'entire connection' and the updated credential is applied across all endpoints.

# **5. Assumptions**

* All sensitive credential fields (API keys, client secrets, passwords) are encrypted at rest in FloQast's infrastructure. This PRD captures the encryption requirement; implementation details are owned by engineering and security.
* Sandbox credential fields are optional for onboarding speed. Whether sandbox credentials are required before a connection is promoted to production is a product decision - see Open Questions.
* OAuth 2.0 grant_type defaults to client_credentials as this is the dominant server-to-server pattern for ERP and accounting API integrations. The field remains editable for edge cases.
* OAuth 2.0 token refresh is handled automatically by the system using token_ttl_seconds (if provided) and/or the standard expires_in field in the token response. Manual credential re-entry is only required when a refresh fails or the client credentials themselves change.
* Expiration alert notifications are sent to the FloQast admin or implementor who owns the connection. Notification to the technical contact (captured as an informational field) is out of scope for this PRD.
* The ip_allowlist_required field captures the customer's need to allowlist FloQast IPs. The actual list of FloQast IP ranges is maintained by infra and surfaced from a system-managed source - not hard-coded in this PRD.
* This auth framework applies identically to both pull API and push API connections. The integration point within each connection setup wizard is defined in the respective sub-PRDs.
* The auth framework is designed to be extensible. Adding a new auth type in a future phase should require configuration changes, not architectural rework.
* base_url is captured in connection basics (defined in the Pull/Push API sub-PRDs) and does not need to be re-captured in the auth step. The auth step references the connection's base_url where needed.

## **Explicitly Out of Scope for Data**

* base_url and sandbox_base_url - captured in connection basics (Pull/Push API sub-PRDs); referenced by auth but not re-captured here.
* Runtime OAuth access token values - managed by the system at runtime, not stored as user-configured credential data.
* FloQast IP address lists - maintained by infra; surfaced dynamically in the UI but not stored in this data model.
* Auth configuration for standard pre-built connections (QBO native OAuth, Workday, SAP, Yardi, etc.).

# **8. Requirements**

## **Auth Type Selection**

**REQ-01  As an admin or implementor, I want to select the authentication type for my API connection so that FloQast collects the correct credentials for that pattern.**

_**Functional spec:**_ The authentication step must present a selector for three auth types: API Key, OAuth 2.0 / Bearer Token, and Basic Auth. Selecting a type dynamically renders the relevant field form for that type. The selector must be presented clearly with a brief description of each type to guide less technical users (e.g., 'API Key - A single key provided by the vendor, passed in every request header'). Changing the auth type after fields have been entered must prompt the user to confirm, as it will clear the current field values.

‌

## **API Key Authentication**

**REQ-02  As an admin or implementor, I want to enter and configure my API key so that FloQast can authenticate requests with the correct credentials.**

_**Functional spec:**_ The api_key_value field must be rendered as a masked input (similar to a password field) with a show/hide reveal toggle. The field is required. The header_name field is required and must accept free text (e.g., Authorization, X-API-Key). The header_prefix field is optional; if left blank, the key value is used directly. Inline helper text must explain the expected format: for example, 'If prefix is Token, the header will read: Authorization: Token <your-key>'.

**REQ-03  As an admin or implementor, I want to specify whether my API key expires and when so that FloQast can alert me before the key becomes invalid.**

_**Functional spec:**_ The expires field is a required boolean (Yes/No toggle). If expires = true, the expiration_date field must appear conditionally and require a date value. If expires = false, the expiration_date field must not be shown. The expiration date must be stored and used to trigger expiration alerts (see REQ-15 and REQ-16). The expiration date must be displayed as a status badge on the connection detail view.

‌

## **OAuth 2.0 / Bearer Token Authentication**

**REQ-05  As an admin or implementor, I want to configure OAuth 2.0 credentials so that FloQast can obtain and refresh access tokens automatically.**

_**Functional spec:**_ Required fields: token_endpoint_url (URL format validated), client_id, client_secret (masked with reveal toggle). The client_secret is encrypted at rest. Inline helper text must clarify that client_id and client_secret are provisioned in the customer's ERP or API provider - not created by FloQast. All three fields are required; if any are missing, the user must not be able to proceed.

**REQ-06  As an admin or implementor, I want to configure the OAuth grant type, scopes, and token lifetime so that FloQast handles token acquisition correctly for this API.**

_**Functional spec:**_ The grant_type field must be a dropdown that defaults to client_credentials. Other values may be supported but are not required for Phase 1. The scopes field is optional free text. The token_ttl_seconds field is optional integer; if provided, FloQast uses it to proactively refresh the token before it expires. If not provided, FloQast relies on the expires_in field in the token response.

‌

## **Basic Authentication**

**REQ-08  As an admin or implementor, I want to enter Basic Auth credentials so that FloQast can authenticate using username and password.**

_**Functional spec:**_ The username field is required free text. The password field is required, rendered as a masked input with a reveal toggle, and encrypted at rest. Both fields are required; if either is missing, the user must not be able to proceed.

**REQ-09  As an admin or implementor, I want to indicate whether these credentials belong to a service account so that FloQast can warn me if they belong to a personal user account.**

_**Functional spec:**_ The is_service_account field is a required boolean (Yes/No). If is_service_account = false, the system must display a prominent inline warning: 'We recommend using a dedicated service account. If this user's access changes or they leave the organization, this connection will stop working.' The warning must be visible but must not block the user from proceeding - it is advisory.

**REQ-10  As an admin or implementor, I want to indicate whether the Basic Auth password expires and when so that FloQast can alert me before the password becomes invalid.**

_**Functional spec:**_ The password_expires field is a required boolean. If password_expires = true, the expiration_date field must appear conditionally and require a date value. Behavior is identical to REQ-03 for API Key expiration: the date is stored, displayed as a badge on the connection detail view, and used to trigger expiration alerts (REQ-15 and REQ-16).

‌

## **Universal Configuration**

**REQ-12  As an admin or implementor, I want to indicate whether I need to allowlist FloQast's IP addresses with my API provider so that I can complete that step before going live.**

_**Functional spec:**_ The ip_allowlist_required field is a required boolean. If true, the system must display FloQast's current outbound IP ranges below the toggle, with a note explaining that the customer's IT team must configure these allowlists on the API provider side before the connection can successfully sync. The IP ranges are sourced from a system-managed list maintained by FloQast infra (not hard-coded in the UI).

**REQ-13  As an admin or implementor, I want to record a technical contact for this connection so that there is a clear escalation path for authentication issues.**

_**Functional spec:**_ The technical_contact_name and technical_contact_email fields are both optional. They are informational only - no automated notifications are sent to the technical contact as part of this PRD. The fields must be displayed on the connection detai settings pagel view.

‌

## **Expiration Tracking & Alerts**

**REQ-14  As FloQast (system), I need to track credential expiration dates so that expiration can be surfaced to admins proactively.**

_**Functional spec:**_ For API Key and Basic Auth connections where an expiration date has been entered, the system must track the expiration_date and compare it against the current date. The connection detail view must display an expiration status badge for the auth credentials: 'Active', 'Expiring soon' (within the alert threshold - TBD), or 'Expired'. The badge must link directly to the auth edit flow.

**REQ-15  As an admin or implementor, I want to see a clear visual warning when my credentials are approaching expiration or have already expired so that I can take action without waiting for a sync to fail.**

_**Functional spec:**_ When the current date is within the expiration alert threshold of the credential's expiration_date, the connection detail view must display a prominent 'Expiring soon' warning banner with the expiration date and a call-to-action link to the auth edit flow. When the expiration_date has passed, the banner must change to 'Credentials expired' and persist until credentials are updated. The alert threshold is TBD (see Open Questions).

**REQ-16  As an admin, I want to receive a proactive email notification before my credentials expire so that I can update them before any syncs are affected.**

_**Functional spec:**_ The system must send an automated email notification to the connection owner when a credential's expiration_date is within the configured alert threshold. The email must include: the connection name, the credential type (API Key or Basic Auth password), the expiration date, and a direct link to the authentication edit flow for that connection. The expiration_alert_sent_at timestamp must be updated when the alert is sent. If the credential is not updated and the expiration date passes, a follow-up 'Credentials have expired' email must also be sent. Alert frequency and repeat timing are TBD (see Open Questions).

‌

## **Authentication Failure & Re-Authentication**

**REQ-17  As FloQast (system), I need to log authentication failures with specific error detail so that admins can identify the cause without engineering support.**

_**Functional spec:**_ When a sync fails due to an authentication error, the system must log: last_auth_failure_at (timestamp), auth_failure_reason (e.g., 'API key rejected by provider', 'OAuth token endpoint returned 401', 'Basic Auth credentials invalid', 'Credential expired'), and the endpoint identifier. This log entry must be visible in the connection's sync log section, distinct from other failure types.

**REQ-18  As an admin, I want to see a clear re-authentication prompt on the connection detail view when credentials have failed so that I can resolve the issue quickly without searching for where to update them.**

_**Functional spec:**_ When an authentication failure is logged for a connection, the connection detail view must display a persistent 'Credentials need updating' prompt. The prompt must include: the failure reason, the timestamp of the failure, and a direct action link that navigates to the authentication edit step for that connection. The prompt must be automatically dismissed and removed from the view once the credentials are successfully updated and tested. The reauth_prompt_dismissed_at timestamp must be recorded when dismissed.

**REQ-19  As an admin, I want to receive an email notification when a sync fails due to an authentication error so that I am alerted even if I am not actively viewing the connection.**

_**Functional spec:**_ When a sync fails due to an authentication error, the system must send an email notification to the connection owner. The email must include: the connection name, the auth failure reason, the timestamp, and a direct link to the authentication edit flow. The email must not be sent more than once per auth failure event (i.e., one notification per failed sync, not per retry attempt). If the same connection fails on multiple consecutive syncs, a summary notification covering the consecutive failures is preferred over repeated individual emails (TBD - see Open Questions).

‌

## **Credential Security**

**REQ-20  As FloQast (system), I need all sensitive credential fields to be encrypted at rest so that credentials are not exposed if the underlying data store is compromised.**

_**Functional spec:**_ All fields designated as masked in the field tables above - api_key_value, sandbox_api_key_value, client_secret, sandbox_client_secret, password, sandbox_password - must be encrypted at rest using an encryption standard approved by FloQast's security team. The encryption implementation is owned by engineering; this requirement defines the scope of fields that must be covered. UI masking alone is not sufficient.

‌

## **Auth Editing**

**REQ-21  As an admin or implementor, I want to edit my authentication credentials after initial setup so that I can update them when they change without reconfiguring the entire connection.**

_**Functional spec:**_ An Edit action for authentication must be accessible from the connection detail view. All auth fields for the current auth type must be pre-populated (with sensitive fields masked). The admin must be able to change any field, including switching auth type entirely (with a confirmation prompt, as switching type clears current values). Upon saving, the updated credentials must be validated via a connection test before the edit is committed. If validation fails, the previous credentials must remain active and the admin must be shown the specific failure reason.

**REQ-22  As an admin or implementor editing auth credentials for a connection that has multiple endpoints, I want to choose whether the change applies to the entire connection or a specific endpoint so that I don't unintentionally affect other endpoints.**

_**Functional spec:**_ When an admin edits authentication for a connection that has more than one configured endpoint, the system must prompt: 'Apply this authentication change to this endpoint only, or to the entire connection?' The admin must make an explicit selection before the change is saved. If 'entire connection' is selected, the updated credentials are applied to all endpoints. If 'this endpoint only' is selected, only the targeted endpoint's auth configuration is updated. (Cross-reference: Pull API sub-PRD REQ-08.)

‌

# **9. User Interaction and Design**

The authentication step is a discrete panel within the API connection setup wizard (step 3, after connection basics). It is also accessible as an edit flow from the connection detail view. The design goals are: clarity for less technical users, minimal visual noise through collapsible sandbox sections, and proactive surfacing of issues before they cause sync failures.

‌

## **Auth Type Selector**

* Presented as a card or dropdown selector with three options: API Key, OAuth 2.0 / Bearer Token, Basic Auth.
* Each option includes a one-line description to help less technical users choose correctly (e.g., 'API Key - A single key provided by the vendor, passed in every API request header').
* Selecting a type dynamically renders the relevant form below. Changing the selection after data has been entered triggers a confirmation prompt.

‌

## **API Key Form**

* API Key Value: masked input with reveal toggle. Placeholder text: 'Paste your API key here'.
* Header Name: free-text input. Placeholder: 'e.g., Authorization or X-API-Key'. Helper text: 'This is the header name your API provider told you to use.'
* Header Prefix: optional free-text input. Helper text: 'If your provider says to format the header as "Authorization: Token abc123", enter Token here. Leave blank if the key is used directly.'
* Expires toggle: Yes/No. If Yes, expiration_date date picker appears below.

‌

## **OAuth 2.0 / Bearer Token Form**

* Production credentials section (always expanded): Token Endpoint Url, Client Id, Client Secret (masked with reveal toggle).
* Inline helper text on client_id and client_secret: 'These are provided by your ERP or API vendor when you register an application. FloQast does not create these.'
* Grant Type: dropdown, defaulting to Client Credentials. Other values available but not recommended for standard setups.
* Scopes: optional free-text. Helper: 'Enter space- or comma-separated scopes if your provider requires them (e.g., read:accounts data:read).'
* Token ttl seconds: optional integer. Helper: 'If you know how long tokens last (in seconds), enter it here to help FloQast refresh them proactively.'

‌

## **Basic Auth Form**

* Username: required free-text input.
* Password: required masked input with reveal toggle.
* Service Account: required Yes/No toggle. If No is selected, a prominent amber warning box appears: 'We recommend using a dedicated service account. If this user's access changes or they are offboarded, this connection will stop working.' The warning is advisory and does not block the user from proceeding.
* Password Expires toggle: Yes/No. If Yes, Expiration Date date picker appears below.

‌

## **Universal Fields (Bottom of All Auth Forms)**

* IP Allowlist Required: Yes/No toggle. If Yes, an expandable section appears below showing FloQast's current outbound IP ranges with a copy-to-clipboard action and a note: 'Your IT team or API provider must allowlist these IP addresses before this connection can sync.'
* Technical Contact Name and Technical Contact Email: Optional fields in a collapsible 'Technical Contact (Optional)' panel. Helper: 'Add a contact at your organization who can help resolve authentication issues.'

‌

## **Connection Detail Settings View - Auth Status**

* The authentication section on the connection detail view displays: auth type, a masked summary of the credential (e.g., last 4 characters of an API key), and an expiration status badge (Active / Expiring soon / Expired) when an expiration date is set.
* 'Expiring soon' badge: amber color, displays the exact expiration date and a link to edit auth.
* 'Expired' badge: red color, persistent, displays expiration date and a link to edit auth.
* 'Credentials need updating' re-auth prompt: displayed as a banner at the top of the connection detail view when an auth failure has been logged. Includes failure reason, timestamp, and a direct link to the auth edit flow. Automatically dismissed when credentials are updated and tested successfully.
* If there are multiple auth paths across the endpoints, all sets of credentials (sans the masked information) can be viewed

‌

## **Auth Edit Flow**

* Accessible from the connection detail settings view via an Edit action on the auth section.
* All current auth fields are pre-populated; sensitive fields remain masked but can be cleared and re-entered.
* After updating fields and saving, a lightweight connection test is automatically run to validate the new credentials before the edit is committed.
* If the connection has multiple endpoints, the connection vs. endpoint scope prompt appears before the test is run.
* If validation fails, the previous credentials remain active and the failure reason is displayed inline.
* If there are multiple auth paths across the endpoints, all sets of credentials (sans the masked information) can be edited; prompt to apply for a single endpoint or all endpoints that use the credentials is included when edited

# **11. Out of Scope**

* Authentication configuration for standard pre-built connections (QBO native OAuth, Workday, SAP, Yardi, etc.) - those connections have vendor-specific auth flows managed separately.
* SAML, JWT, HMAC, and other auth types not listed - not in scope for Phase 1. The framework should be extensible to accommodate these in future phases without rework.
* Runtime OAuth token caching, refresh, and revocation logic - implementation detail owned by engineering. This PRD captures the configuration requirements (token endpoint, TTL, client credentials) but not the runtime token lifecycle.
* Automated notifications to the technical contact captured in the universal fields - the technical contact fields are informational only. Notifications go to the connection owner.
* FloQast IP address provisioning and maintenance - the IP allowlist required flag and the display of IP ranges are in scope, but maintaining the IP list itself is an infra responsibility.
* Multi-credential or key rotation support (simultaneous active credentials during rotation windows) - flagged for a future phase.
* Audit logging of who accessed or viewed credentials - recommended as a future security requirement but not defined here.
* Push API authentication specifics - if push APIs require a distinct auth pattern (e.g., inbound webhook signing or token validation), that will be defined in the Push API sub-PRD. This PRD covers outbound API auth (pull) and any push auth that follows the same API Key, OAuth, or Basic Auth patterns.
