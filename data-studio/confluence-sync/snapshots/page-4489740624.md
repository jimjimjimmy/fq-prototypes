## Objective

Data Studio requires four foundational capabilities before it can be released to clients as a Beta product. This Idea captures the work required to reach that milestone.

**Entity Mapping** is the most critical of the four. Downstream FloQast applications permission data to individual users by entity — without reliable entity tagging at the point of ingestion, multi-entity customers and CAS firms cannot achieve proper data isolation, and no downstream application can correctly scope its data requests.

**Field Mapping improvements** address gaps in the current UI that prevent admins from expressing how multiple source fields map to a single target field, and deliver the transformation function experience required for production-quality data configuration.

**Scheduling** defines when data should be received or requested from a source. This is the groundwork for identifying late data and is a prerequisite for any SLA or monitoring capability built on top of Data Studio.

**On-demand Refresh** gives admins the ability to re-request data outside of a schedule — critical for API-based connections where a change to transformation logic requires the source data to be re-fetched and reprocessed.

**Logging & Audit** ensures all configuration changes and data job executions are captured in tamper-evident logs, satisfying SOC 1 controls 6.1, 6.8, and 6.18. This is a compliance requirement with a target of operating effectively by 2026-09-30.

**Notifications** closes the feedback loop between what Data Studio does and what admins need to know — proactively alerting the right people when jobs fail, data is late, or refreshes complete.

Together, these capabilities bring Data Studio to the level of completeness needed to onboard and support live client environments.

## Key Benefits

1. **CAS firms and multi-entity customers** can achieve proper data isolation per client entity — enabling Data Studio to serve the most complex customer segment from day one of Beta.
2. **Downstream FloQast applications** (reconciliation, close management, etc.) receive accurately entity-scoped data without building their own filtering logic.
3. **FloQast admins and implementation teams** can configure field mappings that reflect real-world data shapes, including many-to-one source field relationships, without workarounds or engineering escalation.
4. **FloQast as a business** can onboard live clients with confidence — Beta readiness means the platform is accountable for data delivery timing and supports self-service correction when logic changes.
5. **Data operations and support teams** gain scheduling visibility and on-demand refresh capability, reducing manual intervention when data is late or needs to be re-requested.
6. **Auditors and compliance teams** have access to a complete, tamper-evident record of all configuration changes and data job executions — satisfying SOC 1 controls 6.1, 6.8, and 6.18.
7. **FloQast Admins** receive proactive alerts when jobs fail or data is late, enabling them to investigate and resolve issues before they affect the close process.

## Use Cases

* **Entity Mapping — Multi-entity data isolation:** An admin configures connections for a customer with multiple FQ entities. Each connection is mapped to one or more FQ entities at setup. All ingested data is tagged accordingly, so downstream applications can request and display only the data relevant to the entity a given user is permissioned for.
* **Field Mapping — Many-to-one source field:** An admin is configuring a model where the source system splits account name across two fields (prefix + code). Using the updated Field Mapping UI, they select both source fields for a single target field and define a concatenation transformation.
* **Scheduling — Defining a data delivery window:** An admin configures a nightly schedule for a file-based connection. The platform knows when data is expected. If data doesn't arrive within the window, it can be flagged as late.
* **On-demand Refresh — Logic change on an API connection:** An admin updates a transformation function on an API-based connection. Rather than waiting for the next scheduled run, they trigger an on-demand refresh so the corrected logic is applied to re-requested data immediately.
* **Logging & Audit — SOC 1 compliance review:** A SOC 1 auditor requests evidence that field mapping changes were made by authorized users. The audit log shows the change, the user who made it, and the timestamp — satisfying SOC 1 control 6.8.
* **Notifications — Job failure before close:** A nightly GL transaction job fails at 2am. The FloQast Admin receives an email notification and logs in to investigate before the close team starts work at 8am.

## Assumptions

1. The list of FQ entities is maintained in FloQast and available for retrieval at connection configuration time.
2. Source datasets are linked before field mapping begins — the Field Mapping tab is only accessible once Sub-PRD 1 (Model Creation & Source Configuration) is complete.
3. Scheduling applies at the connection level — each connection has its own schedule definition.
4. On-demand Refresh is available for API-based connections; behavior for file-based connections is TBD.
5. Unmapped records (no entity tag) are retained and not dropped — rehydration is supported once a mapping is configured.
6. Standard Models (CDC/Fivetran) use pre-configured default mappings — AI field mapping suggestion is skipped for these.
7. Audit logs are append-only and cannot be edited or deleted by any user, including admins.
8. Notifications are triggered by job log events — the Logging & Audit sub-PRD defines the event schema that notifications build on.

## Requirements

| Capability | Core Requirement |
| --- | --- |
| Entity Mapping | Admins can associate one or more FQ entities with a connection. All ingested data is tagged at the point of ingestion. Unmapped records are retained with a null tag and support retroactive rehydration. |
| Field Mapping | The Field Mapping UI supports selection of multiple source fields per target field and provides a transformation function editor. AI auto-suggests mappings on first load; admins review and confirm. |
| Scheduling | Admins can define a recurring schedule per connection. The platform tracks expected vs. actual data arrival against this schedule. |
| On-demand Refresh | Admins can trigger an immediate re-request of data for API-based connections outside of the defined schedule. |
| Logging & Audit | All in-scope configuration changes are captured in a tamper-evident, append-only audit log. All data job executions are recorded and accessible to customers (Logs tab) and FQ engineering. Scheduling config changes require approval before taking effect (SOC 1 6.18). |
| Notifications | Admins receive proactive email notifications when data jobs fail or expected data is late. Notification preferences are configurable per user. |

## Out of Scope

* **Entity mapping by company** — confirmed future need, explicitly deferred.
* **Automatic or rule-based entity mapping** — not in scope for this release.
* **On-demand Refresh for file-based connections** — API-only at launch.
* **Transformation function library definition** — engineering deliverable.
* **User-level entity access controls** — governed by FloQast's existing permissions model.
* **Audit logging for non-Data Studio FloQast products** — separate compliance scope.
* **Real-time log streaming to external systems** — not in scope.
* **Slack or third-party notification channel integrations** — V1 is email-only.
* **Automated remediation or retry logic on job failure** — separate capability.
