This page defines requirements for logging, error messaging, and troubleshooting behavior in Data Studio. The goal is to ensure errors are specific, actionable, and customer-friendly — and that internal system states never surface directly to end users.

| \# | Requirement | Example Message | Notes |
| --- | --- | --- | --- |
| 1 | The system must retain uploaded files through processing lifecycle disruptions and resume processing once the system is ready, rather than failing the upload. |  | Files should never be lost due to transient system states. |
| 2 | When a file fails during field mapping, the error must identify the specific field(s) that failed and the reason for each failure (e.g., incorrect data type, missing required value, value out of expected range). | “FloQast was not able to transform the data received because \[field name\] is a \[actual type\] data type and was expected to be a \[expected type\] data type." |  |
| 3 | All user-facing error messages must use plain language. Internal system terminology (e.g., references to infrastructure states or internal processes) must not appear in customer-facing UI or notifications. |  | Engineering terminology is acceptable in internal logs only. |
| 4 | Generic error messages are only permitted when the root cause cannot be determined. All other errors must include a specific, actionable description. |  | This message is only acceptable when the root cause is truly unknown. It must not be used as a fallback for known failure types. |
| 5 | When a file name does not match the expected naming pattern, the error message must explicitly state that the file name did not match the expected format and, where possible, indicate what the expected pattern is. | *"The file name did not match the expected pattern."* |  |
| 6 | When the system cannot extract data from a file name (e.g., missing date, entity code, or other expected segments), the error must state that the file name could not be parsed and identify which segment was missing or unreadable. | “FloQast was not able to detect the accounting period from the file name, based on the existing file configurations." |  |
| 7 | Field-level validation failures must call out each affected field by name. Errors must not be aggregated into a single message when multiple distinct fields are involved. | “FloQast was not able to transform the data received because \[field name\] is a \[actual type\] data type and was expected to be a \[expected type\] data type." |  |
| 8 | When the root cause of a failure is unknown, the error message must include a correlation or reference ID (e.g., upload ID, file ID, timestamp) that support and engineering can use to locate the relevant logs and diagnose the issue. | “FloQast encountered an unexpected error while processing this file. Please reference ID \[upload ID\] when contacting support." |  |
