# 1. Objective

FloQast is building Data Platform 2.0 as a centralized, ERP-agnostic data layer that will serve all FloQast products — Close Management, Reconciliations, JEM, and Transform — with normalized financial data from a single platform. Intacct is one of FloQast's largest ERP integrations and a critical integration to bring onto this platform.

Today, FloQast's Intacct integration operates outside of Data Platform 2.0 as a legacy direct connection. Customers on Intacct cannot be onboarded through Data Studio and are served by a separate integration path that creates ongoing operational overhead for Engineering and Customer Success.

This project brings the Intacct direct API connection into Data Platform 2.0 — enabling new customer self-serve onboarding through Data Studio, providing a structured migration path for all existing legacy Intacct customers, and delivering normalized financial data to all downstream app teams.

Success is defined as new Intacct customers being onboarded through Data Studio without manual Engineering or CS intervention, and all existing legacy Intacct customers having a clear, low-risk path to the new platform.

Intacct's API is XML-based, communicating over a single HTTPS POST endpoint. Authentication uses a two-step model: FloQast's sender credentials combined with the customer's company ID, user ID, and password establish a session token, which is then used for all subsequent API calls within a sync job. Multi-entity customers may also require a client ID to access the top-level company context. This authentication model is materially different from NetSuite and will require its own connection setup UX and credential validation logic.

# 2. Key Benefits

* New Intacct customers can be onboarded self-serve through Data Studio — no manual Engineering or CS setup required.

* Existing legacy Intacct customers have a structured, low-risk migration path to the new platform.

* All Intacct data is normalized, giving app teams (Close, Reconciliations, JEM, Transform) a consistent, ERP-agnostic data feed.

* Platform-native integration means Intacct customers benefit from all Data Platform 2.0 capabilities as the platform evolves.

* A single integration codebase replaces the legacy path, reducing long-term maintenance burden.

* Multi-location, multi-book, and multi-currency support is built in from day one.

# 3. Use Cases

1. A new Intacct customer is set up by their CS team, who navigates to Data Studio, selects Intacct as the ERP source, and completes the connection wizard — entering their company ID, user ID, and password, selecting locations, and confirming mapping — in under 30 minutes, without Engineering involvement.

2. A CS team generates a setup link for a customer's IT team, who clicks the link, lands in a pre-populated connection wizard, and completes setup independently.

3. A customer's IT team completes onboarding via the setup link and immediately triggers an on-demand sync to validate that data is flowing into FloQast correctly.

4. A Close Management or Reconciliations user accesses balance data that has been refreshed from Intacct within the last 5 minutes, with no manual action required.

5. An existing legacy Intacct customer is migrated to the new platform during a scheduled migration window; their scheduled sync continues without interruption and their data is validated for parity before cutover.

6. An app team engineer subscribes to the `intacct.data.available` event and their service receives a notification when new data is ready, without polling the database.

# 4. Success Metrics

* New Intacct customers onboarded via Data Studio without Engineering intervention (target volume TBD with CS).

* Time-to-connect for a new customer under 30 minutes end-to-end.

* Data latency from Intacct to CDA under 5 minutes for scheduled syncs.

* Sync success rate of 99%+ under normal Intacct API availability.

* Zero data loss during legacy-to-platform migration for all migrated customers.

# 5. Assumptions

* Intacct customers have a valid company ID, user ID, and password for their Intacct account with appropriate API permissions configured.

* Multi-entity customers provide a client ID to enable top-level company access; single-entity customers may omit it.

* Data Platform 2.0 is available and supports the Intacct account and balance schema required by this integration.

* The existing legacy Intacct integration remains live in parallel throughout the transition period; no hard cutover until all customers are successfully migrated.

* Intacct's XML API is available and stable across all Intacct editions used by FloQast customers.

* Customers are responsible for configuring the correct roles and permissions in their Intacct account prior to connection setup.

* Existing legacy customers will be migrated automatically (opt-out model); customers will not need to take action to initiate migration.

* Historical sync data from the legacy integration must be preserved through migration; a re-sync will not be acceptable. This will require coordination with application teams.

* Customers may have multiple active Direct API connections per Intacct account.

* Schema changes required to support Intacct-specific fields will include standard dimensions at minimum; full scope to be confirmed with the Data Platform team.

* Intacct locations map to FQ entities for the purposes of sync scoping; this mapping is managed in Data Studio and is distinct from the FQ entity concept used elsewhere in FloQast products.

# 7. Scope

The following capabilities and data types are in scope for this initiative:

**Connection & Auth**

* Direct API connection creation and management (company ID / user ID / password, with optional client ID)

* Session token establishment and caching within sync jobs

* Multiple active connections per Intacct account supported

* Credential storage, validation, and lifecycle management

* Setup link generation and auto-connect flow

**Data**

* Chart of Accounts

* GL Balances (via `get_trialbalance` XML function)

* Locations / Entities (including parent-child hierarchy and child location rollup)

* Reporting Books and Adjustment Books

* Currencies and Reporting Periods

* Departments (as a standard dimension)

**Platform**

* Normalization for all ingested data

* Scheduling (preset frequencies) and on-demand sync

* App-team event notifications (pub/sub)

* Audit logging and sync job observability

* Custom endpoint configuration for non-standard data needs

* Migration path from legacy integration to new platform

# 8. Requirements

**REQ-01: As a CS team member or customer IT team, I want to create an Intacct direct API connection in Data Studio so that I can connect a customer's Intacct account to FloQast without Engineering involvement.**

*Functional spec: The connection wizard collects the customer's Intacct credentials (company ID, user ID, password, and optional client ID for multi-entity accounts), validates them against Intacct in real time by establishing a session token, and creates an active connection on success. Credential storage, validation behavior, session management, edit flow, and error states are defined in Sub-PRD 1: Connection Management.*

**REQ-02: As a CS team member, I want to generate a setup link for a customer so that their IT team can complete the initial connection setup independently.**

*Functional spec: An admin user generates a time-limited, JWT-signed setup link scoped to a customer. A successful connection setup via the setup link creates a connector in Data Studio and triggers the setup of a standard Intacct mapping. Auto-connect flow is defined in Sub-PRD 3: Setup Link & Auto-Connect.*

**REQ-03: As a CS team member or customer IT team, I want to select which Intacct locations to sync so that only the relevant locations are connected to the data feed.**

*Functional spec: After connection setup, an admin user can assign the relevant Intacct locations to the connection. Location discovery traverses the customer's location hierarchy, including parent-child relationships and optional child location rollup. Data stored in the data platform is tagged with the appropriate locations. Location assignment and change flow are defined in Sub-PRD 2: Location Management.*

**REQ-04: As a CS team member or customer IT team, I want field mappings to be automatically configured from Intacct fields to FQ fields so that no manual mapping is required for standard setups.**

*Functional spec: A standard mapping configuration is applied at connection creation, covering all required fields for accounts and balances. Reporting book and adjustment book configuration is included. Location-level overrides are supported for non-standard account structures. Mapping logic and book configuration are defined in Sub-PRD 4: Mapping Configuration.*

**REQ-05: As a CS team member or customer IT team, I want to configure a sync schedule for a connection so that Intacct data is refreshed automatically at a defined frequency.**

*Functional spec: The connection setup includes a scheduling step with preset frequency options. On-demand sync is also available at any time. Frequency options, timezone handling, missed run behavior, and on-demand API spec are defined in Sub-PRD 5: Scheduling & On-Demand Refresh.*

**REQ-06: As an app team engineer, I want to receive a notification when new Intacct data is available so that my service can consume updated data without polling.**

*Functional spec: The integration publishes events to a pub/sub topic when sync jobs complete. App teams subscribe to receive data-available and failure notifications. Event types, payload schema, SNS/SQS architecture, and failure notifications are defined in Sub-PRD 6: Notifications & Logging.*

**REQ-07: As a CS team member or Engineering team, I want sync job outcomes and API call history to be logged so that I can diagnose issues and confirm data delivery.**

*Functional spec: All sync jobs produce structured log entries including job ID, connection, location, status, record counts, and error details. Intacct-specific error codes (including rate-limit retries on XMLGW_JPP0001 and auth failures on XMLGW_JPP0002 and PL04000005) are captured and surfaced. Logs are retained per defined policy and accessible via internal tooling. Log schema and retention policy are defined in Sub-PRD 6: Notifications & Logging.*

**REQ-08: As an Engineering or CS team member, I want to configure additional or non-standard Intacct object types for a connection so that customers with custom dimensions or non-standard data needs can be supported.**

*Functional spec: Endpoint configuration supports standard and custom Intacct object types via the readByQuery XML function. Each endpoint has its own enable/disable state and failure isolation. Full endpoint model and approval workflow are defined in Sub-PRD 7: Additional Endpoint Configuration.*

**REQ-09: As a CS or Engineering team member, I want existing legacy Intacct customers to be migrated to the new Data Platform 2.0 integration so that all Intacct customers are served from a single platform.**

*Functional spec: A structured migration path allows legacy Intacct customers to be transitioned to the Data Platform 2.0 integration with parallel validation to confirm data parity before cutover. Migration is automatic (opt-out). Historical data is preserved through migration in coordination with application teams. Migration phases, rollback strategy, and legacy integration sunset plan are defined in Sub-PRD 8: Legacy Migration.*

# 9. User Interaction and Design

The end-to-end flow spans four stages: Connection Setup, Location & Mapping Configuration, Ongoing Sync, and (for existing customers) Migration.

**Stage 1: Connection Setup**

* User navigates to Data Studio and selects Intacct as an ERP source, or clicks a CS-generated setup link.

* User enters Intacct credentials: company ID, user ID, password, and optionally a client ID (required for multi-entity top-level access).

* System validates credentials against Intacct in real time by establishing a session token, and surfaces clear error messages on failure — including auth failures, permission errors, and rate-limit conditions.

* On success, the connection is created and the user proceeds to location selection.

**Stage 2: Location & Mapping Configuration**

* System retrieves available Intacct locations from the customer's account and presents them for selection, including the parent-child hierarchy.

* User selects one or more locations to include in the sync. Child location rollup is configurable per location.

* Standard field mapping and reporting/adjustment book configuration are applied automatically. Location-level overrides are available if needed.

**Stage 3: Ongoing Sync**

* Scheduler triggers sync jobs per the configured frequency.

* On-demand sync is available via UI or API at any time.

* App teams receive event notifications when new data is available.

* Sync job status and logs are visible in Data Studio.

**Stage 4: Migration (Existing Legacy Customers)**

* Existing legacy Intacct customers are migrated automatically in a phased approach with parallel validation.

* Data parity is confirmed before legacy cutover for each customer.

* Historical data is preserved; scheduled syncs continue without interruption post-migration.

* See Sub-PRD 8 for full migration design.

# 11. Out of Scope

* Write-back from FloQast to Intacct (e.g., posting journal entries).

* Non-financial data domains (AP, AR, purchasing, inventory, HR).

* sFTP-based data ingestion (separate pipeline; not in scope for this project).

* Real-time event streaming from Intacct (webhook-push model).

* Intacct Platform Services or custom SuiteApp-equivalent delivery.
