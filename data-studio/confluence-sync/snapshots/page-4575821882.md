> **Context:** Mapping configuration defines how fields from NetSuite API responses are mapped to FloQast's Financial Data Model (FDM). A default mapping is applied automatically on first sync. Customers and admins can override individual field mappings to handle NetSuite account customizations (custom segments, renamed fields, custom lists).

---

## 1. Feature Overview

Mapping configuration is the layer between raw NetSuite API data and FloQast's normalized schema. Because NetSuite accounts vary significantly — customers use custom segments, multi-currency, custom account numbering schemes, and subsidiary-specific chart of accounts configurations — mapping must be flexible while providing safe, opinionated defaults.

This sub-PRD covers two areas: (1) standard mapping setup — the mechanism by which mapping is created, versioned, and applied; and (2) accounts and balances mapping specifically — the most critical and complex mapping domain for the Close and Reconciliations workflows.

### 1.1 User Stories

| Story ID | User Story |
| --- | --- |
| US-MAP-01 | As a Data Studio admin, I want the system to apply a default mapping automatically so that I don't have to configure every field before the first sync. |

## 2. Standard Mapping Setup (Item 6)

### 2.1 Mapping Levels

Mapping occurs at the connection level. It is created automatically when the connection is set up.

### 2.2 Default Mapping Generation

When the first SyncJob runs for a connection, if no MappingConfig exists, the system:

1. Fetches sample data from the Account endpoint to discover available fields.
2. Matches NetSuite fields to FQ fields using the standard default mapping table (see Section 2.3).
3. Creates a MappingConfig record at the connection level with version = 1.
4. Logs: "Default mapping created for connection \[name\] on \[date\]. 47 fields mapped; 3 fields unmapped."

> **Note:** Unmapped fields do not block the sync — they are simply not written. Unmapped required FQ fields are flagged as warnings in the sync log and visible in the mapping UI.

### 2.4 Custom Field Mapping

NetSuite customers frequently add custom fields to their account records. The mapping UI allows admins to:

* View all fields returned by the Account API endpoint for their specific NetSuite account.
* Map any available NetSuite field to a FQ field via a dropdown selector.
* Map a NetSuite field to a custom FQ field

### 2.5 Mapping Versioning

As is already present in Data Studio, the mapping version is incremented every time a user adjusts the rules for the field mappings.

### 2.6 Acceptance Criteria – Standard Mapping

| AC-ID | Criterion |
| --- | --- |
| AC-MAP-01 | If no MappingConfig exists when the first SyncJob runs, a default MappingConfig is created automatically using standard defaults. |
| AC-MAP-03 | An admin can add, edit, or remove field mappings; each save creates a new version. |
| AC-MAP-04 | Unmapped required FQ fields are highlighted in the UI and noted as errors in the sync log — they block the ability to sync. |

## 3. Accounts & Balances Mapping (Item 7)

### 3.1 Overview

Account and balance data are the core of FloQast's Close Management and Reporting workflows. The mapping for these domains determines which fields are pulled from NetSuite, how often they are refreshed, and how they are normalized in FQ.

### 3.2 Account Data Pull

#### 3.2.2 When to Pull Account Data

| Trigger | Scope | Rationale |
| --- | --- | --- |
| Initial sync (connection) | Full account list | Populate FQ with complete chart of accounts |
| Scheduled incremental sync | Accounts modified since last sync (using modifiedDate filter) | Capture account additions and name changes without full re-pull |
| Monthly full refresh (first sync of the accounting period) | Full account list | Guard against missed incremental changes; align with period close |
| On-demand sync | Full account list | Admin-triggered catch-up or troubleshooting |
| Mapping config change (field added to mapping) | Full account list | Populate the new field for all existing accounts |

### 3.3 Balance Data Pull

#### 3.3.2 When to Pull Balance Data

| Trigger | Scope | Rationale |
| --- | --- | --- |
| Scheduled sync (standard cadence) | Current and prior period | Keep FQ balances current for active close period and the current period |
| On-demand sync | Application selected periods | Allow spot refresh during close |
| Initial sync | All periods in the current fiscal year + prior fiscal year | Populate historical context for Reconciliations |
| Mapping change (balance field added) | All periods in current + prior fiscal year | Ensure new fields are populated historically |

### 3.5 Acceptance Criteria – Accounts & Balances Mapping

| AC-ID | Criterion |
| --- | --- |
| AC-MAP-07 | On initial sync, all accounts accessible to the assigned entities are fetched and written to FQ with the standard default field mapping. |
| AC-MAP-08 | Incremental account syncs use the modifiedDate filter; only accounts modified since the last sync are fetched. |
| AC-MAP-09 | Balance data is retrieved and mapped per the balance definition above |
| AC-MAP-10 | Balances are stored per account, per FQ entity, per accounting period, and if additional dimensions are provided, at their level of granularity — there are no duplicate records for the same combination. |
| AC-MAP-13 | NetSuite account types are normalized to FQ Account Type and Balance Type using the standard type mapping table. |
| AC-MAP-14 | A mapping config change that adds a new account field triggers a full account re-sync. |
| AC-MAP-15 | Balance pull for the current period completes within 5 minutes for an entity with up to 5,000 accounts and 12 periods. |

## 4. Non-Functional Requirements

| Requirement | Target |
| --- | --- |
| Balance query execution time | P95 < 60 seconds per entity for current-period balance query with up to 10,000 accounts |
| Timeout handling | Queries exceeding 300 seconds are cancelled; partial results are discarded; entity marked PARTIAL; retry scheduled |
| Mapping config save latency | P99 < 500ms |
| Mapping history retention | All versions retained for 2 years; available in the UI for 90 days (older via API/export) |
| Account data freshness | Incremental account sync must detect changes within 1 full sync cycle of the change occurring in NetSuite |

## 5. Edge Cases & Error Handling

| Scenario | Expected Behavior |
| --- | --- |
| NetSuite account has 0 accounts (new or incorrectly permissioned) | Sync completes with 0 records; warning: "No accounts found. Verify that the connected role has access to the Account record type." |
| NetSuite account type is unrecognized (custom type) | Mapped to FQ Account Type = UNKNOWN; flagged in sync log for admin review. |
| Balance query for a very large account (100,000+ transactions per period) | Query may time out. Implement chunking by date range sub-query. Alert if > 3 retries needed. |
| Mapping config edited while a SyncJob is running | The running job uses the mapping version active when the job started. The new version is applied on the next job. |
| Admin deletes a custom field mapping that FQ consumers depend on | Mapping deletion is logged; deletion does not remove historical FQ data. A warning is shown: "Removing this mapping will stop populating \[field\] in FQ going forward." |
