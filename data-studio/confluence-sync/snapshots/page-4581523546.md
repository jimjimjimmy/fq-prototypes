## 1. Objective

This sub-PRD defines when and how data syncs are triggered for a NetSuite Direct API connection in Data Studio. Two trigger types are supported: a scheduled daily sync and an on-demand sync initiated by a downstream FloQast application. There is no user-facing configuration UI — scheduling behavior is fixed and system-managed. Queue behavior follows the pattern established in the On Demand Data PRD.

---

## 2. Requirements

**REQ-01: The system must trigger a sync for every active NetSuite Direct API connection once every 24 hours at midnight in the customer's timezone.**

_Functional spec: The scheduled trigger fires at midnight local time for each connection, where local time is determined by the company timezone already stored in FloQast. No new timezone configuration is required. This trigger applies to all active connections — a connection in an archived or error state is skipped._

**REQ-02: The system must accept and process on-demand sync triggers from downstream FloQast applications.**

_Functional spec: On-demand triggers follow the interface, request schema, processing behavior, and notification pattern defined in the On Demand Data PRD. Scope (period, entity, and other criteria) is provided by the requesting application. This sub-PRD does not redefine on-demand behavior — it only establishes that the NS Direct API connection participates in that pattern._

**REQ-03: Before initiating any sync, the system must check whether a sync is already active or queued for that connection.**

_Functional spec: This check applies to both scheduled and on-demand triggers equally. The possible states and resulting behavior are:_

| Current state | New request behavior |
| --- | --- |
| No active sync | Sync starts immediately |
| Active sync running | New request is queued (queue depth: 1) |
| Active sync + 1 queued request | New request is rejected; ID of the existing queued sync is returned |

**REQ-04: Queue depth must not exceed 1. A scheduled trigger that cannot be queued must retry before being dropped, and must log an error if all retries are exhausted.**

_Functional spec: Only one request may be queued behind an active sync at any time. If a scheduled sync fires and the queue is full (active + queued), the system must retry the trigger a defined number of times at a defined interval before giving up. Retry count and interval are TBD (see Open Questions). If the queue remains full after all retries are exhausted, the scheduled trigger is dropped for that window and a log entry is written at error severity. The log entry must include: connection ID, trigger timestamp, number of retries attempted, and the reason for failure (queue full). The trigger is not retried again until the following midnight. If an on-demand request arrives when the queue is full, the On Demand Data PRD rejection behavior applies — no retry logic is applied to on-demand requests._

---

## 3. Assumptions

* Customer timezone is sourced from the existing company timezone setting in FloQast. No new configuration is required at the connection level.
* Scheduled sync scope follows the data pull triggers defined in Sub-PRD 4: incremental for accounts (modifiedDate filter), current and prior open periods for balances.
* Retry logic applies only to scheduled triggers, not to on-demand triggers (on-demand rejection behavior is defined in the On Demand Data PRD).
* The on-demand trigger interface and notification mechanism are defined by the On Demand Data PRD. This sub-PRD defers to that document for those details.

---

## 4. Out of Scope

* Sync scheduling UI or customer-configurable sync frequency
* User-triggered "Sync Now" from Data Studio UI (covered in On Demand Data PRD)
* Sync logging, monitoring, and audit trail (covered in On Demand Data PRD)
* Completion notifications to downstream applications (covered in On Demand Data PRD)
* Any sync behavior for non-API connections (e.g., ERP File Connector)

## 5. Acceptance Criteria

| AC-ID | Criterion |
| --- | --- |
| AC-SCH-01 | Every active NS Direct API connection receives a sync trigger at midnight in the company's FloQast timezone, once every 24 hours. |
| AC-SCH-02 | A connection in archived or error state is skipped by the scheduled trigger without raising an error. |
| AC-SCH-03 | On-demand triggers are accepted and processed per the On Demand Data PRD. |
| AC-SCH-04 | If a sync is active when a new trigger arrives (scheduled or on-demand), the new request is queued. |
| AC-SCH-05 | If a sync is active and a queued request already exists when a new trigger arrives, the new request is rejected and the queued sync ID is returned. |
| AC-SCH-06 | If a scheduled trigger fires and the queue is full, the system retries the defined number of times before dropping the trigger. |
| AC-SCH-07 | If all retries are exhausted, the scheduled trigger is dropped and an error log entry is written recording the connection ID, trigger timestamp, retry count, and failure reason. |
| AC-SCH-08 | A dropped scheduled trigger does not retry again until the following midnight window. |
