# **1. Objective**

This sub-PRD defines requirements for how FloQast Data Studio resolves query parameter values at configuration time and at run time - covering static variables, dynamic date/time expressions, and last-run metadata. It is a sibling document to the Endpoint Nesting sub-PRD, which covers a fourth variable source type: output values from other endpoints.

A query parameter value is not always a fixed, known string. Many financial APIs require values that change with each sync run - a date range scoped to the current period, a timestamp representing the last time data was fetched (for incremental loads), or an identifier like a realmId that is captured at connection setup rather than typed per endpoint. Without a principled variable resolution model, admins must hardcode values that go stale, re-enter the same identifiers repeatedly across endpoints, and manually manage date math - all of which is error-prone and creates maintenance overhead. This PRD defines the variable types the system must support, how each is sourced, and how the UI surfaces them during endpoint configuration.

## **Variable Type Reference**

The following table summarizes all supported variable source types. All four are in scope for this sub-PRD.

‌

| **Variable Type** | **Resolved When** | **Examples** |
| --- | --- | --- |
| Static - connection variable | At connection setup (auto) or endpoint config (manual) | realmId (QBO), companyId (Workday), clientId (SAP) |
| Static - user-defined value | At endpoint configuration; same on every run | accounting_method: Accrual, report_type: Summary, currency: USD |
| Dynamic - relative date/time | At run time, relative to execution timestamp | today, yesterday, start_of_month, end_of_last_month, N_days_ago |
| Dynamic - last run metadata | At run time, from most recent successful sync run for this endpoint | last_run_timestamp (for modified_since), last_cursor (for pagination) |

# **2. Key Benefits**

* Eliminates hardcoded, stale values - date parameters and identifiers are resolved at run time rather than frozen at configuration time.
* Reduces setup repetition - connection-level identifiers (e.g., realmId) are captured once and reused across all endpoints for that connection.
* Enables incremental data loading - the last run timestamp pattern allows endpoints to fetch only records modified since the previous sync, dramatically reducing data transfer and API quota usage.
* Consistent date handling - a standard library of relative date expressions removes ambiguity and ensures all endpoints use dates computed the same way.
* Faster endpoint configuration - admins select from known, pre-populated variable options rather than looking up and typing values manually.
* Auditability - the system records which variable values were resolved and used on each run, making sync behavior transparent and debuggable.

# **3. Use Cases**

1. QBO trial balance with dynamic date range: An implementor configures a Trial Balance endpoint that requires start_date and end_date parameters. Rather than hardcoding specific dates, they set start_date to 'start of current month' and end_date to 'today'. On each daily sync, the system resolves these to the correct calendar values and passes them to the API request.
2. Incremental transaction sync using last run timestamp: An admin configures a Transactions endpoint that supports a modified_since parameter. They set it to 'last run timestamp'. On the first run, the system uses a configured fallback date (e.g., a user-defined start date). On all subsequent runs, it passes the timestamp of the most recent successful sync, fetching only new or modified records.
3. realmId reused across multiple QBO endpoints: During QBO OAuth connection setup, the system captures the realmId automatically. When an implementor adds multiple endpoints for the same connection, realmId is available as a pre-populated connection variable and does not need to be entered again.
4. Manually entered static identifier: An admin configures a Workday endpoint that requires a company_id that was not captured during connection setup. They enter it once as a static connection variable during endpoint configuration. It is stored at the connection level and reused for all subsequent runs without re-entry.
5. Accounting method as a static user-defined value: An implementor sets accounting_method to 'Accrual' as a static value on a Trial Balance endpoint. This value is the same on every run and does not need dynamic resolution.
6. Admin previews resolved values before activating: Before saving a new endpoint configuration, an admin clicks 'Preview values' to see what the system would resolve each variable to if the endpoint ran right now - verifying the date expressions and connection variables before going live.

# **4. Success Metrics**

‌

| **Metric** | **Target / Description** |
| --- | --- |
| Static variable reuse rate | Connection variables (e.g., realmId) captured at setup are available in the endpoint config UI for 100% of endpoints on that connection without re-entry |
| Dynamic date resolution accuracy | 100% of relative date expressions resolve to the correct calendar date at run time with no off-by-one or timezone errors |
| First-run fallback coverage | 100% of last-run-timestamp parameters with no prior run history have a defined fallback value; no endpoint fails on first run due to a missing prior timestamp |
| Variable preview reliability | Admin-triggered 'Preview values' must reflect the same resolved values that would be used on an actual run at that moment |
| Run-time variable resolution logged | 100% of sync runs record the resolved values for each dynamic parameter (field names and values) in the run log for auditability |
| Endpoint setup success rate (variable-reliant endpoints) | > 95% of endpoints using variable-based parameters are saved and first-run successfully without error, consistent with the parent PRD target |

‌

# **5. Assumptions**

* Connection-level variables captured during OAuth or connection setup (e.g., realmId) are stored in a connection variable store that is accessible to all endpoints configured for that connection.
* Not all connection-level variables are auto-captured. Some must be manually entered by the admin during endpoint configuration and stored at the connection level for reuse. The system must support both patterns.
* Relative date expressions are evaluated in UTC unless the connection or endpoint is configured with an explicit timezone. Timezone handling is TBD (see Open Questions).
* For last run timestamp parameters: 'last run' refers to the most recent successful completed run for that specific endpoint on that connection - not a connection-wide timestamp.
* When a last-run-timestamp parameter is used and no prior successful run exists (i.e., first run), the system must require a fallback value to be configured at endpoint setup time. The endpoint cannot be activated without a fallback.
* Close calendar integration (deriving dates from the FloQast accounting close calendar) is out of scope for this phase. Relative date expressions are the mechanism for date-based parameters in this sub-PRD.
* Static user-defined values (e.g., accounting_method: Accrual) do not require a separate storage model - they are stored as part of the endpoint configuration record, consistent with the parent PRD.
* Pagination cursor/token handling (last_cursor) may require additional design consideration for multi-page response patterns; this is flagged as an open question.

# **6. Milestones**

This work spans Phases 1 and 3 of the parent PRD. Variable resolution is a prerequisite for correct endpoint execution.

‌

1. Phase 1a - Static variables (connection-level and user-defined): System stores connection variables captured at OAuth/setup and allows manual entry of additional static variables scoped to the connection. All static variables are available in the endpoint configuration UI as selectable options for query parameter values.
2. Phase 1b - Relative date/time expressions: System resolves a defined library of relative date expressions at run time (today, yesterday, start/end of current month, start/end of last month, N days ago, start/end of current quarter, start/end of last quarter). Admins can assign these to date-type query parameters.
3. Phase 3a - Last run timestamp (incremental loads): System captures the completion timestamp of each successful endpoint run and makes it available as a dynamic parameter value for subsequent runs. Admins can configure a fallback date for first-run scenarios. Run log records the resolved timestamp used.
4. Phase 3b - Pagination cursor/token: System supports capturing and reusing a pagination cursor or token from a prior run response to enable cursor-based incremental pagination patterns. Scope and mechanism to be defined in collaboration with engineering.
5. Future - Close calendar date integration: Date parameters can reference FloQast close period dates (e.g., start of current close period, end of last closed period). Deferred pending close calendar API availability.

# **7. Scope of Data**

* Connection variable store: per-connection key-value store holding variables captured at connection setup (e.g., realmId from OAuth) and manually entered static variables (e.g., company_id). Includes variable name, value, source (auto-captured vs. manually entered), and the date last updated.
* Endpoint query parameter configuration: updates to the existing endpoint configuration record to support variable references in parameter values - storing the variable type (static-connection, static-user, relative-date, last-run-timestamp, last-cursor) and the specific expression or variable name, in addition to or instead of a literal value.
* Last run metadata per endpoint: per-endpoint, per-connection record of the most recent successful run's completion timestamp and (where applicable) pagination cursor or token. Used to resolve last-run-timestamp and last-cursor parameter values.
* Resolved variable log: per-run record of the variable name, variable type, and resolved value used for each dynamic parameter in that run. Stored as part of the run log for auditability.

‌

Explicitly out of scope:

* Close calendar date values (deferred to future phase).
* User authentication tokens or OAuth credentials - these are managed by the connection auth layer, not the variable resolution system.
* Cross-connection variable sharing - connection variables are scoped to a single connection.

# **8. Requirements**

‌

**REQ-01: As the system, I must capture and store connection-level variables from the OAuth or connection setup flow so that they are available for use in endpoint query parameter configuration without requiring re-entry.**

_Functional spec:_ During connection setup (e.g., OAuth callback), the system must extract and store known connection-level variables (e.g., realmId for QBO, companyId for Workday) in a per-connection variable store. These variables must be available in the endpoint configuration UI as selectable options for any query parameter on that connection. The variable name, value, and source ('auto-captured at setup') must be stored and visible to the admin.

**REQ-02: As an admin or implementor, I want to manually define and store a static variable at the connection level so that I can reuse it across multiple endpoints without re-entering it each time.**

_Functional spec:_ Admins must be able to add static variables to the connection variable store manually during endpoint configuration. Each manually entered variable requires a name and a value. Once saved at the connection level, the variable is available as a selectable option for any query parameter on any endpoint for that connection. The source must be recorded as 'manually entered' to distinguish it from auto-captured variables.

**REQ-03: As an admin or implementor, I want to assign a static user-defined value directly to an endpoint query parameter so that fixed values (e.g., accounting method, currency code) are clearly configured and stored with the endpoint.**

_Functional spec:_ When configuring a query parameter, admins must be able to select a 'Static value' type and enter a literal value inline. For parameters with known enumerated options (e.g., accounting_method: Accrual / Cash), the UI must surface those options as a dropdown. The value is stored as part of the endpoint configuration and is the same on every run. This is the same as static parameter behavior defined in the parent PRD; this requirement establishes its relationship to the variable resolution model.

**REQ-04: As an admin or implementor, I want to assign a relative date expression to a date-type query parameter so that the correct date is automatically resolved on every sync run without manual updates.**

_Functional spec:_ The system must support a defined library of relative date expressions that can be assigned to date or datetime query parameters. The minimum required set includes: today, yesterday, start_of_current_month, end_of_current_month, start_of_last_month, end_of_last_month, start_of_current_quarter, end_of_current_quarter, start_of_last_quarter, end_of_last_quarter, and N_days_ago (where N is a configurable integer). When the endpoint runs, the system resolves the expression to a concrete date value at execution time. The resolved value must be logged in the run record.

**REQ-05: As an admin or implementor, I want to configure a query parameter to use the timestamp of the last successful run so that the endpoint only fetches records created or modified since the previous sync.**

_Functional spec:_ For endpoints that support a 'modified since' or equivalent incremental parameter, admins must be able to assign 'last run timestamp' as the parameter value. On runs after the first, the system resolves this to the completion timestamp of the most recent successful run for that endpoint. The timestamp must be stored per endpoint per connection and updated after each successful run. If no prior successful run exists, the system must fall back to a user-configured fallback date (see REQ-06).

**REQ-06: As an admin or implementor, when I configure a last-run-timestamp parameter, I must also define a fallback date value to be used on the first run so that the endpoint does not fail when no prior run history exists.**

_Functional spec:_ When an admin assigns 'last run timestamp' to a query parameter, the configuration panel must require a fallback date value. The endpoint cannot be activated without a fallback. The fallback must support both a specific date (manually entered) and a relative date expression from the supported library (e.g., start_of_last_month). The fallback is used only on the first successful run; subsequent runs use the actual last run timestamp.

**REQ-07: As an admin or implementor, I want to preview the resolved values for all variable-based parameters before saving or running an endpoint so that I can verify the configuration is correct.**

_Functional spec:_ The endpoint add/edit panel must include a 'Preview values' action that shows, for each configured parameter, the value that would be resolved and passed to the API if the endpoint ran at the current moment. For relative date expressions, the preview must show the resolved calendar date. For last-run-timestamp, it must show the stored timestamp or the fallback label ('fallback: \[value\]') if no prior run exists. For connection variables, it must show the stored value. The preview must not execute an actual API call.

**REQ-08: As an admin, I want to see a clear summary of the variable type and source for each query parameter in the endpoint configuration view so that I can understand how each value will be obtained at run time.**

_Functional spec:_ In both the endpoint configuration panel and the read-only endpoint detail view, each query parameter row must display its variable type (Static - connection variable / Static - user-defined / Dynamic - relative date / Dynamic - last run timestamp / Dynamic - cross-endpoint output) and a brief description of its source (e.g., 'Captured at connection setup', 'Resolved at run time: start of current month'). This ensures admins have full visibility without needing to open the edit panel.

**REQ-09: As the system, I must record the resolved parameter values used on each sync run so that admins can audit and troubleshoot endpoint behavior.**

_Functional spec:_ The run log for each endpoint execution must include, for each query parameter, the variable type and the resolved value used in that specific run (e.g., start_date resolved to '2026-03-01', realmId resolved to '1234567890'). For sensitive connection variables, the value may be masked or truncated in the UI display but must be stored for debugging. This log must be accessible from the endpoint detail view and the connection sync log.

**REQ-10: As the system, when I run the data sync for an endpoint, I leverage the static or dynamic parameter values in my request.**

_Functional spec:_ When an endpoint sync is triggered, the parameters that have been established for the endpoint are used in generating the API request. Static and dynamic parameter values are determined and then used in the specific API request to retrieve the data. If there is an error with the parameters in the request, it needs to be surfaced so that it is clear there is a problem with the parameters and which parameter specifically.

# **9. User Interaction and Design**

## **Query Parameter Type Selector**

When adding or editing a query parameter in the endpoint configuration panel, the admin selects the value source from a type selector. The options and their sub-flows are:

‌

* Static - Connection variable: A dropdown lists all variables in the connection variable store (auto-captured and manually entered). The variable name, current value, and source are shown. An 'Add new connection variable' option is available inline if the needed variable doesn't exist yet.
* Static - User-defined value: A free-text input field, with a dropdown for parameters that have known enumerated options (e.g., accounting_method).
* Dynamic - Relative date: A dropdown presents the supported relative date library. A summary label shows the expression name and an example resolved value (e.g., 'start_of_current_month → 2026-03-01'). For N_days_ago, an integer input appears.
* Dynamic - Last run timestamp: A toggle enables the option. A required fallback date field appears immediately, supporting both manual date entry and relative date expression selection. The UI shows the currently stored last-run timestamp (or 'No prior run - fallback will be used') so the admin understands what will resolve on the next run.
* Dynamic - Cross-endpoint output: Handled in the Endpoint Nesting sub-PRD.

‌

## **Connection Variable Store**

Accessible from the connection detail view (separate from endpoint configuration), the connection variable store shows all variables for a connection:

* Variable name, value, source (auto-captured / manually entered), and date last updated.
* Admins can add new manually-entered variables and edit existing manually-entered ones. Auto-captured variables are read-only (with a note explaining they were set during connection setup).
* Variables in use by one or more endpoints are flagged, so an admin knows the impact before editing or deleting a value.

‌

## **Preview Values Panel**

Accessible via a 'Preview values' button in the endpoint add/edit panel:

* Displays each configured parameter, its variable type, and the resolved value as of the current moment.
* For relative dates: shows the concrete date (e.g., '2026-03-01').
* For last run timestamp: shows the stored timestamp or 'No prior run - fallback: \[fallback value\]'.
* For connection variables: shows the stored value.
* A timestamp on the preview indicates when it was generated, since relative dates resolve in real time.
* No API call is made; this is a local resolution preview only.

‌

## **Run Log Additions**

In the sync run log for each endpoint execution:

* A 'Parameters used' section lists each query parameter, its variable type label, and the resolved value sent to the API.
* For last-run-timestamp parameters, the log notes whether the actual prior timestamp or the fallback was used.

# **10. Open Questions**

‌

| **Question** | **Owner** | **Notes** |
| --- | --- | --- |
| What timezone should relative date expressions use when resolving? The customer's local timezone, the connection's configured timezone, or UTC? | Engineering / Product | For financial data, the customer's accounting timezone matters (a 'start of month' in PST differs from UTC). Defaulting to UTC may produce incorrect date ranges for US-based customers. Needs a decision before Phase 1b ships. |
| How should the system handle a connection variable (e.g., realmId) that changes after initial setup - e.g., if a customer re-authorizes OAuth with a different account? | Engineering | The variable store would need to be refreshed. If the stored value silently goes stale, all endpoints using it will break. Need a mechanism to detect and surface stale connection variables. |
| For cursor/token-based pagination (last_cursor): does the system handle multi-page response looping automatically within a single sync run, or is this a separate execution model from standard parameter resolution? | Engineering | Cursor-based pagination may be fundamentally different from a single-value parameter substitution. This may require its own design and should not be assumed to fit the same model as last_run_timestamp. Deferred to Phase 3b for scoping. |
| Should the connection variable store be editable by end-customer admins, or only by FloQast implementation team members? | Product | Some variables (e.g., realmId) are sensitive and auto-captured; others are user-entered. The edit permissions model needs definition - particularly for CAS customers who configure their own connections. |
| For the N_days_ago relative date expression: is N a fixed integer entered at config time, or can it be a FloQast system value (e.g., 'number of days in the current close window')? | Product | If N must be a hardcoded integer, this is simple. If it should reflect close window length, it requires FloQast context - closer to close calendar integration. Clarify scope before Phase 1b. |
| Should the close calendar date integration (deferred to future phase) be spec'd as an extension of the relative date library, or as a separate variable type? | Product | Designing the relative date library with extensibility in mind now will reduce rework when close calendar dates are added. Engineering input on architecture would help. |

# **11. Out of Scope**

* Cross-endpoint output variables - covered in the Endpoint Nesting sub-PRD.
* Close calendar date integration - deriving parameter dates from FloQast close period dates is deferred to a future phase.
* OAuth credential or token management - auth tokens are handled by the connection authentication layer and are not part of the query parameter variable model.
* Cross-connection variable sharing - variables are scoped per connection only.
* Field-level transformation of variable values (e.g., reformatting a date from ISO 8601 to MM/DD/YYYY for a specific API) - values are passed as resolved without transformation. Format requirements must be handled in the relative date expression library design.
* Pagination cursor/token handling within a single run (multi-page looping) - deferred to Phase 3b pending additional scoping with engineering.
* Customer-facing variable configuration UI for end-customers (non-FloQast admins) - variable management is an admin/implementor capability in this phase.
