## Objective

This sub-PRD defines the transformation functions required to convert raw QuickBooks Online (QBO) source data into FloQast's standard data models for Accounts, Balances, and GL Transactions. These functions form the transformation layer between ingested QBO data and the normalized FloQast data platform, ensuring that downstream surfaces -including close management, reconciliation, and reporting - receive data in a consistent, model-compliant format.

## Key Benefits

1. Consistent data output: QBO source data reliably maps to FloQast standard models regardless of ingestion path (direct API or Fivetran).
2. Correct balance computation: debit/credit classification and subtraction logic produce accurate balances across all account types.
3. Date-aware reporting: month and year extraction enables period-based close and reporting workflows.
4. Flexible data shaping: concatenation, parsing, constants, and arithmetic support a wide range of field mapping scenarios without custom engineering per customer.
5. Reusable function library: functions are composable and can be applied across Accounts, Balances, and GL Transactions models.

## Use Cases

* Balance computation: A QBO trial balance row contains separate debit and credit columns. The transformation layer classifies the account type using the If/Then function, then applies debit_amount - credit_amount to produce the normalized balance value stored in the FloQast Balance model.
* Account type normalization: Raw QBO account type values (e.g., 'Expense', 'OtherCurrentLiability') are mapped to FloQast's standard debit/credit designation using the If/Then classification function.
* Period tagging: A GL transaction's transaction date is parsed by the date extraction function to produce discrete month and year fields, enabling period-level aggregation in close management and reporting surfaces.
* Multi-field label construction: A customer requires a display name that combines account code and account name. The concatenation function joins two source fields into a single derived field on the FloQast Account model.
* Substring extraction: A QBO description field contains a structured string (e.g., 'DEPT:Finance | PROJECT:Q1'). The parse function extracts the department or project segment as a standalone field.
* Currency arithmetic: FX rate and local currency amount fields are multiplied to derive the functional currency amount on a GL Transaction record.
* Constant tagging: A hard-coded string value (e.g., source system identifier 'QBO') is stamped onto ingested records to support downstream filtering and data lineage.

## Assumptions

1. QBO account types map deterministically to FloQast's debit/credit classification. The mapping is: Assets and Expenses = Debit; Revenue, Liabilities, and Equity = Credit.
2. Source date fields are consistently formatted or parseable; the date extraction function does not need to handle arbitrary or malformed date strings.
3. Multiplication and division functions operate on numeric fields only; type validation is handled upstream in the ingestion layer.
4. Concatenation produces a string output; delimiter behavior (e.g., space, dash) is configurable at mapping time.
5. The parse/extract function targets structured or semi-structured string fields; regex or delimiter-based extraction patterns are defined per field mapping.
6. Hard-coded string constants are set at configuration time and do not change dynamically at runtime.
7. These transformation functions are applied after raw data is ingested and before it is written to the FloQast standard model layer.

## Scope

* **Target models (transformation output):**

    * FQ Accounts model: account type, account code, account name, debit/credit designation
    * FQ Balances model: computed balance (debit minus credit), period month, period year
    * FQ GL Transactions model: transaction amounts, functional currency amount (derived), transaction month, transaction year, source system identifier  
        
      **Explicitly out of scope for this sub-PRD:**
    
        * Raw ingestion logic, API calls, or Fivetran connector configuration
        * FX rate sourcing or currency conversion beyond field-level arithmetic
        * Write-back or bi-directional sync

## User interaction and design

‌

#### **9.1 Mapping Configuration**

* Each transformation function is registered as a named, reusable function type in the mapping configuration schema.
* Functions are assigned to specific source → target field pairs in the model mapping definition (e.g., account_type → normal_balance using the If/Then classifier).
* Parameters (e.g., delimiter for concatenation, regex pattern for parse, literal value for constant) are defined per mapping instance, not globally.

#### **9.2 Error and Warning Behavior**

* Pipeline-level errors (e.g., division by zero, invalid function input type) are logged with record identifier, function name, and input values.
* Warnings (e.g., unrecognized account type, parse pattern no-match) are surfaced in sync run logs accessible to admins in the integration settings UI (per parent PRD REQ-11).
* Neither warnings nor record-level errors halt the full sync run; only the affected record's field is nulled or flagged.

## Out of Scope

* Raw data ingestion — API calls, Fivetran connector setup, and sync scheduling are covered in the parent QBO Integration PRD.
* Connection management and authentication — OAuth, token refresh, and realmId management are out of scope for this sub-PRD.
* Write-back — transformation functions are read/compute only. No data is pushed back to QBO.
* Non-QBO sources — these transformation functions are scoped to QBO model mapping in v1, though the library may be generalized in a future data platform initiative.
* Complex aggregation logic — SUM, COUNT, GROUP BY, and similar set-level operations are not part of this function set.
* QBO Desktop — this sub-PRD applies to QBO Online only, consistent with the parent PRD scope.
