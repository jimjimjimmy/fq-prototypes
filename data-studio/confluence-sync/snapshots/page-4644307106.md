## 🎯 Objective

The Draft concept exists in Data Studio today, but the current publish workflow is destructive: any mapping change triggers a teardown of the model's processed data, requiring a full re-upload. There is no effective date and no way to make a configuration change without losing historical data.

This PRD replaces that behavior with a non-destructive publish workflow for canonical models. Admins set an effective date when publishing; the new version applies from that date forward, and historical data is preserved. The current "change a mapping and re-upload everything" pattern is eliminated.

> **Open dependency:** It is not yet confirmed whether publishing with an effective date suppresses teardown, or whether teardown still fires and rehydration (currently feature-flagged for SFTP only) is what achieves non-destructive behavior. This distinction affects whether the non-destructive promise is deliverable in Q3. See OQ-6.

Q3 scope covers the core lifecycle controls that enable this: draft creation, publish with effective date (forward-looking), autosave, and mapping rule changes in a Draft. Block second Draft, Discard Draft, historical reprocessing, and dimension version interactions are either existing behavior or future phases.

Primary users: Data Studio admins.

## 🔤 Definitions

For a complete glossary of terms, see the shared [Data Studio: Definitions & Terms](https://floqast.atlassian.net/wiki/spaces/Data/pages/4464869099) page.

**Draft** — An editable, unpublished version of a model. Not processing data. Only one Draft may exist per model at any time.

**Active** — The live, published version of a model. Currently processing data. Only one Active version may exist per model at any time.

**Archived** — A previous Active version that has been superseded by a newer publish. Read-only, preserved for audit. Cannot be re-activated directly — a new Draft must be created from it.

**Effective Date** — The date from which a published version's configuration applies. In Q3, effective date is forward-looking only — historical reprocessing is a future phase.

**TTL (Time To Live)** — An engineering pattern where a record automatically expires and is deleted after a set duration, without requiring explicit cleanup code. Referenced in G3: the teardown blocklist entry currently has no TTL, meaning a stuck teardown block persists indefinitely unless manually removed by engineering.

## 🏅 Why This Is Important

Today, any mapping change on a model triggers a teardown — the model's processed data is wiped and the customer must re-provide it. Every configuration change, no matter how small, carries this cost. This is a significant barrier to iteration: admins are disincentivized from making legitimate corrections because the recovery cost is too high.

For a platform that sits upstream of the financial close, this is a serious risk. A mapping that needs a small fix can't be corrected safely mid-period. The teardown-on-every-change behavior as it exists today is not compatible with a production-grade data platform.

The Q3 versioning work eliminates this by introducing effective date-based, non-destructive publishing for canonical models. Configuration changes go live from the effective date forward; historical data is untouched. Admins can iterate confidently without fear of data loss.

> **Note on teardown mechanics:** Teardown is scoped to the individual model (catalog). A teardown on one model has no effect on other models — including those of the same type. For SFTP, a rehydration path is feature-flagged that would allow data to be restored without customer re-upload. All other ingestion methods currently require full re-upload. The non-destructive publishing goal in this PRD depends on resolving whether effective-date publishing suppresses teardown or relies on rehydration — see OQ-6.

---

## 🔐 Value Unlocked

Admins can confidently iterate on model configurations without fear of breaking live data processing. Changes happen in a Draft, reviewed before publish, and the previous configuration is always preserved. The publish workflow enforces intentionality — nothing goes live by accident.

---

## 🗝️ Key Examples

* **Example 1:** An admin needs to correct a field mapping mid-period. Today this would require publishing and re-uploading all data. With Q3 versioning, they update the Draft and publish with today's effective date — only runs from today forward use the new mapping, and nothing historical is touched.

* **Example 2:** An admin starts editing a Draft and navigates away. When they return, their changes are exactly where they left them — autosave means nothing is lost.

## 💡 Key Benefits

* Changes to live model configurations are always intentional — nothing goes live without a publish action

* Autosave means admins never lose work in progress

* One Draft at a time prevents conflicting parallel changes

* The Active version is never disrupted while a Draft is in progress

* Every publish creates an auditable record of what changed and when it took effect

## 🤔 Assumptions

**Established**

* Only one Draft per model at any time

* Only one Active version per model at any time

* Opening a model opens the most recent version (highest version number)

* Changes to a Draft are autosaved — there is no manual Save button

* Archived versions are read-only and cannot be directly re-activated; a new Draft must be created from them

* Discarding a Draft is permanent — it cannot be recovered *(existing behavior)*

* Only one Draft is permitted per model — attempting to create a second Draft is blocked with a link to the existing Draft *(existing behavior)*

* The version number increments on Draft creation, not on each individual save

* Pipeline run logs are not in scope for this PRD — see Logging & Audit PRD

* Mapping rule changes and data type changes are permitted in a Draft

* In-flight runs complete under the version they started with — publishing a new version does not interrupt runs already in progress

**Open Items to Confirm**

* When both a Draft and an Active version exist, which opens by default? (OQ-1)

* Is publishing gated on valid field mappings — i.e., can an admin publish a model with incomplete or invalid mappings? (OQ-2)

* Is autosave server-side or client-side persistence? (OQ-4)

## 🗺️ Scope

### 🚗 In Scope

* **Draft creation** from an Active version (manual)

* **Publish Draft** — set effective date (forward-looking only), Draft becomes Active, previous Active becomes Archived

* **Autosave** — all Draft changes saved automatically; no Save button; "Saved" / "Saving…" indicator

* **Mapping rule changes** in a Draft, including data type changes

### 🚦 Out of Scope (Q3)

* Historical reprocessing — effective date is forward-looking only in Q3; past effective dates and bounded reprocessing are future phases

* Dimension version interactions — future phase

* Auto-draft creation on structural changes (source dataset added/removed, field mapping edited) — future

* Draft creation from an Archived version — future

* Delete Draft-only model — future

* Version history view (table of all versions with metadata) — future

* Manual archive — future

* View Archived field mappings (read-only audit access) — future

* Data preview from Active version — future

* Pipeline run logs — see Logging & Audit PRD

### V1 — Create Draft from Active Version

**User Story:** As an admin, I can create a new Draft from the current Active version of a model so that I have a safe workspace to make configuration changes without affecting live data processing.

**Importance:** High

**Acceptance Criteria:**

**AC-V1-01 — Draft created as a copy of Active**

```
Given a model has an Active version and no existing Draft
When I initiate creating a new Draft
Then a Draft is created with all configuration copied from the Active version
And it is assigned the next version number
And the Active version continues processing data unchanged
```

**AC-V1-02 — Draft is editable; Active is not**

```
Given a Draft and an Active version both exist
When I view the model
Then the Draft is editable
And the Active version is read-only
```

---

### V8 — Publish Draft

**User Story:** As an admin, I can publish a Draft with an effective date so that my configuration changes go live in a controlled, auditable way.

**Importance:** High

**Acceptance Criteria:**

**AC-V8-01 — Publish requires an effective date**

```
Given I initiate publishing a Draft
When the publish dialog appears
Then I am required to set an effective date before confirming
And today's date is pre-populated as the default
```

**AC-V8-02 — Effective date is forward-looking only**

```
Given I initiate publishing a Draft
When I set an effective date
Then only today's date or a future date is permitted
And past dates are not selectable
```

**AC-V8-03 — In-flight runs complete under the previous version**

```
Given a run is in progress when a Draft is published
When publish completes
Then the in-flight run continues to completion under the previous Active version
And the new Active version takes effect for all subsequent runs
And the previous Active version transitions to Archived once the in-flight run completes
```

**AC-V8-04 — Draft becomes Active on publish**

```
Given I confirm the publish action
When publish completes
Then the Draft becomes the new Active version
And the previous Active version transitions to Archived (after any in-flight runs complete)
And the new Active version begins processing data from the effective date forward
```

> **Teardown dependency (partially resolved — action required):** It is not yet confirmed whether publishing suppresses teardown or triggers it. Rehydration — the mechanism that would allow data to be restored without re-upload — is currently feature-flagged for SFTP only and is not available for API or CDC ingestion methods. If teardown fires on publish and the customer is not on SFTP, the "historical data is preserved" promise in this AC cannot be met in Q3. This is a go/no-go dependency that must be resolved with Engineering before these ACs are finalized. See OQ-6.

**AC-V8-05 — Publish is recorded in the Change Log**

```
Given a Draft is published
When publish completes
Then a Change Log entry is created capturing: who published, when, the effective date, and the version number
```

---

### V9 — Autosave to Draft

**User Story:** As an admin, my changes to a Draft are saved automatically so that I never lose work in progress when navigating away or closing the browser.

**Importance:** High

**Acceptance Criteria:**

**AC-V9-01 — Changes saved without manual action**

```
Given I am editing a Draft
When I make a change to any configuration field
Then the change is saved automatically without requiring me to click a Save button
```

**AC-V9-02 — Save state is visible**

```
Given a Draft is being edited
When a save is in progress
Then a "Saving…" indicator is visible
And it transitions to "Saved" once the save is complete
```

**AC-V9-03 — Changes persist across sessions**

```
Given I have made changes to a Draft and navigated away
When I return to the model
Then all previously made changes are present exactly as I left them
```

## 😎 Future Considerations

* **Historical reprocessing:** Allow admins to set a past effective date on publish, triggering bounded reprocessing of historical runs within the new version's effective range. Requires explicit scope boundary enforcement — reprocessing must never extend to all-time data.

* **Dimension version interactions:** Additive-only key insertion on dimension publish; auto-insert of unknown keys surfaced by linked models; key removal warning before publish confirmation; no automatic re-run of linked models.

* **Auto-draft on structural changes:** When a source dataset is added or removed, a custom field is added or removed, or a field mapping is edited on an Active version, the system automatically creates a Draft.

* **Draft from Archived version:** Allow admins to create a new Draft starting from any Archived version, not just the current Active.

* **Delete Draft-only model:** Allow admins to permanently delete a model that has never been published (Draft-only state).

* **Version history view:** A table of all versions for a model showing version number, state, effective date, published by, and published date.

* **Manual archive:** Allow admins to manually archive the Active version without publishing a new one.

* **View Archived field mappings:** Read-only access to Archived version configurations for audit purposes.

* **Data preview from Active version:** A read-only preview of the data the Active version is producing.

## 🚫 Gaps

| \# | Gap | Impact | Proposed Resolution |
| --- | --- | --- | --- |
| G1 | No RBAC / permissions model defined | High | Confirm access model with Engineering — who can create, publish, and discard Drafts? |
| G2 | No error states defined for publish failure (e.g., publish blocked due to invalid mappings) | Medium | Cross-reference Error Patterns PRD; add EP story if needed |
| G3 | Stuck teardown can block publish indefinitely with no customer-facing signal | High | If publish triggers teardown and the teardown job stalls, the model's catalog is blocked and all subsequent uploads fail silently. These can only be cleared by manual engineering row deletion. A TTL on blocklist entries and dead-teardown detection are required before Q3 publish flow can be considered reliable.
