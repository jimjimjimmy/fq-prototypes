## 1. Objective

This sub-PRD defines FloQast Data Studio's retry behavior for API data ingestion failures. It covers which error types trigger a retry, what retry strategies are available, how FloQast applies default parameters, and how retry outcomes are surfaced to admins.

Retry logic is a foundational capability required by Phase 1 (Pull API Support) and applies across all active pull endpoints. It is referenced in the Pull API Support sub-PRD (REQ-16) and the Endpoint Nesting sub-PRD (REQ-08) as the "parent PRD retry policy." This document defines that policy.

## 2. Key Benefits

* Transient failures recover automatically without admin intervention, reducing noise and missed sync windows.
* Rate limit responses are respected properly, preventing FloQast from being blocked by API providers.
* Non-retryable errors surface immediately as actionable alerts, so admins are not waiting for retries that cannot succeed.
* Fixed system defaults keep configuration simple — admins select a strategy, not individual parameters.
* Nested endpoint chains short-circuit cleanly when a parent fails with a non-retryable error, preventing misleading downstream failures.

## 3. Use Cases

1. A QBO Trial Balance endpoint receives a 429 response with a `Retry-After: 45` header. FloQast waits 45 seconds and retries. The second attempt succeeds and the sync completes within the window.
2. A Workday endpoint times out on the first attempt. FloQast retries using exponential backoff with jitter, waiting approximately 5 seconds, then 10, then 20. The third attempt succeeds.
3. An endpoint configured with the fixed interval strategy fails with a 503. FloQast waits 30 seconds and retries. After 3 total attempts, all failing, the endpoint is marked in Error state and the admin receives an alert.
4. An OAuth token expires mid-sync. The endpoint returns a 401. FloQast does not retry. It immediately logs the failure, marks the endpoint in Error state, surfaces a re-auth prompt on the connection detail view, and sends an email notification to the connection owner.
5. A balances endpoint depends on an accounts endpoint (nested). The accounts endpoint fails with a 404. FloQast does not retry the accounts endpoint and immediately marks the balances endpoint as Blocked, surfacing a linked error in the sync log.
6. An admin sets a custom endpoint to No Retry. The endpoint fails on its first attempt. FloQast logs the error immediately and alerts the admin without attempting again.

## 4. Success Metrics

| Metric | Target |
| --- | --- |
| Auto-recovery rate | Greater than 80% of retryable errors recover within the retry window without admin intervention |
| False retry rate | 0% of non-retryable errors (401, 403, 404, 400) trigger a retry attempt |
| Rate limit header compliance | 100% of 429 responses with a Retry-After header use that value instead of the backoff timer |
| Retry outcome logging | 100% of retry attempts logged with attempt number, wait duration, and outcome |
| Nested endpoint short-circuit | 100% of child endpoints blocked immediately when a parent fails with a non-retryable error |

## 5. Assumptions

* Retry logic applies to pull endpoints only in Phase 1. Push endpoints defer retry responsibility to the source system, consistent with Push API Support (Phase 6).
* FloQast defines all retry parameters (wait times, attempt limits). Admins select a strategy per endpoint but do not configure the underlying timing values.
* "Max attempts" counts the initial attempt plus all retries. An endpoint with exponential backoff and a max of 4 attempts makes 1 initial call and up to 3 retries.
* If a 429 response includes a `Retry-After` header, that value overrides the strategy's wait timer for that attempt, regardless of which strategy is selected.
* A sync that exhausts all retry attempts without success is marked as a failed sync. Previously stored good data is not overwritten.
* Retry logic applies per endpoint, not per connection. A failed endpoint does not prevent other endpoints on the same connection from running.
* On-demand syncs follow the same retry policy as scheduled syncs, subject to the open question on SLA interaction (see Section 11).

## 6. Strategy Definitions

Three retry strategies are available, selected per endpoint. All timing parameters are set by FloQast and are not configurable by admins.

### Exponential Backoff with Jitter (Default)

FloQast waits progressively longer between each retry, with a small random offset applied to prevent multiple connections from retrying simultaneously. This is the recommended strategy for most endpoints.

| Parameter | Value |
| --- | --- |
| Max attempts | 4 (1 initial + 3 retries) |
| Base wait | 5 seconds |
| Multiplier | 2x per attempt |
| Jitter | ±20% randomization |
| Wait cap | 60 seconds |

Approximate wait sequence before jitter: 5s → 10s → 20s → 40s.

Use this strategy for most endpoints. It handles transient failures gracefully, spreads retry load over time, and behaves in the way API providers expect from well-behaved clients.

### Fixed Interval

FloQast waits the same amount of time between each retry attempt.

| Parameter | Value |
| --- | --- |
| Max attempts | 3 (1 initial + 2 retries) |
| Wait between attempts | 30 seconds |

Use this strategy when an endpoint's API provider has predictable recovery behavior and a known rate limit reset window. It is simpler to reason about than exponential backoff but does not adapt to variable API load.

### No Retry

FloQast makes a single attempt. If it fails, the endpoint is immediately marked in Error state and the admin is alerted.

Use this strategy for endpoints where retrying would be harmful (non-idempotent requests) or for low-priority endpoints where a single-window miss is acceptable.

## 7. Error Type Handling

Retry behavior depends on the error returned. Not all errors are worth retrying.

| Error | HTTP Status | Behavior | Reason |
| --- | --- | --- | --- |
| Rate limit | 429 | Retry using selected strategy. If Retry-After header is present, use that wait time instead. | Transient — throttling is intentional and time-bounded |
| Server error | 500, 502, 503, 504 | Retry using selected strategy | Transient — server-side issues typically resolve quickly |
| Timeout | No response received | Retry using selected strategy | Transient — network or server load issue |
| Auth failure | 401, 403 | No retry. Log failure, surface re-auth prompt, send email to connection owner. | Not recoverable without a credential change |
| Not found | 404 | No retry. Log failure, surface configuration error alert. | Configuration error — endpoint path is wrong |
| Bad request | 400 | No retry. Log failure, surface configuration error alert. | Configuration error — parameters or headers are malformed |
| Other 4xx | 4xx | No retry. Log failure and surface alert. | Client-side errors are not transient |

### Rate Limit Header Override

If a 429 response includes a `Retry-After` header, FloQast uses that value as the wait time for the next attempt regardless of the selected strategy. The `retry_trigger` field in the sync log records "Retry-After header" to distinguish it from strategy-driven waits. After honoring the header value, FloQast resumes the configured strategy's progression for any remaining attempts.

## 8. Nested Endpoint Behavior

When a parent endpoint in a nested call chain fails:

* If the failure is retryable, FloQast retries the parent according to its configured strategy before attempting any child endpoint.
* If the parent exhausts all retry attempts or fails with a non-retryable error, FloQast immediately marks all dependent child endpoints as Blocked for that sync run. No child endpoint request is made.
* The sync log records each blocked child with status "Blocked — parent endpoint \[name\] failed" and links to the parent's error detail.

This behavior is consistent with Endpoint Nesting sub-PRD REQ-08.

## 9. Scope of Data

The following fields are added to or updated in existing data models.

**Endpoint configuration (addition):**

* `retry_strategy`: enum — `exponential_backoff_jitter` | `fixed_interval` | `none`

**Sync log entries (additions):**

* `retry_attempt_number`: integer — which attempt this entry represents (1 = initial, 2 = first retry, etc.)
* `retry_wait_seconds`: integer — how long FloQast waited before this attempt
* `retry_trigger`: string — whether the wait came from the strategy timer or a Retry-After header
* `final_attempt`: boolean — whether this was the last attempt before the endpoint was marked failed

**Explicitly out of scope:**

* Push endpoint retry state — source system responsibility
* Retry timing parameters — system-defined constants, not stored per endpoint

## 10. Requirements

**REQ-01 As an admin or implementor, I want to select a retry strategy for each endpoint so that I can control how FloQast handles failures for that specific data source.**

_Functional spec:_ The endpoint add and edit flows must include a required retry strategy selector with three options: Exponential Backoff with Jitter (default), Fixed Interval, and No Retry. Each option must display a brief description. The selected strategy is stored per endpoint and applied to all sync runs for that endpoint. Step guidance: "Choose how FloQast should respond if this endpoint fails. Exponential Backoff with Jitter is recommended for most endpoints." Default retry behavior is exponential backoff with 4 retry attempts.

**REQ-02 As FloQast (system), I must retry failed endpoint requests according to the endpoint's configured strategy, up to the defined attempt limit, before marking the endpoint as failed.**

_Functional spec:_ On a retryable error (429, 5xx, timeout), FloQast must wait the appropriate interval per the selected strategy and retry the request. Retries continue until the request succeeds or the max attempt limit is reached. Each attempt produces a sync log entry recording the attempt number, wait duration, and outcome. On exhaustion of all attempts, the endpoint is marked in Error state.

**REQ-03 As FloQast (system), when a 429 response includes a Retry-After header, I must use that value as the wait time for the next retry regardless of the selected strategy.**

_Functional spec:_ FloQast must parse the Retry-After value and wait exactly that duration before the next attempt. The retry_trigger field in the sync log entry records "Retry-After header" to distinguish it from strategy-driven waits. After the header-driven wait, FloQast resumes the configured strategy's progression for remaining attempts.

**REQ-04 As FloQast (system), I must not retry requests that fail with non-retryable errors, and must surface an alert immediately.**

_Functional spec:_ On a 401, 403, 404, or 400 response, FloQast makes no additional attempts. The endpoint is immediately marked in Error state. For auth failures (401, 403), a re-auth prompt is surfaced on the connection detail view and an email notification is sent to the connection owner, consistent with Auth Type Support REQ-17 through REQ-19. For configuration errors (404, 400), a configuration error alert is surfaced on the endpoint with a description of the failure.

**REQ-05 As FloQast (system), when a parent endpoint in a nested chain fails, I must block dependent child endpoints for that sync run and surface a linked error.**

_Functional spec:_ If a parent endpoint fails after exhausting retries or fails with a non-retryable error, all dependent child endpoints must not execute for that run. Each blocked child must appear in the sync log with status "Blocked — parent endpoint \[name\] failed" and a direct link to the parent's error detail. No child endpoint should produce a misleading or silent failure when the root cause is a parent failure. Consistent with Endpoint Nesting sub-PRD REQ-08.

**REQ-06 As an admin, I want to see retry attempts and outcomes in the sync log so that I can understand how FloQast responded to a failure.**

_Functional spec:_ The sync log for each endpoint must display all attempts for a given sync run, including the initial attempt and each retry. Each log entry shows: attempt number, wait duration before the attempt, outcome (success or failure), error type, and whether a Retry-After header was used. On a final failed attempt, the log entry is clearly marked as the last attempt.

## 11. User Interaction and Design

### Retry Strategy Selector (Add/Edit Endpoint Flow)

The retry strategy selector appears as a required field in the endpoint configuration panel, after the rate limit configuration section (consistent with Pull API Support milestone M4). It presents three options with brief inline descriptions:

* **Exponential Backoff with Jitter** — Waits progressively longer between retries with slight randomization. Recommended for most endpoints.
* **Fixed Interval** — Waits the same amount of time between each retry. Use when the API has a predictable recovery window.
* **No Retry** — Makes a single attempt. If it fails, you'll be alerted immediately.

The selected strategy is displayed in the read-only endpoint detail view alongside the rate limit configuration.

### Sync Log — Retry Entries

When retries occur, the sync log entry for that run expands to show individual attempt rows beneath the parent run entry. Each attempt row shows:

* Attempt number (e.g., "Attempt 2 of 4")
* Wait before this attempt (e.g., "Waited 10s — strategy" or "Waited 45s — Retry-After header")
* Outcome (Success or Failed)
* Error type if failed

On final failure, a summary row shows "Max attempts reached — endpoint marked as Error."

### Blocked Endpoint Display (Nested Chains)

In the sync log for connections with nested endpoints, blocked child endpoints appear beneath their failed parent. Each blocked entry shows:

* Status: Blocked
* Reason: "Parent endpoint \[name\] failed after \[N\] attempts"
* A link to the parent endpoint's error detail

## 12. Open Questions

| Question | Owner | Notes |
| --- | --- | --- |
| Should the default retry strategy for new endpoints be set at the connection level, or always default to Exponential Backoff with Jitter? | PM / Engineering | Current assumption: always default to Exponential Backoff with Jitter. A connection-level default would support bulk configuration but adds UX complexity. |
| If a Retry-After value is very large (e.g., 24 hours), should FloQast honor it fully or cap it at some maximum and mark the endpoint failed? | Engineering | Recommend capping at the sync window duration. If the next scheduled sync is in 1 hour, waiting 24 hours for a retry is not useful. Define the cap before implementation. |
| For on-demand syncs with a sub-30-second SLA, should retry behavior differ from scheduled syncs? | PM / Engineering | Current assumption: same policy applies. But retries could blow past the SLA. May need a reduced attempt limit or shorter wait intervals specifically for on-demand runs. |
| Should real-time retry state (e.g., "currently on attempt 3 of 4, waiting 20s") be visible in the Data Studio UI during an active sync, or only in the post-run sync log? | Engineering / Design | Real-time display requires polling or WebSocket support. Define the approach before Pull API Support M7. |

## 13. Out of Scope

* Push endpoint retry logic — source systems are responsible for retry on push connections, consistent with Push API Support.
* Admin-configurable retry parameters (wait times, attempt limits) — system defaults only in this phase.
* Retry behavior for on-demand trigger mechanics — covered in the On Demand Data sub-PRD.
* Retry logic for OAuth token refresh — token refresh is managed by the system and defined in Auth Type Support.
* Pipeline-level retries — if a transformation step fails after data is successfully retrieved from the API, that is a pipeline error, not a retry-eligible API request failure.
