# **1. Objective**

This sub-PRD defines the requirements for Pull API connection setup and automated data ingestion in FloQast Data Studio. It covers the end-to-end workflow for FloQast admins and implementation team members to configure a pull-based API connection - including connection basics, authentication (dependency on the Authentication PRD), endpoint configuration, query parameters, pagination, delta logic, response handling, rate limiting, and sync scheduling.

It also defines the backend behavior required to execute those configurations: scheduled data retrieval, sync logging, data pipeline handoff for lineage, sync log export, and endpoint lifecycle management (add, edit, deactivate, delete, and copy connections). This work corresponds to Phase 1 of the parent PRD, API Endpoint Management in FloQast Data Studio.

‌

# **2. Key Benefits**

* Self-service pull API setup for admins and implementors - no engineering involvement required.
* Guided setup wizard with per-step contextual explanations supports less technical users through a complex configuration process.
* Draft-save capability lets admins configure connections incrementally and resume without losing progress.
* Step-by-step validation prevents broken configurations from being saved or activated.
* Built-in connection test (Swagger-style) gives admins confidence before going live, with targeted failure routing back to the relevant step.
* Multi-endpoint setup in a single flow - admins can configure accounts, transactions, and balances endpoints without leaving the wizard.
* Configurable sync frequency (default: daily) and delta logic give teams control over data freshness without overloading API rate limits.
* Sandbox-to-production copy reduces duplication effort when transitioning configurations between environments.
* Sync logging with background export and email notification gives admins full visibility into pipeline health and makes troubleshooting self-service.
* Endpoint lifecycle management (edit, deactivate, delete) without engineering support enables clean configuration management over time.

# **3. Use Cases**

1. An implementor sets up a new pull API connection for a customer ERP, walking through the multi-step wizard: entering connection name and HTTPS base URL, selecting sandbox environment, completing authentication, configuring multiple endpoints with static and dynamic query parameters, and testing the connection before activating.
2. An admin starts configuring a pull API connection and realizes they need information from the API vendor. They save the setup as a draft and resume the next day, picking up exactly where they left off with all completed fields preserved.
3. An admin copies an existing sandbox connection to create a production version. The copy is automatically named 'COPY - \[original name\]'. All endpoint configurations, query parameters, pagination settings, and sync schedule carry over; the admin only re-enters environment and authentication credentials before activating.
4. An implementor tests a newly configured endpoint and the connection test fails at the authentication step. The system routes them back to the authentication configuration with a clear error, they correct the API key, and the test passes on the second attempt.
5. An admin adds a new transactions endpoint to an existing active QBO connection, confirming the connection basics are the same and starting directly at endpoint configuration. The new endpoint is added and activated without disrupting the existing accounts endpoint.
6. An admin edits authentication credentials for a connection that has multiple endpoints. The system prompts them to confirm whether the change should apply to the entire connection or only the specific endpoint being edited.
7. An admin deactivates a balances endpoint temporarily while a customer migrates ERP systems. The system logs the deactivation with timestamp and user, and warns the admin if the endpoint is used as a nested dependency. The admin later permanently deletes the endpoint, again seeing the nested dependency warning before confirming.
8. An admin reviews the sync log for a connection, identifies a rate limit error in last night's pull, and adjusts the sync frequency. They request an export of the last 90 days of sync history. Because the file is large, the export runs in the background and the admin receives an email when it is ready.

# **4. Success Metrics**

| **Metric** | **Target / Description** |
| --- | --- |
| Setup completion rate | Greater than 80% of started pull API setup workflows result in an active connection (tracks drop-off through the wizard). |
| Time to complete setup | Median end-to-end setup time (from Add Connector to active connection) under 30 minutes. Target TBD based on baseline measurement. |
| Connection test pass rate | Greater than 90% of connections that reach the test step pass on the first or second attempt. |
| Support ticket rate | Less than 10% of pull API setups require a support ticket or engineering intervention to complete. |
| Sync error rate (post-setup) | Less than 5% of scheduled data pulls result in unrecovered errors after the configured retry logic is exhausted. |
| Sync log coverage | 100% of sync attempts - success or failure - produce a log entry with timestamp, status, and error detail where applicable. |

# **5. Assumptions**

* Authentication configuration is defined in and owned by the Authentication PRD. The pull API setup wizard integrates the authentication step as a discrete, required stage but does not define auth-specific field logic here.
* Base URLs must use HTTPS. HTTP URLs or malformed URLs will be rejected at validation.
* Sync frequency defaults to daily and start date defaults to today. Both are editable by the admin before and after activation.
* Delta logic is required for all pull endpoints in Phase 1. Full refresh is explicitly not supported in this phase.
* Nested endpoint support - where a query parameter value is resolved from an upstream endpoint response - is out of scope for Phase 1, but the data model should accommodate it for Phase 2. Warnings about nested endpoint dependencies are surfaced in deactivate and delete flows even in Phase 1.
* Draft connections persist until the admin activates or manually discards them. Draft state is preserved at step granularity.
* Copy connection assumes environment and authentication credentials are the primary fields that differ between sandbox and production. All other configuration fields carry over and are editable before activation. The copy is auto-named 'COPY - \[original connection name\]'.
* Endpoint deactivation is a soft archive state: data stops being pulled, configuration is preserved, and the endpoint can be reactivated. Deletion is permanent.
* Rate limit configuration values are provided by the admin based on the API provider's documentation. FloQast also reads rate limit headers from API responses if the admin indicates they are present.
* A sample response payload is optional but strongly recommended. Without it, field mapping must be configured from raw data after the first live sync.

# **7. Scope of Data**

The following data objects and fields are in scope for this sub-PRD:

## **Connection Configurations**

* Connection name (free-text string)
* Base URL (HTTPS-validated string)
* Environment (sandbox or production)
* API version (optional string)
* Connection type (pull - fixed for this PRD)
* Draft status and current step position

‌

## **Endpoint Configurations**

* Endpoint path (required string)
* HTTP method (GET and POST as primary supported methods; PUT, PATCH, DELETE, and HEAD may be supported if it simplifies shared engineering with push connection handling)
* Request format (the format the API expects to receive requests in, e.g., JSON, XML)
* Response format (the format the API returns data in, e.g., JSON, XML)
* Header definitions: standard key-value pairs (optional) and custom required headers (e.g., tenant ID, org ID, realm ID)
* Query parameters: type (static or dynamic), key, value or value source
* Pagination method and associated configuration fields
* Delta logic type (field-based or timestamp-applied) and associated fields
* Sample response payload (optional, used for field mapping pre-population)
* Data sync behavior: append new records or replace (overwrite) existing dataset - stored per endpoint
* Rate limit values: requests per minute, retry count, retry interval
* Rate limit response header flag: whether the API returns rate limit details in response headers
* Sync frequency and sync start date
* Activation status (Active, Inactive, Draft)

‌

## **Connection Copies**

* Full copy of all connection and endpoint configuration fields from the source connection
* Default name set to 'COPY - \[original connection name\]', editable before activation
* Environment and authentication credentials reset on copy - require re-entry

‌

## **Sync Logs**

* Attempt timestamp
* Endpoint identifier
* Trigger type (scheduled)
* Status (success or failure)
* Record count (on success)
* Error type and detail (on failure - e.g., authentication failure, rate limit exceeded, timeout)
* Next scheduled sync timestamp
* Deactivation events: timestamp, user who deactivated, endpoint identifier

‌

## **Sync Log Exports**

* Configurable date range (default: last 30 days)
* All log fields included in export
* Large exports processed in background with email notification when ready

‌

## **Explicitly Out of Scope for Data**

* Field-level lineage and mapping configuration (separate PRD)
* Authentication credential storage and encryption details (Authentication PRD)
* Fivetran-managed connection data objects
* On-demand trigger event payloads (Phase 4 of parent PRD)

# **8. Requirements**

## **Connection Setup - Basics**

**REQ-01  As an admin or implementor, I want to first select the API type and then the data direction so that the system sets up the correct configuration flow from the start.**

_**Functional spec:**_ During the add connector flow, the user must first select the API type (e.g., standard pre-built connector vs. custom/framework API). If the user selects a custom API, they then choose the data direction: Pull or Push. Selecting Pull initiates the pull API setup wizard defined in this PRD. Both selections are required before any configuration fields are shown.

**REQ-02  As an admin or implementor, I want to provide a name for my API connection so that it is clearly identifiable in the connections list.**

_**Functional spec:**_ The connection name is a required free-text string, displayed on the connections list and detail view. If left blank, the user must not be allowed to proceed and an inline validation error must appear. Step guidance shown to user: 'Give this connection a unique name so you can easily identify it in your connections list.'

**REQ-03  As an admin or implementor, I want to provide the base URL for the API so that FloQast knows where to send requests.**

_**Functional spec:**_ The base URL is required and must begin with HTTPS. HTTP or malformed URLs must trigger an inline validation error and block progression. The base URL is combined with the API version (if provided) and endpoint path at runtime to construct the full request URL. Step guidance: 'This is the root address of the API you are connecting to. All endpoint requests will be sent to this address.'

**REQ-04  As an admin or implementor, I want to specify whether this is a sandbox or production environment so that data and configurations are clearly scoped.**

_**Functional spec:**_ The user must select from Sandbox or Production. Required field. The environment designation displays on the connection detail view. Step guidance: 'Sandbox connections are for testing only. Switch to Production when you are ready to ingest real data.'

**REQ-05  As an admin or implementor, I want to optionally specify the API version so that FloQast constructs versioned requests where required.**

_**Functional spec:**_ The API version field is optional. If provided, it is stored with the connection configuration and incorporated into request URL construction. No specific format validation is enforced. Step guidance: 'If the API provider requires a specific version in the URL (e.g., /v2/), enter it here. Leave blank if not applicable.'

**REQ-06  As an admin or implementor, I want to save my connection setup as a draft at any step so that I can resume configuration later without losing progress.**

_**Functional spec:**_ A Save as Draft action must be available at every step of the wizard. Saving a draft persists all completed field values and the current step position. When reopening a draft, the user can navigate forward and backward through all previously completed steps. Draft connections appear in the connections list with a Draft status indicator. If a user has already filled out a step and moved forward, then can jump back to that specific step in the navigation.

**REQ-07  As an admin or implementor, I want to copy an existing connection so that I can create a production version from a sandbox configuration without re-entering all details.**

_**Functional spec:**_ A Copy Connection action must be accessible from the connection detail view. The copy must pre-populate all configuration fields from the source connection including all endpoints, query parameters, pagination, delta logic, and sync settings. The copied connection must be automatically named 'COPY - \[original connection name\]', which the admin may edit before activation. Environment and authentication credentials must be reset and require re-entry. The copied connection is created as a Draft.

**REQ-08  As an admin or implementor, I want to edit the overall connection configuration and individual endpoint configurations after setup so that I can correct errors or update settings without rebuilding from scratch.**

_**Functional spec:**_ An Edit action must be accessible at both the connection level (connection basics, authentication, sync schedule) and the individual endpoint level (path, method, headers, query parameters, pagination, delta logic, response config, rate limits). When an admin edits authentication information that is shared across the connection, the system must prompt: 'Apply this authentication change to this endpoint only, or to the entire connection?' and apply changes according to the selection. All editable fields must display current values pre-populated. Changes must be validated before saving.

‌

## **Authentication**

**REQ-09  As an admin or implementor, I want to configure the authentication method for my API connection so that FloQast can securely access the API.**

_**Functional spec:**_ The setup wizard must include an authentication step where the user selects the authentication type and provides required credentials. Specific auth types and field logic are defined in the Authentication PRD (dependency). Authentication must be fully completed before the user can advance to endpoint setup. If the connection test fails at the authentication stage, the user must be routed back to this step with a clear, descriptive error message. Step guidance: 'Tell FloQast how to authenticate with this API so it can securely request data on your behalf.'

‌

## **Endpoint Configuration**

**REQ-10  As an admin or implementor, I want to specify the endpoint path and HTTP method so that FloQast constructs the correct API request.**

_**Functional spec:**_ The endpoint path is required; if left blank, the user must not be able to proceed and an inline validation error must appear. The user must select the HTTP method. GET and POST are the primary supported methods for pull connections. PUT, PATCH, DELETE, and HEAD may be supported if doing so simplifies shared engineering with push connections - this is at engineering discretion and not required for Phase 1. The full request URL is constructed from: base URL + API version (if set) + endpoint path. Step guidance: 'Specify the exact path and method for the data you want to retrieve. This is combined with the base URL to form the full API request.'

**REQ-11  As an admin or implementor, I want to configure the request format, response format, and required headers for an endpoint so that FloQast sends and receives data correctly.**

_**Functional spec:**_ The endpoint configuration must include: (1) Request format - the content type the API expects (e.g., JSON, XML), stored and used to set the Content-Type header. (2) Response format - the content type the API returns (e.g., JSON, XML), stored and used to set the Accept header. (3) Standard headers - optional key-value pairs for any additional headers required. (4) Custom required headers - dedicated entry for tenant-specific or context-specific headers such as tenant ID, org ID, or realm ID, with a label field and a value field. The user must be able to add, edit, and remove all header entries. Step guidance: 'Tell FloQast what format this API speaks and any special identifiers it needs - like a tenant ID or org ID - to route requests to the right account.'

**REQ-12  As an admin or implementor, I want to configure query parameters for an endpoint so that API requests are correctly scoped.**

_**Functional spec:**_ The user must be able to define query parameters of two types: (1) Static - a fixed key-value pair that does not change between requests (e.g., entity=accounts). (2) Dynamic - a parameter whose value varies per request based on a configurable source, such as a date range or reporting period. The user must be able to add, edit, and remove parameter entries. Required parameters must be validated before the endpoint can be saved. Nested endpoint parameter resolution (where a parameter value is retrieved from an upstream endpoint response) is out of scope for Phase 1. Step guidance: 'Query parameters refine what data gets returned. Static ones never change; dynamic ones update each time FloQast runs the request.'

**REQ-13  As an admin or implementor, I want to configure how this API paginates so that FloQast reads through all available data correctly.**

_**Functional spec:**_ The user must specify the pagination method used by the API (specific options TBD - see Open Questions). Based on the selected method, the system prompts for the relevant configuration fields (e.g., cursor field name, page size parameter). Pagination configuration is required for endpoints that return multi-page responses. Step guidance: 'Most APIs return data in pages. Tell FloQast how this API handles paging so it knows how to retrieve all records, not just the first batch.'

**REQ-14  As an admin or implementor, I want to specify how FloQast identifies new or changed records so that only incremental data is retrieved on each sync.**

_**Functional spec:**_ The user must specify the delta logic method. Supported approaches: (1) Field-based - the API supports a filter parameter (e.g., modified_since) that accepts a timestamp or cursor, passed on each request. (2) Timestamp-applied - FloQast appends a generated timestamp parameter on each sync. Full refresh is not supported in Phase 1. Delta logic is required for each endpoint. Step guidance: 'Delta logic tells FloQast how to fetch only new or updated records on each run, rather than re-pulling everything from scratch every time.'

**REQ-15  As an admin or implementor, I want to specify the response format and optionally provide a sample response so that FloQast can parse the data and assist with field mapping.**

_**Functional spec:**_ The user must specify the expected response format (e.g., JSON). Providing a sample response payload is optional but strongly recommended - the UI must surface a message indicating that without a sample, field mapping must be configured from raw data after the first live sync. If a sample is provided, it must be accepted as pasted text and used to pre-populate field definitions in the lineage configuration flow. Nested arrays in the response must be supported; the system must apply a defined flattening strategy (TBD). The user must also specify whether the data from this endpoint should be appended to existing records on each sync or replace (overwrite) the dataset. Both the data sync behavior and the response format are required fields. Step guidance: 'Paste a sample of what this API returns so FloQast can understand the data shape. Also tell us whether each sync should add to existing data or start fresh.'

**REQ-16  As an admin or implementor, I want to specify the API rate limits so that FloQast does not exceed them, and indicate whether rate limit details come back in the response headers.**

_**Functional spec:**_ The user must provide: (1) Maximum requests per minute allowed by the API provider. (2) Retry configuration - how many times FloQast should retry a failed request and at what interval. (3) Whether the API returns rate limit details (remaining requests, reset time) in response headers. If yes, FloQast must read and respect these values dynamically during sync operations, in addition to the configured static limits. All three fields are required. If maximum requests per minute and retry config are not provided, the user must not be allowed to proceed. Step guidance: 'Rate limits control how fast FloQast can call this API. If the API tells us its limits in the response headers, we can use that too so we never get throttled.'

‌

## **Sync Schedule**

**REQ-17  As an admin or implementor, I want to configure how frequently FloQast pulls data from this connection so that I can balance data freshness with API rate limit considerations.**

_**Functional spec:**_ The sync frequency field is required and defaults to daily. Available options: every hour, every 2 hours, every 4 hours, every 8 hours, every 12 hours, daily, and a custom interval. Nested endpoint sequencing constraints (child endpoint cannot run more frequently than its parent) are enforced when nested endpoint support is added in Phase 2. Step guidance: 'Choose how often FloQast should check this API for new data. Daily is the default; increase the frequency only if your workflow requires near-real-time data and the API rate limits allow it.'

**REQ-18  As an admin or implementor, I want to specify the date from which FloQast begins pulling historical data so that the initial sync captures the correct range.**

_**Functional spec:**_ The sync start date field defaults to today's date. The user must be able to edit this before activation. The start date is passed as part of the delta logic on the first sync cycle. Step guidance: 'This tells FloQast how far back to go on the first sync. It defaults to today, but you can set an earlier date to backfill historical data.'

**REQ-19  As an admin or implementor, I want each step of the setup wizard to include a brief explanation of what is being configured and why it matters so that less technical users can complete the setup confidently.**

_**Functional spec:**_ Each step of the pull API setup wizard must display a short contextual explanation (one to two sentences) visible to the user that describes the purpose of the step and its importance. These explanations are shown at the top of each step panel. Guidance text for each step is specified in the User Interaction and Design section. Guidance text must be written for a non-engineering audience.

‌

## **Connection Test & Activation**

**REQ-20  As an admin or implementor, I want to test my configured connection before activating it so that I can confirm authentication, request construction, and response parsing work correctly.**

_**Functional spec:**_ The connection test must validate three stages in sequence: (1) Authentication - verifies credentials are accepted by the API. (2) Request generation - verifies that the endpoint path, method, headers, and parameters produce a valid request. (3) Response - executes a sample call (one row of data) and verifies a response is returned. The experience should resemble a Swagger test interface. Failures must route the user back to the relevant step: authentication failure to the auth step; request failure to the endpoint configuration step; response failure to a prompt to review query parameters. All three stages must pass before activation is permitted.

**REQ-21  As an admin or implementor, I want to review all configured settings and activate my connection so that I can confirm everything is correct before data starts being pulled.**

_**Functional spec:**_ After passing the connection test, the user must be presented with a full summary of all connection and endpoint configuration. The user must explicitly confirm activation. Upon activation, the connection status changes from Draft to Active, the first scheduled sync is queued based on the configured frequency and start date, and all configured endpoints are displayed in the endpoint library with an Active status. The endpoint library must also show any endpoints configured in prior sessions for this connection.

‌

## **Backend Data Pipeline**

**REQ-22  As FloQast (system), I need to execute pull API requests for each configured endpoint on the defined schedule so that data is ingested at the expected frequency.**

_**Functional spec:**_ For each active pull connection, the system must execute API requests to all configured endpoints on the connection's sync schedule. Requests must incorporate all configured settings: HTTP method, headers (including custom headers), query parameters, delta logic, and pagination traversal. The system must respect the configured static rate limits and, if enabled, dynamic rate limit values from response headers.

**REQ-23  As FloQast (system), I need to log every sync attempt so that admins can monitor pipeline health and troubleshoot issues without engineering support.**

_**Functional spec:**_ Every sync attempt must produce a log entry containing: attempt timestamp, endpoint identifier, success or failure status, record count on success, error type and description on failure (e.g., authentication failure, rate limit exceeded, timeout), and next scheduled sync time. Log entries must be visible in the sync log section of the connection detail view. Errors must be specific enough for an admin to identify the root cause and resolve independently.

**REQ-24  As FloQast (system), I need to pass successfully retrieved raw data through the data pipeline so that it is available for lineage configuration and downstream use.**

_**Functional spec:**_ On successful retrieval, raw data from each endpoint must be passed through the FloQast data pipeline. The system must apply the data sync behavior selected during endpoint setup: append new records to the existing dataset, or replace (overwrite) the existing dataset with the current pull. Partial or failed retrievals must not overwrite previously stored good data. Lineage configuration is not handled here.

**REQ-25  As an admin, I want to export the sync log for a connection so that I can review historical pipeline activity or share it for troubleshooting.**

_**Functional spec:**_ The connection detail view must include a sync log export action. The default view displays the last 30 days of sync activity. The export must allow specifying a custom date range. For large exports, the operation must run in the background without blocking the user. When a large export is complete, the system must notify the user via email with a link to download the file. Export format is TBD (CSV assumed as default).

‌

## **Endpoint Lifecycle Management**

**REQ-26  As an admin or implementor, I want to add a new endpoint to an existing active connection so that I can expand data collection without reconfiguring the entire connection.**

_**Functional spec:**_ An Add Endpoint action must be accessible from the connection detail view. The view must display all currently configured endpoints (standard and custom) for this connection. The system must ask the user to confirm whether the new endpoint uses the same connection basics (base URL, authentication). If yes, the setup flow begins at the endpoint configuration step (REQ-10) and proceeds through endpoint-specific steps, skipping connection basics. If no, the setup flow begins from the connection basics step (REQ-02) to capture the differing configuration. The new endpoint is added to the connection upon successful configuration and test, and immediately visible in the endpoint library.

**REQ-27  As an admin or implementor, I want to deactivate an endpoint without deleting it so that I can pause data collection while preserving the configuration.**

_**Functional spec:**_ Each configured endpoint must have a Deactivate action in the connection detail view. Before deactivation, if the endpoint is used as a nested endpoint dependency for another endpoint, the system must display a warning indicating that deactivation will cause issues with dependent data retrieval, and list the affected endpoints. The admin must acknowledge the warning before proceeding. Upon deactivation, a log entry must be created recording: timestamp of deactivation, the user who performed the action, and the endpoint identifier. This log is visible in the connection's activity log. A deactivated endpoint retains its full configuration, remains visible with an Inactive status, and can be reactivated from the same view.

**REQ-28  As an admin or implementor, I want to permanently delete an endpoint I no longer need so that the connection configuration stays clean.**

_**Functional spec:**_ Each configured endpoint must have a Delete action. Deletion requires a confirmation prompt before proceeding and is permanent. Before deletion, if the endpoint is used as a nested endpoint dependency for another endpoint, the system must display a warning identifying those dependent endpoints and explaining that deleting this endpoint will cause downstream data retrieval failures. The admin must explicitly acknowledge this before deletion is allowed to proceed. If the endpoint is referenced by downstream lineage or other dependencies, the system must surface a specific, descriptive error message. Full dependency error logic is defined in a separate PRD. If a user delete an endpoint, the deletion is also logged with the user name, endpoint, and timestamp of when the endpoint was deleted. Similar to the requirement for deactivation, if the endpoint is used as a nested endpoint dependency for another endpoint, the system must display a warning indicating that deletion will cause issues with dependent data retrieval, and list the affected endpoints. 

# **9. User Interaction and Design**

The pull API setup experience is a multi-step wizard with forward/back navigation, inline validation, and Save as Draft available at every step. Each step displays a brief contextual explanation (one to two sentences) to guide less technical users. The wizard is initiated from the Add Connector flow after the user selects a custom API type and then Pull as the data direction.

‌

## **Setup Wizard - Step Sequence**

Each step shows contextual guidance text (italicized below). Engineering must ensure these are rendered in the UI at the top of each step panel.

‌

1. Select API type (standard pre-built connector or custom/framework API). Then select data direction: Pull or Push. Selecting Pull initiates this wizard.

_Tell us what type of connection this is. Choosing 'Custom API' allows you to configure any API that FloQast does not yet have a built-in connector for._

2. Connection basics: connection name (required), base URL (required, HTTPS validated), environment (sandbox or production), API version (optional).

_Give FloQast the essential details it needs to know where this API lives and what environment it is in._

3. Authentication: auth type selection and credential entry - integrated from the Authentication PRD. Fully required before advancing.

_Tell FloQast how to authenticate with this API so it can securely request data on your behalf._

4. Endpoint request: endpoint path (required), HTTP method selector (GET/POST primary), request format, response format, standard headers, custom required headers.

_Specify the exact path and method for the data you want to retrieve, and tell FloQast what format the API speaks and any special identifiers it needs._

5. Query parameters: static and dynamic parameter builder with add, edit, and remove actions.

_Query parameters refine what data gets returned. Static ones never change; dynamic ones are updated each time FloQast runs the request._

6. Pagination: pagination method selector and associated configuration fields.

_Most APIs return data in pages. Tell FloQast how this API handles paging so it can retrieve all records, not just the first batch._

7. Delta logic: delta method selector (field-based or timestamp-applied) and associated configuration.

_Delta logic tells FloQast how to fetch only new or updated records on each run, rather than pulling everything from scratch every time._

8. Response and data sync: response format, optional sample response (pasted text), and data sync behavior (append or replace).

_Paste a sample of what this API returns so FloQast can understand the data shape. Also tell us whether each sync should add to existing data or start fresh._

9. Rate limiting: requests per minute (required), retry count and interval (required), whether rate limit details are returned in response headers.

_Rate limits control how fast FloQast can call this API. If the API communicates its limits in response headers, FloQast can use that information dynamically to avoid being throttled._

10. Sync schedule: frequency selector (default: daily) and start date (default: today).

_Choose how often FloQast should check this API for new data and how far back to go on the first sync._

11. Review and test: three-stage connection test (auth, request, response) in a Swagger-style interface with pass/fail per stage and step-specific failure routing.

_This step validates that your configuration actually works before going live. FloQast will test authentication, generate a sample request, and retrieve one row of data._

12. Multi-endpoint prompt: add another endpoint (returns to Step 4) or finalize and activate. All configured endpoints display in the endpoint library upon completion.

_You can set up all the data you need in one session. Add as many endpoints as required, then activate when you are ready._

## **Validation Behavior**

* All required fields display an inline validation error if the user attempts to advance without completing them. The user cannot proceed past a step with an unresolved validation error.
* Fields with format constraints (base URL, rate limit values) validate on blur or on advance attempt, with a specific message describing the expected format.

‌

## **Draft Connection Behavior**

* Draft connections appear in the connections list with a clear Draft status badge.
* Opening a draft resumes the wizard at the step where setup was saved, with all previously completed fields pre-populated.
* The user can navigate backward through completed steps to review or edit entries.

‌

## **Connection Test UI**

* The test interface resembles a Swagger page: structured display of the outgoing request and a response panel showing the result of a sample one-row API call.
* Each of the three stages (auth, request, response) shows a distinct pass or fail state.
* On failure, the system shows an actionable error message and routes the user back to the configuration step that corresponds to the failure type.

‌

## **Connection Detail View - Endpoint Library & Actions**

* All configured endpoints for a connection are displayed in a unified endpoint library accessible from the connection detail view. This includes both standard pre-built endpoints and custom endpoints, giving the admin a single view of everything configured.
* Each endpoint row shows: endpoint name, API path, activation status (Active / Inactive), last successful sync timestamp, and next scheduled sync time.
* Action links per endpoint: Edit, Deactivate / Reactivate, and Delete.
* An Add Endpoint button initiates the add-to-existing-connection flow (as defined in REQ-26), consistent with the standard API connection path so that adding custom endpoints feels native alongside standard ones.

‌

## **Sync Log**

* The sync log section in the connection detail view displays the last 30 days of pull attempts by default, with status, timestamp, record count (success), and error detail (failure).
* An Export action is available with a custom date range selector for exporting beyond the default 30-day window.
* For large exports that take significant time to generate, the operation runs in the background so the admin is not blocked. The admin remains free to navigate away. When the export is complete, the system sends an email notification with a download link. The size threshold for background processing and email notification is TBD.

# **11. Out of Scope**

* Authentication configuration details - auth type options, credential field logic, and secure storage are owned by the Authentication sub-PRD. This PRD defines only the integration point.
* AI assistant for API documentation ingestion during setup - covered in a separate sub-PRD. The setup wizard will have a placeholder integration point but the AI-assisted configuration flow is not built here.
* Nested endpoint support for dynamic query parameter resolution - where a parameter value is retrieved from an upstream endpoint response. Scoped to Phase 2 of the parent PRD. Nested dependency warnings in deactivate and delete flows are in scope for Phase 1.
* Push API configuration - scoped to Phase 6 of the parent PRD. The API type and direction selectors in this flow must accommodate push, but push configuration logic is not defined here.
* Field mapping and lineage configuration. This PRD ensures raw data and sample responses are passed to the lineage flow.
* Standard endpoint auto-provisioning - automatic creation of standard endpoints on new standard API connection creation is scoped to Phase 5 of the parent PRD.
* On-demand data run triggers from downstream FloQast applications (e.g., Close for rec refresh) - scoped to Phase 4 of the parent PRD.
* Write-back or bi-directional sync - this PRD covers read-only data ingestion only.
* Fivetran-managed connection endpoints - these have a separate configuration path and are not governed by this PRD.
* External customer-facing push trigger interface - push is initiated by the source system. FQ does not expose a public API for customers to trigger pushes.
