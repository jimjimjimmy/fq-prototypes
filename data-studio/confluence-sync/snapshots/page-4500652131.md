# **1. Objective**

This sub-PRD defines the field-level specification for the GL Transactions endpoint (POST /gl-transactions). It covers the required and optional fields of the GL Transaction data model, submit mode behavior (append vs. replace), custom field passthrough, dimension field support, and the metadata FloQast applies to all incoming records.

The GL Transactions endpoint is a Phase 1 core data model endpoint in the FQ APIs initiative. It enables customers to push general ledger transaction data directly into FloQast using FloQast's own object model, without requiring a pre-built ERP integration.

Auto-configure behavior triggered by the first push is defined in the Auto-Configure sub-PRD. Upsert key design and conflict handling are defined in the Data Handling sub-PRD. Authentication is defined in the Authentication & API Key Management sub-PRD.

# **2. Key Benefits**

* The endpoint accepts the required core set of fields needed for accurate GL transaction ingestion, with clear validation and error messaging for missing fields.
* Optional fields give customers flexibility to provide richer transaction data where available, without requiring full schema population on every record.
* Submit mode (append vs. replace) gives customers explicit, per-push control over how multiple submissions for the same period and entity are handled - no ambiguity about whether a re-submission adds to or replaces existing data.
* Custom field passthrough allows customers to include non-standard fields without being rejected by the API, and auto-configure captures those fields in the lineage automatically.
* Dimension fields allow customers to carry dimensional metadata alongside transactions, enabling downstream analysis and reporting without requiring pre-declaration of the full schema.
* FloQast-applied metadata provides traceability and auditability for every batch of data received, including ingestion timestamp, source connection, and update history.

# **3. Use Cases**

1. A customer pushes the full set of GL transactions for a period in append mode, including all required fields and several optional fields. FloQast ingests the records, applies metadata, and returns a success response with row counts.
2. A customer discovers an error in their previously submitted dataset for a period and re-submits in replace mode. FloQast removes all previously submitted GL transactions for that period and entity and replaces them with the corrected records.
3. A customer submits additional GL transactions for a period that were not included in the initial push, using append mode. The new records are added without affecting the previously submitted data.
4. A customer's payload includes non-standard fields not in the required or optional model spec. The API accepts the records, passing the custom fields through, and auto-configure registers them in the lineage on first push.
5. A customer includes dimension entries in their payload, providing a key and value for each dimension per record. Auto-configure detects and registers the dimension fields in the lineage.
6. After a successful push, FloQast applies ingestion metadata - including created date, source connection identifier, and touch count - to all records in the batch.

# **4. Success Metrics**

* GL Transactions endpoint available and functional at Phase 1 launch.
* Required field validation correctly rejecting payloads with missing required fields, with actionable error messages identifying the missing fields.
* Optional fields correctly accepted when present and treated as absent (not as errors) when omitted.
* Submit mode (append and replace) operating correctly for all combinations of period, entity, and sequence of pushes.
* Custom fields accepted without error and captured by auto-configure on first push.
* Dimension fields accepted and classified correctly by auto-configure.
* FloQast metadata accurately applied to all ingested records (target accuracy: 100%).

# **5. Assumptions**

* Customers are responsible for pre-formatting GL transaction data to match the field specifications defined in this document. FloQast does not perform transformation or normalization.
* submit_mode is a required parameter on every push. There is no default mode - customers must explicitly specify append or replace on each submission.
* In replace mode, all existing GL Transaction records for the specified period and entity are removed and replaced by the submitted batch. Replace is scoped to the period and entity combination - it does not affect other periods or entities.
* In append mode, records are added to the existing dataset for the period and entity. Record-level upsert behavior within an append submission is defined in the Data Handling sub-PRD.
* Entity association must be provided: either pre-configured in connection setup (entity pre-selection) or supplied per record via the entity association/data domain field. See Connection Setup sub-PRD.
* Custom fields are passed through as-is. FloQast does not validate, transform, or interpret custom field values. Customers are responsible for ensuring custom field data is well-formed.
* Dimension fields must follow the structured format defined in REQ-GL-05. The specific payload mechanism for identifying dimension fields is TBD (see Open Questions).
* System-applied metadata fields (Created date in FQ, Created by, Touch count) are generated by FloQast at ingestion time and cannot be overridden by customer-submitted data.
* The "Created Date" field refers to the transaction's creation date in the customer's source system and is distinct from "Created date in FQ," which is FloQast-managed.

# **8. Requirements**

**REQ-GL-01: As a customer technical team, I want to submit the required set of GL Transaction fields so that FloQast can correctly ingest and associate the transaction data.**

_**Functional spec:** The GL Transactions endpoint accepts the required fields defined in Section 7. Every record in the push payload must include all required fields. Payloads containing records with missing required fields are rejected with a 400 Bad Request response that identifies the specific missing fields. Required field values must conform to the specified data types and formats defined in Section 7._

**REQ-GL-02: As a customer technical team, I want to include optional GL Transaction fields in my payload so that I can provide richer data where available without being required to populate every field.**

_**Functional spec:** The GL Transactions endpoint accepts the optional fields defined in Section 7. Optional fields may be included or omitted on a per-record basis. When included, they must conform to the specified data types; a type mismatch on an optional field returns a 422 error identifying the offending field. When omitted, the field is treated as absent - the record is accepted without it and no error is raised. Optional fields present in the payload are captured by auto-configure on first push per the Auto-Configure sub-PRD._

**REQ-GL-03: As a customer technical team, I want to specify whether my submission should append to or replace the existing data for the target period and entity so that I have explicit control over how multiple submissions are handled.**

_**Functional spec:** Each push to the GL Transactions endpoint must include a submit_mode parameter with one of two values: "append" or "replace". In append mode, the submitted records are added to any existing GL Transaction records for the specified period and entity; existing records are not modified or removed. In replace mode, all existing GL Transaction records for the specified period and entity are removed and replaced with the submitted records; customers use this mode when re-submitting a corrected or complete dataset. submit_mode is required on every push - requests without it are rejected with a 400 error. submit_mode applies to the entire batch; a single push cannot mix append and replace behavior. Record-level upsert behavior within an append submission is defined in the Data Handling sub-PRD._

**REQ-GL-04: As a customer technical team, I want to include fields in my GL Transaction payload that are not part of the standard required or optional model so that I can pass non-standard data through to FloQast without being rejected.**

_**Functional spec:** Fields present in a push payload that are not defined as required or optional fields in the standard GL Transaction model are treated as custom fields. The API accepts records containing custom fields without error. Custom fields are passed through as-is - FloQast does not validate, transform, or interpret their values. Custom fields require a data type upon submission so that FQ knows how to use the data. On first push, auto-configure detects and registers custom fields in the lineage per the Auto-Configure sub-PRD. Custom fields introduced in subsequent pushes after the initial auto-configure has run are flagged as unregistered schema additions; see the Auto-Configure sub-PRD for handling._

**REQ-GL-05: As a customer technical team, I want to specify that certain fields in my payload represent dimensions - providing a key, optional value, and optional additional descriptor fields for each dimension - so that dimensional data is correctly classified and usable in FloQast.**

_**Functional spec:** Customers may include dimension entries in their GL Transaction payload. Each dimension entry must include a key (the dimension name or identifier, required) and may optionally include a value (the dimension value for the record) and additional optional descriptor fields providing further context about the dimension. The specific payload mechanism for identifying dimension entries (e.g., a dedicated dimensions array, an inline flag, or a payload wrapper) is an open question to be resolved in conjunction with the Auto-Configure sub-PRD (see Section 10). On first push, auto-configure detects dimension entries and registers them in the lineage. Dimension entries are not validated against a pre-declared schema - they are detected from the push payload._

**REQ-GL-06: As a FloQast system, I want to apply standard metadata to all GL Transaction records received via the API so that submissions are traceable, auditable, and correctly attributed to their source.**

_**Functional spec:** FloQast applies the following metadata fields to each GL Transaction record at the time of ingestion. These fields are system-generated and cannot be overridden by customer-submitted data: Created date in FQ (timestamp of ingestion), Created by (the connection and API key identifier associated with the push), Touch count (number of times the record has been updated via subsequent pushes, starting at 1 on first ingestion). Metadata fields are visible within FloQast for reporting and audit purposes._

**REQ-GL-07: As a customer technical team, I can easily see documentation for this endpoint so I can get information about how the endpoint works.**

_**Functional spec:** FloQast publishes an API spec document that has information about the fields required and optional for the endpoint, the append vs. replace function, the use of dimensions and custom fields, authentication, and a sample API output. The functionality uses the FQ standard documentation platform to provide details about the API usage._

**REQ-GL-08: As a customer technical team, I get errors for data that is incorrectly submitted so I can adjust my integration.**

_**Functional spec:** When a push comes through that has invalid/missing data, there is a log registered that indicated that there is an error. FQ surfaces the error for the API and provides details about the specific error (missing required fields, incorrect format of a field, etc.)._

# **9. User Interaction and Design**

The GL Transactions endpoint is a developer-facing API. There is no UI component - customers interact with it programmatically through their integration code or API tooling.

## **Endpoint**

POST /gl-transactions

## **Authentication**

API key passed in the Authorization: Bearer header, consistent with all other FQ API endpoints. See Authentication & API Key Management sub-PRD.

## **Request Structure**

The request body is a JSON object with the following top-level parameters:

* submit_mode (required): "append" or "replace". Controls how the submitted batch is applied to the existing dataset for the target period and entity.
* period (required): the target period for the submission (format TBD with Engineering).
* entity_id (conditional): the FQ entity ID for the submission. Required if entity association is not pre-configured at the connection level. See Connection Setup sub-PRD.
* records (required): array of GL Transaction objects, each conforming to the field specification in Section 7.

Within each record, fields are organized as follows:

* Required fields: must be present on every record. Missing required fields cause the entire batch to be rejected.
* Optional fields: may be included or omitted per record. Absent optional fields are treated as null.
* Custom fields: any field not in the standard model spec. Passed through without validation.
* Dimensions: structured entries identifying dimensional data. Format TBD (see Open Questions).

## **Submit Mode Behavior**

| **submit_mode** | **Behavior** | **When to Use** |
| --- | --- | --- |
| **append** | Submitted records are added to existing records for the period/entity. Existing records are not modified or removed. | Initial load, incremental additions, or when adding transactions not included in a prior push. |
| **replace** | All existing GL Transaction records for the period/entity are removed and replaced with the submitted batch. | Re-submitting a corrected dataset or replacing a prior full-period submission. |

## **Error Responses**

* 400 Bad Request: missing required fields, missing or invalid submit_mode, malformed payload structure. Response body identifies the specific issue.
* 401 Unauthorized: API key missing, invalid, or revoked.
* 403 Forbidden: valid key used outside its connection scope.
* 422 Unprocessable Entity: field value present but wrong data type.
* 429 Too Many Requests: rate limit exceeded. Includes Retry-After header.
* 500 Internal Server Error: unexpected system failure.
