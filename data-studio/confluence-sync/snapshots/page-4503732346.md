# **1. Objective**

This sub-PRD defines the UI updates required so that configured API endpoints become visible and selectable as data sources within the lineage definition flow in Data Studio. When an endpoint is set up - whether auto-provisioned on connection creation or manually activated by an admin - it must immediately appear in the lineage source picker. Once selected, all fields returned by that endpoint must be surfaced as available options for source-to-target mappings.

This document is scoped to the visibility and selection layer only. Grouping and linking of endpoint data within a lineage are covered in separate PRDs.

# **2. Key Benefits**

* Zero additional setup: configured and auto-provisioned endpoints are immediately available in the lineage source picker with no manual steps.
* Full field transparency: all fields returned by an endpoint are surfaced for mapping, eliminating the need for admins to independently discover the endpoint's schema.
* Clear error signaling: erroring endpoints are visibly flagged in the source picker, allowing admins to identify and resolve issues before lineage execution.
* Reduced confusion in setup: already-linked endpoints are excluded from the source picker, keeping the selection list clean and scoped to available options.

# **3. Use Cases**

1. Standard QBO connection setup: A FloQast implementor creates a QBO connection. TrialBalance and Accounts endpoints are auto-provisioned. When the implementor opens the lineage definition flow, both endpoints are immediately available in the source picker - no additional configuration required.
2. Endpoint source selection with field mapping: An admin building a lineage selects an active endpoint from the source picker. The field mapping panel populates with all fields returned by that endpoint's last successful run, each displaying its field name, data type, and a sample value.
3. Error state awareness: An admin notices an endpoint in the source picker is flagged with an error indicator. They can see that the endpoint needs to be fixed before the lineage will execute, and are directed to the endpoint configuration to resolve it.
4. Deduplication in lineage setup: An admin who has already linked an endpoint in the current lineage does not see it again in the source picker. It appears in the linked data view instead, keeping the picker free of already-used options.
5. Custom endpoint activation flows into lineage: An admin activates a custom endpoint from the endpoint library. The endpoint immediately appears in the lineage source picker for any lineage associated with that connection.

# **4. Success Metrics**

| **Metric** | **Target / Description** |
| --- | --- |
| Endpoint availability in source picker | Active endpoints appear in the lineage source picker immediately after activation or auto-provisioning, within a single page load |
| Field coverage | 100% of fields returned by the endpoint's last successful run are available as mapping options |
| Deactivated / already-selected endpoint exclusion | Deactivated and already-linked endpoints are correctly excluded from the source picker in 100% of cases |
| Error state visibility | Erroring active endpoints display a visible error indicator in 100% of cases; admins can identify the issue without navigating away from the lineage flow |

# **5. Assumptions**

* Field names, data types, and sample values in the mapping panel are derived from the endpoint's most recent successful run response.
* Endpoint visibility in the source picker reflects current activation status at the time of page load or source picker interaction.
* Auto-provisioned standard endpoints (e.g., TrialBalance, Accounts) follow the same visibility rules as manually activated endpoints - no separate configuration is required to make them appear in the lineage source picker.
* This PRD covers only the visibility and selection layer. Grouping and linking of endpoint data within lineage, and source-to-target mapping execution logic, are out of scope.

# **6. Milestones**

No milestones defined for this sub-PRD. This work represents a single, contained set of UI updates delivered as part of the broader endpoint management initiative.

# **7. Scope of Data**

The following data objects and fields are in scope for this work:

‌

* API endpoint configurations: endpoint name, API path, activation status (active / inactive), error status, and last successful run timestamp - used to determine visibility and state in the source picker.
* Endpoint field metadata (from last successful run): field name, data type, and sample value - surfaced in the source-to-target mapping panel upon endpoint selection.
* Lineage source selection state: which endpoints are already linked to the current lineage - used to exclude already-selected endpoints from the source picker.

‌

Explicitly out of scope for the data layer:

* Grouping and linking logic for endpoint data within lineage (covered in separate PRDs).
* Source-to-target mapping execution and transformation logic.
* Fivetran-ingested data objects.

# **8. Requirements**

‌

1. **REQ-01 - As an admin or implementor, I want to see all active, unselected endpoints for a connection in the lineage source picker so that I can select the appropriate data source for my lineage definition.**

_Functional spec:_ The lineage source picker must display all active endpoints for the associated connection. Deactivated endpoints must not appear. Endpoints already selected and linked within the current lineage must also be excluded from the picker - they appear in the linked data view instead. The displayed list must reflect current activation status.

‌

2. **REQ-02 - As FloQast (system), I want auto-provisioned standard endpoints to appear in the lineage source picker immediately after connection setup so that no manual steps are required before beginning lineage configuration.**

_Functional spec:_ When standard endpoints are auto-provisioned on connection creation (per the parent PRD), they must be immediately available in the lineage source picker without any additional admin action. Auto-provisioned endpoints follow the same visibility rules as manually activated endpoints and are indistinguishable from them in the picker.

‌

3. **REQ-03 - As an admin or implementor, I want to see a clear error indicator on endpoints that are active but in an error state so that I know they need to be fixed before relying on them in a lineage.**

_Functional spec:_ Active endpoints in an error state must appear in the lineage source picker but must display a visible error indicator (e.g., a warning icon or badge). The indicator must communicate that the endpoint needs to be fixed before the lineage will execute successfully. The admin must be able to understand that an issue exists and be directed toward the endpoint configuration to resolve it, without being forced to navigate away from the lineage flow first.

‌

4. **REQ-04 - As an admin or implementor, I want all fields returned by a selected endpoint to be available as mapping options in the source-to-target field panel so that I can map any data point from the endpoint to a target field.**

_Functional spec:_ When an endpoint is selected as a source in the lineage definition, all fields returned by that endpoint's last successful run must be listed as available mapping fields. Each field entry must display: field name, data type, and sample value from the last run. All returned fields must be selectable as mapping sources - no fields should be hidden or pre-filtered. If no successful run has yet occurred, see Open Questions.

‌

5. **REQ-05 - As an admin or implementor, I want deactivated endpoints to be excluded from the lineage source picker so that I cannot accidentally configure a lineage against an inactive data source.**

_Functional spec:_ Endpoints with an activation status of Inactive must not appear in the lineage source picker under any circumstances. This applies to endpoints that were manually deactivated and to endpoints that were never activated. Behavior for lineages where a previously linked endpoint is subsequently deactivated is out of scope for this PRD.

# **9. User Interaction and Design**

‌

**Lineage Source Picker**

* Displays all active, unselected endpoints for the associated connection.
* Each entry shows: endpoint name, API path (abbreviated), and a short description of the endpoint's purpose.
* Endpoints in an error state are displayed with a visible warning indicator (e.g., a warning icon or badge). The indicator surfaces a message informing the admin that the endpoint needs to be fixed before the lineage will execute, with a path to the endpoint configuration.
* Deactivated endpoints are not shown.
* Endpoints already linked in the current lineage are not shown in the picker; they appear in the linked data view instead.
* Auto-provisioned endpoints appear here automatically, without any distinction from manually activated endpoints.

‌

**Source-to-Target Field Panel (post-selection)**

* After an endpoint is selected as a source, the field mapping panel displays all fields from that endpoint's last successful run.
* Each field displays: field name, data type (e.g., string, number, date), and sample value from the last run.
* All fields are available for selection as mapping sources - no pre-filtering is applied.
* If an endpoint has never successfully run and has no field data, behavior is an open question (see Section 10).

# **10. Open Questions**

| **Question** | **Owner** | **Notes** |
| --- | --- | --- |
| What should happen if an endpoint has never successfully run? Should it still appear in the source picker, and what does the field panel display? | PM / Engineering | Options include: hiding the endpoint entirely, showing it with a 'no run data' state, or showing it with an empty field panel and a prompt to run the endpoint first. |
| Should the field list in the mapping panel refresh automatically when a new endpoint run completes, or only on page reload? | Engineering | Real-time refresh would require a push/polling mechanism; page-reload-only is simpler but may surface stale fields during active sessions. |
| What is the behavior for a lineage that already references an endpoint that is subsequently deactivated? Does the lineage show an error, break silently, or preserve the last known state? | PM / Engineering | Out of scope for this PRD but should be resolved before this feature is considered complete. |

# **11. Out of Scope**

* Grouping of endpoint data within a lineage - covered in a separate PRD.
* Linking of endpoint data within a lineage - covered in a separate PRD.
* Source-to-target mapping execution and transformation logic (beyond field visibility and selection).
* Endpoint error resolution workflows - covered in the parent PRD (API Endpoint Management).
* Behavior when a previously linked endpoint is deactivated after a lineage has already been created.
* Fivetran-sourced data visibility in lineage.
* Write-back or bi-directional sync.
