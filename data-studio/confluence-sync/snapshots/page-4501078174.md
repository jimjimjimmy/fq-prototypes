# **1. Objective**

This sub-PRD defines the authentication requirements for the FQ API - covering how customers prove identity when pushing data to FloQast, how API keys are generated and managed in Data Studio, and the security properties that govern key lifecycle. It also establishes the roadmap for OAuth 2.0 support as a Phase 2 enhancement for enterprise customers.

Phase 1 uses API key authentication: a static key generated in Data Studio, scoped to a specific connection, and transmitted in the request Authorization header. Phase 2 will introduce OAuth 2.0 Client Credentials flow as an alternative for customers who require token-based, short-lived authentication - particularly large ERP integration teams and enterprise security environments.

Authentication is the entry point for every FQ API call. Getting it right is foundational to the security, reliability, and ease of integration of the entire initiative.

# **2. Key Benefits**

* API key authentication is simple to implement, widely understood by integration developers, and requires no OAuth infrastructure in Phase 1.
* Connection-scoped keys limit the blast radius of a compromised key - exposure is contained to a single connection rather than the entire organization.
* Self-serve key generation and revocation in Data Studio puts customers and FloQast implementation teams in control without requiring FloQast engineering involvement.
* HTTPS/TLS enforcement and Authorization header transmission prevent keys from appearing in server logs or browser history.
* Rate limiting per key protects the platform from runaway integrations and ensures fair usage across customers.
* OAuth 2.0 support in Phase 2 provides a path for enterprise customers with stricter security requirements, without requiring a rearchitecture of Phase 1.

# **3. Use Cases**

1. A customer IT team generates a new API key in Data Studio during connection setup for their GL Transactions connection, copies the key once, stores it securely in their secrets manager, and uses it in the Authorization header for all subsequent data pushes on that connection.
2. A FloQast implementation specialist generates an API key on behalf of a new customer during onboarding, hands it off to the customer's technical team to store, and confirms that the first push authenticates successfully.
3. A customer rotates their API key as part of a quarterly security review. They generate a new key for the connection, update their integration to use the new key, verify successful pushes, and then revoke the old key - with no downtime during the transition.
4. A customer's API key is suspected to be compromised. They immediately revoke it in Data Studio, generate a new key, and update their integration - stopping any unauthorized pushes within seconds.
5. A customer with multiple connections generates a separate API key per connection, allowing them to revoke access to one connection without affecting others.
6. (Phase 2) An enterprise customer with strict security policies requires short-lived token authentication. They register a client ID and secret with FloQast and use OAuth 2.0 Client Credentials flow to obtain and refresh access tokens for their integration.

# **4. Success Metrics**

* Customers are able to generate, use, and revoke API keys entirely self-serve - no FloQast engineering involvement required.
* Authentication errors (401 responses) represent less than an acceptable threshold of total API requests (target TBD with Engineering).
* Zero incidents of key exposure via server logs, query parameters, or unencrypted transport.
* Key revocation takes effect immediately upon customer action - no delay window.
* Rate limit enforcement operates correctly - legitimate integrations are not throttled below their expected throughput targets.

# **5. Assumptions**

* All FQ API communication is over HTTPS/TLS. The API rejects HTTP requests entirely.
* API keys are connection-scoped: each key is associated with a single connection and grants access only to the endpoints configured for that connection.
* API keys are stored server-side in hashed form. FloQast never stores or can retrieve the plaintext key after initial generation.
* The full API key value is shown to the customer only once, at the moment of generation. Customers are responsible for storing the key securely.
* API keys are non-expiring by default. Customers may optionally set an expiration date on a key if their security policy requires enforced rotation. Keys without an expiration remain valid until explicitly revoked.
* A maximum of two active keys are allowed per connection at the same time.
* API keys follow a standardized format with a fq_ prefix.
* When a connection is archived, all associated API keys are automatically deactivated.
* OAuth 2.0 is a Phase 2 feature.
* Rate limiting applies per key / per connection.

# **7. Scope of Data**

In scope: API key generation/storage/revocation, connection-scoped keys, Bearer auth, HTTPS/TLS, rate limiting, error responses, OAuth 2.0 Phase 2.
Out of scope: Connection setup UI, rate limit values, end-user auth.

# **8. Requirements**

REQ-AUTH-01 through REQ-AUTH-08 covering key generation, Bearer auth, revocation, connection scoping, rate limits, error responses, OAuth 2.0 Phase 2, and internal logging.

# **9. User Interaction and Design**

Key management UI in connection setup and edit views. Zero-downtime rotation with max 2 active keys. Error response format for 401/403/429.

# **10. Open Questions**

Max two keys feasibility, rate limit thresholds, per-customer limits, OAuth token lifetime.

# **11. Out of Scope**

Connection setup UI, rate limit values, end-user auth, IP allowlisting, mTLS, OAuth implementation details, SSO/IdP federation.
