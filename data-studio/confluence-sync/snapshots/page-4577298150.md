## Overview

This document defines the canonical data model for a **BankTransaction** — a single normalized transaction record ingested from any bank data source.

Current supported sources: **Trovata API**, **BAI2**, **MT940**, **MT970**. The model is designed to accept additional bank file formats without structural changes.

The model follows FloQast's **Bronze / Silver / Gold medallion architecture**:

* **Bronze** — Raw, unmodified source data preserved for audit and replay (`raw_data` field)

* **Silver** — Normalized, source-agnostic record consumed by FQ products

* **Gold** — Pre-computed aggregations (daily balances, monthly summaries — to be defined in a follow-on spec)

## SourceType (Enum)

Identifies the origin of a transaction. New values are added here when new sources are onboarded — no schema changes required.

| Value | Description |
| --- | --- |
| TROVATA_API | Trovata treasury management API |
| BAI2 | BAI2 cash management file format |
| MT940 | SWIFT MT940 customer statement |
| MT970 | SWIFT MT970 netting statement |

## Bank Transaction

The core entity. One record per transaction in the Silver (normalized) layer. Each record embeds its original source data via `raw_data` for Bronze traceability.

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| id | UUID | Yes | Internal identifier |
| tlc_id | string | Yes | FloQast customer ID |
| statement_id | UUID | Yes | FK → BankStatement (the file or API batch this transaction came from) |
| account_id | UUID | Yes | FK → BankAccount |
| source_type | SourceType | Yes | Source format — denormalized for query performance |
| source_transaction_id | string | No | Original transaction ID from source system |
| value_date | date | Yes | Date transaction is valued (effective date) |
| entry_date | date | No | Date posted / booked to account |
| debit_credit_indicator | enum | Yes | DEBIT or CREDIT |
| amount | decimal | Yes | Absolute transaction amount — always positive |
| currency_code | string | Yes | ISO 4217 (e.g., USD, EUR) |
| transaction_type_code | string | No | Source-specific type code (BAI2 type code, SWIFT TID code) |
| normalized_category | string | No | Standardized category resolved via TransactionTypeMapping |
| bank_reference | string | No | Bank-assigned reference number |
| customer_reference | string | No | Customer-assigned reference |
| description | string | No | Narrative / memo text |
| running_balance | decimal | No | Account balance after this transaction |
| funds_type | string | No | BAI2 funds availability code (S, 1, 2, etc.) |
| status | enum | Yes | POSTED, PENDING, REVERSED |
| is_reversal | boolean | Yes | Whether this entry reverses another transaction |
| reversal_of_id | UUID | No | FK → BankTransaction being reversed |
| raw_data | JSON | Yes | **Bronze layer** — full source-level transaction record, stored verbatim |
| ingested_at | timestamp | Yes | When the record was first received |
| knowledge_date | timestamp | Yes | Bi-temporal: when FloQast normalized this version |
| created_at | timestamp | Yes |  |
| updated_at | timestamp | Yes |  |
| metadata | JSON | No | Extensible field for source-specific data that does not map to standard fields |

### Notes

* `amount` is always stored as a positive decimal. Direction is captured by `debit_credit_indicator`.

* `value_date` is the effective date of the transaction. `entry_date` is the bank posting date — not always available depending on source.

* `knowledge_date` supports bi-temporal queries: use it to reconstruct what FloQast knew about a transaction at any point in time.

* `metadata` allows new sources to attach additional fields without schema changes.

## TransactionTypeMapping

Reference table that maps source-specific transaction codes to standard normalized categories. Enables consistent `normalized_category` values across all source formats.

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| id | UUID | Yes | Internal identifier |
| source_type | SourceType | Yes | Which source this code belongs to |
| source_code | string | Yes | Original code (e.g., BAI2: "399"; SWIFT: "NCHG") |
| normalized_category | string | Yes | Standard category |
| description | string | Yes | Human-readable description |
| created_at | timestamp | Yes |  |
| updated_at | timestamp | Yes |  |

**Normalized category examples:** WIRE_IN, WIRE_OUT, ACH_CREDIT, ACH_DEBIT, CHECK_DEPOSIT, CHECK_PAYMENT, FEE, INTEREST, SWEEP, INTERNAL_TRANSFER, OTHER

### BAI2 → BankTransaction

| BAI2 Field | BankTransaction Field | Notes |
| --- | --- | --- |
| Record 16: Type Code | transaction_type_code | 3-digit BAI2 code (e.g., 399, 469) |
| Record 16: Amount | amount | Always stored as positive |
| Record 16: Funds Type | funds_type | Availability code (S, 1, 2, etc.) |
| Record 16: Bank Reference | bank_reference |  |
| Record 16: Customer Reference | customer_reference |  |
| Record 88: Continuation Text | description | May span multiple continuation records |
| Account Identifier (03): Currency | currency_code |  |
| Account Identifier (03): Date | value_date | BAI2 has no per-transaction value date — statement date is used |
| Derived from type code | debit_credit_indicator | Via TransactionTypeMapping |
| (raw record text) | raw_data | Bronze layer |

> **Note:** BAI2 does not carry a value date at the individual transaction level. The statement date from the Account Identifier (03) record is used as the effective date for all transactions in that account record.

### MT970 → BankTransaction

MT970 (Netting Statement) uses the same field structure as MT940. The distinction is captured in `source_type = MT970` and in `raw_data`. All MT940 mappings above apply.

## Adding a New Source Format

To onboard a new bank file format (e.g., CAMT.053, OFX, SWIFT MT942):

1. Add a new value to the `SourceType` enum

2. Build a parser that maps source fields to the `BankTransaction` Silver schema

3. Store the full source-level record in `raw_data` (Bronze)

4. Add rows to `TransactionTypeMapping` for any new source-specific type codes

5. Use `metadata` for any source-specific fields that do not map to standard columns

6. No changes to the core `BankTransaction` schema required
