## Objective

This PRD defines the requirements for API endpoint management within FloQast Data Studio for API connections. Specifically, it covers how Data Studio provisions, displays, and manages API endpoints as configurable data sources including a standard set of endpoints auto-provisioned on connection setup, user-controlled custom endpoint activation, and the mechanisms for scheduled and on-demand data retrieval.

The primary users are FloQast admins and implementation team members who need to configure, inspect, and troubleshoot API data endpoints without engineering involvement. This work also establishes the foundational trigger and delivery pattern for on-demand data runs requested by downstream FloQast applications (e.g., Close reconciliations, completeness reports).

## Key Benefits

* Zero-engineering endpoint activation: admins and implementors can configure, activate, and edit endpoints directly from Data Studio.
* Faster time to first data: standard endpoints are auto-provisioned when a new standard connection is created, reducing setup friction.
* Configurable sync frequency: default 24-hour sync can be adjusted per connection, giving customers control over data freshness.
* On-demand data retrieval: downstream FloQast applications can trigger data runs directly, enabling near-real-time data availability for workflows like rec refreshes.
* Fast data delivery: target retrieval-to-delivery under 60 seconds (optimally under 10 seconds), with downstream notification when new data is ready.
* Endpoint transparency: admins have clear visibility into which endpoints are configured, their status, and what data objects they populate.
* Future API patterns: establishes a pattern of working with API endpoints in the future, paving the way for the NetSuite, Intacct, QBO, Xero, Dynamics, and future API sources

## Use Cases

* Standard QBO setup: A FloQast implementor sets up a new QBO API connection. Data Studio automatically provisions the TrialBalance and Accounts endpoints and displays them in the Source Data section of the connection detail view. No additional configuration is required for standard close workflows.
* Endpoint library browsing: An admin navigates to the connection in Data Studio and opens the endpoint library. They browse available API endpoints, see descriptions and current activation status, and activate an additional endpoint (e.g., a custom field endpoint) without opening a support ticket.
* Custom endpoint with query parameters: An implementor adds a non-standard endpoint that requires specific query parameters (e.g., a realmId-scoped report with a date range for QBO). They configure the required parameters, and where parameter values depend on data from another endpoint, the system resolves those through a nested endpoint call.
* Endpoint editing and troubleshooting: An admin notices a data endpoint is returning errors. They open the endpoint detail from the Source Data view, edit the configuration (e.g., correct a malformed query parameter), and re-run the endpoint to confirm it resolves.
* On-demand data run: A Close user triggers a reconciliation refresh. Close sends an internal trigger to Data Studio, which executes a data run for the relevant endpoints, transforms the response into FloQast data models, and notifies downstream applications that new data is available, all within the target SLA.
* Sync frequency adjustment: An admin for a high-activity customer reduces the default 24-hour sync interval to 2 hours to ensure more timely data availability during close.

    Success metrics

| Goal | Metric |
| --- | --- |
| Endpoint setup success rate | Greater than 95% of new standard API connections successfully auto-provision standard endpoints without error |
| Data retrieval latency (on-demand) | Less than 60 seconds end-to-end; optimally less than 10 seconds from trigger to data available in store; dependent on speed of APIs |
| Data retrieval latency (scheduled) | Completes within scheduled window; no missed sync windows in steady state |
| Endpoint error rate | Less than 5% of endpoint data requests result in unrecovered errors after retry |
| Time to resolve broken endpoint | Admin can identify and edit a misconfigured endpoint without engineering support |
| Downstream notification reliability | 100% of successful data runs emit a downstream notification; no silent failures |

## Assumptions

1. APIs we are working with are stable, supported API surface. FloQast will monitor standard connection API documentation for changes/deprecataions.
2. The internal FloQast application that triggers on-demand data runs (e.g., Close for rec refreshes) will need to define its trigger interface as part of this project. The trigger mechanism is currently undefined and is a key open question.
3. Default sync frequency is 24 hours. Admins may adjust this per connection.
4. Rate limit constraints: Endpoint configuration and scheduling must operate within the rate limiting constraints.
5. Custom endpoint configurations are scoped per connection, allowing for support of CAS customers as well as standard customers..
6. Nested endpoint calls (to resolve query parameter values from upstream endpoint responses) are supported but limited in depth (TBD, see Open Questions).

## Milestones

1. Phase 1:
  Pull APIs. Admins and implementors can set up pull endpoints for FQ to use for data ingestion. FQ can capture the necessary configurations to pull data from the API configurations and run the APIs to ingest data based on the configured scheduling.
2. Phase 2
  Nested endpoint support. Admins and implementors can use dynamic data from multiple endpoints in order to ingest data.
3. Phase 3:
    Endpoint management. Admins and implementors can browse the endpoint library, add custom endpoints, configure query parameters (including nested endpoint calls to resolve parameter values), edit existing endpoints, and configure sync frequency per connection.
4. Phase 4:
  On-demand data runs and fast delivery. Define and implement the trigger interface for internal FloQast application requests. Execute data runs on demand, transform data into FloQast data models, and notify downstream applications when new data is available. Meet the <60s (optimally <10s) latency target.
5. Phase 5:
  Standard endpoint auto-provisioning and display. When a new standard API connection is created, the endpoints are provisioned automatically and visible in the Source Data section of the connection detail view. Includes endpoint list view with name, description, API path, data objects, and activation status
6. Phase 6:
  Push APIs. Admins and implementors can set up push endpoints for FQ to use for data ingestion. FQ can capture the necessary configurations to pull data from the API configurations and run the APIs to ingest data based on the configurations.

## Scope

The following data objects and entities are in scope:

* Accounts, transactions, and trial balances supported by existing direct connection APIs
* API endpoint configurations: stored per connection, including: endpoint name, API path, description, query parameters, sync frequency, activation status, and last run metadata.
* Accounts: data retrieved, parsed and classified by account type (balance sheet vs. income statement).
* Trial Balances: data retrieved with date range and accounting method parameters.
* Query parameter definitions: parameter names, types, whether they are user-defined or resolved from upstream endpoint responses, and the source endpoint if nested.
* Data run logs: per-run metadata including trigger source (scheduled vs. on-demand), start/end time, status, records processed, and error details. This should be partitioned by the TLC and entity/data domain as is relevant.
* Downstream notification events: event payload confirming new data availability, scoped to connection and data object type.

Explicitly out of scope for the data layer:

* Field mapping configuration (covered in other PRDs
* Fivetran-ingested data objects

## User interaction and design

Prototype: https://www.figma.com/make/3c2VXFNTKrtHJWu6Cs4kra/AI-API-setup-workflow?p=f&t=2iZ8C5mBPbMOQNxP-0

### Connection Detail View: Source Data Section

The Source Data section of the connection detail view must display all configured endpoints for that connection. The list view includes:

* Endpoint name and API path
* Short description of the endpoint's purpose
* Data objects currently populated by this endpoint
* Activation status (Active / Inactive / Error)
* Last successful run timestamp and next scheduled run
* Action links: Edit, Run Now, Deactivate

Standard endpoints are displayed here automatically after connection setup with no additional action required.

### Endpoint Library

Accessible from the connection detail view, the endpoint library is a browsable catalog of available API endpoints for the source. The library:

* Lists all available endpoints with name, description, API path, data objects, and current activation status for this connection
* Supports search/filter by endpoint name or data object
* Allows an admin to select and activate an endpoint, which opens the endpoint configuration flow

### Add / Edit Endpoint Flow

When adding a new endpoint or editing an existing one, the user is presented with a configuration panel that includes:

* Endpoint name and API path (read-only if selected from library; editable if manually entered)
* Brief description of the endpoint
* Query parameter fields with labels, descriptions, format hints, and enumerated options where applicable
* Nested data source indicators. If a parameter requires data from another endpoint, the system shows which upstream endpoint it calls and what value it retrieves
* Sync frequency selector (default 24h; options: 1hr, 2hr, 4h, 8h, 12h, 24h, Custom)
* Save / Cancel actions; saved endpoints appear in the Source Data list immediately
* For edit mode: current values are pre-populated; a "Test Now" or "Run" action is surfaced to validate the configuration before leaving

### On-Demand Run Trigger (Internal / System)

The on-demand trigger is an internal interface consumed by other FloQast applications (e.g., Close). It is not a user-facing UI element. Key design considerations:

* The trigger interface (webhook, internal event bus, or API call - TBD) must be defined in collaboration with the downstream application teams
* The trigger must be scoped to a specific connection and optionally a specific endpoint or data object
* The system acknowledges the trigger immediately and processes asynchronously
* Downstream applications receive a notification event when the data run completes and new data is available in the store
* Run status (triggered, in-progress, completed, failed) is visible in the admin's sync log view

## Out of Scope

* Write-back or bi-directional sync: This PRD covers read-only data ingestion. No data will be pushed back to the API.
* Fivetran endpoint management: Fivetran-connected data sources have a separate configuration path and are not governed by this PRD.
* Data preview / test & sample capability: Covered in other PRD. Out of scope here but should be considered in the Phase 2 endpoint configuration flow
* External customer-facing trigger interface: The on-demand trigger is an internal interface for FloQast applications only, not a public API for customers.
